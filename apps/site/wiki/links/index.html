Links & URIs

Nothing in hoi names a server to start from, so links carry everything a device needs: an invite carries a community's key, its signed genesis and a few routes; a node link carries a public node's addresses and its operator's signed notice; a pairing link carries a home node's address and a one-time token. All three pack their fields into one masked code, so no IP address or token can be read from the link. This page gives the exact fields, encodings, limits and checks of each, the older clear-text forms that still open, and what the web app, the desktop app and hoi-node do with them.

The links

Each link has two spellings: a hoi:// URI, and the same query after #/<verb>? in the web app's address, which a phone's camera or any browser can open. The core parses both the same way.

How a link is read

All three parsers start with query_after(link, verb). It trims the link, finds the first <verb>? anywhere in it, and takes what follows up to a # as the query. So hoi://join?…, web+hoi://join?…, https://hoi.sh/app/#/join?… and a link with any other base all read the same, and the parser never looks at the host part of an https link.

  1. Split

    The query is split on &; empty pairs are skipped; each pair splits at its first = (a key with no = gets an empty value).

  2. Decode values

    Values are percent-decoded (%XX, and + as a space) and must be UTF-8. Keys are taken as written.

  3. Code or clear text

    If a code key is present, the link is read from the code alone: there must be exactly one code, and none of the clear-text keys of that link type may appear beside it, so nothing outside the code can change what a preview showed. Otherwise the older clear-text keys are read, and keys the parser doesn't know are ignored.

  4. Check

    The decoded fields are checked like a record's: CBOR must be canonical, unknown fields are refused, types and lengths must match, and each link type adds its own rules.

The web forms are made by to_web(base): the base with any fragment cut off, then #/<verb>? and the query. Nodes and apps write their links after the web app address they were configured with; hoi-node and the mobile libraries use https://hoi.sh/app/.

Masked codes

Every link the software writes today carries one code. The code is an envelope: four magic bytes saying what it is, a 16-byte checksum, and the payload XORed with a keystream derived from the checksum. Its job is narrow and the code says so: a generic Base64 decoder no longer shows the addresses, tokens or names inside, so a link pasted into a chat, a screenshot or a log doesn't spell out where a node is. It is public obfuscation, not encryption.

/// A public mask, not a secret key: a generic Base64 decoder no longer exposes addresses,
/// but anyone with the link and this algorithm can undo it. The checksum detects damage;
/// it does not authenticate the link. Signed genesis and notice checks happen separately.
fn mask(context: &str, payload: &mut [u8], checksum: &[u8]) {
    let mut hasher = blake3::Hasher::new_derive_key(context);
    hasher.update(checksum);
    let mut stream = hasher.finalize_xof();
    let mut mask = [0u8; 64];
    for chunk in payload.chunks_mut(mask.len()) {
        stream.fill(&mut mask[..chunk.len()]);
        for (byte, mask_byte) in chunk.iter_mut().zip(mask.iter()) {
            *byte ^= mask_byte;
        }
    }
}

fn encode_code(magic: &[u8; 4], context: &str, mut payload: Vec<u8>) -> String {
    let digest = blake3::hash(&payload);
    let checksum = &digest.as_bytes()[..16];
    mask(context, &mut payload, checksum);
    let mut envelope = Vec::with_capacity(CODE_HEADER + payload.len());
    envelope.extend_from_slice(magic);
    envelope.extend_from_slice(checksum);
    envelope.extend_from_slice(&payload);
    b64(&envelope)
}
magic | 4 B | sun | 2 | HOI 02, HON 01 or HOP 01 checksum | 16 B | lilac | 3 | first 16 bytes of BLAKE3(payload), before masking masked payload | n B | coral | 7 | payload XOR BLAKE3-XOF(derive-key mode, context, checksum)
  1. Pack

    The fields become a canonical CBOR map. Node and pairing payloads are then deflated; invite payloads are not (they mostly hold a signed genesis, which doesn't compress much).

  2. Checksum

    checksum = BLAKE3(payload)[0..16], over the unmasked payload.

  3. Mask

    The keystream is BLAKE3 in key-derivation mode with the link type's context string, fed the checksum, read as an extendable output for as many bytes as the payload. Each payload byte is XORed with it.

  4. Wrap

    magic ‖ checksum ‖ masked, base64url without padding.

Opening reverses it: the envelope must be longer than the 20-byte header (code is truncated), the magic must match, and after unmasking the checksum must match the payload (code is damaged). Tests flip every bit and cut every length of a code and check that each one is refused, and that an invite code opened as a node link (or the other way round) is refused by its magic.

What masking is not

Anyone who has the link and this page can unmask it. The checksum catches damage, not forgery: a masked link is exactly as trustworthy as the person who sent it. What protects a joiner is checked separately: an invite's genesis must be signed by the community key it names, and a node link's notice must be signed by the node it names. A pairing link's token is a bearer secret either way: masking keeps it from being read off a screen, not from being used by whoever holds the link.

Join links (invites)

An invite to a public community. Node::invite writes one with the community key, its genesis wire, up to 16 peer routes and 8 relays the node knows for it, and up to 2 trackers; the app shows both uri and web, with the addresses inside and whether any reaches the internet. Private communities never get one: they use encrypted invitations (Private communities).

The parser refuses an unknown field, a v other than 1, a key of the wrong length, a non-text route, non-bytes g, and zero or more than two trackers written. A tracker passes tracker_ok when it starts https:// (or http:// on 127.0.0.1, localhost or [::1], for tests), has a host, has at most 200 bytes, all printable ASCII, and contains none of ? # @, spaces, backslashes or line breaks.

Older forms that still open

  • The original code: code= holding plain canonical CBOR, unmasked. If the decoded bytes don't start with HOI they are read as CBOR directly; if they start with HOI but not HOI 0x02, the code is refused as an unsupported version. A frozen v1 code is kept in the tests.
  • The clear-text query: c= the community key in z-base-32 (required: invite has no community key), r= and p= comma-separated lists, i= z-base-32, g= base64url genesis wire. Unknown keys are ignored.

What opening one does

lanes: Person | Web app | Core Person -> Web app: opens …#/join?code=… or pastes a link Web app -> Core: previewInvite("hoi://join?" + query) Core: Invite::parse; refuses a private community's key Core: checks the genesis in g: decodes, verifies its signature, kind is community, its key is c, content rules hold Core --> Web app: name, color, description, limits, owners, relays, peers, trackers, verified Web app: shows the card: retention, admission, newcomer posts, the stamp in bits and time Person -> Web app: Join (after the join warning) Web app -> Core: join(link) Core: stores the genesis, keeps up to 16 valid peer routes and 8 valid relays, and up to 2 trackers Core --> Web app: the community; sync starts with the routes

Without g, the preview falls back to a genesis this device already holds or one a directory listing brought; with none of those it answers "This invite doesn't carry the community's details". Routes from an invite are hints: remember_hints keeps only those that pass route validation, fresh ones first. What happens next is on Joining, step by step.

Node links

A public node's address, for anyone to open: no credential and no community. Whoever opens one connects to that node, sees the open communities it carries and hears of the other public nodes it reached (Discovery). A node offers its link only while it serves strangers (node_link): its WebRTC and native routes, those on the internet first, then those on its own network, and its operator's notice with the endpoint key's signature when it has one. hoi-node writes it to DIR/node-link and prints it with a line saying what it holds ("it holds 1 WebRTC route and 1 native route, and the operator's notice, signed; the addresses are packed into the code").

Fields in the code

vuintyesmust be 1

Empty strings in w and p are skipped. After decoding, a link needs at least one route (node link has no address), a notice needs its signature and a signature needs its notice. A code that isn't masked is refused rather than read. The endpoint a notice is checked against is the key of the first native route (NodeLink::endpoint).

The notice and its signature

The notice is what the operator tells people before the node serves them: what it processes and keeps, and, if the operator says, who runs it, how to reach them and where the server is (hoi-node covers writing one). In the link it travels as its canonical CBOR bytes (one-letter keys); its hash is BLAKE3 of those bytes; the signature is over the UTF-8 statement

hoi node notice v1
<endpoint key, 64 hex>
<notice hash, 64 hex>

Naming the endpoint means a notice signed for one node means nothing in another node's link. The vector in node-notice.json carries such a link: 638 characters with the notice, starting hoi://node?code=SE9OAV1m6-1etSPt…, beside its clear-text form of 590 characters. Deflated, a plain notice keeps the link short enough for a QR code; a test requires under 900 characters.

The clear-text form

Earlier links spelled the same fields out: w=<fp>@<addr>,…, p=<endpoint>@<addr>,…, nt= the notice deflated and base64url (at most 2,048 bytes packed and inflated), ns= the 64-byte signature in base64url. They still open, with the same checks; a code beside any of w p nt ns is refused.

What opening one does

lanes: Person | App | Core | Public node Person -> App: opens …#/node?code=… or pastes it under Communities App -> Core: previewNodeLink(link) Core: parses it; the first route with an address gives host and its scope Core: with a notice: checks size and format, the endpoint, and the signature over the statement Core --> App: {host, scope, endpoint, notice, verified, problem} App: shows where it points and the notice, or a box to tick when there is none Person -> App: Accept and connect App -> Core: acceptNotice(node, hash), then openNodeLink(link) Core: refuses unless that notice was accepted (the consent gate); keeps up to 2 routes of each kind App -> Public node: dials the routes Public node --> App: its hello, with the notice it carries

The consent gate is on in browsers, the desktop app and phones, never on a headless node: there a link whose notice the person hasn't accepted by its hash is refused (Read and accept the operator's notice first.). A link without a notice opens, but the web app asks the person to tick "I understand, and want to connect to this node anyway" first. open_node_link drops routes that are this device's own, keeps the node first among at most 32 known nodes, and passes its routes on to others only once it has answered as a public node. Declining a notice leaves the node uncontacted.

Pairing links

Pairs a browser or phone with a home node: the device then syncs its communities through that node. A home node serving paired devices shows its current link (Serving.pairing and pairing_web); hoi-node writes it to DIR/pairing-link, readable only by its user, and prints it only with --show-pairing or --new-pairing, because the link is a credential.

Fields in the code

KeyTypeRequiredHolds
vuintyesmust be 1
utextyes (may be empty)the WebSocket address; empty when the node is reachable only over WebRTC
ttextyesthe pairing token; empty counts as missing
w[text]yes (may be empty)WebRTC routes without rtc:, at most 4 written and read
ntextnothe node's name, as the link says ("lena's laptop")

After decoding, the address must be wss://, or ws:// only to this very machine: localhost, 127.0.0.0/8 or [::1], with nothing before the host that could smuggle another one in (ws://localhost@evil/ is refused). Plain ws:// to anywhere else carries the token unencrypted and is refused (a home node elsewhere needs wss:// (or its WebRTC routes)). No address at all is fine when there are WebRTC routes, since a phone on the same network can reach the node over WebRTC without a certificate. A token is required. The clear-text form u=…&t=…&n=…&w=… (routes comma-separated) still opens; a code beside any of those keys is refused, and a pairing code is never accepted unmasked.

The token is spent once

A home node's pairing token (serve_token) is 18 random bytes in base64url, 24 characters. It pairs exactly one device: that device is given a credential of its own and the link is replaced, so a link left in a screenshot or a browser history pairs nobody else.

lanes: Device | Home node Device: pair(link): stores the address, token, name and valid routes as its home Device -> Home node: connects over wss:// or WebRTC; hello with token = the link's token Home node: compares it with the current link token in constant time Home node: issues a credential (32 random bytes), keeps only its digest, replaces the link token with a fresh one Home node --> Device: hello with token = the credential, pairing = the next link's token, link_key Device: keeps the credential, remembers a digest of the spent token, keeps the next link to show other devices

A home node keeps at most 32 paired devices (the least recently seen goes first) and stores only digests of their credentials. A device opening a link it already spent gets its existing pairing back instead of an error, and previewPair tells the app it is "already paired here" when the link's token is the spent one, the next one or the current credential. The web app removes the token from the address bar and the browser history the moment pairing succeeds (router.replace('#/pair')).

Where a link points

Before a person connects, the apps say whether a link points at this device, at a computer on their network, or at the internet. For node links the core decides (ip_scope): loopback is device; private, link-local, broadcast, 0.0.0.0/8 and carrier-grade NAT (100.64.0.0/10) IPv4, and unique-local or link-local IPv6, are network; anything else is internet. For pairing links the web app decides from the address and routes previewPair returns, in describeHome:

const local = (h: string) => h === 'localhost' || h === '::1' || /^127\./.test(h);
const lan = (h: string) => /^(10|192\.168|169\.254|172\.(1[6-9]|2\d|3[01]))\./.test(h) || /^(f[cd]|fe80)/i.test(h) || h.endsWith('.local');
const scope: HomeScope = hosts.every(local) ? 'device' : hosts.every((h) => local(h) || lan(h)) ? 'network' : 'internet';

Every host in the link counts: one internet address makes the whole link "on the internet", and the pairing page then asks "Yes, connect to …" and warns that everything posted would pass through that node. The name in a link is "whatever the link says"; the address is what the device dials.

In the web app

The web app is a hash-routed single page (router.ts), so links work under any base path. Three routes take a link's query verbatim and hand it to the core; the app never reads a code itself.

With a query it shows the preview card ("✓ signed details check out" when the genesis verified), and joins after the join warning.

Public join pages

#/public?c=<key>&name=<name>&p=<protocol> is the page a registry listing links to ("Review and join"). It carries no routes and no genesis, only what a registry already publishes, and publicTarget checks it strictly before anything happens:

ParameterRule
crequired: the full community key, 64 lowercase hex digits
nameoptional: a registry name, ^[a-z0-9][a-z0-9._-]{0,31}$
poptional: a protocol label, ^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$; the page can join only if it is empty or one of the release's supportedProtocols

Joining looks the name up in the registry again and refuses if the listing's community or protocol differs ("This public link does not match the verified community name"), then asks the core to join through at most 16 public routes: nodes that announced they carry the community first, then the registry's general list. Registry covers the listings.

Desktop and hoi-node

  • Desktop. The Tauri app registers the hoi URL scheme (tauri-plugin-deep-link). open_link turns hoi://join?… (or hoi://join/?…) into #/join?… and hoi://pair?… into #/pair?… and shows the window there; a second launch with a hoi:// argument is handed to the running instance. It doesn't route hoi://node? links; those open in the app's Communities screen or from their https form.
  • hoi-node. --node LINK (repeatable) takes a node link in either form and refuses anything NodeLink::parse won't read. The node writes its own node link to DIR/node-link while it serves strangers (removing the file when it stops) and its pairing link to DIR/pairing-link; --new-pairing issues a new pairing link, so devices paired before must pair again. --public-url URL puts a wss:// TLS proxy address in pairing links.

Vectors

uris.json pins the invite encodings for the community of seed 01…01: its key in hex and z-base-32, the masked invite and invite_web (genesis only), routed_invite with its routed_peers, routed_relays and routed_trackers, the unmasked v1_invite and v1_invite_web, the clear-text legacy_invite and legacy_invite_web, the genesis id and a root's did_key_root. Every one of them must parse to the same community. node-notice.json pins a notice's canonical bytes, hash, statement and signature, and the node link and clear-text link that carry it.
