Releases & verification

How a version is prepared, tested, built, signed and uploaded as a draft, what the release list says about every file, which parts anyone can rebuild byte for byte, how you check a download yourself, and how the apps learn about a new notice without ever being told to wipe anything.

Source release.json docs/RELEASES.md release-version.mjs release-manifest.mjs reproduce.mjs release.yml release-version.yml verify/

Versions

Three numbers travel separately. The product version (now 1.0.0-preview.1) names a build of every program. The protocol version (now "0.3") names the family of formats a build speaks. The index version (now 1) names the registry index edition. A release changes the product version every time; it changes the other two only when someone asks for it explicitly.

The product version

A release's tag is v plus the product version, and every first-party manifest must carry exactly that version. versionFiles() in scripts/release-version.mjs lists them:

FileWhere the version is
core/Cargo.toml[workspace.package] version: the one read first, and the one whose change starts an automatic release
apps/desktop/src-tauri/Cargo.toml, apps/setup/src-tauri/Cargo.toml[package] version
apps/desktop/src-tauri/tauri.conf.json, apps/setup/src-tauri/tauri.conf.jsontop-level "version"
apps/*/package.json, packages/*/package.jsontop-level "version", for every one that has a version (the root package.json has none)
core/Cargo.lock, apps/desktop/src-tauri/Cargo.lock, apps/setup/src-tauri/Cargo.lockthe version of every local hoi-* package (those without a source); external and vendored crates keep theirs

The pnpm lockfile uses workspace links and needs no edit. The mobile wrappers use the Rust workspace version and have no version of their own. Versions are SemVer; prereleases and 0.x versions default to the preview channel, everything else to stable, and a prerelease can never be stable. The intended sequence is 1.0.0-preview.1, 1.0.0-preview.2, …, optionally 1.0.0-rc.1, then 1.0.0, with a new version for every published release.

release.json

The root release.json is the one manifest every surface reads: the channel, the notice everyone sees, and the compatibility it declares. It is compiled into the site, the app and the Rust core, so a build always knows what it is even offline.

{
  "schemaVersion": 1,
  "revision": 1,
  "channel": "preview",
  "protocolVersion": "0.3",
  "indexVersion": 1,
  "supportedProtocols": ["0.3"],
  "notice": {
    "title": "Preview — unstable",
    "message": "hoi is in development. Protocol changes may cause data loss. Do not rely on this preview to preserve data."
  }
}
schemaVersion1
Must be exactly 1. Anything else fails closed.
revisionpositive safe integer
Goes up by one whenever any release metadata changes. A newer notice wins only with a revision at least as high as the one already shown.
channel"preview" | "stable"
Preview builds show the warning banner, set GitHub's pre-release flag, and keep the app out of search results.
protocolVersionstring
1–64 characters of [A-Za-z0-9._-], starting with a letter or digit. Bound into every community publication proof this build signs.
indexVersioninteger 1 – 2,147,483,647
The registry index edition, independent of the product version. Also bound into publication proofs.
supportedProtocols1–16 strings
Distinct versions, each in the same format, and it must include protocolVersion. The app joins a public listing only if its protocol is in this list and its index version equals this build's.
notice.title1–100 characters
Not blank after trimming.
notice.message1–1200 characters
Not blank after trimming.

validateRelease() in scripts/release-schema.mjs enforces all of this and returns a copy with exactly these fields, dropping anything else; release-schema.d.mts declares it as the ReleaseConfig interface. loadRelease() in release-config.mjs refuses a file over 16 KiB, and the Rust copy in hoi-node/src/registry/release.rs applies the same rules with the same message.

Metadata never wipes

Changing a notice does not reset device data, migrate storage or re-sign existing community proofs. Release metadata is informational: no notice, channel, index or protocol label deletes IndexedDB or keys. The Rust storage format guard is a separate mechanism. Rebuild native, WASM and UI artifacts together when compatibility fields change, and never list a protocol you have not tested.

Preparing a version

pnpm release:version (scripts/release-version.mjs) edits files and nothing else: no build, commit, tag, push, deployment or network access.

pnpm release:version                              # show and check the current version
pnpm release:version 1.0.0-preview.1 --dry-run    # preview the edits
pnpm release:version 1.0.0-preview.1              # prepare it
pnpm release:version --check 1.0.0-preview.1      # verify all manifests and lockfiles
pnpm release:version 1.0.0-preview.2 --protocol 0.4 --index 2
pnpm release:version 1.0.0-preview.2 --protocol 0.4 --supported-protocols 0.3,0.4
OptionEffect
VERSIONSemVer, optional v prefix; validated by releaseTier()
(nothing)the same as --check on the current version
--dry-runprints the plan, writes nothing
--checkevery manifest and lockfile has the version, release.json is valid, a prerelease is on preview; prints vX: channel, tier checks. Can't be combined with editing options
--channel preview|stableoverrides the default (preview for 0.x and prereleases); a channel change replaces the notice with that channel's default
--protocol VERSIONsets protocolVersion; a changed protocol resets supportedProtocols to just itself
--supported-protocols LISTan explicit comma-separated list, only for formats this build really supports
--index NUMBERa positive integer for indexVersion
--notice-title TEXT, --notice-message TEXTcustom notice words
--github-outputwith --check: appends version, tag, tier, channel and prerelease to GITHUB_OUTPUT

planVersion() reads and validates every file before it writes any of them, so a malformed manifest late in the list prevents every earlier write. Any change to the release metadata raises revision by exactly one; repeating an identical command changes nothing. Line endings are preserved (a Windows checkout's CRLF stays CRLF). The default notices are "Preview — unstable" (the text above) and "Stable release" / "This build is on the stable release channel."

Then review the edits, run pnpm check:quick, and commit only the intended changes, for example as chore(release): v1.0.0-preview.1, and push to main. With automatic releases on, that push starts the pipeline; there is no separate local tagging step.

release-plan.mjs

For an automatic run (a push), it releases only when all of these hold; otherwise it prints why and sets release=false:

  • the ref is refs/heads/main;
  • there is a previous commit (an initial branch push, all zeros, never releases: use a manual run for the first release of an imported repository);
  • the previous commit's core/Cargo.toml has a workspace version, and it differs from the current one.

Then, for manual runs too, checkVersion() must pass, the tag vX must not exist on any other commit ("existing tags are never moved"), and it outputs release, version, tag, tier, channel, prerelease, sha and create_tag (false when the tag already points at this commit, so a retry reuses it). A malformed previous SHA or missing history fails the job rather than silently releasing.

The GitHub release pipeline

Two workflows. Release: version turns a committed version into a tag; Release turns a tag into a signed draft. A tag made with the built-in token doesn't trigger push workflows, so the first explicitly dispatches the second.

lanes: Maintainer | Version | Release | GitHub release -- Version -- Maintainer -> Version: push to main with a new version in core/Cargo.toml, or Run workflow Version: plan: release-plan.mjs decides Version -> GitHub release: create refs/tags/vX on the validated commit (if new) Version: check that vX still names that commit Version -> Release: gh workflow run release.yml --ref vX -f tag=vX -f desktop=… -- Validate -- Release: plan: tag format, release-version.mjs --check, tier, pin the commit Release: checks; for a major tier also long, security, npm-audit Release: signing: every needed secret present? -- Build -- Release -> GitHub release: create the draft (pre-release flag from the channel) Release => GitHub release @sky: desktop and setup bundles, hoi-node archives and digests, side by side Release => GitHub release @coral: manifest.json, manifest.json.minisig, install.sh, install.ps1; a provenance attestation -- Publish -- Maintainer -> GitHub release: publish the draft by hand

Release: version (release-version.yml)

Triggers: a push to main touching core/Cargo.toml (with HOI_RELEASES_ENABLED, in hoi-project/hoi), or a manual run on a selected branch with a desktop boolean (default true); the version is read from that commit, no tag input. plan checks out github.sha with full history and runs release-plan.mjs. start (with contents: write and actions: write) creates the tag through the GitHub API when needed, refuses if the tag no longer matches the validated commit, and dispatches Release. Its success only means the build was started; follow the Release run.

Release (release.yml)

Triggers: a pushed v* tag (the switch), or a manual run naming an existing tag, with desktop (default true; off releases hoi-node only, without the setup app either). Runs for one tag never cancel each other.

The public key

The release signing key is not published yet. The verify page shows a placeholder, and both installers ship with an empty default key (RELEASE_PUBKEY="", -PubKey ''): until one is given with --pubkey/-PubKey, they check every file against the list's SHA-256 only and say so. With a key, a missing .minisig or a signature that doesn't verify stops the install; without minisign installed, they note that the signature went unchecked.

Reproducible builds

scripts/reproduce.mjs builds the parts of a release that come out byte for byte the same on any machine with the same toolchains, and prints their SHA-256. What makes the bytes the same: the toolchain in core/rust-toolchain.toml, --locked Cargo and the pnpm lockfile, every build path remapped, and a fixed environment.

PartBuilt withDigest of
wasmnode scripts/build-wasm.mjs (wasm-bindgen and wasm-opt included)apps/web/src/lib/core/wasm/pkg/hoi_wasm_bg.wasm
nodecargo build --release --locked -p hoi-node [--target T]the hoi-node (or hoi-node.exe) binary

The environment is the caller's plus SOURCE_DATE_EPOCH set to the commit's time (git log -1 --format=%ct, or 0 without Git), TZ=UTC, LC_ALL=C, CARGO_INCREMENTAL=0, and the build-path remapping. The tree digest hashes each file, sorts the lines path sha256 (forward slashes), and hashes the joined text with a final newline, so it depends on paths and bytes, never on order or times:

const lines = files.map((p) => `${relative(dir, p).split('\\').join('/')} ${sha256(readFileSync(p))}`).sort();
return { digest: sha256(lines.join('\n') + '\n'), files: lines.length };

The digest in a .digests.json file is of the binary inside the archive; the archive's own SHA-256 is in manifest.json.

Not byte for byte

The desktop and setup installers are signed per platform and carry their own timestamps and certificates. Their programs are built the same way from the same sources; their packaging is not reproducible.

Checking a download

The verify page walks through it. The app you run is the trust boundary: it checks every record it receives, but it can't check itself.

  1. Find the checksum

    Every file has its SHA-256 in manifest.json; the download page shows it next to the file with a copy button.

  2. Hash your file

    shasum -a 256 FILE on macOS, sha256sum FILE on Linux, certutil -hashfile FILE SHA256 or Get-FileHash FILE -Algorithm SHA256 on Windows. It must match character for character (case doesn't matter). If it doesn't, delete the file: a broken download and a swapped one look the same.

  3. Check the list is the project's

    Put manifest.json and manifest.json.minisig in one folder and run minisign -Vm manifest.json -P <public key>. It should say "Signature and comment signature verified". Compare the key on the verify page with the one in the repository next to the release notes; if they ever disagree, trust neither.

  4. Or build it yourself

    Check out the release tag, pnpm install --frozen-lockfile, node scripts/reproduce.mjs, and compare: the WASM, hoi-node and the website come out byte for byte the same. For one hoi-node: node scripts/reproduce.mjs --only node --target <triple> --compare hoi-node_<v>_<triple>.digests.json. The desktop app needs Tauri's prerequisites and pnpm --filter @hoi/desktop tauri build.

The installers do the SHA-256 part on their own: install.ps1 refuses a file whose hash differs from the list (the major suites test exactly that on Windows PowerShell 5.1), and install.sh the same (scripts/install.test.mjs). A folder of release files installs as it is, offline too: install.sh uses the manifest.json beside it.

Desktop bundles and installer art

Which Windows bundles a version gets

Windows Installer (.msi, made with WiX) takes numeric versions only, and Tauri refuses any other only after the whole build has run. msiTakesVersion() in scripts/tauri-bundles.mjs checks a version the way Tauri's bundler does: major and minor at most 255, patch at most 65535, and a prerelease (or build metadata, which Tauri reads first) that is a number up to 65535. When it says no, windowsBundles() adds --bundles nsis to a Windows tauri build, unless bundles were chosen on the command line. Both apps' scripts/tauri.mjs call it, so a preview such as 1.0.0-preview.1 builds only the NSIS setup (*-setup.exe, the one install.ps1 prefers) and 1.0.0 gets both.

findBundles() walks a Tauri target folder for .dmg, .msi, .exe, .AppImage, .deb and .rpm files, skipping .app folders; release-local.mjs and build-all.mjs both use it. releaseBundleName() turns the setup app's hoi Node Setup_… (with spaces, from its product name) into hoi-node-setup_….

How the apps learn about releases

No app downloads or installs a new version on its own: neither Tauri app includes an updater plugin. What updates by itself is the browser app's code, through its service worker, and every app's notice, through release.json.

The browser app's code

Production web builds register sw.js (never in development, inside Tauri or in sandbox builds) and call reg.update() every hour while the app is open. A new worker precaches every file of its build and checks each against the SHA-256 the build recorded; when it is installed and waiting, the app offers "A new version is ready · Reload", and only that click sends skip-waiting. The worker never serves release.json from its cache, so an installed worker can't freeze a notice (Supply chain).

Notices

lanes: App | Same origin or registry App: shows the notice compiled into this build, at once and offline App -> Same origin or registry: GET release.json: no credentials, no referrer, no-store, redirects refused, 5 s timeout Same origin or registry --> App: release.json App: validateRelease(); kept only if its revision is at least the current one App: noticeForBuild() picks the words to show App .. Same origin or registry: again every 60 s and whenever the page becomes visible

The app asks the registry it was built with (/release.json there), else the release.json beside the app. A registry is someone else's server, so with one configured the app doesn't ask until the person has accepted the Network & Safety notice. An invalid or unreachable answer keeps the bundled warning. The website itself fetches nothing: every page carries the notice it was built with.

export function noticeForBuild(build, remote) {
  const current = remote && remote.revision >= build.revision ? remote : build;
  const sameBuildFamily = current.protocolVersion === build.protocolVersion
    && current.indexVersion === build.indexVersion && current.channel === build.channel;
  const notice = sameBuildFamily ? current.notice : build.notice;
  return {
    title: notice.title, message: notice.message,
    build: `${build.channel} · protocol ${build.protocolVersion} · index ${build.indexVersion}`,
    preview: build.channel === 'preview',
    update: sameBuildFamily ? '' : `Operator update: ${current.notice.title}. ${current.notice.message} …`,
  };
}

So a newer notice can change the words for the same build family, but never relabel what this build is: if the remote file names another protocol, index or channel, the banner keeps this build's own notice and adds one line, "Operator update: … Current protocol P, index I. This installed build remains preview." The compiled protocol snapshot that signs publication proofs is not affected by any runtime file.
