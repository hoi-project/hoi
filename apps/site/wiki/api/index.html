Core API

Every hoi interface talks to the same thing: a Node in hoi-core. The web app and the desktop call it with JSON (Node::call("createPost", [draft])), phones call typed UniFFI methods, and all of them get the same data shapes back, the same events and the same error codes. This page lists every method, the main data types field by field, and how each host carries a call.

Source hoi-core/src/dispatch.rs · api.rs · dto.rs · error.rs · packages/core-api/src · hoi-wasm/src/lib.rs · hoi-ffi/src · apps/web/src/lib/core

One API, four ways in

UIs never touch keys, storage or the network. They call HoiCore, the TypeScript interface in packages/core-api/src/types.ts, or its typed mirror on phones. Behind it the same Rust code runs everywhere:

The rule that keeps the shells honest is in dto.rs's first line: the Rust DTOs mirror types.ts field for field, in camelCase, and both files change together.

lanes: Page | Core worker | WasmNode | Storage Page -> Core worker: {id, method, args} (args copied through JSON first) Core worker -> WasmNode: call(method, JSON.stringify(args)) WasmNode: Node::call runs the method, then commit() WasmNode --> Core worker: JSON result, or a JSON {code, message} error Core worker -> WasmNode: take_changes() Core worker => Storage: the changes, sealed by the vault, in one write Core worker -> WasmNode: take_outbox(), then take_events() Core worker --> Page: {kind: "event", event} for each event Core worker --> Page: {kind: "reply", id, ok: true, result}

Messages go out and events reach the page only after storage accepted the changes (durable-settle.ts): a record is never gossiped, and the UI never hears of a change, before it is durable.

Node::call: the JSON dispatcher

dispatch.rs is one function that takes a method name and positional arguments, runs the method and persists:

impl Node {
    /// Calls one API method with positional JSON arguments, then persists.
    pub fn call(&mut self, method: &str, args: Value) -> R<Value> {
        let a = Args(match args {
            Value::Array(v) => v,
            Value::Null => Vec::new(),
            other => vec![other],
        });
        let out = self.call_inner(method, &a);
        self.commit()?;
        out
    }
}
Argumentspositional
A JSON array in the order HoiCore declares them. null means no arguments; any other single value is taken as the one argument. A missing argument reads as null, so optional trailing arguments may be left out.
Bytesbase64url
Images, files, nonces' puzzles and exports travel as base64url strings without padding (hoi_types::uri::b64). An optional bytes argument that is absent or null is empty.
Keys and idshex
Lowercase hex, 64 characters. Where a person's key is expected, parse_key also takes a did:key.
Bad argumentsinvalid
An argument that does not deserialize fails with code invalid and argument <name>: <serde error>; an unknown method with unknown method <name>.
Persistenceafter every call
commit() runs even when the method failed, so whatever it changed before failing is saved and the journal is retried. If commit() itself fails, that error replaces the method's result.
function call(method: string, args: unknown[]): unknown {
  if (!node) throw { code: 'offline', message: stolen ? 'hoi is open in another tab. Reload to use it here.' : 'hoi is still starting.' };
  try {
    return JSON.parse(node.call(method, JSON.stringify(args)));
  } catch (e) {
    throw toError(e);
  }
}
let draft = serde_json::json!([{ "community": community_hex, "title": "hello", "text": "first post" }]);
let post = node.call("createPost", draft)?;          // a PostSummary as JSON
let feed = node.call("feed", serde_json::json!([{ "community": community_hex, "sort": "fresh" }]))?;

All methods call_inner knows, in the groups of HoiCore. Argument names are the ones the dispatcher reports in errors; ? marks an argument that may be null or left out. Return types are the DTO names in dto.rs (the same names in types.ts unless noted); null means the method returns nothing.

Three methods live in the hosts

takeOver is answered by the web worker (it steals the one-tab lock, then calls boot). previewPublicNode and vpnInterfaces are answered by the desktop shell's hoi_call before it reaches the core: the core does not talk to routers or list network interfaces.

Draft, mine, publish

A post, a reply or an edit needs a stamp: about a second of hashing. Doing that inside one core call would freeze the worker or hold the node's lock, so rpc-core.ts splits it in three. The core builds and signs nothing until the nonce comes back; it only hands out the puzzle, the canonical bytes before and after the nonce.

lanes: UI | rpc-core.ts | Core | Miners UI -> rpc-core.ts: createPost(draft) rpc-core.ts -> Core: looked(hash, look) for each picture (browser only) rpc-core.ts -> Core: draftPost [draft] Core --> rpc-core.ts: DraftDto {token, prefix, suffix, bits} rpc-core.ts: emits stamp {phase: "start", bits, estimateMs} rpc-core.ts => Miners: mine(prefix, suffix, bits) Miners --> rpc-core.ts: nonce rpc-core.ts -> Core: publishDraft [token, nonce] Core: checks stamp_bits(id, nonce) ≥ bits, signs, takes it in, queues gossip Core --> rpc-core.ts: PostSummary (or {signing: id}) rpc-core.ts: emits stamp {phase: "done", tookMs} rpc-core.ts --> UI: PostSummary
  • Browsers mine with a pool of miner.worker.ts workers (one fewer than navigator.hardwareConcurrency, between 1 and 4), each calling mine_range on every n-th nonce in chunks of 20,000.
  • The desktop mines with the hoi_mine Tauri command on a blocking thread, without the node lock; its rate comes from hoi_benchmark.
  • Phones do the same inside HoiNode: draft under the lock, mine_puzzle without it, publish under it again, and emit the two stamp events themselves.
  • If the miners can't run, rpc-core.ts falls back to the core's own mine (native) or, for a new identity, to createIdentity.
  • On a browser whose computer signs for it, publishDraft returns {signing: id}; rpc-core.ts waits up to 120 seconds for a signed event, then calls published.

New identities go the same way: draftIdentity returns an IdentityDraft, the host mines the Argon2id work (the browser across its miners with IdentityMiner, reporting every try), and publishIdentity(rootKey, work) finishes it.

HostDelivery
Web workerJSON.parse(node.take_events()) after storage committed, each posted as {kind: "event", event}; worker-core.ts hands it to every subscriber.
DesktopShared's event sink calls app.emit("hoi://event", e) for each; tauri-core.ts listens on that channel.
PhonesEventListener.on_event(json), one JSON string per event, on a background thread. events.rs drops net events identical to the last, notes the last changed (to tell when a sync burst has gone quiet), and writes the time the home node was last reached to last-sync at most every 30 seconds.
Native hosts in generalhoi_net::Shared::with commits, then takes the events and calls the sink. When commit() fails it sends one notice (“This node could not save changes. Sync is paused…”), drops the outbox and closes every link; on recovery it adds “Storage is working again…”.

Errors

Every failure is an ApiError { code, message }: a code a UI can branch on and a sentence a person can read, shown as is. Over JSON it is {"code": "…", "message": "…"}; in TypeScript a HoiError (an Error with code); over UniFFI HoiError::Api { code, message }, whose message Kotlin calls reason.

The TypeScript ErrorCode union lists the first thirteen; the others arrive as strings in HoiError.code. A refused record maps from hoi_validate::Reject: RateLimited, Banned, TooBig, Expired to their codes, Content to invalid, UnknownCommunity to not-found, NotAllowed, WeakIdentity and Burned to not-allowed, NoIdentity to no-identity, anything else to invalid; messages are capitalized and end with a period.

The web worker and the desktop shell

Worker messages

worker-core.ts starts core.worker.ts as a module worker named hoi-core and speaks a small protocol over postMessage:

DirectionMessageMeaning
page → worker{id, method, args}A call; args are copied through JSON.parse(JSON.stringify()) first, which also strips Svelte's state proxies.
worker → page{kind: "reply", id, ok, result} or {…, ok: false, error}The answer.
worker → page{kind: "event", event}A CoreEvent.
worker → page{kind: "locked"}Another tab took over: the page tears down and reloads.
worker ↔ pagertc-open, rtc-send, rtc-close, direct-offer, direct-answer, direct-accept; {kind: "rtc", ev, id, …} backWorkers can't open WebRTC, so the page carries those links.
worker ↔ page{kind: "look", id, mime, data}; {kind: "looked", id, look} backMedia the core wants looked at in the page's look worker.

Methods beginning with __ never reach the core: __init (web base, store name, take the one-tab lock), __vaultStatus (create, migrate, locked, ready or blocked), __unlock, __vaultPasskeys, __unlockPasskey, __addPasskey, __removePasskeys, __resetVault (needs "RESET"), __lock and __takeOver. A few core methods get extra work around them: boot answers without the core when another tab holds the lock, pair and unpair reconnect the home link, publicJoin, openNodeLink and acceptNotice dial right away, setSettings closes direct links when they were turned off, and wipe restarts every link.

Everything that touches the node or storage runs through one promise queue (run), so calls, incoming messages, timers and the sweep never interleave. After a storage failure, no new call runs until the pending changes are saved again. A timer runs scatterTick() every 5 seconds and sweep() every 36th round (about every three minutes); a watchdog every 30 seconds closes links whose catch-up stalled.

Every method blocks its thread while it reads storage, validates, mines or writes. The app implements two foreign traits: KeyStore (get(key), set(key, value?); Keychain on iOS, an AES-GCM key in the Android Keystore on Android) and EventListener (on_event(json)). Both are called on background threads and must not call back into HoiNode.
