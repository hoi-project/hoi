One core, many shells

hoi is one Rust core that does all the thinking (records, keys, checks, moderation, sync) wrapped in thin shells: a browser app, phone libraries, a desktop app, a headless node and a setup wizard. They all speak the same protocol to each other over a handful of transports. Nothing in the middle is required, and nothing the project hosts is more than static files.

The core, layer by layer

The crates form a strict stack: each depends only on the ones below it, so the pure parts (types, crypto, validation) build for every target, including WebAssembly and the WASI test runner, and know nothing about networks or disks.

  1. hoi-types

    What a record is, byte for byte: the envelope, every kind's body, canonical DAG-CBOR with a strict decoder, ids, limits, did:key, hoi:// links. Records & encoding.

  2. hoi-crypto

    Ed25519 with weak keys refused, BLAKE3 stamps and the miner, Argon2id identity work, the keystore, Shamir, sealed boxes, scattered pieces and HPKE envelopes. Stamps & work, Keys & identity.

  3. hoi-validate

    The pipeline's pure stages: decode, stamp floor, signature and consent, identity, time, rate windows, content. Validation pipeline.

  4. hoi-store, hoi-moderation, hoi-trust, hoi-spam, hoi-sync

    What a device remembers, what a community decided, whom you trust, who misbehaved, and how two devices compare notes. Storage, Communities, Trust, Spam, Sync.

  5. hoi-core

    The Node: one object holding all of it, with one entry point for the interfaces (Node::call, JSON in and out) and one for the network (messages in, effects out). Core API.

  6. hoi-net, hoi-wasm, hoi-ffi, hoi-node

    The edges: real sockets for native programs, bindings for browsers and phones, and the headless binary. Transports, Crates.

A post, end to end

What happens between pressing Post in the web app and the post showing up on a member's device. The stamp is mined outside the core, by a pool of workers, so the interface never freezes.

lanes: Interface | Core worker | Miner workers | Home node | Members Interface -> Core worker: draftPost {community, title, text, media} Core worker: builds and checks the record; media stripped and hashed Core worker --> Interface: draft {token, prefix, suffix, bits} Interface -> Miner workers: mine(prefix, suffix, bits) Miner workers: BLAKE3(id ‖ nonce) until enough zero bits Miner workers --> Interface: nonce Interface -> Core worker: publishDraft {token, nonce} Core worker: signs; the full pipeline accepts its own record; stored Core worker -> Home node @mint: recs [the post] Home node: checks it again, stores it Home node => Members @mint: recs to every connected member Members: each checks it before showing it

Every receiver runs the same pipeline; a device that was away gets the post later by range reconciliation. The method names are the core's dispatch names; see Core API.

Where it lives in the repository

Every crate above, the fuzz targets and the conformance vectors. Crates, Test vectors.

apps/interfaces

web, desktop, setup, mobile and site (this website and wiki).

packages/shared JS

core-api (the TypeScript types of the core's API), tokens (design tokens for CSS, Swift and Kotlin), vite-plugin-hardening (CSP and SRI).

The optional registry and encrypted relay, each as a Node.js server and a Cloudflare Worker.

deploy/templates

Static hosting, home nodes, servers and the installers. Deploying & hosting.

scripts/, sandbox/tooling

Builds, releases, checks, end-to-end tests and an isolated test network. Building & testing.

vendor/patched deps

Published packages with small reviewed patches. Supply chain, SBOM.
