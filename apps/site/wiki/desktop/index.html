Desktop companion

The desktop app is the web app's UI in a Tauri 2 window, over the native Rust core instead of the browser's wasm one. Because it is a real program, it can do what a tab can't: accept connections, stay awake in the tray, serve your browser and phone as their home node, and keep your communities reachable while the computer is on.

Source apps/desktop · src-tauri/src/lib.rs · tauri.conf.json · capabilities/default.json · scripts/tauri.mjs · apps/web/src/lib/core/tauri-core.ts

What it is

apps/desktop is the package @hoi/desktop; its Rust side is the crate hoi-desktop (library hoi_desktop_lib, edition 2024, Rust 1.94). The product is called hoi with the identifier sh.hoi.desktop, for Linux, Windows and macOS. The crate is a Cargo workspace of its own, so the core workspace builds without WebKitGTK; it depends on hoi-core and hoi-store with the sqlite feature, hoi-net, hoi-crypto and hoi-types by path, and patches the same vendored crates as the core (openmls_rust_crypto, openmls_basic_credential, dimpl, core-models, netdev).

It has two faces in one bundle. It opens as the companion: a small window and a tray icon with status, what passes through, a QR code for your phone and Open hoi in my browser, no forum and no key needed. The full app (read and post right here) opens from the companion or the tray menu and widens the window.

How the web UI is reused

There is no separate desktop UI. tauri.conf.json builds the web app before the shell:

"build": {
  "beforeDevCommand": "pnpm --filter @hoi/web dev:desktop",
  "devUrl": "http://localhost:5174",
  "beforeBuildCommand": "pnpm --filter @hoi/web build:desktop",
  "frontendDist": "../../web/dist-desktop"
}

build:desktop is vite build --mode desktop --outDir dist-desktop: __HOI_DESKTOP__ is true, there is no CSP <meta> (Tauri sets the policy), no service worker and no _headers. scripts/desktop-build.test.mjs checks that this build loads no browser workers and no generated wasm. In the window, src/lib/core/index.ts sees __TAURI_INTERNALS__ and picks tauri-core.ts; the screens are the same as in a browser (see Web app). A few things go to the shell directly:

What hoi_call adds

  • vpnInterfaces is answered by the shell itself: hoi_net::vpn::interfaces() as {name, label, tunnel, addresses}, the choices for "Only through my VPN".
  • previewPublicNode is answered by the shell too: the core doesn't talk to routers. It starts or ends asking the router which address it would forward, without publishing it, and returns the net status.
  • wipe first removes the router's forwards, then shuts down the iroh endpoint and WebRTC before the core erases their identities, keeps the serving URL, closes every client- link and starts fresh transports. The transport locks are held through the wipe so an endpoint can't publish its old address into the wiped node.
  • setSettings is followed by follow_vpn (the transports follow "Only through my VPN" at once), sync_forwarding and sync_pieces.
  • pair, unpair and wipe restart the link to this computer's own home node, if it is paired with one.

Starting locked

The app starts locked, including when launched at login. No node, keys, listener or network transport exists before the person unlocks the local vault; the tray tooltip says "hoi: unlock to connect". The vault is the same LocalVault as the browser's (a passphrase of at least 15 characters wraps a random data key with Argon2id at 64 MiB, three passes), stored through hoi_store::vault::EncryptedSqlite. There is no passkey unlock on the desktop. See Storage for the format.

  1. Status

    hoi_vault_status opens hoi.db in app_data_dir(): a vault header means locked, an empty database create, anything else migrate. A mutex (VaultStartup) serializes status, unlock and reset.

  2. Unlock

    On a blocking thread, open_vault_node unlocks the header, or, for an old plaintext database, first opens it through an in-memory Journal to prove it is valid and then creates a vault. Unsupported or damaged data is never rewritten just because someone tried to unlock it.

  3. Open

    Node::open(EncryptedSqlite, "desktop", "https://hoi.sh/app/", system_clock()), with the node named after the computer (COMPUTERNAME, /etc/hostname or hostname, without .local or .lan), so your phone and browser can call it that.

  4. Start

    start_unlocked builds the transports (next section) and shows the window, sized for the face the settings ask for.

Locking restarts the process

Hiding or reloading the webview would leave keys reachable by background transports and the tray, so hoi_vault_lock removes the router's forwards, then holds the node mutex, commits pending writes and calls app.restart() while still holding it: no background task can add a write between the flush and the end of the process. If the flush fails, the process stays up and the window reads "Changes could not be saved. Keep hoi open and restore storage access before locking."

Recovery while locked

hoi_vault_reset needs the exact confirmation RESET and is refused while the core is open ("Lock hoi before using recovery."). It removes hoi.db, hoi.db-wal, hoi.db-shm and hoi.db-journal and nothing else, without opening or parsing the database, so a malformed one can be cleared too. SQLite runs with secure_delete = ON and the WAL is truncated after a migration (wal_checkpoint(TRUNCATE)); that doesn't reach backups or filesystem snapshots.

Serving your browser and phone

The desktop is a home node for the person's own devices. A device that pairs gets a link with the WebSocket address, a token and the WebRTC routes; devices without the token are turned away, and nothing about them is logged.

  • The browser on the same computer connects over the loopback WebSocket. Open hoi in my browser (companion, tray, You → Connection) opens the node's pairing_web link in the default browser. Chrome asks before a website may reach apps on this computer ("Apps on device"); if it was blocked, the app says so under Home node.
  • A phone scans the QR code. Its browser opens hoi, connects over WebRTC on the same network (the link pins this computer's certificate) and can ask to be linked to your key; you compare four digits here.
  • Across the internet a phone reaches the computer through a forwarded port; with "Be a public node" on, the app asks the router itself.
lanes: Tray | lib.rs | Browser | Home node (this app) Tray -> lib.rs: menu item browser lib.rs: net_status().serving.pairing_web lib.rs -> Browser: open_url: an https:// link to the app with #/pair?… Browser: opens hoi, reads the pairing link Browser -> Home node (this app): WebSocket to ws://127.0.0.1:7842 with the token Home node (this app) --> Browser: paired; sync begins

The other direction works too: this computer can itself be paired with another home node (a hoi-node on a server). restart_home_link dials it with hoi_net::dial over WebSocket only (a WebRTC-only pairing link is for browsers and phones), stops the old link first, and with a VPN set waits until the VPN is up unless the home node is on loopback or, when allowed, the home network. Pairing itself is described on Links & URIs and Transports.

Being a public node

Off, the desktop publishes no address of its own. With Be a public node on, it serves strangers: it carries open communities for whoever asks, tells whoever connects about the other public nodes it reached, and asks the router to forward its ports so other networks can reach it.

Port forwarding

sync_forwarding collects the ports in use: the WebRTC port, the iroh endpoint's IPv4 ports and, while running, the DHT's two ports. It starts a hoi_net::portmap::PortMapper for them, through the default route, or through the VPN's own interface when one is set (the home router would publish the home). What the router forwards from goes into the advertised routes, and so into invites and the node link. While the person only previews (previewPublicNode(true) before turning it on), the mapper runs but nothing is published, so they see the address first. Turning it off, quitting from the tray or locking removes the forwards and the public addresses they added.

DHT, LAN and mailboxes

  • DHT: hoi_net::dht::start_dht runs among public nodes while this computer is one, bound to the VPN's IPv4 under "Only through my VPN" and stopped while that VPN is down. See Discovery.
  • LAN beacons: hoi_net::lan::start_lan on the native transport's first IPv4 port, for members of the same communities on the local network. Off under "Only through my VPN", because a beacon goes out on the home network.
  • Mailboxes for others: with hold_pieces_gb above zero while a public node, pieces.db beside the database keeps other people's private communities' sealed messages and pieces, which this computer can't read. Off, or no longer a public node, the file is deleted. See Mailboxes.

Only through my VPN

net_policy reads the setting into NetPolicy {vpn, home_network}; its state is Off, Up or Down. follow_vpn runs every 5 seconds and after each settings change, and acts only when the policy or the VPN's state changed:

  1. Report

    The VPN's status goes to the core (set_vpn_status) for the UI.

  2. Forwards off

    The router's forwards are removed.

  3. Native transport

    The iroh endpoint restarts bound to the VPN's IPv4 address when it is up, and doesn't start at all while it is down: the kill switch.

  4. WebRTC

    A new policy restarts it; a changed VPN only makes it rescan its interfaces.

  5. The rest

    Forwarding and the home link follow.

Start at login and single instance

  • tauri_plugin_autostart registers hoi with MacosLauncher::LaunchAgent and the argument --hidden: started at login, it stays in the tray with no window.
  • --start-at-login registers autostart from outside, for an installer (deploy/install uses it for the role companion), and shows nothing.
  • tauri_plugin_single_instance forwards a second launch to the running app: --start-at-login enables autostart, a hoi:// argument opens that link, anything else shows the window.

Permissions

The window's capabilities file grants the core set and nothing else:

{
  "$schema": "../gen/schemas/desktop-schema.json",
  "identifier": "default",
  "description": "The main window may call hoi's own commands and listen for core events. Nothing else: no shell, no file system, no HTTP from the UI.",
  "windows": ["main"],
  "permissions": ["core:default"]
}

So the plugins (dialog, opener, autostart, deep link) are only reachable through hoi's own commands, which decide what they may do.

Which links open

web_link(url) allows https:// anywhere, and http:// only to localhost or 127.0.0.1 with a numeric port. The authority is parsed, not prefix-matched: a URL longer than 4 096 characters, with control characters or whitespace, or with an @ in its authority is refused, so http://localhost:1@evil.example/ is not a local link. Anything else gets "Only web links open from here." The test only_web_links_open_in_the_browser pins the list, including file:///etc/passwd and hoi://join?c=1 as refusals.

Building it

Prerequisites: Node 22, pnpm 10, the Rust version in core/rust-toolchain.toml and Tauri's system libraries (on Linux libwebkit2gtk-4.1-dev libsoup-3.0-dev libjavascriptcoregtk-4.1-dev libgtk-3-dev librsvg2-dev libayatana-appindicator3-dev).

pnpm --filter @hoi/desktop dev      # the web UI on :5174 and the app around it
pnpm --filter @hoi/desktop build    # bundles for this system
pnpm --filter @hoi/desktop icons    # icon.svg → source.png → every platform size

scripts/tauri.mjs

Every package script goes through this wrapper rather than the Tauri CLI directly, so the native policy and the web bundle agree:

  • Registry: when the registry address is set it must be https: (or http: on loopback) with no credentials, query or fragment, and its exact origin is merged into connect-src. No wildcard origins.
  • Relays: each URL in the relay addresses is added the same way; the relative /relay is refused here ("Desktop relay URLs must be absolute HTTPS addresses.").
  • Windows bundles: Windows Installer (.msi, WiX) takes numeric versions only, so scripts/tauri-bundles.mjs adds --bundles nsis to a Windows build whose version it refuses, such as 1.0.0-preview.1, and prints why. Bundles chosen on the command line are left alone.

Release profile and deny.toml

The release profile is lto = true, codegen-units = 1, opt-level = 3, strip = true. src-tauri/deny.toml applies the core's cargo-deny policy with one difference: unmaintained = "workspace" flags unmaintained crates only when they are direct dependencies, because Tauri's GTK, zbus and URL-pattern stacks carry transitive ones the project doesn't control. Yanked crates are denied; licenses must be one of AGPL-3.0-only, Apache-2.0 (also with the LLVM exception), BSD-2-Clause, BSD-3-Clause, BSL-1.0, CC0-1.0, CDLA-Permissive-2.0, ISC, MIT, MIT-0, MPL-2.0, Unicode-3.0, Unlicense or Zlib at confidence 0.9; wildcards are denied; only crates.io is an allowed registry and unknown git sources are denied. See Supply chain.

pnpm build:all --only app copies this system's bundles into builds/hoi-<version>/app/ as hoi-desktop_<version>_<os>-<arch>…; signed release builds come from the release workflow. See Releases.
