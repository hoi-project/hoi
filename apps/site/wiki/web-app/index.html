Web app

The hoi app is a static Svelte 5 page. The screens never touch keys, storage or sockets: they call one interface, HoiCore, and a Web Worker running the Rust core as WebAssembly does the rest. The same build, in other modes, is the window of the desktop companion and of the node setup app. This page follows every thread, every file the app stores and every screen it has.

What it is

The app lives in apps/web (package @hoi/web, version 1.0.0-preview.1). It is Svelte 5 with runes switched on in svelte.config.js, built by Vite. Its runtime dependencies are short: @hoi/core-api (the HoiCore types, see Core API), @hoi/tokens (colors and fonts), @tauri-apps/api (used only inside the desktop shell), animejs 4.5.0 for motion and uqr for QR codes. Fonts and Anime.js are bundled, so the app makes no third-party request of its own.

One source tree makes three builds. Vite's --mode picks which:

CommandOutputWhat differs
pnpm --filter @hoi/web builddist/The PWA served at /app/: CSP <meta>, SRI attributes, sw.js, _headers, release.json.
build:desktop (--mode desktop, or HOI_TARGET=desktop)dist-desktop/The window of the desktop companion. No CSP meta (Tauri sets its own), no service worker, no _headers.
build:setup (--mode setup)dist-setup/The window of hoi Node Setup: root setup/, one page, no core, no worker, no service worker, no public/ folder.

Development has three more entry points: dev (the real core in a worker), dev:mock (the mock backend switch, a seeded in-memory core, no Rust needed) and dev:desktop / dev:setup on the fixed ports 5174 and 5175 that the two Tauri apps load. The wasm core itself is built once with pnpm core:wasm (scripts/build-wasm.mjs), which runs cargo build -p hoi-wasm --target wasm32-unknown-unknown --profile wasm, then wasm-bindgen --target web into src/lib/core/wasm/pkg/, then wasm-opt -O3 when binaryen is installed.

Rules the app keeps

No third-party requests. The relay pill is honest about being a browser: it says "only in this browser" until a home node is paired. Every signed action ends in a toast. Removed things show "Poof." with the reason and a link to the ledger. Reduced motion is respected and every view is complete at rest. Nothing scrolls sideways at 320 px.

Threads and backends

In a browser the app runs on up to seven threads. The page (the main thread) draws the screens, holds the reactive state and carries everything only a window can do: WebRTC, WebAuthn and the <video> element. One worker named hoi-core owns the node. A small pool of miner workers searches for stamps, and one look worker decodes pictures so that a decoder crash never takes the node down.

rpc-core: one interface over two transports

createRpcCore(transport, stamper, looker?) builds the whole HoiCore from two small things: a Transport with call(method, args) and subscribe(fn), and a Stamper that mines. Both the web worker and the Tauri shell speak call(method, args) to the core's JSON dispatcher, so almost every method is a one-liner such as ledger: (id) => c('ledger', id). Errors come back as {code, message} and become HoiError. Bytes cross the JSON boundary as base64url (toBase64Url, fromBase64Url).

Three kinds of call do more than forward:

  • Posts, replies and edits go draft, mine, publish, so the stamp is mined outside the core and the composer can draw its work bar. If the miners can't run, the page asks the core to mine itself (one thread, slower).
  • A new key is drafted by the core (draftIdentity, with the first-run gesture "stir" mixed into the core's randomness), its Argon2id identity work is mined by the pool with every try reported, then publishIdentity(rootKey, work). If the pool fails, createIdentity lets the core do the work unseen.
  • More key work (You → Key work) runs through mineMore, which can take minutes, reports progress and stops on abort.
async function stamped<T>(draftMethod: string, args: unknown[]): Promise<T> {
  const d = (await c(draftMethod, ...args)) as DraftDto;
  const estimateMs = stampEstimateMs(d.bits, await stamper.rate());
  emit({ type: 'stamp', phase: 'start', bits: d.bits, estimateMs });
  let nonce: number;
  try {
    nonce = await stamper.mine(fromBase64Url(d.prefix), fromBase64Url(d.suffix), d.bits);
  } catch {
    // The miners couldn't run here: the core stamps it itself (slower, one thread).
    nonce = (await c('mine', d.prefix, d.suffix, d.bits)) as number;
  }
  const published = await c('publishDraft', d.token, nonce);
  if (published && typeof published === 'object' && 'signing' in published)
    return (await signedThere(published.signing as string)) as T;
  return published as T;
}

The signing branch is for a browser whose computer signs for it: the core answers with an id instead of a record, the page waits for a signed event for that id and then calls published. If nothing comes within 120 000 ms it fails with offline and "Your computer didn't answer. Is it on and connected?". Pictures attached to a post are first passed to the looker's compose; a picture nothing here can read is refused with "That picture can't be read here, so nobody else could check it either."

core.worker.ts: one queue for everything

The worker imports WasmNode and WasmVault from the wasm package. Every call that touches the node or storage goes through run(f), which chains it on one promise queue, so two calls never interleave. After each call settle() runs: it drains take_changes() and saves them, then sends the outbox, then hands out events, picture looks, domain-name checks and direct-link signals.

/** Serializes everything that touches the node and storage. */
function run<T>(f: () => T | Promise<T>, retryPending = true): Promise<T> {
  const p = queue.then(async () => {
    // Do not accept another mutation while an earlier one still cannot be saved.
    if (storageFailed && retryPending) await settle();
    return f();
  }).then(async (v) => {
    await settle();
    return v;
  });
  queue = p.catch(() => undefined);
  return p;
}

The order inside settle matters. durable-settle.ts keeps the drained journal until storage has committed it, and only then calls flushOutbox() and emits events. A record is never sent to a peer, and never shown as saved, before it is on disk.

How the worker connects

The worker keeps three kinds of link, all named as peers of the node: home, member-N and node-N, plus direct-N for other browsers. Nothing connects before the person has read the Network & Safety notice (see Notices), because the core is only started after that. The protocol on the wire is the subject of Transports and Sync & gossip; here is what the app does around it.

Your home node

  1. WebSocket first

    node.home() gives {url, token, name, rtc}. The worker opens new WebSocket(url) with binaryType = 'arraybuffer' and gives it 5 000 ms to open. On a phone (user agent matching Android|iPhone|iPad|iPod) a loopback address is skipped when WebRTC routes exist: a loopback address there is someone else's.

  2. Then WebRTC

    The routes (rtc:<base64url SHA-256 of the node's DTLS certificate>@<ip:port>) are grouped by certificate, one group per node, and tried in order with mode c.

  3. Back off

    If nothing opened, the next try waits backoff: 1 000 ms, doubling up to 60 000 ms. A link that opens resets it to 1 000 ms, and so does pair or unpair.

When the socket fails, the worker checks whether the browser refused this page the home node's address space (Local Network Access). It queries the permissions loopback-network or local-network (and the older local-network-access) and, if one is denied, the error tells the person to allow "Apps on device" or "Local network" in the site settings. Loopback means localhost, ::1 or 127.*; local means 10/8, 192.168/16, 169.254/16, 172.16/12, fc/fd/fe80 IPv6 or a .local name.

An openNodeLink clears that node's wait and replaces the current discovery link. Accepting an operator's notice clears every wait, so the node is dialed at once. When the core closed a link because a notice is unread (consent_closed), the node is not counted as refusing. Direct links with other browsers exist only while directLinks is on; turning it off closes every open one.

Screens and routes

Routing is by hash (src/lib/router.ts), so the same build works under /app/, on its own origin and inside tauri://. Ids in a route must match ^[0-9a-zA-Z_-]{1,128}$ and wiki page names ^[a-z0-9](?:[a-z0-9-]{0,62}[a-z0-9])?$; anything else is notfound. router.go changes the route at once, not on the next hashchange, so whatever the same click opens can take focus; a new screen scrolls to the top, a tab change inside a community keeps the scroll.

App state and data loading

src/lib/app.svelte.ts is one class, AppState, exported as app. Its fields are Svelte $state: phase (booting | blocked | error | locked | ready), vaultState, boot, me, communities, privateGroups, net, warmth, settings, stats, linkAsks, linkChecks, the composer's state and a counter, rev.

Screens load their data with resource(() => { void app.rev; return app.core.x() }). Reading app.rev before the first await makes the effect depend on it, so every changed event re-runs the fetch and new records from peers appear on screen. Old data stays shown while the new fetch runs.

Storage: OPFS or IndexedDB

The core never touches storage itself. WasmNode collects changes in memory; the worker drains them with take_changes() after every call and applies them to a store. A change is one of four:

put{id, community, expiresAt, wire}
A record by its hex id, its community (or null), when it expires (Unix seconds) and its canonical bytes.
delete{id}
A record removed.
blob{key, value}
A keyed value (identity keys, MLS state, settings); null deletes it.
wipe{}
Everything cleared.

openStore(name) picks the store. Where the browser has sync access handles in a dedicated worker (createSyncAccessHandle on FileSystemFileHandle) and the store doesn't already live in IndexedDB, it is two log files in the origin-private file system, directory store-<name>. Otherwise, and in a private window that refuses OPFS, it is the IndexedDB database hoi, version 1, with object stores records and blobs. An OPFS write is one append and one flush instead of an IndexedDB transaction.

The OPFS log format

A store is log-a and log-b. Each file is a run of frames. A frame is there whole or not at all: on opening, the first frame that is cut short or fails its CRC ends the log and the file is truncated there. The file whose first frame is valid and whose generation is higher is the store, and its first frame always starts with a wipe.

magic | 4 B | sun | 2 | HOIF, u32 0x464f4948 little-endian generation | 4 B | sky | 2 | u32 LE, the same for every frame of a file length | 4 B | lilac | 2 | u32 LE, the body's length body | n B | mint | 4 | a batch of changes crc | 4 B | coral | 2 | CRC-32 (poly 0xedb88320) of the body
op | 1 B | sun | 1 | 1 put · 2 delete · 3 blob · 4 wipe id | 2 + n B | sky | 3 | u16 LE length, UTF-8; 0xffff is null community | 2 + n B | lilac | 3 | same string form expiresAt | 8 B | peach | 2 | f64 LE wire | 4 + n B | mint | 3 | u32 LE length; 0xffffffff is null

Compaction starts once the log passes COMPACT_AT (4 MiB) and is more than three times what is live (each record counts its bytes plus 64). Everything live is written as one frame into the other file under the next generation, then the old file is emptied. A crash in between leaves one of the two whole. If the compacted frame doesn't fit (the disk is full), the old log stays in use. A tab that just took over retries createSyncAccessHandle up to 20 times, 100 ms apart, while the old tab lets go.

One tab owns the store

The worker holds the Web Lock hoi-core (in the sandbox, <store>:core) for its lifetime, asked with ifAvailable. A second tab gets blocked and shows "hoi is open in another tab." Choosing to use it here asks again with steal: true; the first tab's lock request then rejects, it stops touching storage and sockets and posts locked, and its page reloads. A browser without Web Locks is refused: "This browser cannot safely open your saved data. Use an up-to-date browser." While locked, the worker closes the store, so the OPFS files stay free for another tab or a reset.

When saving fails

If applying a batch fails, the worker emits the notice "This browser could not save changes. Sync is paused. Keep this tab open, check free storage and allow site storage; saving will retry." The journal is kept, the next call first retries it, and no new mutation is accepted until it succeeds; then "Storage is working again." follows. A boot that finds records this build can't decode shows a banner: "Some saved data needs compatible software." with the count of preservedRecords, and asks the person not to reset to recover them.

The deeper model (the in-memory index, SQLite on native, the journal) is on Storage.

The encrypted browser vault

Every value the store holds is sealed first. WasmVault wraps hoi_crypto::vault::LocalVault: a random 32-byte data key, wrapped once per way in. The worker keeps it only while the store is unlocked; locking frees it and reloads the page, so no rendered content or worker outlives the lock.

The passphrase

A new passphrase needs at least 15 characters and at most 1 024 bytes. The Rust side checks both again (chars().count() < 15 || len() > 1024). It wraps the data key with Argon2id at 64 MiB, three passes, one lane, then XChaCha20-Poly1305; the header starts with the magic HOIV\x03. Unlocking refuses a header whose Argon2 cost isn't exactly that, so a tampered header can't ask for an expensive derivation. The login form exposes username (read-only, "hoi — browser vault" or "hoi — desktop vault"), current-password and new-password fields so password managers can save it, shows "Caps Lock is on." when it is, and clears both fields after every attempt. The app never stores the passphrase.

Three different secrets

The local vault passphrase only opens storage on this device. It is not the recovery key (hoi-key-1-…) and not the passphrase of a .hoikey file. The unlock screen and "Recover or start over" both say so.

What is stored

idb.ts seals each cell with a context that binds its address: record:<id> for records, blob:<key> for blobs (stored under v:<key>), manifest for the manifest. Each seal is XChaCha20-Poly1305 under a BLAKE3-derived key for the context hoi local vault cell v1:<address>. Three plaintext blobs remain:

vaultbytes
The header: the passphrase slot and any passkey slots.
formatbytes

On unlock the manifest must list exactly the cells present, with matching hashes, or loading stops with "Saved data is incomplete or damaged. No data was replaced." That catches a deleted cell and a single older ciphertext put back, not only a modified one. A v: cell or a manifest without a header, or a header next to anything unexpected, is reported as damage and nothing is changed. Migration seals everything first and then writes it in one batch that starts with wipe, so a crypto failure writes nothing.

Passkey unlock

A browser vault can also be opened by up to four passkeys through WebAuthn's prf extension. The WebAuthn calls happen on the page (src/lib/passkey.ts); the worker only ever sees the credential id and the 32-byte answer.

  • Adding (You → Unlock with a passkey, browsers only): navigator.credentials.create with rp: {name: 'hoi'}, a random 16-byte user id, algorithms -7 and -257, residentKey: 'preferred', userVerification: 'required' and a fresh 32-byte salt. Authenticators that answer the PRF at creation are used as is; the rest are asked once more. The worker calls add_passkey and saves the changed header with saveHeader; the cells stay as they are.
  • Unlocking: WasmVault.passkeys(header) lists each slot's credential id and salt in the clear, so the page can ask before anything is unlocked. navigator.credentials.get uses evalByCredential with each salt; the answer opens the slot. A passkey never creates a vault: "Set a passphrase first; a passkey can be added after."
  • Removing: remove_passkeys keeps only the passphrase slot.
lanes: Unlock screen | Page | Core worker | Store Unlock screen -> Page: app.unlock(passphrase) Page -> Core worker: __unlock [passphrase] Core worker -> Store: openStore("hoi"), snapshot() Store --> Core worker: records and blobs, still sealed Core worker: WasmVault.unlock(header, passphrase): Argon2id, 64 MiB Core worker: check the manifest, unseal every cell Core worker: new WasmNode("web", base, records, blobs) Core worker -> Store: first settle() Core worker: start links, the 5 s tick Core worker --> Page: ok Page -> Core worker: boot, me, settings, net

Errors and recovery

A wrong passphrase reads "Could not unlock. Check this browser's local passphrase; a key-file backup can have a different passphrase. A damaged vault header can also cause this. No data was replaced." A right passphrase whose data won't load answers saved-data: "The passphrase opened your vault, but its saved data could not be loaded. No replacement key was created." A failed unlock never creates an identity, changes the passphrase or rewrites ciphertext.

"Can't unlock? Recover or start over" (VaultRecovery.svelte) explains which secret is which, offers "Lock and reload" when the vault is still open, and clears local data only with a ticked box and the exact text RESET. The worker refuses while the node is open ("Lock hoi before using recovery."), releases everything, deletes the IndexedDB database without opening its schema and removes the OPFS directory. The page then removes hoi:theme, hoi:motion, hoi:sync-hidden and hoi:consent:network from localStorage and hoi:sort from sessionStorage, and reloads. Clearing doesn't revoke the old key or erase other devices' copies. The vault format itself is described on Storage.

Stamp miners and the look worker

The miner pool

createMinerPool() starts n = max(1, min(4, hardwareConcurrency − 1)) module workers running miner.worker.ts. Miner i tries nonces i, i + n, i + 2n, … with mine_range(prefix, suffix, bits, start, step, 20000), yielding between chunks so a stop can arrive. Nonces stay below 253 so they survive a JavaScript number. The first rate() benchmarks one worker on 30 000 hashes of a 180-byte prefix and 60-byte suffix, floors it at 50 000 hashes per second, and multiplies by n; the composer's estimate is stampEstimateMs(bits, rate).

Identity work runs one Argon2id try at a time through IdentityMiner (an 8 MiB buffer per miner); every try's 32-byte output is posted with its leading zero bits, so the first run can draw it. Between tries the miner yields through a MessageChannel, not setTimeout, because a try takes about 15 ms and the timer would add a 4 ms clamp. A stamp job and an identity job can run in the same miner, taking turns. mineMore reports {tries, best} every 250 ms and resolves null when stopped. If every miner fails (no memory, wasm didn't load), the job rejects and the caller falls back to the core.

What a stamp is and how difficulty is set: Stamps & work.

A miner tries nonce after nonce until the hash of the record and the nonce starts with enough zero bits. Each extra bit doubles the expected work.

The pool splits exactly this search across up to four workers.

The look pool

The core runs as wasm with panic = "abort", so a bug in a picture decoder would end the whole node. In a browser the node is therefore told to look at media elsewhere (set_look_elsewhere(true)). createLooker() keeps one look.worker.ts named hoi-look and gives it one job at a time:

MessageWasm functionResult
look {mime, data}look_mediaThe media is checked by hoi_validate::media::check, then looked at: {picture: {hashes, quality}}, or unreadable.
sanitize {data}sanitize_and_lookA file someone attaches, sanitized as the core will: {hash, mime, look}.
frames {frames}look_lumaFingerprints of video frames: {video: [...]} or nothing.

A job that takes longer than LOOK_MS (20 000 ms), or a worker that errors, gets the worker terminated and replaced; that one picture counts as unreadable (a video as nothing). Video frames come from the page: video-frames.ts plays the video muted and detached, waits up to 5 000 ms per step and 30 000 ms in all, and draws FRAMES = 8 frames spread over its length at no more than 512 px on the longest side, converted to luma with weights 0.299, 0.587 and 0.114. A video this browser can't play has nothing to say. See Media.

The service worker

The service worker is hand-written (vite/service-worker.js); the build fills in two placeholders. vite/sw-plugin.js runs as the last generateBundle hook, so it sees the final bytes of every file. It takes every emitted chunk and asset (worker chunks and the .wasm included) and every file copied from public/, skips _headers, sw.js, release.json, source maps and dotfiles, and records each file's SHA-256. The cache version is the first 16 hex characters of the SHA-256 over the sorted "<file> <hash>" lines, so any change ships a new worker and a new cache hoi-<version>. index.html is listed with a null hash: its own SRI attributes pin the entry script and stylesheet.

RequestHandling
Not GET, another origin, or outside the scopeNot touched.
release.jsonNot touched: release notices can change without a build and must never be frozen or faked from cache.
A navigation, index.html or the scope rootNetwork first; a good same-origin answer updates the cached index.html; offline, the cached one.
Any precached fileCache first. A miss is fetched and checked against the build's hash; bytes that differ give Response.error(), never the file.

On install every precached file is fetched with cache: 'reload' and checked; one mismatch fails the whole install. On activate other hoi-* caches are deleted and the worker claims its clients. This covers what SRI attributes can't: dynamic imports, workers and the wasm.

The update flow

registerServiceWorker() does nothing in development, in desktop or sandbox builds, inside Tauri, or without navigator.serviceWorker. Otherwise it registers sw.js after the page's load event and asks for an update every hour.

lanes: Page | Service worker | Host Page -> Host: reg.update(), hourly Host --> Service worker: a new sw.js Service worker -> Host: every precached file, cache: "reload" Service worker: checks each SHA-256; state installed, waiting Service worker --> Page: statechange: sw.waiting is set Page: "A new version is ready · Reload" Page -> Service worker: {type: "skip-waiting"} Service worker: activates, deletes old hoi-* caches, claims clients Service worker --> Page: controllerchange Page: location.reload(), once

Network & Safety, before anything connects

The notice's words live in src/lib/legal/texts.ts (NETWORK_SAFETY, PRIVACY_NOTICE, OPERATOR_RESPONSIBILITY) so the screens, the setup app and the tests read the same text. Its versions live in plain JavaScript, src/lib/legal/version.mjs, so browser tests and the site can import them:

export const NETWORK_NOTICE_VERSION = '1.2';
export const PRIVACY_NOTICE_VERSION = '1.2';

/** localStorage key of the Network & Safety acknowledgement: `{"version":"1.2","date":"2026-11-05"}`. */

The acknowledgement is kept in localStorage, not in the vault, so it can be read before unlocking. Continue needs both boxes: the IP address box and the VPN box. A wipe resets it, and so does "read again" on the privacy screen. In a private window where localStorage throws, the acknowledgement lasts for the visit.

Sandbox mode

The repository's sandbox/ runs a local community simulator: a dashboard on port 7070 and three browser personas of the real app on 7071 (owner), 7072 (member) and 7073 (watcher). The app is built with HOI_SANDBOX=1 for it. Only then is src/lib/sandbox.ts compiled in, and it acts only on http: loopback at those three ports.

  1. Bootstrap

    GET /__sandbox/bootstrap (no credentials, no cache) returns {session, role, name, pairing, invite, community}. The pairing link must start hoi://pair? and point at a ws: home node on loopback, the invite must start hoi://join?, the name is 1 to 32 characters and the community 64 hex digits.

  2. Separate storage

    Each persona's store is hoi-sandbox:<session>:<role>; the worker accepts only names matching ^hoi-sandbox:[a-zA-Z0-9_-]{1,128}:(owner|member|watcher)$.

  3. A real identity

    The owner links this browser to the founder through the normal device-link flow (linkRequest, the dashboard approves, linkComplete); the others make their own keys. Then pair, join and a visit report, and the app opens the community.

  4. Canary links

    Links to https://sandbox-canary.example/<run>/<agent>/<token> in posts are observed: exposure when at least half visible, and a click only when it is a real person's (isTrusted); the navigation itself is always prevented.

The real core still owns every key, signature and membership; the bridge only automates the normal setup. Normal web builds keep ordinary onboarding.

Accessibility in the code

  • A "Skip to the main view" button focuses <main> (its id is main, its tabindex −1).
  • Modal is a real <dialog> opened with showModal(): focus is trapped, Esc closes, the page behind is inert. A required modal has no Esc, backdrop or ✕.
  • Toasts sit in one role="status" aria-live="polite" region; errors carry a hidden "Problem: ". The work bar, the id line, vote scores and the first-run game announce politely too.
  • Motion is skipped when prefers-reduced-motion: reduce or the app's own motion setting (data-motion="reduced") says so. motion.ts clears inline styles on completion, on a fallback timer and on destroy, so nothing is left at opacity 0.
  • Focus rings are a 3 px cobalt outline; inputs and bottom-bar targets are 44 px high.
  • Trust is never color alone: TrustTag always carries the ✓.
  • Password fields use standard autocomplete values; paste always works.
  • scripts/e2e-a11y.mjs runs axe-core on every route against the mock, light and dark, with reduced motion, and fails on serious and critical findings.
