hoi Node Setup

hoi Node Setup is a small desktop app with a wizard for people who would rather not type the installer's commands. It logs in to a server over SSH (or works on this computer), shows every command before it runs it, runs the same install.sh the download page offers, and remembers the server, never its password. Afterwards it manages the node: status, logs, the join notice, updates and removal.

What it is

The app installs and manages a public node (or a public node with a registry) on a server over SSH, or on this computer. It runs deploy/install/install.sh and nothing else; what that script does is the subject of Deploying & hosting, and what the node then does is hoi-node. It ships beside the hoi app for macOS, Windows, Linux x64 and Linux ARM64 (a Raspberry Pi 5 with a desktop), and the download page offers it once the visitor ticked "I understand that I am responsible for the data processed on my node."

The crate is a Cargo workspace of its own with the engine as its one member, like the desktop app, so the core workspace stays free of SSH and WebKitGTK. The engine uses russh 0.65 with only the ring feature: pure-Rust SSH on ring, no OpenSSL, no aws-lc-rs, no compression, and no RSA, because the rsa crate leaks private-key timing (RUSTSEC-2023-0071) and has no fix. sha2 0.11 hashes uploads.

The window reuses the web app's server kit (lib/server-kit.ts: names, the configuration file, the README), the notice model and texts (lib/notice.ts, lib/legal/texts.ts), and the components NoticeEditor, NoticeText, QR and Logo. pnpm --filter @hoi/web build:setup writes apps/web/dist-setup/; the installer scripts are imported as text (install.sh?raw, install.ps1?raw), so each build carries the installer of its own version, with line ends turned to LF.

The wizard, step by step

The window's STEPS are Responsibility, Server, Host key, The node, Join notice, Check, Install, Done. Each has a two-part headline as the website sets them, ink then blue.

  1. Responsibility

    "Before you run a public node." The OPERATOR_RESPONSIBILITY text as ledger rows, and a box to tick before Continue.

  2. Server

    "Where does it run? A server or this computer." Over SSH: host, port (22), user (root), and a login: ssh-agent, a key file (with its passphrase, if it has one) or a password "used for this session only, never stored". Servers set up here before are offered as one-click fills. This computer skips to step 4.

  3. Host key

    "Is this your server? Check its key." The fingerprint the server answered with, to compare with the provider's or with ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub. "This is my server: pin it and log in" connects and runs uname -m.

  4. The node

    "What it runs. And what it keeps." Public node, or public node and registry (a domain with Caddy, or an address of your own); the name (random, "Another" rolls again) and whether the server's host name follows it; Keep mailboxes for private communities (on, 2 GB); the program; under More, extra registries to announce to and a daily cap.

  5. Join notice

    "Your join notice. In your own words." NoticeEditor for the operator's fields, and the notice as people will read it, with its size against the 1 536-byte budget ("fits a QR code" up to 1 100 bytes). "Upload and check the server" runs the check.

  6. Check

    "Before it installs. Nothing has changed yet." The installer's rows, tagged ok, info, warn or BLOCK. Install is enabled only when the installer printed "Ready to install". A sudo password field appears for a non-root user who didn't log in with a password.

  7. Install

    The installer's output line by line: the hoi-node from this computer or from the signed release list, the notice next to the service, the hardened service, the firewall.

  8. Done

    "Your node is up. Share its link." The node's link, with the notice in it, as text and a QR code, and the notice hash. Open in hoi opens the link (an https:// one) in the person's browser, where founding a community happens.

Under the steps, "What was run on <host>" holds every command and every line it printed; it opens by itself from step 6.

One field that stays in the window

More also shows "Public address, when NAT maps it (IP:7844)". In this version its value is not part of the options the wizard builds, so it doesn't reach the configuration file; install.sh --rtc-advertise PUBLIC-IP:7844 on the server is the way to set it.

The host key

Every connection goes through one russh client handler whose check_server_key records the key it saw and answers by a Trust:

Trust::Probestep 2
Record the key, accept nothing. The handshake stops, nobody is authenticated, and the window gets HostKey {algorithm, fingerprint}.
Trust::Pinned(fingerprint)every login after
Accept only a key whose SHA-256 fingerprint is exactly this string.

The fingerprint is printed the way people compare it, SHA256:…, with the algorithm (ssh-ed25519, …). A host certificate shows as "<algorithm> (certificate)" and its public key's fingerprint is used. When a later connection meets another key, russh fails with UnknownKey and the engine turns it into:

#[error("the server's host key changed: expected {expected}, got {got} ({algorithm}). Stop here unless you know why (a reinstalled server, say), then forget this server and start again")]
HostKeyChanged { expected: String, got: String, algorithm: String },

The window checks first too: if a saved server with the same user@host:port has a pinned key that differs from the probed one, step 3 shows both, disables the login button and says to forget the server under Your servers to start over.

Logging in

  • Password: authenticate_password. The password lives in the window's memory for the session.
  • Key file: load_key(path, passphrase), then public-key authentication. An RSA key file is refused before anything is signed, with the advice to make an Ed25519 key (ssh-keygen -t ed25519) or use a password. The window passes only the path; a native dialog picks it.
  • Agent: SSH_AUTH_SOCK on macOS and Linux, the named pipe \\.\pipe\openssh-ssh-agent on Windows; every identity the agent lists is tried until one is accepted.

A refused login disconnects and reads "<user>@<host> did not accept that login". An unreachable port reads "could not reach <host>:<port> (…)".

Running commands

Session::exec opens a channel, optionally asks for a pty, runs the command and hands each complete line to the window as it comes, stdout as out and stderr as err, keeping a partial last line (a prompt) back. With a pty, when the output so far ends in password: (or [sudo] password for … :, ignoring a trailing bell), the engine types the given answer once. A second prompt means the answer was wrong: the run ends with exit status 255 and "the password was not accepted"; a prompt with no answer given ends it with "a password is asked and none was given".

Uploading without SFTP

Files go through the same login with cat, not scp or SFTP. The path and mode are single-quoted for the shell by quote() (a quote inside becomes '\''):

let command = format!("umask 077 && cat > {p} && chmod {m} {p}", p = quote(path), m = quote(mode));
// … the bytes go to the command's stdin in 256 KiB pieces, then EOF …
let want = crate::node_files::sha256_hex(bytes);
let (code, text) = self.read(&format!("sha256sum -- {}", quote(path))).await?;
if got != want {
    return Err(SetupError::Upload(format!("{path} arrived damaged (SHA-256 {got}, sent {want}); upload it again")));
}

upload is used for the kit's text files; upload_verified for a hoi-node archive, which the server must hash to the same SHA-256 this computer computed.

A hoi-node from this computer

A node can install without a published release: the wizard looks for a hoi-node archive built on this computer and uploads it. Release archives are named hoi-node_<version>_<rust target>.tar.gz, as pnpm build:all puts them in builds/hoi-<version>/server/.

After login the window maps the server's uname -m to a target with nodeTarget: x86_64 or amd64 to x86_64, aarch64 or arm64 to aarch64, then -unknown-linux-gnu for a server; for this computer, Rust's own OS and architecture, with -apple-darwin on a Mac and only x86_64-pc-windows-msvc on Windows. The first archive found for that target is chosen ("Built on this computer"); otherwise "The signed release list". "Another file…" opens a dialog filtered to .gz and refuses a file built for another target ("… is for <target>; this server needs <target>."). The file is read by the Rust side, never through the window, and its size is checked again after reading.

What install.sh sets up

On Linux the installer (node_linux) needs systemd. For the public and registry roles the data directory is /var/lib/hoi-public: a key holder's data and a public node's are kept apart, so switching roles never hands a person's key to a public node. It installs the binary at /usr/local/bin/hoi-node (mode 0755), the notice at /etc/hoi-node/notice.json (0644), sets the host name (and, on cloud images, preserve_hostname: true), sets up Caddy for a registry with tls=caddy, writes the unit, opens the firewall, then systemctl daemon-reload, enable and restart.

A registry adds --registry, --registry-url and --index for its own address; extra registries become --index, the notice --notice, a cap --daily-cap-gb and mailboxes --hold-pieces. Netlink is in the allowed address families because the node lists its network addresses and finds the router through it.

The firewall

The check reads the host firewall: ufw when its status is active, else firewalld when firewall-cmd --state is running. The node's ports are 7843/udp 7844/udp 7846/udp 7847/udp, plus 80/tcp 443/tcp with Caddy. Any of them not yet allowed are opened at install with ufw allow <port> comment hoi-node or firewall-cmd --quiet --permanent --add-port=<port> and a reload; --no-firewall leaves the firewall alone, and the check then warns that nobody outside reaches the node. A firewall in front of the server (the provider's) is reported as something to open too.

In a plain browser

pnpm --filter @hoi/web dev:setup serves the window on port 5175 without Tauri; getBridge() then returns mockBridge() and a callout says a pretend server answers. The mock pins SHA256:mock…, accepts the password correct horse, can't reach down.example, answers uname -m with x86_64, has hoi-node 9.9.9 archives for x86_64 and aarch64 Linux "built" on this computer, prints the check rows and installs a node whose link carries a real notice (from core/vectors/node-notice.json).

The portable app

pnpm build:all --only server,node-setup builds the server parts and this app into one folder. The setup app needs no installing:

server/       hoi-node_<v>_x86_64-unknown-linux-gnu.tar.gz, hoi-server_<v>_linux-x64.tar.gz
node-setup/   hoi-node-setup_<v>_<os>-<arch>-portable.exe   (Windows: the program itself)
              hoi-node-setup_<v>_<os>-<arch>-portable.zip   (macOS: the .app, zipped with ditto)
              the .AppImage on Linux, and the installers

Run from node-setup/, it finds the hoi-node in ../server/ by itself, so a node installs before any release is published. Installers come from pnpm build:setup; like the desktop app, a preview version is built for Windows without the .msi. In a release, scripts/release-manifest.mjs marks this app's files with product: "setup", so the download page lists them in their own row and the installers never take them for the app. Its icon is the hoi mark on an ink tile with a server (pnpm --filter @hoi/setup icons), and its installer art comes from the same scripts/installer-art.mjs as the desktop app's.
