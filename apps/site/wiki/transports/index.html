Transports & NAT

Every hoi program speaks the same sync conversation; only the pipe differs. Native nodes (the desktop app and hoi-node) talk iroh QUIC to each other. A browser, the phone app or a second computer reaches its own home node over a WebSocket. Browsers reach native nodes, and with the person's say-so each other, over WebRTC data channels. This page is every pipe: how it is set up, authenticated, framed, kept alive and limited, and what each party on it can see.

Three pipes, one conversation

The core (hoi-core) never opens a socket. It decides what to say and reads what comes; a host (the hoi-net crate on native builds, the web worker in a browser) moves the bytes. Whatever the pipe, the bytes are the same hoi-sync messages, every record that arrives passes the same validation pipeline, and the first message on every link must be a hello, or the link is dropped. There is no separate gossip protocol: live records ride the same link as catch-up.

The host owns sockets, the node owns the conversation

The contract between the two is six calls. The host says a connection opened (net_connect, with a role), says how it travels (set_peer_meta), hands over each whole message (net_receive, which returns false when the link should end), collects what to send (take_outbox, a list of (peer, bytes)), says a connection ended (net_disconnect) and asks now and then whether a catch-up stalled (sync_stalled: wanted ids outstanding and no progress for 120 seconds). The web worker calls the same functions through hoi-wasm; how the core spends them is on Sync & gossip.

On native builds hoi_net::Shared holds one Node behind a lock. Every caller (UI commands, WebSocket handlers, the sweeper) goes through Shared::with, which runs the call, commits to storage, then routes the outbox into each link's queue and reports events.

  • Bounded queues. Each link may have 128 messages and 32 MiB waiting. A message that doesn't fit cancels the link: a reader that can't keep up is dropped, never buffered without end. On the WebSocket and the iroh stream, any single write that takes longer than 30 seconds ends the link too.
  • Identity work off the lock. Shared::receive scans a message for identity records before taking the lock, asks the node which of them it would really check, and runs those Argon2id checks (8 MiB each) on a blocking thread, at most two at once (WORK_AT_ONCE). Under the lock the pipeline only looks the answers up, so the UI and other links never wait on a stranger's identity work.
  • Storage failures stop the network. When a commit fails, the outbox is thrown away and every link is closed; while storage keeps failing, incoming messages aren't taken in. The person sees "This node could not save changes. Sync is paused…", and "Storage is working again…" once a commit succeeds. Fresh links then catch up from what was saved.

iroh QUIC between native nodes

Native nodes run one iroh endpoint (iroh 1.4). iroh gives authenticated QUIC with hole punching and optional relays, and on its own would also reach for its makers' DNS discovery and default relays. hoi turns all of that off: the endpoint starts from presets::Minimal, which installs only the TLS provider (ring), and from a relay map that is empty unless the operator or an invite supplies relays.

Endpoint keys are not posting keys

The endpoint's secret is Node::transport_secret: an Ed25519 key of its own, made once, committed to storage before it is used, and separate from the person's root and device keys. So the address a node is reached at says nothing about who posts from it. A native node puts its endpoint key in the node field of its hellos; a browser has no endpoint, so it names a fresh random 32-byte id per connection to strangers, and its stored node id only to its own devices and home node. Strangers never get a name.

Routes for iroh are text: <endpoint hex>@<ip:port> for a direct address, or the bare <endpoint hex>, which means "through my relays". A node publishes the public side of a forwarded port first (from the port mapper), then up to eight of the endpoint's own direct addresses, and puts the bare key in front when it has relays. A hello carries at most four direct routes, the bare key and three WebRTC routes, eight in all (OWN_DIRECT, OWN_RTC, MAX_ROUTES). A desktop that isn't a public node strips internet-scope addresses from what strangers see.

Dialing

Every five seconds (RESCAN) the supervisor asks the core for its dial candidates (bootstrap_hints): routes from accepted invites, paired devices, members met in the last 30 days, routes on trial for a public join, a few public nodes while this node serves strangers, holders for private mailboxes and forwarded pieces. Never a default relay, and under the consent gate never a node whose notice waits for an answer or was declined. WebRTC routes are left to browsers.

  • A hint without a direct address needs a relay; a direct address must be reachable (not unspecified, not multicast, not port 0). Relay URLs must be https:// (plain http:// only to 127.0.0.1, localhost or [::1]), with no credentials, query or fragment, at most 2,048 characters. At most 16 relays are configured, and at most 16 known in all; new ones from hints are added to the endpoint as they appear.
  • Each dial has 20 seconds (CONNECT_TIMEOUT). A failed endpoint waits 2, 4, 8, 16, 32 and then 60 seconds between tries (min(2^n, 60), n capped at 6), and the core hears dial_failed.
  • Dials and accepted connections share 32 slots (MAX_PEERS), held from the attempt until the link ends, so a hostile handshake can't create unbounded work.
  • When both ends dial at once, they keep the connection dialed by the endpoint with the lower key and close the other with reason duplicate.

Accepting

An incoming connection is refused at once while the node doesn't accept members (the relay switch is off, or today's cap is used up). A direct one must first answer a stateless QUIC retry, so its source address is one that receives; a relayed one counts as the endpoint the relay vouches for, since the relay's own address says nothing about the sender. Each source (an IPv4 address or IPv6 /64, or a relayed endpoint) may open ten connections a minute, in a table of at most 4,096 sources; then it waits for the next minute.

A headless node never holds its hello back. A person's desktop under the consent gate waits for a stranger's hello before its own. A link ends with close reason no sync stream if no stream opens within 15 seconds, storage unavailable while storage fails, and sync closed otherwise.

Frames

length | 4 B | sun | 2 | big-endian u32, 1 to MAX_MESSAGE message | length B | sky | 10 | one canonical CBOR map, {t: "hello", …}

A zero length, or one over MAX_MESSAGE (16 MiB plus 64 KiB: the largest media item plus framing), ends the link before anything is buffered. The first byte of a frame may wait forever (quiet communities stay connected; iroh owns keepalives and loss detection), but once it arrives the rest of the frame must follow within 30 seconds.

Media over iroh-blobs

Between native nodes, pictures and videos go over iroh-blobs on the same endpoint instead of as blob messages on the sync link, so a large file never waits in front of records and a bad peer is caught at its first wrong chunk. A node says blobs in its hello when its host runs this.

  • Serving. A connection is taken only from an endpoint with a sync link here, and each request only for media the core says this node serves to it: a visible public post in a community the two share and this node pins. The bytes are copied into a small in-memory store just before they are sent; past 64 MiB (SERVE_CACHE) the ones added longest ago leave first, and the store's garbage collection runs every 30 seconds. Requests for many blobs, pushes and observing are refused. Eight connections are served at once (BLOBS_SERVED); a ninth is closed with busy. What goes out counts against the relay's daily cap like a blob message.
  • Fetching. Every 250 ms the host takes the core's fetches, at most two under way (BLOBS_FETCHED), each over a connection of its own to the same paths the sync link uses. The stream must announce exactly the size the post states and match its BLAKE3 hash; dialing to the last byte has 60 seconds (FETCH_SECS). What arrives goes through every check a blob message gets. A fetch that fails turns that community's media on that link to bwant for the rest of the link.

The home-node WebSocket

A home node (the desktop app, or hoi-node without --peer-only) serves the person's own browsers and phones on a WebSocket. Pairing links point at it; the link format is on Links & URIs.

Serving

  • Address. hoi_net::serve binds a TCP listener and tells the core it serves at ws://<bound address>. The listener doesn't look at the request path. The desktop takes 127.0.0.1:7842 and any free loopback port if another hoi holds it; hoi-node takes --listen (default 127.0.0.1:7842), and with --public-url advertises a wss:// address of a TLS proxy in front of it instead.
  • Pairing link rules. A pairing link's address must be wss://, or ws:// to this very machine: plain ws:// would carry the token unencrypted. A link may carry only WebRTC routes instead.
  • Origins. Any web page can try to open a WebSocket to a loopback port, so a request carrying Origin must come from the web app this node's pairing links open (its web base, normally https://hoi.sh) or from one listed in HOI_ALLOWED_ORIGINS (comma separated: a self-hosted app, a development server). Anything else gets 403 Forbidden at the handshake. A request without Origin is a native app and goes on to the credential check.
  • Limits. 32 paired devices at once (MAX_CLIENTS); the upgrade must finish within 10 seconds; messages and frames over MAX_MESSAGE are refused by the WebSocket layer itself.
  • Encryption, as reported. A loopback client counts as local ("stays on this device") unless the advertised address is wss://: behind a TLS proxy, loopback is the proxy, not you.

Dialing

Native programs dial with hoi_net::dial: a 10-second handshake, then the link runs until it ends, then a retry after 1 second, doubling to 60, reset after every success. The desktop dials only a ws:// or wss:// address (a WebRTC-only pairing link is for browsers and phones) and, with "only through my VPN" on, waits for the VPN unless the home node is on loopback or the home network.

The web worker tries the WebSocket first (fast on the same computer), giving it 5 seconds to open, then each group of the home node's WebRTC routes in turn (one certificate, one group), retrying with the same 1-to-60-second backoff. On a phone it skips a loopback address when the pairing has WebRTC routes: a loopback address there is someone else's. When Chrome's Local Network Access permission blocks the page, the app says which permission to allow.

Frames

One sync message is one binary WebSocket message: no length prefix, since WebSocket frames already have one. The first message must be a binary hello and must come within 15 seconds (HELLO); a text message or anything else first ends the link.

The credential in the first hello

A device that dialed in hears nothing, not even that a hoi node listens there, until its first hello shows a credential. The home node compares the token against every stored device credential, in constant time and all of them, so timing says nothing about which matched; credentials are stored only as BLAKE3-derive-key("hoi 2026 pairing credential v1", token). Failing that it compares the pairing link's own token. A pairing link pairs one device: that device gets a credential of its own (32 random bytes, base64url) and the link is replaced by a new one (18 random bytes), so a link left in a screenshot or a browser history pairs nobody else. A wrong or missing token ends the link without a word. The home node keeps credentials for 32 devices (MAX_PAIRED); a 33rd pushes out the one seen longest ago. Rotating the pairing link (--new-pairing) forgets every credential: every device must pair again.

lanes: Browser | Home node -- First contact, with the link's token -- Browser -> Home node: WebSocket upgrade; Origin must be the app's Home node: registers client-N, says nothing Browser -> Home node: hello {token: the link's token, c: its public communities, fx} Home node: no stored credential matches; the link's token does Home node: joins and pins the browser's communities, while it is in fewer than 256 Home node --> Browser: hello {token: its own credential, pt: the next link's token, lk: the link key, c: every public community} Home node: its other devices get a fresh hello with the new pt Browser: keeps the credential; the link's token is spent Browser => Home node @mint: rng, want, recs -- Every later connection -- Browser -> Home node: hello {token: its credential} Home node --> Browser: hello -- A guessed token -- Browser -> Home node: hello {token: "guess"} Home node: closes the link: no hello, no version, no reason

A hello with another sync version than 2 gets a bye ("this node speaks sync version 2") and the link ends. Route hints in a hello (hints) are taken only from a credentialed device, or from the home node once it delivered valid records: a pairing link could have come from anyone, and a stranger must never make a node dial addresses of its choosing.

Keepalive and stalls

  • The native side of every WebSocket (serving or dialing) sends a ping every 30 seconds. Browsers answer pings by themselves and send none.
  • After the hello, a link with nothing read for 180 seconds ends: a pong counts as something.
  • At each 30-second tick the link also ends if the core says the catch-up on it stalled (sync_stalled). The web worker runs the same check every 30 seconds (SYNC_WATCHDOG_MS) over all its links and redials the home node.

The sweeper

Every native host runs spawn_sweeper: a tick every 5 seconds runs the scattered-delivery round (scatter_tick: answers that never came, holder sightings, private mailboxes), and every 36th tick, every three minutes, runs sweep. The web worker does the same (TICK_MS 5,000, SWEEP_EVERY 36). A sweep, among other things, asks for communities nobody here serves, ends range sessions idle for two minutes, refreshes direct-link handles, deletes expired records, lets go of carried communities nobody touches, gossips the directory, and frees unused media. Expiry itself is on Expiry & removal.

WebRTC from browsers to native nodes

A web page can't accept connections, and the only encrypted ones it can open are TLS (which needs a certificate from an authority, so a domain) and WebRTC. WebRTC needs no authority: the browser pins the node's DTLS certificate by its fingerprint. So a native node listens on UDP as an ICE-lite peer, and a route rtc:<fingerprint>@<ip:port> in a pairing link, an invite or a node list is all a browser needs. The browser writes the node's half of the session description itself. No STUN server, no TURN, no signaling server is involved.

Routes and the certificate

The fingerprint in a route is the SHA-256 of the node's DTLS certificate, base64url without padding (43 characters). The certificate is a self-signed ECDSA P-256 one, common name hoi node, valid from 2026-01-01 to 2099-12-31 with a random 16-byte serial (Firefox refuses two certificates with the same issuer and serial). Browsers check its fingerprint, never its dates or names, so it lives as long as the node and routes in old invites keep working. It is made once and kept with the node's other secrets.

The listener binds one socket per local address on the same port (ICE needs every packet's destination address): loopback, and every interface that is up, minus link-local addresses (a route can't carry a scope id), as the VPN policy allows; or only the --rtc-bind addresses. Unless a port was given, it tries UDP 7844 and takes any free port if that's taken. Interfaces are looked at again every 30 seconds, and at once when the VPN comes or goes.

Routes are ordered for the few a hello or a pairing link has room for (MAX_PAIR_ROUTES is 4): the best local address first (private IPv4 and carrier-grade NAT space, then other IPv4, then unique-local IPv6, then other IPv6), then up to two advertised addresses (--rtc-advertise, or a port the router forwards), then the rest. Loopback is never advertised. A browser offers them all as candidates of one session, in that order.

The username fragment carries the browser's certificate

The browser picks the ICE username fragment, used for both sides, and the same string as the password. It carries the mode and the browser's own certificate fingerprint, so the node pins the browser's certificate too.

version | 2 chars | sun | 2 | h1 mode | 1 char | coral | 1 | c a paired device, p a member's browser fingerprint | 43 chars | sky | 8 | SHA-256 of the browser's certificate, standard base64, no padding random | ≥ 8 chars | mint | 3 | the web app sends 10 letters and digits

The node accepts 54 to 256 characters of letters, digits, + and /, mode c or p, and a fingerprint that decodes to 32 bytes; anything else is ignored. A p session starts only while the node accepts members; paired devices (c) still prove themselves with their credential in the first hello.

The browser makes a fresh ECDSA P-256 certificate per link, creates an offer with no ICE servers, rewrites its ice-ufrag and ice-pwd to the fragment above, sets it, and sets this answer as the remote description. The node is ICE-controlled and DTLS-passive, so the browser is the DTLS client. The channel must open within 12 seconds (OPEN_TIMEOUT_MS). WebRTC lives on the page, since Web Workers can't create an RTCPeerConnection: the core worker asks the page with rtc-open and swaps whole sync messages with rtc-send.

Return routability before any state

Every binding request carries the username fragment, so the password, in the clear: ICE checks prove nothing about where a packet came from, and anyone can write a binding request with any source address. So a first binding request costs the node one stateless binding request back (a probe, no larger than what came in) and nothing else. The browser, a full ICE agent, answers it; its answer proves it receives at that address, and only then does its next binding request start a session.

A probe's 12-byte transaction id is the first 12 bytes of HMAC-SHA256(probe key, epoch ‖ local address ‖ remote address), addresses as IPv4-mapped IPv6 bytes plus a big-endian port, with a random probe key per run and 5-second epochs. An answer is checked against the current and the previous epoch, so nothing is kept per probe. An address that answered is proven for 10 seconds, in a table of 1,024 (when full, the oldest proof makes way). DTLS then asks for a cookie as well, before any key exchange or certificate (below).

DTLS and the vendored crypto provider

The WebRTC stack is str0m (0.24) in sans-IO style: the host feeds it datagrams and timeouts and sends what it produces. Its crypto provider is str0m-rust-crypto 0.6.0, vendored into hoi-net/src/rtc_crypto/: DTLS through dimpl, SRTP ciphers, STUN's HMAC-SHA1 and SHA-256, all RustCrypto. Two things differ from upstream. The certificate is made with rcgen on ring, which iroh already brings in, instead of pulling aws-lc-rs (a C and CMake build) into every desktop, phone and node build. And DTLS server cookies are on, where upstream turns them off because "ICE verifies return routability": here it doesn't, since the node is ICE-lite and its ICE password travels in every binding request. DTLS version is Auto: 1.2 or 1.3, whichever the browser offers.

// The cookie (HelloVerifyRequest in DTLS 1.2, a HelloRetryRequest cookie in 1.3) makes
// a client show it receives at its address before the server does key exchange or sends
// its certificate flight.

The channel and its frames

One data channel per session: label hoi, negotiated with id 0 (no in-band channel setup), ordered. It carries the same frames as the iroh stream (a 4-byte big-endian length, then the message, above), cut into data channel messages of at most 16 KiB, which every browser takes in one message. A frame's length is checked as soon as its four bytes are in: zero or over MAX_MESSAGE ends the session before any of it is buffered.

channel message 1 | 16,384 B | sky | 4 | length (4 B, 00 00 9c 40), then 16,380 bytes of the message channel message 2 | 16,384 B | sky | 4 | the next 16,384 bytes channel message 3 | 7,236 B | sky | 2 | the last 7,236 bytes
  • Node side. SCTP may hold 1 MiB unacknowledged per session (SCTP_BUFFER); the rest waits in the session's queue and is written when the channel reports its buffered amount below 256 KiB. What a session may have waiting for the core is bounded at 4,096 frames and 32 MiB; a session past either ends.
  • Browser side. rtc-frames.ts stops sending above 4 MiB unsent (HIGH_WATER) and resumes when the channel drains below 1 MiB. Each incoming frame is allocated once at its announced size and filled at a running offset, so a 16 MiB frame trickled in 16 KiB pieces costs one copy per byte.
  • Endings. The channel closing, ICE disconnecting, or the session not opening within 15 seconds ends it. Before closing, the node lets the last queued messages (a bye) go out.

The binding: the key behind the channel

The channel is encrypted between the two pinned certificates, and a hello names the node's endpoint key; but nothing yet shows that the key's holder is the one at the other end of the channel, rather than someone who forwards another node's hello. So right after its hello on a WebRTC link it accepted, a native node sends bind: its endpoint key's Ed25519 signature over this statement.

hoi/rtc-binding/1
<the node's certificate fingerprint, hex>
<the browser's certificate fingerprint, hex>
<the ICE username fragment>
<the node's endpoint key, hex>

The browser takes nothing from that link but hello, bind and bye until the signature checks out against the key the hello named and the channel the browser actually opened; anything else, or a bad signature, ends the link. Nothing binds in the other direction: browsers name no lasting key to strangers, and paired devices prove themselves with their credential.

The node's port also answers plain STUN (a binding request with no USERNAME, 20 to 512 bytes, as browsers send their STUN server) with the address the request came from, while it passes signals between browsers (next). Which nodes a browser dials

  • Its home node, as home, in mode c: the WebSocket first, then its WebRTC routes.
  • Members' and public nodes, as member-N, in mode p: routes from accepted invites, public joins and members met in the last 30 days (rtc_candidates, at most 8, never its own home node's). At most two such links (MAX_MEMBER_LINKS), plus those private mailboxes need. A node that doesn't answer, or closes the link within a minute, counts as a refusal: it waits 60 seconds, doubling to 30 minutes.
  • One public node for finding things, as node-N: three candidates are dialed at once (DISCOVERY_RACE) and the first to answer is kept; the others are closed before they carry anything. See Discovery.

The worker looks at both every 15 seconds, and 3 seconds after starting.

Direct links between browsers

Two members' browsers linked to the same native node can open a data channel to each other, so records and media flow between them without going through that node. The browsers learn each other's addresses, which is why the setting (Direct links with members' browsers, direct_links) is off at first.

  • The node says signal while its WebRTC listener runs and it accepts members. To each browser link that said direct it gives a random 16-byte handle, and sends it, per community, the handles of the other such browsers that share it (here, at most 16). It passes sig messages (an offer or an answer) between two such links that share a public community, at most 30 a minute per link (SIGS_PER_MINUTE; more costs peer score), naming the sender by its handle. Its port answers plain STUN so each browser learns the address it is seen from.
  • A browser with the setting on says direct. Of two handles, the lower one offers. Its page makes the connection (rtc-direct.ts) with the node's own stun:ip:port addresses (from the routes it dialed, at most 4) as ICE servers and nothing else, gathers candidates for up to 3 seconds (no trickling: one message each way), and gives the channel 15 more seconds to open. At most four direct links (MAX_DIRECT), none for private communities; a handle tried and not linked is offered again after 10 minutes.
  • On the channel the browsers speak the usual sync protocol as peers: every record is checked as from anyone, and the hello names communities only as salted hashes.

Relays

When neither of two native nodes can reach the other directly (both behind routers that won't forward), their QUIC packets can go through an iroh relay. A relay forwards packets it can't read, by destination endpoint, from an in-memory table of who is connected now. The protocol assumes relays are untrusted.

Where relays come from

Never from hoi or iroh defaults. A node uses the relays its operator configured (--relay URL, at most 16) and those an accepted invite or a credentialed device's hints name for a community (at most 8 per community, MAX_HINT_RELAYS), added to the endpoint as the dial loop meets them. While a node has relays, its routes include its bare endpoint key, which a dialer can reach only through those relays.

The packet relay in hoi-node

hoi-node --packet-relay ADDR runs iroh's own relay server beside the node, so a community's members can connect through a relay their community's operator runs instead of anyone's default. Its public address (--packet-relay-url, or http://ADDR for one on loopback) goes first in the node's relays, so its routes and invites name it.

  • Who may use it. Everyone but the endpoints on the operator's block list: packet-relay-blocked.txt in the data directory, one 64-hex endpoint key at the start of a line, # comments, read again within 30 seconds of a change (hoi-node admin relay block|unblock|list). With --packet-relay-members, only endpoints this node knows as members of the communities it carries: connected now and sharing one, or named in a route it learned or was invited with. iroh's clients send no token of their own, so this stands in for one.
  • How much. Each client may send at most 1 MiB a second, in bursts of up to 4 MiB.
  • TLS. Plain HTTP behind a TLS proxy, or HTTPS from a PEM certificate chain and key (--packet-relay-cert, --packet-relay-key, together or not at all); then the plain HTTP side (captive-portal checks) moves one port down.
  • Logs. None: the node installs no tracing subscriber.

Browsers and relays

A browser never uses an iroh relay. Its way into the network when nothing can reach it is its own home node, or a public node it dials over WebRTC. That is why something a browser alone posts is readable by others only once a node carrying the community has it.

Port mapping

A public node at home is reachable from the internet only if the router in front of it forwards its UDP ports. hoi_net::portmap asks the router itself, and the router says which public address it forwards from: no outside service (no STUN) learns that the node exists, and the project runs nothing for it. hoi-node does this by default for its WebRTC port, its iroh IPv4 ports and, on a public node, its DHT ports (--port-mapping; --no-port-mapping, and off with --no-public-relay). The desktop does it for its WebRTC and native ports while Be a public node is on, showing the address before publishing it. What the router forwards from joins the node's routes near the front: first among the iroh routes, right after the best local address among the WebRTC ones.

  1. PCP

    One UDP MAP request (RFC 6887) to the default gateway's port 5351. A NAT-PMP-only router answers in its own version 0, which counts as silence here.

  2. NAT-PMP

    One UDP map request (RFC 6886) to the same port, then an external-address request for the public address.

  3. UPnP IGD

    Only on the default route, never through a VPN. An SSDP M-SEARCH for InternetGatewayDevice:1 and :2, answers collected for 2 seconds and taken only from the gateway's own address; its description fetched over plain HTTP from that same private address (up to four tried); the first of WANIPConnection:2, WANIPConnection:1, WANPPPConnection:1; then AddPortMapping and GetExternalIPAddress by SOAP to a control URL on that same host and port.

A UDP request is sent up to three times, waiting 250, 500 and 1,000 ms; an answer must come from the gateway's address and match the request (the PCP nonce, the opcode, the internal port). Every HTTP answer is read to at most 64 KiB within 5 seconds, with no proxy and no redirects. A UPnP router that keeps only permanent forwards (error 725) gets one with lease 0; a port another computer holds (718) makes way for a random one between 20,000 and 59,999, at most twice. Mappings show as hoi-node on the router's page.

A forward is asked for 7,200 seconds and renewed after half the granted lifetime, but no sooner than 60 seconds and no later than an hour, which also notices a new public address. After a round with a port not forwarded, the next comes within 5 minutes. When the network changes (another router), the old forwards are forgotten; when the mapper stops, it removes them (lifetime 0, or DeletePortMapping), all within 3 seconds.

Only through a VPN

A native node can be told to reach the internet through one network interface only, a VPN's (hoi-node --vpn-only wg0, or the desktop's setting), so the peers it talks to see the VPN's address and never the home's. It is off by default. Three things hold while it is on:

  1. Bound to the VPN

    Every socket toward the internet is bound to the VPN interface's own address, and pinned to the interface where the system allows it: SO_BINDTODEVICE on Linux and Android, IP_BOUND_IF on macOS and iOS; on Windows the strong host model sends from an address only over its own interface. A pin the system refuses leaves the address binding and the route check in place. Home-network addresses may still be used directly if the person allows it (home_network, on by default; --no-home-network), so a phone on the Wi-Fi keeps working. A home-network socket never sends to an internet address.

  2. Routed through it

    The system itself must send internet traffic through the VPN: the source address it would pick toward 192.0.2.1 (a documentation address, never contacted) must be one of the VPN's. This is asked the way connecting a UDP socket asks it, which sends nothing, and it follows policy routing (the way WireGuard and most VPN apps route), not just the main table's default route.

  3. A kill switch

    While the VPN is down, or the system routes around it (split tunnelling), nothing goes to the internet: the sockets on it close and the host stops the native transport until the VPN is back. hoi-node waits for the VPN before starting anything.

Connection limits

The listeners strangers reach (QUIC and WebRTC) count sources with one small structure, PerSource: how many connections each source may start per minute, in a table of at most a given number of sources. The window is a fixed minute: the first count after a minute has passed clears the table. A full table turns newcomers away until the minute is over rather than forgetting anyone's count early. Only addresses that proved they receive what is sent to them are counted (the QUIC retry, the WebRTC probe), so a spoofed flood can neither use up someone else's allowance nor fill the table. Nothing is logged or kept past a minute.

/// The source an address counts as: an IPv4 address, or the /64 an IPv6 address is in (what one
/// host or household gets, so fresh addresses inside it are free to whoever holds it).
pub(crate) fn source(ip: IpAddr) -> IpAddr {
    match ip {
        IpAddr::V6(v6) => match v6.to_ipv4_mapped() {
            Some(v4) => IpAddr::V4(v4),
            None => {
                let s = v6.segments();
                IpAddr::from([s[0], s[1], s[2], s[3], 0, 0, 0, 0])
            }
        },
        v4 => v4,
    }
}

The relay switch and the daily cap

Other people's devices may connect to a native node only while it accepts members: the relay switch is on (native nodes relay by default, and the app tells the person once) and today's bytes with them are under the daily cap (default 5 GB, settable from 0.1 to 1,000; --daily-cap-gb). The bytes counted are those in and out on links that someone else's device dialed in; the count outlives a restart. Hosts ask before accepting a connection. A link already open from someone else's node gets a bye on its next message: "this node isn't relaying right now", or "this node is done relaying for today". Paired devices and direct browser links are never turned away by it.

Before connecting: notices and previews

The operator's notice comes first

A public node's operator tells people what the node processes and keeps and, when they choose to, who runs it, where, and how to reach them (a NodeNotice, set with hoi-node --notice FILE). The node puts its canonical bytes and their BLAKE3 hash into every hello to a stranger (nt at most 2,048 bytes, nh), and, signed by its endpoint key over "hoi node notice v1\n<endpoint hex>\n<hash hex>", into its node link.

A person's device runs the consent gate (on in browsers, the desktop and the phone app, never on a headless node). A stranger this device dialed hears nothing until its hello was read. No notice in it (an older node, a member's device): our hello follows at once. A notice the person accepted before, the same. Otherwise the link ends there without counting as a refusal, the words are kept to be shown (at most 64 notices; the oldest not accepted go first), and the node is dialed again once the person accepted. A declined node is not dialed and gets a bye "declined" until the person forgets it. A hello whose notice is missing, over 2,048 bytes, doesn't match its hash or doesn't decode costs the peer score. What the device says of itself (its communities, hashed or named) waits for the person's answer; the node has seen this device's address by then, as any connection shows it, and the app's own network notice says so before the first connection is ever made.

Link previews

When the person turns previews on (link_previews, off by default), a post's link shows the page's title, description and picture. Only native programs fetch: a desktop or hoi-node fetches for itself and for the browsers paired with it, which ask over the sealed home link; a browser with no home node fetches nothing. The core decides what to fetch; hoi_net::preview does the network part:

  • https only, no credentials in the URL, at most 2,048 characters; at most three redirects, each hop checked like the first.
  • The host name must resolve only to addresses on the internet (the same public_ip test that refuses loopback, private, link-local, carrier-grade NAT, documentation, benchmarking and multicast ranges), and the connection goes to exactly those addresses: no second lookup an attacker's DNS could answer differently.
  • No cookies, no referrer, user agent hoi link preview, Mozilla's roots compiled in; Accept names only HTML pages or PNG, JPEG, WebP and GIF pictures.
  • At most 512 KiB (PREVIEW_BYTES) and 5 seconds (PREVIEW_SECS) per fetch, four fetches at once; a page is cut at the limit, a picture over it is none. The picture then passes the same sanitizer as a post's and must end up under 384 KiB.
  • With "only through my VPN", every request leaves from the VPN's address on its interface, and none while it is down.

A preview is kept on this device (64 at most, fetched again after a week, a failed one after an hour) and never published. A browser asks its home node for at most 8 a minute, and a home node serves one paired device at most 12 a minute.

Addresses are not hidden

Every node you connect to sees your IP address, as every internet connection does. hoi keeps your network key apart from your posting keys and names communities to strangers only as salted hashes, but it does not route through anonymizing networks. The VPN mode changes which address peers see, not whether they see one.

In a browser, You → Your address shows a connection's source IP when WebRTC reports a reflected address for its active connection. This readout stays in the page and is cleared when the connection changes or ends. WebSocket links and browsers that withhold the address show it as unavailable; that does not hide it from the other device. Direct browser links also exchange connection addresses. The readout does not verify VPN protection or replace the separate list of listening addresses on native devices.
