Stamps & work

Every record carries a stamp: a nonce chosen so that a BLAKE3 hash of the record's id and the nonce starts with enough zero bits. It costs the author about a second for a post and costs a receiver one hash to check. Every root key also carries identity work, done once with memory-hard Argon2id. This page gives the exact inputs, every difficulty rule and floor, how the miners work on native hosts and in the browser, and what the numbers mean in tries and time.

What a stamp is

A stamp is hashcash over the record id. The record's nonce field is the author's choice; the stamp holds when

valid iff leading_zero_bits(BLAKE3(id ‖ u64be(nonce))) >= bits_required

where id is the record id, the BLAKE3 hash of the canonical record, which itself contains the nonce. Changing the nonce changes the id, so every try needs a fresh id and a fresh stamp hash. A stamp can't be moved to another record, and a record can't be changed after mining without mining again.

id | 32 B | sun | 8 | BLAKE3 of the canonical record, nonce included nonce | 8 B | coral | 2 | the same nonce, as a big-endian u64 
pub fn stamp_hash(id: &Id, nonce: u64) -> [u8; 32] {
    let mut h = blake3::Hasher::new();
    h.update(id.as_bytes());
    h.update(&nonce.to_be_bytes());
    *h.finalize().as_bytes()
}

/// Bits of work a record actually carries.
pub fn stamp_bits(id: &Id, nonce: u64) -> u32 {
    leading_zero_bits(&stamp_hash(id, nonce))
}

The hash is plain BLAKE3 (no key, no context string) of 40 bytes. Nothing else goes in: not the signature, not the author's key separately (the id already covers it), not the time.

An interactive demo: a miner tries nonce after nonce, hashing each, until the hash starts with as many zero bits as the slider asks for. Each extra bit doubles the expected number of tries.

Counting leading zero bits

The 32-byte hash is read from its first byte: each zero byte counts 8, and the first non-zero byte adds its own leading zeros, most significant bit first. A hash of all zeros counts 256.

pub fn leading_zero_bits(h: &[u8; 32]) -> u32 {
    let mut n = 0;
    for b in h {
        if *b == 0 {
            n += 8;
        } else {
            n += b.leading_zeros();
            break;
        }
    }
    n
}

The nonce, twice

The nonce appears in two encodings in one stamp:

  • inside the record, as the nonce field, a canonical CBOR unsigned integer in its shortest form: 1 byte for 0–23, 2 bytes up to 255, 3 up to 65,535, 5 up to 232−1, 9 above;
  • appended to the id for the stamp hash, as exactly 8 bytes big-endian.

So the record's length changes as the search crosses 24, 256 and 65,536, and the miner re-encodes the CBOR head for every try. Native miners search the whole u64 range. The browser's miners pass nonces through JavaScript numbers, so they stay below 253 (the comment on mine_range in hoi-wasm); at any difficulty the protocol allows, a stamp is found long before that.

How many bits a record needs

For a record in a community the node holds, the required bits are the community's difficulty, minus a discount for the kind, minus a discount for the key's age:

pub fn required_bits(pow_bits: u32, kind_discount: u32, key_age_secs: u64) -> u32 {
    let d = key_age_secs / 86_400;
    let age = if d < 30 {
        0
    } else if d < 90 {
        2
    } else if d < 365 {
        4
    } else {
        6
    };
    pow_bits.saturating_sub(kind_discount).saturating_sub(age)
}

The community's pow_bits

limits.pow_bits is set in the genesis and changed by a limits ledger entry (Communities & the ledger). The default is 22; hoi_validate::limits allows 8 to 30. A record is judged against the easier of the community's current difficulty and the one in force when the record was made (limits_for takes the minimum), so raising the difficulty never invalidates records stamped before.

Kind discount

Kind::pow_discount takes 8 bits (256 times less work) off small signed actions:

Key age discount

Older keys pay less. The age is that of the author's root (the person, not the device), counted from first_seen: when this device first accepted a record from that root, never from anything a record claims, so nobody can backdate their way to a discount. A device's own new key is entered as first seen when it is made.

Authors stamp for the full difficulty

Each device counts key age from its own first sighting, so a device that has never seen your key gives no discount. The author's node therefore mines at key age 0 (bits_to_stamp calls bits_for(r, 0)): a post in a default community is always mined at 22 bits, and receivers who know the key simply find it has more than they need.

Records outside a community: 16 bits

When a record has no community, or is itself a community genesis, bits_for asks for GLOBAL_POW_BITS = 16, with no discount of any kind. That covers identity, delegation, revoke, rotate, every genesis, and a label published outside a community. Those records don't belong to any community whose limits could set a price, and they are kept for 100 years, so they pay a fixed one.

Floors: the cheap check first

The stamp is checked twice in the pipeline. First, stage 2, before the signature: a floor, the least work any record of this kind could need here. A flood of unstamped junk then costs a receiver one BLAKE3 hash per record instead of an Ed25519 verification. Failing it drops the record quietly (stamp too weak, no strike).

/// The least work any record of this kind could ever need: community difficulty may be as low
/// as 8 bits, minus the kind and the largest age discount. Checked before the signature, so a
/// flood of unstamped junk costs one hash each instead of a signature verification.
pub fn stamp_floor(kind: Kind) -> u32 {
    match kind {
        Kind::Community | Kind::Delegation | Kind::Revoke | Kind::Identity | Kind::Rotate => hoi_types::GLOBAL_POW_BITS,
        k => 8u32.saturating_sub(k.pow_discount()).saturating_sub(6),
    }
}

For a community the node holds, the floor is raised to what that community could ever ask: its pow_bits minus the kind discount minus the largest age discount (the code passes a key age of 366 days).

// stage 2: the cheapest check first, before any signature work. For a community we
// hold, the floor is the least any key could need there (its stamp minus the kind and
// the largest age discount), not the protocol-wide minimum.
if !loading {
    let floor = match community.and_then(|c| self.communities.get(&c)) {
        Some(st) if kind != Kind::Community => hoi_validate::stamp_floor(kind).max(hoi_crypto::pow::required_bits(
            limits_for(st, d.wire.record.created_at).pow_bits,
            kind.pow_discount(),
            366 * 86_400,
        )),
        _ => hoi_validate::stamp_floor(kind),
    };
    hoi_validate::stamp(&id, d.wire.record.nonce, floor)?;
}

Then, after the signature has shown whose record it is, the full check: bits_for(record, key_age(root)), with the real key age.

  • Records replayed from this device's own storage at startup (Source::Load) skip both checks: they passed when they arrived, and the limits that applied then aren't replayed yet.
  • Genesis records in directory listings and in requests to carry a community are checked against the 16-bit floor before anything else (directory.rs, carry.rs), and identity records in a batch are checked against it, then their signature, before any Argon2id runs.
  • When the author's node finishes a draft (publish_draft), it checks the nonce it was handed carries the bits the draft asked for, and refuses it otherwise (That stamp doesn't hold enough work.).

Identity work

A root key becomes an identity by publishing an identity record whose work nonce makes a memory-hard Argon2id hash start with enough zero bits. The work depends on the key alone, so it is done once and stays with the key for life; it can't be moved to another key. Argon2id makes each try cost 8 MiB of memory, so graphics cards and server farms gain far less over a phone than they would with a plain hash, and minting thousands of keys costs thousands of times the work.

The parameters are fixed by the protocol "so nobody can claim cheaper work": only the nonce varies. Three numbers bound how much work is asked for:

BitsNameMeaning
4MIN_BITSno identity carrying less is stored at all (invalid identity, and the sending peer gets a strike)

A person may publish a stronger identity later ("Key work" in the app, strengthenIdentity, 4 to 20 bits); communities count the best identity along the person's chain of roots. A root made later by recovery mines only the 4-bit minimum, because the person's earlier identity still counts. Receivers check the work with hoi_validate::identity, which also refuses a weak key, and cache the answer per author and nonce, so each identity costs a node one Argon2id run. On native hosts the run happens before the message takes the node's lock (crate::work), so a batch of identities doesn't stall other connections. Which community needs how much, and what happens without enough, is on Keys & identity.

Mining: the prefix trick

A miner doesn't re-encode the whole record for every try. Record::split_for_nonce cuts the canonical bytes around the nonce's value, so that encode() == prefix ‖ cbor_uint(nonce) ‖ suffix. Since nonce is the fourth key in canonical order, the prefix is the map head, v, body, kind and the nonce key; the suffix is everything from author on.

prefix | 127 B | sky | 6 | map head, v, body, kind, the key "nonce": hashed once nonce | 1–9 B | coral | 1 | shortest CBOR uint: the only bytes that change suffix | 117 B | mint | 5 | author, community, created_at, expires_at

Puzzle::search feeds the prefix into a BLAKE3 hasher once, then for every try clones that state, adds the nonce head and the suffix, finishes the id, and computes the 40-byte stamp hash. A try is therefore two short BLAKE3 finishes, whatever the length of the body.

/// Tries `start, start+step, …` for at most `tries` nonces. Returns the first nonce that works.
pub fn search(&self, start: u64, step: u64, tries: u64) -> Option<u64> {
    let mut base = blake3::Hasher::new();
    base.update(&self.prefix);
    let mut nonce = start;
    let mut buf = Vec::with_capacity(9);
    for _ in 0..tries {
        buf.clear();
        cbor::head(0, nonce, &mut buf);
        let mut h = base.clone();
        h.update(&buf);
        h.update(&self.suffix);
        let id = Id(*h.finalize().as_bytes());
        if stamp_bits(&id, nonce) >= self.bits {
            return Some(nonce);
        }
        nonce = nonce.checked_add(step)?;
    }
    None
}

The start, step form is how the search is split: worker i of n tries i, i + n, i + 2n… so no two workers ever try the same nonce. The core hands hosts exactly this puzzle: a draft is {token, prefix, suffix, bits}, prefix and suffix in base64url.

Mining on native hosts

The desktop app, hoi-node and the mobile libraries run the Rust core natively.

Threads check the shared found between chunks, so they stop within 4,096 tries of the first success; if two find one in the same round, the smaller nonce wins. Posts, replies and edits go draft → mine → publish even natively: the desktop mines with hoi_mine on a blocking thread without holding the node, and the mobile libraries draft under the node's lock, mine without it, then publish, so other calls and the network keep going. Before a phone's own benchmark is in, the mobile libraries assume 4,000,000 tries a second for the work bar.

Identity work natively

  • identity::mine: at 4 bits or fewer, or on one core, a single search; otherwise one thread per core (at most 16), each trying chunks of 8 nonces with step = threads.
  • identity::mine_watched: the same, but every try is counted in a Watch (tries so far, best bits so far) and a stop flag ends it after the current try. The desktop's "Key work" uses it (hoi_mine_identity), polls hoi_identity_progress twice a second and calls hoi_identity_stop when the person stops it.
  • identity::Miner keeps one 8 MiB buffer for all its tries and hands back each output, so a host can show the work as it happens.

Mining in the browser

In the web app the core runs in one Web Worker (hoi-wasm), and mining runs in a small pool of others, each loading the same wasm package. rpc-core.ts sends posts, replies and edits through draft → mine → publish so that mining uses several cores and the interface can show the work bar.

lanes: Page | Core worker | Miner pool -- Draft -- Page -> Core worker: draftPost(draft) Core worker: builds and checks the record, works out bits, keeps the draft for an hour Core worker --> Page: {token, prefix, suffix, bits} Page: emits stamp start with an estimate from rate() -- Mine -- Page -> Miner pool: mine {job, prefix, suffix, bits, start: i, step: n} to each worker Miner pool: each worker calls mine_range for 20,000 tries, yields, repeats Miner pool --> Page: found {job, nonce, tries, ms} Page -> Miner pool: stop {job} to every worker -- Publish -- Page -> Core worker: publishDraft(token, nonce) Core worker: checks the stamp carries bits, signs, runs the pipeline Core worker --> Page: the post as published Page: emits stamp done with the time it took

The pool

createMinerPool starts max(1, min(4, hardwareConcurrency − 1)) workers: one fewer than the cores the browser reports, at least one and at most four. Worker i searches nonces i, i + n, … The first found wins; the pool then sends stop to every worker. If every worker fails (out of memory, a wasm that didn't load), the promise rejects and rpc-core asks the core's own mine method instead, which native cores serve on every core; hoi-wasm compiles that method out.

const CHUNK = 20_000;

async function mine(j: Job) {
  active.add(j.job);
  await ready;
  let nonce = j.start;
  let tries = 0;
  const t0 = performance.now();
  while (active.has(j.job)) {
    const found = mine_range(j.prefix, j.suffix, j.bits, nonce, j.step, CHUNK);
    tries += CHUNK;
    if (found >= 0) {
      active.delete(j.job);
      self.postMessage({ type: 'found', job: j.job, nonce: found, tries, ms: performance.now() - t0 });
      return;
    }
    nonce += j.step * CHUNK;
    // let a stop message in
    await new Promise((r) => setTimeout(r, 0));
  }
}

mine_range is a thin wasm export over Puzzle::search: it takes the prefix, suffix, bits, start, step and tries as JavaScript numbers and returns the nonce or -1. Between chunks the worker yields with setTimeout(0) so a stop can arrive. A worker tracks the jobs it is on in a set, so a stamp that comes while a long identity job runs is mined alongside it, the two taking turns, rather than ending it.

The work-bar estimate

rate() runs a benchmark once, on the first worker: 30,000 tries of a puzzle that never succeeds (a 180-byte prefix of 0xa9, a 60-byte suffix of 0x01, 255 bits). The pool's rate is that, but at least 50,000 tries a second, times the number of workers. The estimate is stampEstimateMs(bits, rate) = round(2^bits / rate × 1000); the core emits stamp events with phase: "start" (bits and estimate) and "done" (the time it really took). The interface keeps its own running figure for other estimates, such as the join screen's "≈ … per post here": it starts at 222 tries a second (22 bits in about a second) and is updated from how long each stamp of 16 bits or more really took.

Identity work in the browser

A new key goes the same way: draftIdentity makes the key and returns {root, rootKey, short, fingerprint, bits}; the pool mines; publishIdentity(rootKey, work) checks the work and adopts the key. Each worker builds one IdentityMiner (one 8 MiB Argon2id buffer, so up to 32 MiB for four workers), tries one nonce at a time and posts every try back ({type: "try", work, hash, bits}, the hash transferred, not copied), so the first run can show the work as it happens. Between tries it yields through a MessageChannel rather than setTimeout, avoiding the 4 ms clamp; the code's comment puts a try at about 15 ms. "More work" (mineMore) reports progress every 250 ms and stops on an abort signal. If no miner can run, the core does the work itself, on one thread and without showing it.

lanes: Page | Core worker | Miner pool Page -> Core worker: draftIdentity(name, stir) Core worker --> Page: {rootKey, bits: 10, fingerprint…} Page -> Miner pool: identity {job, root, bits, start: i, step: n} Miner pool --> Page: try {work, hash, bits} for every Argon2id try Miner pool --> Page: found {nonce} Page -> Miner pool: stop {job} Page -> Core worker: publishIdentity(rootKey, work) Core worker: checks work_bits ≥ bits, keeps the keys, publishes identity and delegation

What checking costs

So the asymmetry is about 2bits to 1 for stamps: millions of tries to make a 22-bit stamp, one hash to check it. Identity work is the one expensive check, and the reason the node checks it last among the cheap stages, after stamp and signature, and only once per key.

Expected work, in tries and time

Each try succeeds with probability 2−bits, independently, so the number of tries is geometric with mean 2bits. That is an average, not a cap: about 63% of searches finish within 2bits tries, 86.5% within twice that, 95% within three times and 99% within 4.6 times.

Why both kinds of work

Stamps price every record, so a million posts cost a million seconds; identity work prices every key, so a thousand fresh keys cost a thousand times one key's work, which is what makes throwaway identities expensive. Neither stops a determined attacker alone: rate windows, the trust ladder and moderation do the rest (Spam & rate limits, Standing & review).

Checking an implementation

Every entry in records.json carries nonce and stamp_bits: the generator searches nonces from 0 at 8 bits, so stamp_bits is at least 8 and is the exact count of leading zero bits of BLAKE3(id ‖ u64be(nonce)). The identity vector also gives identity_bits: its work is searched from 0 at MIN_BITS, giving work: 56 worth 5 bits for the root of seed 02…02. Unit tests in pow.rs pin the discount arithmetic (required_bits(22, 8, 40 days) == 12, required_bits(22, 0, 400 days) == 16, required_bits(4, 8, 0) == 0) and the counting (00 10 … is 11 bits).
