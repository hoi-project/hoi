Records & encoding

Everything hoi stores or sends about a community is a signed record: one small envelope, encoded as canonical DAG-CBOR, named by the BLAKE3 hash of those bytes and signed with Ed25519. This page goes through the envelope field by field, the exact encoding rules and what the strict decoder refuses, how the id and the signature are made, how keys and ids are written as text, and the size, version and time rules every receiver applies.

The envelope

Every record has the same eight fields. Only body changes shape from kind to kind (Record kinds lists them all). The Rust type is hoi_types::Record; on the wire each field is a key of one CBOR map, under the protocol's snake_case name.

pub struct Record {
    pub v: u64,
    pub community: Option<Id>,
    pub author: Id,
    pub parent: Option<Id>,
    pub created_at: u64,
    pub expires_at: u64,
    pub body: Body,
    pub nonce: u64,
}

Fields

vuint
Protocol version of the record format. Must equal PROTOCOL_VERSION, which is 1; anything else is refused with unsupported protocol version before any other field is read (see Versions).
kindtext
Which body follows: one of the 24 strings Kind::as_str knows (post, comment, vote, profile-color…). It is not a field of the Rust struct: the encoder writes it from the body's variant and the decoder uses it to pick the body's schema. An unknown kind fails with unknown kind.
communitybytes(32), optional
The community's Ed25519 public key. Required for most kinds, forbidden for delegation, revoke, identity and rotate, optional for label (see Shape rules). Left out of the map when absent.
authorbytes(32)
The public key that signed the record: a device key (blessed by a root through a delegation), a root key signing directly, a community key (only its genesis), or a recovery key (only a rotate).
parentbytes(32), optional
What the record is about: a record id (the post a comment answers, the record a vote, edit, delete, label or review targets) or a person's root key (the person a vouch, report or share names). Left out when absent.
created_atuint, Unix seconds
When the author says the record was made, UTC. It drives rate windows, time checks and ordering; it may be at most CLOCK_SKEW (600 s) in the future of a receiver's clock.
expires_atuint, Unix seconds
When every compliant device deletes the record. Never earlier than created_at, never later than the community's max_retention allows (or 100 years for the kinds kept until superseded). See Time fields.
bodymap
The kind's fields. Optional body fields are left out when absent; the decoder refuses unknown and mistyped ones.
nonceuint
The stamp nonce the author's miner found. It is part of the record, so the id covers it. Stamps & work explains the search.

The wire wrapper

A record travels and is stored as a Wire: a two-entry map holding the record under r and its 64-byte signature under sig. The signature is outside the record, so it is not part of what the id hashes.

/// `Wire = { r: Record, sig: bytes64 }`
pub struct Wire {
    pub record: Record,
    pub sig: Sig,
}

impl Wire {
    pub fn encode(&self) -> Vec<u8> {
        Value::map([("r", self.record.to_value()), ("sig", Value::B(self.sig.0.to_vec()))]).encode()
    }
}

The wrapper adds exactly 73 bytes to the record: the post in records.json is 247 bytes of record and 320 bytes of wire. Size caps are measured on the whole wire (Size caps).

Canonical DAG-CBOR

hoi encodes with a small, deterministic subset of DAG-CBOR, written by hand in hoi-types/src/cbor.rs rather than by a general CBOR library. The point is that one value has exactly one encoding. The same record always gives the same bytes, so the same id and the same signature, and nobody can re-encode a record into different bytes that still verify. The module comment says it plainly: the decoder "rejects anything the encoder would not produce, so encode(decode(b)) == b for every accepted b".

The value model

The whole data model is eight variants of cbor::Value. There are no floats, no tags, no undefined, no indefinite lengths and no non-text map keys.

Integers and lengths: shortest form

Every integer, and every length of a string, array or map, is written in the shortest head that holds it. cbor::head picks the form:

Map keys: length first, then bytes

Map keys are text, and a map's entries are sorted the DAG-CBOR way: shorter keys first, keys of equal length bytewise. Value::map sorts whatever it is given, so code building a record never has to think about order.

/// DAG-CBOR key order: shorter keys first, then bytewise.
pub fn key_cmp(a: &str, b: &str) -> Ordering {
    a.len().cmp(&b.len()).then_with(|| a.as_bytes().cmp(b.as_bytes()))
}

So a record's keys always come out in this order (those present): v, body, kind, nonce, author, parent, community, created_at, expires_at. body comes before kind because both have four letters and b sorts before k. The order matters to miners: nonce sits fourth, so most of the record comes after it (Stamps & work uses this).

Absent is not null, and defaults are not written

Optional fields are left out of the map. Value::map keeps Null entries, so "absent" and "null" stay different values; record encoders never write Null. Where a field has a default, the encoder leaves the default out and the decoder refuses it written, so the value still has one encoding:

  • A post with no media has no media key. media: [] is refused (media must be a non-empty array).
  • limits.scatter is written only when it differs from the default (resist: 10, open: false); written as the default it is refused (the default scatter setting is left out).
  • limits.trackers and limits.age_issuers are written only when non-empty; an empty array is refused.

This also keeps older communities readable: a decoder that predates a field still reads limits that never mention it.

The strict decoder

cbor::decode reads exactly one value that spans all of the input. Then the typed layer (Fields in record.rs) takes the fields it expects out of each map and complains about anything left. Together they refuse every encoding the encoder would not have made.

The TooLong checks happen before allocating: every array item and every map entry needs at least one byte (two for an entry), so a header claiming a billion items in a 300-byte message is refused at once instead of reserving memory for it. Property tests in cbor.rs pin both directions: any value round-trips, and any byte string the decoder accepts re-encodes to exactly the same bytes.

What the typed layer refuses

  • Unknown fields. After a map's expected fields are taken, anything left fails with <what>: unknown field "…". A record with one extra key, anywhere, does not decode. There is no forward-compatible "ignore what you don't know" inside records.
  • Missing or mistyped fields. missing or mistyped "…". Keys and ids must be byte strings of exactly 32 bytes (expected 32 bytes, got n), signatures exactly 64.
  • Out-of-range numbers. Fields typed u32 in Rust (pow_bits, threshold, ladder steps, media w/h) refuse values above 232−1. Signed fields (vote.value, vouch.value) accept U(n) up to i64::MAX and N(n) below it.
  • Unknown enum strings. An unknown kind, admission, verdict or ledger action fails by name.
  • Shape violations. After decoding, Record::from_value runs check_shape (Shape rules).
Decoding is not validating

A record that decodes is well-formed, nothing more. Whether its signature holds, its stamp is strong enough, its author may write it and its text follows the content rules is decided by the later stages of the validation pipeline.

The record id

A record's id is the 32-byte BLAKE3 hash of its canonical encoding: the record map, nonce included, signature not.

/// `id = BLAKE3(canonical_cbor(Record))`
pub fn id(&self) -> Id {
    Id::hash(&self.encode())
}

On the receiving side, Wire::decode takes the value under r, re-encodes it and hashes that. Because the decoder only accepts canonical bytes, the re-encoding is byte for byte what arrived, so the id is the hash of the exact bytes received.

pub fn decode(bytes: &[u8]) -> Result<(Wire, Id), TypesError> {
    let v = cbor::decode(bytes)?;
    let mut f = Fields::new(v, "wire")?;
    let rv = f.take("r")?;
    let sig = Sig::from_slice(&f.bytes("sig")?)?;
    f.done()?;
    let id = Id::hash(&rv.encode());
    let record = Record::from_value(rv)?;
    Ok((Wire { record, sig }, id))
}
  • Content addressing. Two devices that hold the same record hold the same id, so sync can compare ids alone (Sync & gossip), and a record fetched by id can be checked against it.
  • Any change is a new record. One flipped bit gives a different id, so the old signature no longer verifies. A property test in hoi-validate flips random bits of a signed record and checks that the result either fails to decode or fails its signature.
  • Bytes that no longer decode. Wire::loose_id hashes the r value of stored bytes that are still a CBOR map but no longer a valid record (an older format), so storage can find and delete them by id.

An interactive demo: edit a field of a small record and watch its canonical bytes change, then its BLAKE3 id, and finally the Ed25519 signature check fail, because the signature was made over the old id.

Change one character and every later step changes with it: new bytes, a new id, and a signature that no longer verifies.

Signatures

The author signs the 32-byte id with Ed25519. Not the record bytes, not a hash of the wire: the id. Signing is Keypair::sign_record; checking is stage 3 of the pipeline, hoi_validate::signature, which verifies sig against author over id.

/// `sig = Ed25519.sign(author_sk, id)`
pub fn sign_record(&self, record: Record) -> (Wire, Id) {
    let id = record.id();
    let sig = self.sign(id.as_bytes());
    (Wire { record, sig }, id)
}

pub fn verify(pk: &Id, msg: &[u8], sig: &Sig) -> bool {
    let Ok(vk) = VerifyingKey::from_bytes(pk.as_bytes()) else { return false };
    let s = ed25519_dalek::Signature::from_bytes(&sig.0);
    vk.verify_strict(msg, &s).is_ok()
}

Strict verification

Every signature in hoi goes through verify, which uses ed25519-dalek's verify_strict. Plain Ed25519 verification tolerates a few kinds of malleability; strict verification does not. A signature fails when:

  • the public key is not a valid compressed curve point (VerifyingKey::from_bytes fails);
  • the scalar s (the last 32 bytes of the signature) is not canonical, that is not below the group order;
  • R (the first 32 bytes) does not decompress, or is a small-order point;
  • the public key itself is a small-order point (a "weak" key);
  • the recomputed R differs from the encoded one, compared as bytes, so a non-canonical encoding of the right point fails too.

Together with canonical CBOR this means a record has one valid byte form and its signature cannot be tweaked into a second one that still verifies.

Weak keys

A weak (small-order) public key can make signatures that verify for many messages. Strict verification already refuses signatures from one, and key_is_strong lets the code refuse such a key outright where a key becomes something: an identity (hoi_validate::identity answers weak key), both keys of a delegation (delegation_consent answers bad signature), a recovery key in a rotate, and an open community's drop key in a ledger entry.

/// A public key that is a valid curve point outside the small-order subgroup. Weak keys can
/// produce signatures that verify for many messages; no identity may use one.
pub fn key_is_strong(pk: &Id) -> bool {
    VerifyingKey::from_bytes(pk.as_bytes()).is_ok_and(|vk| !vk.is_weak())
}

did:key

did:key is the W3C method that writes a public key as a DID. For Ed25519 the key is prefixed with the multicodec ed25519-pub code, written as the varint 0xed 0x01, then encoded base58btc (the Bitcoin alphabet) under the multibase prefix z. Every hoi did:key therefore starts did:key:z6Mk.

ed 01 | 2 B | lilac | 2 | multicodec ed25519-pub, as a varint key | 32 B | sky | 6 | the raw public key base58btc | ≈47 chars | sun | 4 | of the 34 bytes, after did:key:z 
const ED25519_PUB: [u8; 2] = [0xed, 0x01];

pub fn did_key(pk: &Id) -> String {
    let mut b = Vec::with_capacity(34);
    b.extend_from_slice(&ED25519_PUB);
    b.extend_from_slice(pk.as_bytes());
    format!("did:key:z{}", bs58::encode(b).into_string())
}

pub fn parse_did_key(s: &str) -> Result<Id, TypesError> {
    let rest = s.trim().strip_prefix("did:key:z").ok_or(TypesError::Did)?;
    let b = bs58::decode(rest).into_vec().map_err(|_| TypesError::Did)?;
    if b.len() != 34 || b[..2] != ED25519_PUB {
        return Err(TypesError::Did);
    }
    Id::from_slice(&b[2..])
}

Parsing accepts nothing else: another multibase prefix, another codec, or a decoded length other than 34 bytes is bad did:key. The vector did_key_root in uris.json is did:key:z6Mko9hTggMwjSTEaJaPUfE6tqcy2xvU6BnNq3e3o8qVBiyH, the root of seed 02…02. Display names can never pass for one: the name rules refuse any name starting did: or containing · (Text, links & names).

Shape rules

Record::check_shape runs inside from_value, so a record with the wrong shape doesn't even decode. It needs no state, only the record.

RuleKinds
must have communityevery kind except delegation, revoke, label, identity, rotate
must not have communitydelegation, revoke, identity, rotate
must have parentcomment, vote, edit, delete, label, report, vouch, review, share
must not have parentprofile, profile-color, post, delegation, revoke, community, ledger, identity, pointer, roster, rotate, trust, wiki, tally, blocklist

And per kind:

  • A community record (the genesis) must have community == author: only the community key signs it.
  • A delegation's body.root may not be its author (a key can't be its own device), and body.expires_at must equal the record's expires_at.
  • A vouch may not name its own author as parent (nobody vouches for themselves).
  • Lists must be sorted, each entry once, and within their caps: roster.holders 1–32, trust.keys 0–256, blocklist.exact and .pdq 0–1000 each, tally.counts 0–500 sorted by post.
  • A wiki edit names a valid page (1–64 of a-z, 0-9, -, not starting or ending with -) and carries a non-empty update of at most 32 KiB.
  • For every kind, expires_at may not be before created_at.

Size caps

Stage 1 of the pipeline, hoi_validate::decode, limits size twice. Before decoding anything it refuses any wire longer than 65,792 bytes (64 KiB + 256). After decoding, it compares the wire's length with Kind::max_size for the record's kind. Either failure is too big for its kind, and the peer that sent it gets a strike.

pub fn decode(bytes: &[u8]) -> Result<Decoded, Reject> {
    if bytes.len() > 64 * 1024 + 256 {
        return Err(Reject::TooBig);
    }
    let (wire, id) = Wire::decode(bytes).map_err(|e| Reject::Decode(e.to_string()))?;
    if bytes.len() > wire.record.kind().max_size() {
        return Err(Reject::TooBig);
    }
    Ok(Decoded { wire, id, size: bytes.len() })
}

Media never counts against these caps: a post carries only MediaRefs (hash, type, size, dimensions, alt text), and the bytes travel separately by hash (Media). Text fields have their own character limits on top of the byte caps, set by the content rules (Record kinds lists them per field).

Versions

The v field is checked first: Record::from_value reads v and refuses anything but PROTOCOL_VERSION (1) with TypesError::Version before the kind or any other field is looked at. A record of an unknown version therefore costs a receiver one CBOR parse and nothing more.

Three other version numbers exist, each for its own layer, and none of them is the record's:

  • the sync protocol's hello carries v: SYNC_VERSION, currently 2 (Sync & gossip);
  • codes in links carry their own v: 1 inside the code, and magic bytes with a version (Links & URIs);
  • the release metadata in release.json names a protocol label (protocolVersion, supportedProtocols) that registries and public join pages compare; it never changes how a record decodes.

Domain-separation strings carry versions too: hoi/delegation/1, hoi/identity/v1\0 (the identity-work salt), hoi 2026 key fingerprint v1. A new format gets a new string rather than reusing the old one.

Time fields

Times are Unix seconds, UTC, as unsigned integers. Stage 4, hoi_validate::time, applies four rules, with CLOCK_SKEW = 600 seconds:

pub fn time(record: &Record, now: u64, live: bool, max_retention: Option<u64>) -> Result<(), Reject> {
    if record.created_at > now + CLOCK_SKEW {
        return Err(Reject::FromTheFuture);
    }
    if live && record.created_at + CLOCK_SKEW < now {
        return Err(Reject::TooOld);
    }
    if record.expires_at <= now {
        return Err(Reject::Expired);
    }
    let cap = max_retention.unwrap_or(KEEP);
    if record.expires_at > record.created_at.saturating_add(cap) {
        return Err(Reject::ExpiryTooFar);
    }
    Ok(())
}

The cap is KEEP, 100 × 365 days, for records exempt_from_retention lists: community, delegation, revoke, identity, rotate, vouch, share and wiki, and the ledger entries kept until superseded (rules, limits, mod-add, mod-remove, retire, drop-key). A review that answers a pending proposal is kept as long as the proposal. Everything else is capped by the community's max_retention (default 15,552,000 s, 180 days; allowed range one hour to ten years). The node uses the larger of the community's current retention and the one in force when the record was made, so a later tightening doesn't retroactively refuse old records.

  • Delegations also may not outlast created_at + 400 days (MAX_DELEGATION); the apps bless devices for 180 days at a time.
  • Threshold proposals (ledger entries carrying cosignatures) are not judged "live", so cosigning can take time, but one older than 7 days (PROPOSAL_MAX_AGE) is refused when it arrives live or is made locally.
  • Key age for stamp discounts counts from when this device first saw the key, never from a record's created_at, so backdating buys nothing (Stamps & work).
  • Rate windows count by created_at, so every device reaches the same answer and backdated records can't skip them (Spam & rate limits).

What happens at expires_at (deletion, tombstones, what stays) is on Expiry & removal.

Immutability and edits

A record never changes. Its id is the hash of its bytes, so "changing" one would make a different record with a different id, and the original signature would not cover it. Everything that looks like a change is a new record that points at an old one.

ChangeNew recordWhat counts
edit a post or commentedit, parent = the original, new text and optional titlethe edit with the latest created_at by the same root as the original; the original stays and keeps its id
delete your own post or commentdelete, parent = the original, empty bodythe original's body is dropped and it becomes a skeleton marked "deleted by the author"; replies under it stay
change a votea new vote with a higher seq (the app uses the time in seconds × 1000, always above its last one); value 0 takes it backthe highest seq per voter and target
change a vouch or a reviewa new one with a higher seqthe latest (seq, created_at, id) per author and target; older ones are dropped
a new profile picture or colorprofile / profile-color with a higher seqthe highest (seq, created_at, id) per person and community
new trust list, tally or blocklista new record of the same kindthe latest (created_at, id) per author, community and kind; older ones are dropped
moderationa ledger entry with the next seqreplayed in order; removals tombstone their target (Communities & the ledger)

Only the author can edit or delete: the node checks that the edit's or delete's root is the original's root, that the target is a post or comment, and that both are in the same community. Edits carry their own expires_at, which the app sets to the original's (and at least a minute ahead).

Conformance vectors

core/vectors/records.json holds one signed record of each common kind: genesis, identity, delegation, post, post with media, comment, vote, vouch, review, edit, label, report, delete, revoke, pointer, roster, two identities of a recovery line, rotate and share. Each entry gives the signer's seed (32 repeated bytes: 01… for the community, 02… for the root, 03… for the device, 04… and 05… for two other members), the canonical record bytes, the id, the nonce, the stamp bits it carries, the signature and the full wire. Times start at created_at_base 1,790,000,000 and stamps are mined at 8 bits, searching nonces from 0, so the file is deterministic.

The generator is cargo run -p hoi-validate --example vectors; with -- --check it fails if the file would change. An implementation that decodes each wire_cbor, re-encodes the record to record_cbor, hashes it to id and verifies sig against signer agrees with this page. More on Test vectors.
