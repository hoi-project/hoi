Private communities

A private community is an MLS group whose group id is the community key. Members write the same signed records as anywhere else, but those records leave a device only inside MLS messages, sealed again for the epoch's room and padded to a few fixed sizes. This page follows the core's private.rs: the OpenMLS setup, how a device is bound to its person's key, inviting, posting, removing, what stays on the device and who can read what.

What a private community is

A public community syncs its records in the clear between devices (Sync & gossip). A private one never does. Its records are ordinary signed records (Records & encoding) and every device still runs the full validation pipeline on them, but they reach other devices only inside an MLS group (RFC 9420) that holds only invited devices. The core implements this on OpenMLS, in hoi-core/src/private.rs.

  • One group per community. The MLS group id is the 32-byte community key. The community's genesis is a normal community record (Communities & the ledger), but it travels only inside the group.
  • One owner. create_private_community refuses co-owners and any threshold but 1 ("Encrypted membership currently requires one owner."). The device that created the group coordinates membership and cannot leave it.
  • Devices, not people, are members. Each MLS leaf is one device, bound to its person's root key. A group holds at most 128 leaves.
  • No conversion. A Welcome for a community this device already knows as public is refused ("Public communities cannot become private."). The owner of a members-only community (admission invite or approve) can make a private copy instead (privateCopy): a new group with the same name, description, color, limits and rules, whose membership follows its records. Posts stay where they were; people join the copy by request.
  • Unlisted. A private community is never in discovery, has no registry registration or publication proof, no public join and no invite link or bundle export.

Where MLS state lives

The provider is OpenMlsRustCrypto with its in-memory storage. The core keeps that storage as a list of key–value pairs in PrivateState.storage: provider() copies them into a fresh provider for each operation and save() copies them back, zeroizing the old values first. The whole PrivateState is saved as the JSON blob mls (what is stored).

Credentials bound to hoi keys

Each leaf uses an MLS BasicCredential whose identity is a small JSON document. A leaf cannot gain owner powers by naming the owner's root: the credential must carry the device's own delegation, signed by that root.

/// A BasicCredential's identity is cryptographically bound to the hoi root's signed device
/// blessing. A leaf cannot acquire owner powers by merely claiming the owner's root in JSON.
#[derive(Serialize, Deserialize)]
#[serde(deny_unknown_fields)]
struct BoundCredential {
    device: String,
    root: String,
    delegation: String,
}
devicehex
The device's Ed25519 key. It must equal the leaf's MLS signature key.
roothex
The person's root key.
delegationbase64url
The wire bytes of the device's delegation record (Keys & identity). It must decode, its signature must verify, its author must be the device, and its root's consent must name root.

Every message's sender is checked again (private_sender) against what the device knows now:

  • The root must not be burned, and the device must not be revoked or blessed by another root. A revocation always wins.
  • An expired delegation is not the end of a leaf: "MLS credentials bind a key, not a permanently frozen authorization lifetime." A later root-signed renewal for the same device and root, made after the original and expiring after it, with the global stamp, extends it. The outbox always counts the device's identity and current delegation among what it sends, so a renewal reaches the others; a committer whose own leaf's delegation has expired sends its renewal ahead of a commit (queue_membership_renewal).
  • A commit is followed only from a committing device whose delegation scope covers moderate:<community hex>, in both the leaf's original credential and the delegation the device holds now. A broader renewal does not widen the original leaf's scope.
Note

Device delegations last 180 days by default (DELEGATION_LIFETIME). A member who was offline past that is recognised again once a renewal arrives; a test covers an offline member recovering after its original blessing expired.

Creating a group

  1. Check the owners

    One owner, threshold 1, no co-owners.

  2. Renew and sign

    The device renews its delegation if due and builds its MLS signer from its device key and the bound credential.

  3. Mark it private first

    create_community_with_privacy(draft, true) adds the key to state.private_communities before the genesis exists, so the genesis never takes a public path. A private community does not get open-community pieces settings; its posts go in pieces through the group anyway.

  4. Make the group

    MlsGroup::new_with_group_id with the configuration above, group id = community key. Epoch 0 has one leaf: this device.

  5. Save

    A SavedGroup with owner: true; registration and publication proofs for the key are dropped; rules are set if the draft had any.

  6. Choose mailboxes

    From then on the owner's device looks for public nodes that keep pieces and lists two to four of them in the group context by a commit (Mailboxes).

lanes: Owner's app | Owner's core | Holders Owner's app -> Owner's core: createPrivateCommunity {name, description, color, limits, threshold: 1} Owner's core: refuses co-owners and any threshold but 1 Owner's core: marks the key private, then signs and stores the genesis Owner's core: MLS group, group id = community key, epoch 0 Owner's core --> Owner's app: the community view -- Choosing mailboxes -- Owner's core -> Holders: links to public nodes that keep pieces Owner's core: picks 2 to 4, each in a place of its own Owner's core: commit: extension 0xff44 lists them (next epoch) Owner's app: shows "Choosing mailboxes" until then

The web app's form (PrivateStart.svelte) creates the community with color lilac, the default limits with maxRetention set to 30 days, and threshold 1, then starts syncing it.

Inviting and joining

Joining takes a request from the newcomer and an invitation back. The request binds the invitation to one device: the Welcome inside opens only with that device's key package.

The join request

privateJoinRequest returns hoi:private-request: followed by base64url (no padding) of this JSON:

vu8
1.
packagebase64url
The TLS-serialized MLS KeyPackage: suite SUITE, leaf capabilities listing all five required types, the bound credential.
records2 × base64url
The person's identity record and the device's delegation.
pickup{key, holders}
A fresh one-time X25519 public key and up to 4 holders (endpoint, up to 4 routes of at most 128 bytes each, no endpoint twice) that the newcomer's app reaches. The committer stores the invitation there, sealed to the key (picking it up).

A device has one request out at a time. Asking again within 7 days returns the same request; after that its key package is deleted and a new one built. The pickup key's seed stays on the device (and is zeroized when the request goes).

The owner's check

privatePreviewRequest runs checked_request and returns {device, root}. It refuses a request unless: v is 1; there are exactly two records; the pickup reads well; the key package validates for MLS 1.0 in SUITE and lists every capability; its credential is bound and its signature key is the device; the identity is authored by the root and passes its identity-work check; the delegation is authored by the device, consents to the root and has not expired; both records are within the clock window; and the device is not revoked. The app shows the person key and device key and asks the owner to verify the key through a trusted conversation before approving.

Adding the device

  1. May this device commit?

    The owner's device, or in a group that follows its records a committer in line once the group has mailboxes (below).

  2. Admit first, where records decide

    A banned person is refused. A person not yet admitted gets an admit ledger entry before the commit.

  3. Room for one more

    Refused at 128 members or for a device already in the group.

  4. Nothing out of order

    Anything waiting to go out must already have its place ahead of the commit (ready_for_commit): nothing pending, or every pending object assigned a mailbox slot. On a relay the app sends what waits first.

  5. Commit

    add_members makes a commit and a Welcome. The commit is sealed for the room of the epoch it ends, so members still there read it; then it is merged.

  6. Bootstrap

    A bootstrap payload (v 2) with this device's identity and delegation and the community's genesis (and, from a moderator's device, the mod-add that made its person one, with its signer's records) is sealed for the new epoch's room and queued. The same sealed bytes go into the invitation.

  7. History again

    The newcomer's identity and delegation are ingested, and send_all_again makes this device resend the whole live history into the new room: the newcomer reads only from its own epoch on.

  8. Invitation

    hoi:private: + base64url of {"v": 2, "welcome": …, "bootstrap": …}. It is also queued for pickup: sealed to the request's one-time key and stored on the holders the request named.

Joining

privateJoin processes the Welcome on a temporary provider and changes nothing durable until every check passes:

  • The invitation is v 2; the Welcome is a Welcome; its group id is a community this device does not know as public, and is not already an active group here.
  • Every member's credential in the new tree is bound and valid.
  • The bootstrap opens with the new epoch's room secret, is a PrivateMessage of this group, an application message, and a bootstrap payload v 2 for this community.
  • The genesis it carries has one owner and threshold 1. From the owner's device the bootstrap holds exactly three records (genesis, identity, delegation), each with the global stamp; from a moderator's device at most 16, which must include the moderator's identity and delegation and a mod-add naming them.
  • The records are ingested; if any fails (or the moderator's role does not replay), every record the join added is removed again and the community forgotten.

When membership follows the records

When a private community's admission limit is invite or approve (follows_records), who is in the MLS group is decided by the community's own records, as for any members-only community (Standing & review):

  • Every member checks every commit (check_record_commit). Each person added must be admitted by the records this device holds and not banned; each member removed must be excluded: banned, identity burned, or device revoked or bound to another person. Otherwise the commit is private-pending (its records may be on the way) and is never followed if they do not come. The committer sends the backing records (identity, delegation, positive vouches and admit entries for an addition; bans and revocations for a removal, at most 64) in the old room ahead of the commit.
  • Anyone can pass a request on (privatePassRequest). In an invite community the member who passes it vouches for the person: the vouch is the invitation. The request goes into the group as a request payload; committing devices keep up to 32 per group for 7 days; the member who passed it sends it again in each new epoch until the device is in the group.
  • Several devices commit, in a line. The owner's devices first (since the community began), then moderators' devices by the time of the mod-add that made their person one, then by the age of the blessing in the leaf. Only leaves whose delegation covers moderate:<community> and that the records do not exclude count. Moderators' devices commit only once the group uses mailboxes. Every member holding the same records computes the same line.
  • Turns. The first in line makes a change at once; the device at place r makes it only after r × TURN (3600 s) of silence from those ahead. A committer changes membership by itself only after reading the epoch at least CATCH_UP (60 s) with its mailboxes answering, and one back from a silence of more than 300 s catches up first.
  • Contested epochs. A member that follows a later committer's commit keeps that epoch's MLS state for CONTEST (86,400 s) and keeps reading the slots of the committers ahead. If an earlier committer's commit of the same epoch turns up there and the records back it, it counts instead: the device goes back to that epoch, follows it, drops what it queued and sends everything again; invitations made in the abandoned branch are let go. A device added by the losing commit asks again, and within a day of first joining it takes a newer invitation.
  • Invitations travel in the group. A committing device that adds someone whose request is waiting (follow_records, one change a round) also puts the invitation into the group as a welcome payload, so any member's app shows it ready to hand on in case the pickup fails.
  • The drop key. The mailbox list also carries the group's drop key (Ed25519, public part) and the committer devices that hold its secret. Each committer device announces an X25519 seal key derived from its device key (sealKey) in each epoch it is in line; the secret is sealed to it with HPKE (dropKey, info hoi drop key v1, bound to the community, the device and the public key). It lets committers drop a removed post's pieces from holders (Scattered delivery). A new key is made when a device it was given to leaves the line.

Epochs, rooms and keys

Every commit starts a new MLS epoch, and everything a carrier can see is derived from the epoch's exporter secret. A device that is not a member of the epoch derives none of it; knowing the community key derives nothing either (a test builds a room from the community key and checks it differs).

const RELAY_LABEL: &str = "hoi relay v2";
const SEAL_CONTEXT: &str = "hoi relay v2 object";

fn relay(p: &OpenMlsRustCrypto, g: &MlsGroup) -> R<Relay> {
    let mut exported = g.export_secret(p.crypto(), RELAY_LABEL, &[], 32).map_err(mls)?;
    let secret: [u8; 32] = exported.as_slice().try_into().map_err(mls)?;
    exported.zeroize();
    Ok(Relay::from_secret(secret))
}
impl Relay {
    fn from_secret(secret: [u8; 32]) -> Relay {
        let mut seed = blake3::derive_key("hoi relay v2 room key", &secret);
        let key = Keypair::from_secret(&seed);
        seed.zeroize();
        Relay { key, secret }
    }
}

What a commit changes

  • The commit is sealed for the room of the epoch it ends: members still in that epoch read it there and move on.
  • A newcomer's Welcome is for the new epoch; it never sees an earlier room.
  • A removed device reads its removal in the old room and cannot derive the next. It can still sign for the old room until those objects expire, which reveals nothing new and which other members no longer read.
  • A message from a later epoch than this device's is private-pending ("An earlier encrypted membership update is still missing.") and is tried again later; one from an earlier epoch is remembered and dropped.

What goes again after a commit

A message sent in an epoch may land after the commit that ended it, where members who moved on never read it. So each device remembers in which epoch each record or media item first went (sent_in) and sends some of it again:

It made a commit that adds someoneEverything it has (send_all_again).
It followed someone else's commit that addsWhat it first sent in the ended epoch, and all of its own: its records, its person's identity, its delegation and its own posts' media.
It followed someone else's commit that removes, or changes the mailbox listOnly what it first sent in the ended epoch.
It made a commit that removes, or changes the mailbox listNothing: everything it queued went ahead of its commit, where members read it.

It went back to an earlier committer's commitEverything; its outbox is cleared.

Posting: what leaves the device

A post is written as usual and stored locally first. What leaves the device is made by private_outbox, which the app (or the mailbox loop, every 15 s) calls:

  1. The record

    A normal signed and stamped record (Stamps & work), in the local store. A device without the group's keys refuses to write one.

  2. Gather

    The outbox collects what has not gone out in this epoch: the device's identity and delegation, the carriers (identity and delegation records) of every record, the genesis, and every forwardable record of the community, ordered carriers first, then the genesis, then by created_at.

  3. Pieces or whole

    When the device can keep things in pieces now (can_scatter), each post, comment and edit becomes an object of its own, kept in pieces on holders, and attachments go in raw slices; the group then gets pointer payloads. Everything else (votes, deletions, profiles, a device's own authorization records) goes whole, in records payloads of at most 256 KiB of wire bytes each; attachments that go whole go in 256 KiB media chunks.

  4. MLS

    Each payload is JSON, made into an MLS application message (create_message: AES-128-GCM, signed by the device's leaf) and TLS-serialized.

  5. Seal for the room

    u32 length ‖ message ‖ zeros to a padded size, sealed under the epoch's object key. The id is the SHA-256 of the sealed bytes; it expires 30 days on (RETENTION); the room key signs hoi relay object v2\n<room>\n<id>\n<expires>\n<size>.

  6. Out

    The CipherObject waits in the group's outbox (at most 64) until a mailbox quorum or every configured relay has it, then privateAck drops it.

nonce | 24 B | sun | 2 | random XChaCha20 nonce length | 4 B | coral | 1 | u32 BE length of the MLS message MLS message | n B | lilac | 5 | TLS-serialized PrivateMessage: group id, epoch and content type stay inside zeros | to size | mute | 2 | padding, checked to be zero tag | 16 B | peach | 2 | Poly1305 tag; AAD is hoi relay v2 object

Sizes are at least 4 KiB with at most four significant bits: 4,096, 4,608 … 7,680, 8,192, 9,216 … up to 1 MiB, 65 sizes in all, at most one eighth above the content past 4 KiB. The longest MLS message one object holds is 1,048,576 − 44 bytes.

/// The smallest size of at least 4 KiB with at most four significant bits that holds `size`.
fn padded(size: usize) -> usize {
    let size = size.max(PAD_MIN);
    let step = 1usize << (usize::BITS - 4 - size.leading_zeros());
    size.div_ceil(step) * step
}

Receiving

privateReceive takes one sealed object (base64url, at most 4/3 of 1 MiB plus 8 characters). Its SHA-256 id is skipped if already received. The object must have a padded size and open under this epoch's key with zero padding and a length inside it; the MLS message must be a PrivateMessage of this group and not from a later epoch. Then:

  • Application messages: the sender's credential is checked; a renewal riding in the same payload is taken first. records and bootstrap are ingested from Source::PrivateRelay, which runs full validation and never gossips; media chunks are kept until the item is whole (at most 32 MiB of partial attachments), and only while a forwardable post of this community uses the hash; pointer, request, welcome, sealKey and dropKey go to their own handlers.
  • Commits: the sender must be a committer in this epoch's line with membership permission, and, where records decide, the records must back the commit. After merging, every member's credential is checked again; if this device is no longer active, its outbox and partial media are cleared: "Data made before revocation must never be published after removal."
  • Anything else is refused with private-invalid: "This encrypted message could not be authenticated."

Removing a member

privateRemove(community, device) takes one device out of the group:

  1. Checks

    Only a committing device; never its own device ("Keep this device in the community while managing other devices."). Where records decide, the person must already be excluded: "Membership here follows the community's records: ban this person first, and their devices leave." The committers' devices then remove excluded members by themselves, in their turns.

  2. Order

    As for an addition, everything pending must be ordered ahead of the change, and a renewal goes first if needed. Where records decide, the bans of the person and revocations by them go in the old room ahead of the commit.

  3. Commit

    remove_members; the commit is sealed for the room it ends and merged. The group is in a new epoch with a new room. Nothing is sent again by the committer.

  4. The removed device

    It reads the commit in the old room, merges it, and is no longer active: active false, room empty. It cannot sign reads or open new objects, and its queued objects are cleared.

Other members: cannot derive room e+1 or open its objects
Limit

Removal changes future keys, not copies already received. A removed device keeps what it read while it was a member, and any member can keep copies. The app says so: "Members can keep what they read. Removing a device protects new posts, not copies already received."

A removed device can come back only with a fresh request and a new invitation. A member can also leave on its own device (leave): its MLS group and group state are deleted and the community stays listed as a former membership; the owner's coordinating device cannot leave.

Secrets are zeroized where they are dropped: the pickup seed, the relay secret, storage values replaced on save, contested epochs let go. In the browser these blobs live in IndexedDB behind the vault, which encrypts saved data under the person's passphrase (Storage, Web app). Nothing private is in a device-link approval or an identity backup: both leave out private groups' geneses.

Missing keys

If the mls blob is lost, the marker still stands: the community stays private, unlisted and unwritable on that device (missing keys never allow new local private writes), and its genesis cannot be imported in the clear.

What a holder sees

A group's mailbox slots and its posts' pieces are kept by public nodes that hold pieces for anyone (Scattered delivery). A holder has its own transport and envelope keys and nothing of the group's: no membership, MLS state, community secret or object key. It cannot read a post or an attachment, and nothing it is sent or keeps names a community or an author. It does see metadata, and some of it can be linked:

WhatWhat a holder sees
SizesA slot is an MLS message padded to at least 4 KiB with at most four significant bits; a bell ring is 32 random bytes; a piece has its size class's piece length, which says roughly how large the object is. Requests other than puts are 256 bytes and short answers 64; a got is as long as the asker asked for, whether or not the piece is there.
TimingWhen each put, probe and fetch arrives, and how often a locator is asked for. Writes followed by bell rings, and probes every 5 seconds to 2 minutes, show that a group is active. After a commit, members write the new epoch's first slots and send the live history again: a burst that hints at a membership change.
AddressesThe address of the link each request came over: a forwarder's where one is used, otherwise the member's own. A mailbox no forwarder reaches, or a forwarder that also holds pieces, sees the members linked to it.
ExpiryEach piece's last day and the day it was last asked for. Slots are kept at most 30 days, bell rings 2, a private group's pieces 30 (RETENTION), and no piece more than 400 (MAX_TTL_DAYS).
Deletion metadataA drop hash, which no two locators share, and a drop key id. Every piece of one group carries the group's drop key id, so a holder can tell which of its pieces belong to the same group, and count them, without learning which group it is; a new drop key starts a new id. Slots, bell rings and invitations carry none. A drop by the drop key shows the key's public half and a signature.
Locators32 bytes derived from secrets only members have: a slot's from the epoch's slot key, a piece's from its manifest. Asking for a community key, post id or object id finds nothing, and no request lists what a holder keeps: has answers presence and length, get the piece or nothing.

Epochs, history and removal

Every commit starts an epoch with a new slot key, so a holder sees new locators that share nothing with the last epoch's. A newcomer reads posts made before it joined because members send the live history into the new epoch (What goes again after a commit); posts go again as new objects, under new keys and locators. Removal protects what comes after it, not what came before: a removed device keeps the posts and attachments it read and the manifests it was given, and holders check no membership, so it can fetch those pieces until they expire or are dropped. Nothing it keeps derives a later epoch's slots or opens a later post.

Limits

  • Public communities stay publicly readable: anyone who joins one, a holder's operator included, opens its pointers and rebuilds its posts (Open communities).
  • A holder's operator who is, or becomes, a member of a group derives the same locators and learns its drop key id: they can recognise that group's slots and pieces among those they keep, and read them.
  • The tests below check what holders are sent and keep in one network of test nodes. They are evidence, not a proof of anonymity.

tests/holder_privacy.rs runs a group through three forwarders and fourteen holders that keep their pieces in SQLite. The reader gets the post and its photo. Every request a holder is sent opens with the holder's own keys and carries only its operation's fields, none of them a known identifier; answer keys are used once and a drop hash names one locator; since the post, every locator is a slot or a piece only members derive; answers have the sizes above. Each holder's file, reopened, keeps exactly the rows it was sent, and the reader rebuilds the post from it. Known locators answer presence or the piece, unknown ones nothing at the same size, a community key or post id among them. Distinctive titles, text, names and attachment bytes, the community key, post id and person keys, the object, slot and device secrets and the drop key's secret appear in no message to a holder and in no file it keeps. A second test removes a member: slot locators change, the removed device keeps what it read and can still fetch the pieces it was told about, a newcomer reads the older post, and nothing new reaches the old epoch's slots. hoi-store's pieces.rs pins the columns a reopened file holds.

Vendored crypto patches

Two OpenMLS crates are local copies of their published 0.6.0 source (OpenMLS commit 3a3e35de) with upstream changes applied, through [patch.crates-io] in both application workspaces. vendor/README.md calls them temporary, locally maintained patches, not new crypto implementations or an audited fork, to be replaced by reviewed upstream releases when compatible ones exist.

DirectoryLocal change
vendor/openmls_rust_cryptoThe upstream crypto API migration (055a2b4b); HPKE dependencies upgraded to 0.8 as upstream did (e0b21a70); unused post-quantum dependencies feature-gated as upstream did (27ddc74e).
vendor/openmls_basic_credentialThe same migration, optional ML-DSA feature-gated; the released serialization and storage APIs preserved.

vendor/openmls-crypto-migration.patch is that upstream migration with paths adjusted. What it changes in the source:

  • Randomness comes from getrandom's SysRng (wrapped in UnwrapErr) instead of rand_core::OsRng; the provider's ChaCha20 generator is seeded from it, and the rand_shim.rs adapter is removed.
  • Elliptic-curve keys use the new APIs: generate_from_rng, to_sec1_point and from_sec1_bytes in place of random and EncodedPoint.
  • AEAD nonces and ECDSA private keys are converted with try_into, so a wrong length returns InvalidLength (or a signing error) instead of failing inside a conversion; new tests check wrong nonce and key lengths.

Why a patch rather than OpenMLS main: applying the migration to the published 0.6.0 source keeps the 0.9.2 release's targeted-message security interface. With it, both lockfiles resolve crypto-bigint 0.7.8, above the 0.7.6 that fixes RUSTSEC-2026-0387; the provider's minimum Rust becomes 1.94, and hoi pins 1.97. scripts/check-dependency-security.mjs refuses removing the patches, and cargo test --locked -p hoi-core -p hoi-net --test crypto_backend checks every supported MLS suite, AEAD authentication, signing, HPKE exporters and tampering (Supply chain & hardening).
