Deploying & hosting

The project deploys one thing: static files, the website at / and the browser app at /app/. Everything else is run by the people who use hoi: a home node, a public node on a server, a registry, a relay. This page covers each way to run them, every environment variable and port, what the installers download and check, how to upgrade and what to back up.

The static deployment never launches a node, a registry or a relay, and nothing in the site or the app names one to start from. Reading, joining and, through a home node, posting happen between devices; the app finds communities through the nodes it reaches: a node link someone shared, an invite, its own home node and the public nodes those pass on (Discovery). The node setup app runs the same installer on a server over SSH with a wizard.

Nothing configured by default

No build names a registry, a relay or a node. This is enforced, not just intended:

  • The web app's build reads the registry address with the default '' and the relay addresses with the default []; registry.ts again defaults to ''. Without them, public names stay local and unregistered.
  • The Pages workflow pins both empty (registry: "", relays: "[]") and reads no repository variable for them, so no setting can add one.
  • hoi-node starts with empty relays, indexes, nodes and joins. Its iroh endpoint is built from presets::Minimal with RelayMode::Custom holding only the relays it was given: none of iroh's operator's DNS, pkarr or relay services.
  • The compose files, .env.example files and installers name no registry; --index is the operator's choice.
  • scripts/static-boundaries.test.mjs fails if any of the above changes, if the Pages workflow mentions wrangler, docker, hoi-node or ssh, or if the marketing pages gain telemetry, browser storage or background requests.
  • scripts/e2e-deployment.mjs checks the built dist/: /registry/… and /relay/v1/meta answer 404, writes to them 404 or 405, and the app makes no request to a /registry or /relay path.

The addresses that do appear are the project's own web address in links (node links and pairing links open https://hoi.sh/app/, the node's web base; HOI_SITE_URL for the site's canonical links) and the release list the installers read (https://hoi.sh/releases/manifest.json, overridable). Neither is a service the app or a node talks to for communities.

Static hosting

pnpm build runs pnpm tokens, pnpm core:wasm, pnpm build:site, pnpm build:web and node scripts/assemble-static.mjs. The result, dist/, is files only: no server code, server rendering, registry API, relay, content proxy or public peer. Application JavaScript and WebAssembly run on the visitor's device; assets and fonts are bundled. This website covers how the site itself is built and hardened.

assemble-static.mjs

  1. Check the inputs

    apps/site/dist and apps/web/dist must exist, and each one's release.json must equal the repository's release.json, or the script stops: rebuild both before assembling.

  2. Copy

    Empty dist/; copy the site into it and the app into dist/app/; copy deploy/install/install.sh and install.ps1 to the root, so SITE/install.sh is the installer.

  3. Merge _headers

    The site's catch-all /* block is written out per site path (/, /404.html, /robots.txt, /sitemap.xml, /favicon.svg, /og.png, /release.json, /preview.json, /install.sh, /install.ps1, /.well-known/*, and /NAME/* for each top-level directory), so the site's stricter policy never matches /app/; the app's blocks are prefixed with /app. dist/app/_headers is removed.

  4. Release metadata

    Write dist/release.json from the shared manifest and dist/preview.json: {preview, protocol, indexVersion, revision, note}. No environment flag can make a preview look stable, and the metadata never tells a device to wipe itself.

A host that sends no headers still enforces the CSP and the referrer policy from the pages; frame-ancestors, nosniff and COOP need the headers.

Any static host

Upload dist/ as it is. Serve install.sh and install.ps1 as plain text without caching, and don't cache /release.json or /releases/. The static host never proxies requests; /registry and /relay do not exist on it. Hosting the app on its own origin (a separate subdomain) is better still: its keys then share nothing with the site.

serve-static.mjs

node scripts/serve-static.mjs [--port 8787] [--dir dist] serves dist/ at http://127.0.0.1:8787 the way a plain static host does, and e2e-deployment.mjs imports it as serveStatic({root, port, host}) (port 0 picks a free one; it resolves to {origin, close}).

  • GET and HEAD only; anything else is 405 with Allow: GET, HEAD.
  • dir/ serves dir/index.html; dir redirects 301 to dir/; page falls back to page.html; anything else is 404 with 404.html. A path outside the root is 404; an undecodable one 400.
  • No custom headers, only Content-Type (from a fixed table: .wasm as application/wasm, .sh as application/x-sh, .ps1 as plain text, …) and Content-Length. Whatever the pages need travels inside them.

Home node

A home node is what you run when you want to post: a Raspberry Pi, a Mac mini, an old laptop or a NAS that stays on. It serves your phone and browser and, unless started with --no-public-relay, is a public relay too: it carries open communities for anyone who asks, asks your router to forward its UDP ports, passes on the public nodes it reached and writes a link to share. Every flag is on the hoi-node page. A 64-bit system is needed (Raspberry Pi OS 64-bit on a Pi 3, 4 or 5).

What you share

Whoever connects, and whoever its node link or other public nodes lead there, learns your home's public IP address, the open communities your node carries, and which of theirs they share with it. A registry, if you give one with --index, lists the address and the keys of the open communities the node holds. The node stores other people's public posts and media and can read them. Relaying for others stops for the day at --daily-cap-gb (5 GB by default).

When the router doesn't forward

The log says which case it is. The router answered no PCP, NAT-PMP or UPnP request: turn UPnP or NAT-PMP on, or forward UDP 7843 and 7844 by hand and pass --no-port-mapping --extra "--rtc-advertise PUBLIC-IP:7844". The router refused: check which devices may open ports. The router forwards from a non-public address (100.64.x.x: carrier-grade NAT, or a second router): nobody outside can reach you this way; ask for a public IPv4 address or use a small server. IPv6 needs no forward when the computer has a public IPv6 address and the router lets inbound UDP through.

Public node on a server

A public node (hoi-node --public) has no person's key, no pairing listener and no website. It carries open communities that connected peers hand it, founders' browsers included, passes on the public nodes it reached and writes a link to /data/node-link. It needs no domain, registry or invite. Four ways to run one: install.sh public on the server, the server bundle over SSH, the node setup app, or the Compose file below.

You answer for other people's data

A public node processes other people's IP addresses and connection data; whoever runs it is usually the one responsible for that data. Write a join notice (--notice; the installers take --notice-file) so people read who runs it before it serves them. The interactive installers say this and ask you to acknowledge it. The full text is on the download page.

The server bundle

A folder with a built Linux hoi-node and the service installer, so the server needs no checkout, Docker, Rust, Node or release download. The target needs 64-bit Linux with systemd, Bash, tar, sha256sum and root or sudo; the Docker-built binary needs glibc 2.36 or newer (Debian 12, Ubuntu 24.04 and newer). Alpine and hosts without systemd are not supported.

scripts/build-server.mjs

    Without --binary, docker info must succeed before anything is written.

  2. The binary

    docker buildx build --platform linux/… -f core/crates/hoi-node/Dockerfile --target binary --output type=local,dest=… ., or the supplied file. It must be a regular file (not a link), a 64-bit little-endian ELF for the chosen machine; mode 0755.

  3. The files

    node-installer.sh (a copy of deploy/install/install.sh), install.sh (the bundle's, with @ARCH@ set), deploy.mjs, README.md, server.conf (kept from the previous build of this architecture, else role=public), all with Unix line endings.

  4. Checksums

    SHA256SUMS over hoi-node and node-installer.sh. They detect corruption, not the authenticity of an untrusted bundle; server.conf stays editable.

  5. Pack

    hoi-server-linux-ARCH/ and hoi-server-linux-ARCH.tar.gz in the output directory.

bundle/install.sh

Run on the server from the unpacked folder (or by full path from anywhere): bash install.sh [--role public|registry|home|private|config] [options]. Without a role and with a terminal it asks: 1 public node, 2 public node and registry, 3 home node and public relay, 4 private home node, 5 the saved server.conf; for a registry it asks the HTTPS URL and whether to configure Caddy; then keep or reset the data (keep by default). An explicit role ignores server.conf, so a public node never inherits a saved registry configuration. It then checks that the machine is Linux on the bundle's architecture, runs sha256sum --check SHA256SUMS, restores the executable bit, runs hoi-node --version (a failure points at glibc), and hands over to node-installer.sh ROLE --binary ./hoi-node --yes ….

server.conf is plain key=value lines, read and never executed: role=public, name=…; a registry adds registry_url=https://names.example.org and tls=caddy.

What they download and verify

  1. The release list

    Fetch manifest.json and manifest.json.minisig (or copy them from --from, or download them with gh). A list that names no release yet stops the install.

  2. Its signature

    With a release key set (RELEASE_PUBKEY in the script, or --pubkey): no signature file stops the install; minisign -Vqm must verify it if minisign is installed, otherwise the installer says the signature was not checked. Until the project's key is published the key is empty and the installer says it checked SHA-256 only. Fetched from the site, the installer and the list come from the same place.

  3. Pick the file

    A Mac: the universal .dmg. Linux: a .deb with apt, an .rpm with dnf or zypper, else the AppImage. Windows: the setup .exe. A node: hoi-node_VERSION_TARGET.tar.gz for x86_64 or aarch64, unknown-linux-gnu or apple-darwin (Windows: x86_64-pc-windows-msvc). 32-bit systems are refused.

  4. Check it

    Its SHA-256 must equal the list's, or nothing is installed. The node binary must run (--version), and a notice file must pass hoi-node admin notice check.

The check

Every node install first looks at the computer and prints one row per check: ok, info, warn (it installs, but something won't work as well) or BLOCK (installing would fail or leave a node nobody can reach; it stops before changing anything). The check changes nothing and asks for no password; its only outside lookups are DNS for a registry's name and the release list. No service is asked for this computer's public address.

HTTPS for a registry

With --tls caddy the installer installs Caddy from the system's packages (Debian 12, Ubuntu 24.04, Fedora; it waits up to 300 s for apt's lock, which a server's first-boot updates hold), writes /etc/caddy/hoi-registry.caddy (the registry's host name with reverse_proxy to --registry-listen, 127.0.0.1:7845 by default) and imports it from /etc/caddy/Caddyfile: the packaged example is set aside as Caddyfile.before-hoi, a Caddyfile of your own gets one import line and is put back if caddy validate refuses the result. Then it enables and reloads Caddy, which gets and renews the certificate once DNS leads to the server and keeps no access log. The registry needs the root of a host name of its own (https://names.example.org, not an IP address).

On Linux the installer opens UDP 7843, 7844, 7846 and 7847 (and TCP 80 and 443 with --tls caddy) in an active ufw (ufw allow PORT comment hoi-node) or firewalld (firewall-cmd --permanent --add-port, then reload) unless --no-firewall. A firewall in front of the server (your provider's, a security group) has to let the same ports in. At home, home, public and registry ask the router to forward the node's UDP ports with PCP, NAT-PMP or UPnP; --no-port-mapping skips that. Docker's published ports bypass most host firewalls, which is why the image exposes only UDP ports and keeps 7842 on loopback.

One way

Upgrades go forward. A registry refuses a database written by a newer one, and a node store that holds suppressions refuses to open in an older hoi-node rather than fetch it all again. Keep the backup you took before upgrading until the new version runs.

Checking a deployment

node scripts/e2e-deployment.mjs
node scripts/e2e-registry-browser.mjs
node scripts/e2e-discovery.mjs

e2e-deployment.mjs serves the assembled dist/ with serve-static.mjs (or the loopback URL in HOI_DEPLOYMENT_TEST_URL) and checks, within 60 s of it starting:

  • /, /protocol/, /app/, /release.json and /app/release.json answer 200 without Set-Cookie.
  • The pages checked (/, /protocol/, /relay/, /app/) each carry a CSP <meta> with default-src 'self', style-src 'self', object-src 'none', base-uri 'none' and no unsafe-inline or unsafe-eval, plus <meta name="referrer" content="no-referrer">.
  • robots.txt allows crawling; each main page has a 50–160 character description, names itself as canonical and is in sitemap.xml; a preview app is noindex.
  • /registry/, /registry/v1/meta, /registry/v2/communities?prefix= and /relay/v1/meta are 404; PUT to /registry/v2/communities or /relay/v1/objects is 404 or 405.
  • In a real browser: the demo text stays local, no cookies, no local or session storage, no IndexedDB; the website makes only same-origin GET requests and no fetch, XHR or WebSocket; the app makes no request to a registry or relay path; no page error and no CSP violation anywhere.

For a node: journalctl -u hoi-node -f (or the container log) shows the role line, the port-mapping result and the node link; install.sh check ROLE re-runs the checks at any time.
