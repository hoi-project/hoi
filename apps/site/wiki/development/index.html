A first setup

For browser builds, add the WASM target, install the matching bindings generator and build the core once. The UI can also run without any WASM against an in-memory mock core.

rustup target add wasm32-unknown-unknown
cargo install wasm-bindgen-cli --version 0.2.129 --locked
pnpm install --frozen-lockfile
pnpm core:wasm

pnpm dev:site                     # the website
pnpm dev:web                      # the browser app
pnpm --filter @hoi/web dev:mock   # the app on the mock core, no WASM build
Note

dev:mock picks the mock backend through an environment variable in a POSIX shell. docs/DEVELOPMENT.md gives the PowerShell equivalent.

The workspace

pnpm-workspace.yaml lists five places: apps/site (@hoi/site), apps/web (@hoi/web), apps/desktop (@hoi/desktop), apps/setup (@hoi/setup) and packages/* (@hoi/core-api, @hoi/tokens, @hoi/vite-plugin-hardening). It also holds the one pnpm override, which pins the Svelte plugin's deepmerge to the reviewed patch in vendor/deepmerge (see Supply chain). The Rust code lives in four separate Cargo workspaces, each with its own lockfile: core/, apps/desktop/src-tauri/, apps/setup/src-tauri/ and core/fuzz/.

The build pipeline

pnpm build runs five steps in order. Each needs the one before it: the app imports the WASM bindings, and the assembler refuses to run until both the site and the app exist and carry the same release metadata.

  1. pnpm tokens

    packages/tokens/scripts/generate.mjs reads design/tokens/tokens.json and writes packages/tokens/generated/tokens.css, HoiTokens.swift and HoiTokens.kt, plus copies into apps/mobile/ios/…/HoiTheme/ and apps/mobile/android/…/theme/ when those folders exist. The outputs are committed; --check fails on any stale file.

  2. pnpm core:wasm

    Builds the browser core and its bindings (next section).

  3. pnpm build:site

    Vite builds every website page and every wiki page in wiki/nav.json, with the CSP <meta>, Subresource Integrity and a _headers file (This website).

  4. pnpm build:web

    Vite builds the app with a relative base (./), so the same build works under /app/ and inside Tauri. It adds its own CSP, _headers, a noindex robots tag while the channel is preview, and the hash-checking service worker.

  5. node scripts/assemble-static.mjs

    Puts the two together in dist/ (below).

core:wasm: scripts/build-wasm.mjs

Three commands, then two checks on the result:

  1. Compile

    cargo build --locked -p hoi-wasm --target wasm32-unknown-unknown --profile wasm. The wasm profile inherits release (LTO, one codegen unit) with opt-level = "s" and panic = "abort", but keeps blake3 and hoi-crypto at opt-level = 3 so hashing and stamps stay fast.

  2. Bind

    wasm-bindgen --target web --out-dir apps/web/src/lib/core/wasm/pkg --out-name hoi_wasm on target/wasm32-unknown-unknown/wasm/hoi_wasm.wasm.

  3. Optimize

    wasm-opt -O3 from node_modules/.bin (the binaryen package) or the system, in place on hoi_wasm_bg.wasm, with exactly the features the build uses. The script's comment: about 40% smaller, same speed. Without wasm-opt it prints a line and goes on.

  4. Check for build paths

    The finished binary must not contain the checkout's path or the home directory (in both slash styles). If it does, the script throws: "The browser binary contains a private build path. Do not deploy it."

  5. Report

    It prints the binary's size in KB.

run('cargo', ['build', '--locked', '-p', 'hoi-wasm', '--target', 'wasm32-unknown-unknown', '--profile', 'wasm']);
run('wasm-bindgen', ['--target', 'web', '--out-dir', out, '--out-name', 'hoi_wasm', wasm]);
const features = ['--enable-bulk-memory', '--enable-nontrapping-float-to-int', '--enable-sign-ext',
  '--enable-mutable-globals', '--enable-reference-types', '--enable-multivalue'];
run(wasmOpt, ['-O3', ...features, '-o', opt, opt]);

assemble-static.mjs

  • Both apps/site/dist and apps/web/dist must exist, and the release.json inside each must equal the root release.json after validation; otherwise: "rebuild both site and app before assembling".
  • dist/ is deleted and rebuilt: the site at /, the app at /app/, and deploy/install/install.sh and install.ps1 at the root.
  • The two _headers files are merged. The site's catch-all /* block is written out once per site path (/, /404.html, /robots.txt, /sitemap.xml, /favicon.svg, /og.png, /release.json, /preview.json, /install.sh, /install.ps1, /.well-known/* and every top-level folder), so the site's stricter policy never matches /app/. The app's blocks are prefixed with /app.
  • It writes release.json and a preview.json (preview, protocol, indexVersion, revision, note).

Serving what you built

node scripts/serve-static.mjs [--port 8787] [--dir dist] serves dist/ at http://127.0.0.1:8787 the way a plain static host does: GET and HEAD only (405 otherwise), dir/ serves dir/index.html, dir redirects to dir/ with a 301, page falls back to page.html, anything else is a 404 with 404.html. It sends no custom headers on purpose: the pages must carry their policy in <meta> tags. e2e-deployment.mjs uses it.

build:all and the builds folder

pnpm build:all builds every part this computer can build into builds/hoi-<version>/, which Git ignores. The version is read from [workspace.package] in core/Cargo.toml; when some package says otherwise it warns and goes on. It is for trying a build and posting it: no checks, no signing. The signed, flat release folder is release-local.mjs's (Releases).

Each part is built into .<folder>.new and renamed into place only when it is complete, so rebuilding a part replaces only its folder. A part that fails is reported with a hint, keeps its previous folder, and the rest still build; the script then exits 1. pnpm install --frozen-lockfile runs at most once. Before a Tauri build, bundles of an earlier version are deleted from the target folder so they aren't copied too, and the build must make at least one bundle whose name carries the version.

Afterwards the script writes SHA256SUMS (sha256sum -c format, over every file of every part) and a README.md that says when, from which commit (and whether the tree had uncommitted changes) and on which system it was built, then lists every file with its size and one line on what it is.

The OS comes from the bundle kind (-setup.exe, .exe, .msi are Windows; .dmg macOS; .AppImage, .deb, .rpm Linux) and the architecture from the name (universal, arm64 for aarch64/arm64, x86 for i686/i386/x86, else x64). The node setup app looks for a hoi-node archive beside itself and in ../server/, so the portable app run from node-setup/ uploads server/hoi-node_…; in pnpm dev:setup it also looks in the checkout's builds/*/server/.

build:server

pnpm build:server [--arch x64|arm64] [--binary PATH] [--out DIR] builds the current checkout with Docker Buildx for a Linux VPS (linux/amd64 or linux/arm64), or packages an existing binary, into dist/server/hoi-server-linux-ARCH/ and its .tar.gz. Its tests (scripts/build-server.test.mjs) cover the archive round trip, refusing wrong CPUs and corrupted files, SSH arguments that can't become options or shell commands, and the installer keeping data by default.

Rust tests

Most Rust tests are unit tests next to the code. The integration test files are hoi-core/tests/crypto_backend.rs and persistence.rs, hoi-net/tests/crypto_backend.rs, and hoi-validate/tests/vectors.rs. cargo test --locked -p hoi-core -p hoi-net --test crypto_backend exercises every supported MLS suite, AEAD authentication, signing, HPKE exporters, DTLS key exchange and interoperability with rcgen/ring certificates, including tampering; run it after touching a vendored crate. The vectors test is described on Test vectors. Three long runs are marked #[ignore] and run only in the major suites:

cd core
# M0: two nodes through the embedded relay (5 s, expiry)
cargo test --locked -p hoi-node m0_acceptance -- --ignored --nocapture
# M1: a flood of 1,000 records from 50 fresh keys at five nodes, banned everywhere
cargo test --locked --release -p hoi-core m1_acceptance -- --ignored --nocapture
# 200 real nodes under siege, a fifth offline at any time
cargo test --locked --release -p hoi-sim two_hundred -- --ignored --nocapture

The test functions are m0_acceptance_two_nodes_relay_only_five_seconds_and_expiry (hoi-node/src/packet_relay.rs), m1_acceptance_a_flood_from_fifty_fresh_keys_at_five_nodes (hoi-core/src/tests/gaps.rs) and two_hundred_nodes_with_churn_hold (hoi-sim/src/scenario.rs; see Simulator).

WASI tests: scripts/test-core-wasi.mjs

The byte formats and the exact arithmetic are checked in a WASM build too, not only natively. The script compiles two sets of tests for wasm32-wasip1 with cargo test --locked --target wasm32-wasip1 --no-run --message-format=json-render-diagnostics: the unit tests of hoi-crypto and hoi-types (--lib), and hoi-validate's vectors test. It reads the test executables from Cargo's JSON output and runs each in Node's node:wasi (preview1) with RUST_TEST_THREADS=1, the core/ folder preopened at its own absolute path (the tests find core/vectors through paths compiled in), and --skip committed_vectors_are_current, because that test spawns Cargo, which WASI cannot. It exits 1 if any binary failed.

Site checks

node apps/site/scripts/e2e.mjs [--shots DIR] [--quick] [--shots-only] needs a built site. It serves apps/site/dist with vite preview on localhost:4317 and loads /, /download/, /verify/, /relay/, /communities/, /protocol/, /privacy/ and /404.html at 1280×900 and 390×844, light and dark, scripts on and off, with and without reduced motion, plus a 320×640 layout pass. --quick keeps only light with motion. It fails on any console error, failed request, HTTP status 400 or above, request to another origin, horizontal overflow, touch target under 44 px on phones, or missing <h1>; it also runs the home page's demos and the download page with an empty and a filled release list.

The sandbox

sandbox/ is a local community simulator built on the real app and protocol. Nothing in it is special-cased: the hub is a normal hoi-node, members are normal nodes driven by hoi-sim agent, and the personas open the real app. It is test tooling: it lets honest and adversarial agents, scripted or driven by a language model, try to flood, forge, Sybil, brigade and capture a community, and a referee reports what actually took effect.

What pnpm sandbox launches

On first run it creates sandbox/.state/control.env with a random 32-byte HOI_SANDBOX_TOKEN (mode 0600, Git-ignored), runs docker compose … up --detach --build --wait --wait-timeout 600, waits for the dashboard's /health, then starts the CLI worker on the host with a fresh lease. Runs, scenarios and bounds

The dashboard offers three community scenarios (neighbours: five honest residents; takeover: five honest and one malicious organiser; townhall: eight honest and one organiser, with a town of 1,000 as context only) and the focused exercises Balanced, Protocol and Social. Residents are driven by a local OpenAI-compatible model API, the Codex CLI or the Claude Code CLI through the host's worker, or a scripted demo. A run's defaults: 15 minutes, 24 turns per resident, 15 s between turns, 60 AI calls in total and two decisions at once (ranges 1–120 min, 1–200 turns, 2–120 s, 1–500 calls, 1–3 at once); the CLI worker caps Codex and Claude at two combined requests. Verdicts are Failed, Passed or Inconclusive, and the README is explicit: a run is an observation, not a proof of security.

Terminal sessions and the red and blue teams

./sandbox/hoi-sandbox (with .cmd and .ps1 shims for Windows) runs independent sessions, each an internet-less Docker network with one hub. up, watch, agents, spawn, agent, referee, bots, pentest, battle, info, shell, logs, ls, down, build and brief are its commands; the agent verbs include post, vouch, review, propose-limits and forge with the attacks bad-sig future expired unstamped oversize noncanonical dup-flood no-identity wrong-root-delegation. battle is the in-process siege of hoi-sim with a scored verdict.

sandbox/briefings/red-team.md and blue-team.md are the texts brief red|blue prints for a language-model agent. The red team's playbook: flood, walk the forge catalogue, mint a Sybil ring, brigade a real member, try to rewrite the rules. The blue team posts on topic, vouches the genuine, hides spam with a reason, vetoes wrong moderation, and reports whether five invariants held: no forged record in a feed, spam contained without a central moderator, a Sybil ring sharing one voucher's voice, no real member blocked by a mob, no rule change without the established members' consent.

pentest starts real Claude Code agents with only the Bash tool, no MCP servers, and sandbox/pentest-guard.mjs as a PreToolUse hook. The guard allows only the session's own wrapped command prefixes and refuses any shell metacharacter (; | & ` $ < > \ and newline). Member containers run with all capabilities dropped, no new privileges, read-only, 512 MB and 256 pids, on the session's internal network.

CI workflows

Checks run by themselves in the public hoi-project/hoi repository, where Actions are free: every pull request, forks included, and every push to main. No variable turns them on. Each workflow's small Changes job requires github.repository_owner == 'hoi-project' and a repository that is not private, and every other job needs it, so a private copy and a fork's own pushes start nothing. Run workflow by hand runs anywhere and checks everything, which is how CI is tested in a private repository.

The Changes job (scripts/ci-changes.mjs) reads the pull request's own changes and switches on only what they touch: Rust for core/ and vendor/, Web for apps, packages, tokens and the pnpm files, dependency audits for manifests and lockfiles, workflow linting for .github/, CodeQL for the languages touched. A skipped job counts as passed for required checks, so there are no workflow-level path filters. Rust builds once: cargo llvm-cov nextest runs the tests and SonarCloud uses its coverage. Tools come prebuilt; only pushes to main write the Rust cache.

Starting Release: version or Release by hand is itself the opt-in: the jobs check github.event_name == 'workflow_dispatch' before the switch, so a manual release works with no switch set, including every called validation suite, signing and upload. How the workflows are built

  • Every third-party action is pinned to a full commit SHA with the version in a comment (list on Supply chain).
  • Default permissions are contents: read. Only the release-writing jobs get contents: write; the manifest job adds id-token: write and attestations: write; the tag job adds actions: write to dispatch Release; Pages deployment gets pages: write and id-token: write.
  • Checkouts in called and release workflows use persist-credentials: false and the exact resolved commit.
  • Every job has a timeout. Branch checks cancel obsolete runs (cancel-in-progress: true); release and Pages runs never cancel each other.
  • No long suite runs for a push with an unchanged version, a patch or minor release, or a Pages deployment.

Contributing

CONTRIBUTING.md asks for bug reports with reproduction steps and the version tested, and for focused pull requests; substantial behavior or API changes are discussed in an issue first, and vulnerabilities go through SECURITY.md, never a public issue. The rules for a change:

  • Run pnpm check:quick and the tests for the code you changed.
  • Format Rust with cargo fmt --all from core/; use cargo clippy for touched crates.
  • Cover protocol changes with core tests and conformance vectors (Test vectors).
  • Keep the TypeScript API in packages/core-api aligned with the Rust DTOs (Core API).
  • Edit design/tokens/tokens.json and run pnpm tokens for shared styling.
  • Explain new dependencies and keep their licenses and supply-chain records (Supply chain).

Its conventions: the website and app stay static, and nodes, registries and relays are optional services; keys and validation stay in the core; never log keys, record bodies or peer addresses; bundle assets locally, support reduced motion, and keep interface copy short. The installer artwork (node scripts/installer-art.mjs) and the setup app's icons (pnpm --filter @hoi/setup icons) are committed; run them again after changing the brand.
