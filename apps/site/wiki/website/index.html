This website

hoi.sh is a static site, and the only thing the project hosts. It is plain HTML pages with a few build-time includes, small scripts that every page works without, a strict Content-Security-Policy with Subresource Integrity, and no third-party request of any kind. The web app is copied in beside it at /app/. This page explains every part of the build, the pages that do something, the tests, and the wiki you are reading.

The site is the package @hoi/site in apps/site. Its only runtime dependencies are @hoi/tokens (colors and self-hosted fonts) and animejs 4.5.0; it builds with Vite and the workspace's @hoi/vite-plugin-hardening. Each page is an HTML file with one module script:

Partials

plugins/partials.ts resolves tiny includes in transformIndexHtml (order pre), in development and in the build:

<a class="skip" href="#main">Skip to the good part</a>
<!-- @include preview-{{PREVIEW}}.html -->
<header class="site-header">
  <div class="wrap nav">
    <a href="/" class="logo" aria-label="hoi.sh, home"><!-- @include logo.html -->hoi<span class="logo-sh">.sh</span></a>
    <!-- @include nav-{{nav}}.html -->
    <a href="/download/" class="pill pill-ink pill-sm nav-dl" data-nav>Download</a>
  </div>
</header>
  • <!-- @include name.html a="b" --> inlines partials/name.html; its attributes become variables for that partial.
  • {{NAME}} is replaced by a variable, global or from the include. Variables are expanded first, so an include's name can use one (nav-{{nav}}.html). Every value is HTML-escaped.
  • An unknown variable or a missing partial fails the build; includes nested deeper than 8 are taken for a cycle.
  • A link marked data-nav whose href equals the current page's address gets aria-current="page". PAGE is that address.
  • In development a changed partial reloads every page.

CSP and SRI: the hardening plugin

packages/vite-plugin-hardening is shared by the site and the web app. It runs at build only (development keeps hot reload), as the last generateBundle hook: Vite rewrites dynamic-import preload lists in its own generateBundle, so hashing earlier would give entry chunks a stale integrity value. For every emitted HTML file it does two things:

  1. CSP

    Unless the page already has one, a <meta http-equiv="Content-Security-Policy"> right after <head>, from cspString(directives): each directive and its sources, joined by ; .

  2. SRI

    Every <script src> and every <link rel="stylesheet"> or rel="modulepreload" that points at a bundled file gets integrity="sha384-…" of that file's final bytes, and crossorigin when it has none. References are resolved against the base or the HTML file's folder; remote and data: URLs are left alone.

The site calls hardening() with no options, so it gets the default policy:

DirectiveSources
default-src, script-src, style-src, font-src, connect-src'self'
img-src'self' data:
object-src, base-uri, form-action'none'

That is stricter than the app's (see Web app): no 'wasm-unsafe-eval', no workers, no blob:, no network beyond the site itself. It is also why wiki pages may hold no style attributes, <style> elements or inline scripts.

The _headers file

A <meta> can't set every header. plugins/headers-file.ts emits _headers, the format Netlify and similar hosts read, carrying the exact policy the hardening plugin injected: it reads the <meta> back from the built index.html (and fails the build when there is none), so the two can't drift apart. headers() adds frame-ancestors 'none' and the headers a meta tag can't set:

/*
  Content-Security-Policy: default-src 'self'; script-src 'self'; … ; frame-ancestors 'none'
  X-Content-Type-Options: nosniff
  Referrer-Policy: no-referrer
  Strict-Transport-Security: max-age=31536000; includeSubDomains
  Permissions-Policy: interest-cohort=(), browsing-topics=(), geolocation=(), microphone=(), payment=()
  Cross-Origin-Opener-Policy: same-origin

/assets/*

# The release manifest is what the apps check for updates; always revalidate.

# Operator release notices can change independently of a software build.

  Cache-Control: no-store

# The installers are read by a shell or PowerShell, not rendered: plain text, always fresh.

GitHub Pages ignores _headers; the pages still carry their policy and referrer rule inside them.

Release metadata and notices

One file at the repository root, release.json, says what channel this is and what every surface should say about it. scripts/release-schema.mjs validates it for the site, the app and the registry; scripts/release-config.mjs loads it, refusing a file over 16 KiB.

schemaVersion1
Must be exactly 1.
revisionpositive integer
A newer notice has a higher revision.
channel"preview" | "stable"
Today preview.
protocolVersionstring
Today 0.3; 1 to 64 of letters, digits, . _ -, starting with a letter or digit.
indexVersioninteger
Positive, at most 2 147 483 647; today 1.
supportedProtocolsstring[]
1 to 16, no duplicates, including protocolVersion.
notice{title, message}
Title up to 100 characters, message up to 1 200, neither blank. Today "Preview — unstable" and "hoi is in development. Protocol changes may cause data loss. Do not rely on this preview to preserve data."

The site's releaseMetadata plugin serves /release.json in development (with Cache-Control: no-store, read fresh each time) and emits it in the build. The release bar is rendered into every page at build time from RELEASE_TITLE, RELEASE_MESSAGE, RELEASE_BUILD (preview · protocol 0.3 · index 1) and, for a preview, RELEASE_WARNING "Unstable preview; data may be lost.", so it shows with scripts off. The site does no background polling; the app's own banner checks for newer notices. Metadata is informational: it never changes what a build implements and never tells a device to delete data.

The download page

download/index.html works without scripts: three set-up steps (install the app on a computer that's often on, Open hoi in my browser, scan the code with your phone), the one-command installers, and a row per device whose files link to the release list and the repository's releases page. The rows are macos, windows, linux, browser, ios, android, setup, operators and node.

curl -fsSL https://hoi.sh/install.sh | bash      # macOS and Linux
irm https://hoi.sh/install.ps1 | iex             # Windows (PowerShell)

The operator's box

"Before you run a public node" explains that whoever runs one usually becomes responsible for the personal data it processes. Its checkbox, #operator-ack, is a CSS gate that needs no script: while unchecked, .operator-only rows (the node setup app, the server kit, hoi-node) are hidden by .operator-ack:not(:checked) ~ section .operator-only; once checked, the .operator-gated row that asks for it disappears instead. The desktop app and a home node for your own devices need none of it.

The release list

download.ts fetches /releases/manifest.json from the same origin (cache: 'no-cache', credentials: 'omit'). The shipped file is empty:

{
  "schema": 1,
  "latest": null,
  "signature": "manifest.json.minisig",
  "releases": []
}

A release is {version, date, notes?, files}, and each file is checked before it is shown:

platform · arch · kindstring
macos, windows, linux, …; universal (shown "Apple silicon + Intel"), x86_64 ("x86-64"), aarch64 ("ARM64"); the extension for "Download .kind".
product"setup", optional
The node setup app's files, listed in the setup row only and never in a platform's.
name · urlstring
The URL must be https: or the same origin.
sizenumber
Bytes, at least 0; shown as KB, MB or GB.
sha25664 hex digits
Shown lower-case beside a copy button.

The manifest itself must have schema: 1, a releases array and latest null or a string. With a latest release, the status shows "hoi <version>", the date, release notes when given, and links to manifest.json, its signature and the verify page; rows for macOS, Windows and Linux that lack a build say so. With none, the #tpl-empty template shows "No signed release yet." and the page moves the build-it-yourself commands up to where they are needed. A failed fetch adds "Couldn't load the release list just now." The release list is signed with minisign; see Releases & verification.

The verify page

/verify/ walks through four checks. Compare the file's SHA-256 with the list's (shasum -a 256 on macOS, sha256sum on Linux, Get-FileHash … -Algorithm SHA256 in PowerShell). Check that the list is ours: download manifest.json and manifest.json.minisig into one folder and run minisign -Vm manifest.json -P <public key>; the page's key box reads "not published yet". Or build it yourself: check out the release tag, pnpm install --frozen-lockfile, node scripts/reproduce.mjs, which builds the browser app's WebAssembly, hoi-node and this website byte for byte the same with the pinned toolchains and prints their SHA-256. More on Releases & verification.

Browser tests

scripts/e2e.mjs runs against the built dist/ through vite preview on port 4317 (PORT overrides) and fails on any console error, page error, failed request, HTTP status of 400 or more, request to another origin, or horizontal overflow.

The 320 px pass is a layout check only: light, with motion, scripts on and off. --quick keeps only light with motion. Each combination scrolls the whole page (driven from the test, since with scripts off the page's own timers never fire), checks overflow and that a visible <h1> exists, and, below desktop width, that every link, button and focusable element is at least 44 px tall; inline links inside <p>, <li> or <td> are exempt. Site and app, assembled

The root pnpm build is pnpm tokens, pnpm core:wasm, the site's build, the app's build, then node scripts/assemble-static.mjs. It copies static files only, information at / and the browser client at /app/; no services are bundled.

  1. Check the release

    Both apps/site/dist/release.json and apps/web/dist/release.json must equal the repository's, or it stops: rebuild both before assembling.

  2. Copy

    The site's dist/ becomes dist/, the app's becomes dist/app/, and deploy/install/install.sh and install.ps1 go to the root, static files like the rest.

  3. Merge the headers

    The app's _headers is removed from app/. The site's catch-all rule is written out once per site path (/, /404.html, /robots.txt, /sitemap.xml, /favicon.svg, /og.png, /release.json, /preview.json, /install.sh, /install.ps1, /.well-known/* and each top-level folder as /<name>/*), so the site's stricter policy never applies to /app/; the app's rules follow under /app/*.

  4. Write the metadata

    release.json again, and preview.json: {preview, protocol, indexVersion, revision, note}. robots.txt and the sitemap stay as the site built them.

A separate origin is better

The script's own comment says so: hosting the app on its own origin (a separate subdomain) means its keys share nothing with the site. Build each app's dist/ separately for that.

scripts/serve-static.mjs serves the assembled folder the way a plain static host does, for tests and a look: GET and HEAD only (anything else is 405), dir/ serves dir/index.html, dir redirects to dir/ with a 301, page falls back to page.html, and anything else is a 404 with 404.html. Paths outside the folder are 404. It sends no custom headers, so whatever the pages need must travel inside them. It binds 127.0.0.1, port 8787 by default (--port, --dir), and knows 15 content types, .wasm and .webmanifest among them. Hosting is covered on Deploying & hosting.

The wiki

The wiki is part of the same build. wiki/README.md is its authoring guide; wiki/nav.json is the table of contents, and adding a page there adds it to the sidebar, the pager, the search index, the build inputs and the sitemap. Its file is wiki/<slug>/index.html. loadWiki refuses a group color outside sun, coral, peach, mint, sky, lilac, cobalt, a slug outside [a-z0-9-] and a slug listed twice.

Section explanations

On a secure page, src/wiki/assistant.ts checks the browser's LanguageModel.availability(). Only an available, downloadable or downloading model adds a small question-mark button beside section headings. The check does not create a session or download a model. Opening a button shows one inline card with topic-specific questions; the rest of the page stays ordinary documentation.

The card loads virtual:wiki-passages on demand. plugins/wiki.ts builds it from complete section text, including rendered blocks and SBOM tables, with headings, canonical section links and a content hash. Retrieval keeps the current section and ranks related passages locally. A question creates a browser-managed session, measures the context budget and asks for a structured answer. The card validates source numbers and renders plain text; links always come from the documentation, never from model-supplied URLs. The answer can be mistaken, so its sources remain available.

Following a suggested section continues the explanation there. A same-page link carries context in memory; a different page uses a single-use tab-storage handoff with a 15-minute limit and the corpus version. Questions never go into URLs. A changed corpus starts a fresh explanation. Closing the card or stopping an answer aborts inference and releases the session. There is no remote inference fallback. The privacy policy describes the browser's model download and the temporary handoff.

scripts/wiki-check.mjs

Checks pages without building them: the head include with a title ending "· hoi wiki" and a description, the layout markers, one <h1> and a lead; no style attributes, <style>, inline scripts or event handlers; only the variables REPO_URL, APP_URL and SITE_URL; no email addresses; unique ids and a section id on every wk-sec; balanced tags; every table wrapped for scrolling; known demo names; every /wiki/ link and anchor resolving; no unescaped < in text.
