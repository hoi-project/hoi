Scattered delivery

A post can be kept in pieces instead of whole: sealed under a key of its own, wrapped so that fewer than k pieces reveal nothing, cut into n pieces any k of which rebuild it, and placed one per independent place on public nodes that hold pieces. Devices reach those holders through forwarders, so a holder never sees who stored or fetched. This page describes the code that implements it: the pieces library in hoi-crypto, the shapes in hoi-types, the sealed envelopes, the holders' storage and how the core uses all of it.

Source hoi-crypto/src/scatter/ hoi-crypto/src/envelope.rs hoi-types/src/scatter.rs hoi-core/src/scatter.rs hoi-store/src/pieces.rs core/vectors/scatter.json

What it does

The library has no network in it. It seals an object, cuts a generation of it into pieces, and computes locators, piece hashes, drop secrets and the sizing that keeps a party running less than the community's share of places from rebuilding or withholding an object:

content ──pad to its class──► plain ──XChaCha20-Poly1305(K_obj)──► sealed
sealed ──AONT(K_a,g)──► package ──split into k──► data pieces ──Reed–Solomon──► piece i, any i < 256

An object is sealed, wrapped by the all-or-nothing transform and split into k data pieces and further parity pieces. Some pieces are lost; any k that remain rebuild the package, the transform is undone and the object opens. With fewer than k, nothing of it can be read.

Any k of the pieces rebuild the object; fewer reveal nothing about it.

  • Who holds pieces. Public nodes with the holder role: hoi-node --hold-pieces GB (2 GB by default on a node that serves strangers; 0 turns it off) or a desktop that is a public node with Keep mailboxes for others on. A holder keeps at most one piece of any generation and can read none of them.
  • Who forwards. Public nodes pass sealed piece requests on to the holder they name, and the sealed answer back, without reading either.
  • What goes in pieces. Private groups' posts, comments, edits and attachments, and open communities' when their limits say scatter.open (below). The same holders keep private groups' mailbox slots (Mailboxes).

Media in classes

fit(len, header) picks the classes of the objects a media item goes in: one object of the smallest class that holds the rest whenever that class is at most twice the rest, else an object of the largest class it fills and the rest again. A 300 KB picture goes in a 256 KiB and a 64 KiB object (1.1 times its size), not one of 1 MiB.

Sealing an object

Each object gets a random 32-byte id (not secret) and a random 32-byte object key K_obj. seal_object pads the content to its class and seals it with XChaCha20-Poly1305:

nonce | 24 B | sun | 3 | synthetic, from the key, id, class and plaintext length | 4 B | coral | 1 | u32 BE content length content | len | lilac | 4 | the object's content zeros | to capacity | mute | 2 | padding tag | 16 B | peach | 2 | Poly1305
AAD
hoi scatter object v1 ‖ object id (32) ‖ class index (1): the sealed object is bound to its id and its class.
Nonce
The first 24 bytes of BLAKE3 keyed with derive_key("hoi scatter nonce v1", K_obj) over object id ‖ class ‖ padded plaintext. The same content under the same key and id always seals to the same bytes, so a member who kept the content can make the sealed object again; different content never shares a nonce, even under a reused key.
Opening
open_object requires the class's exact length, a valid tag, zero padding after the content, a length within the class, and the nonce the content seals with (compared in constant time). A hand-sealed object with any other nonce is refused even though its tag verifies.
Sealed hash
sealed_hash: BLAKE3 in derive mode under hoi scatter sealed v1. Generation 0's manifest fixes it; every later generation must rebuild to the same bytes.

The all-or-nothing transform

The transform is the one of AONT-RS (Resch and Plank, FAST 2011). Each generation draws a fresh one-time key K:

C | sealed + 16 B | lilac | 8 | ChaCha20(K, nonce 0) over sealed ‖ 16 zero bytes (the canary) masked key | 32 B | coral | 4 | K ⊕ BLAKE3 derive_key("hoi scatter aont v1", C)
  • Without every byte of C nobody learns K, and without K no byte of the sealed object follows: fewer than k pieces of a generation reveal nothing, whatever key the inner seal used.
  • Unpacking recomputes the mask from C, recovers K, runs the keystream again and checks the canary is zero; any changed byte, in the body or the masked key, fails it.
  • A key wraps exactly one package, so the zero nonce never repeats under it, and packages of two generations share no keystream: their pieces never combine.
pub fn package(sealed: &[u8], key: &[u8; 32]) -> Vec<u8> {
    let mut out = Vec::with_capacity(sealed.len() + OVERHEAD);
    out.extend_from_slice(sealed);
    out.extend_from_slice(&[0u8; CANARY]);
    keystream(key, &mut out);
    let mut mask = blake3::derive_key(CONTEXT, &out);
    for (m, k) in mask.iter_mut().zip(key) {
        *m ^= k;
    }
    out.extend_from_slice(&mask);
    mask.zeroize();
    out
}

Reed–Solomon over GF(2⁸)

The code is systematic Reed–Solomon, the one Backblaze published and many libraries share. It does arithmetic only, on ciphertext: no secrets and no unsafe.

  • Field: GF(2)[x] / (x⁸ + x⁴ + x³ + x² + 1), polynomial 0x11D, generator 2, with log and exp tables built at compile time.
  • Matrix: the Vandermonde rows [r⁰, r¹, …, r^(k−1)] (with 0⁰ = 1), multiplied on the right by the inverse of the top k × k block. Rows 0 to k−1 are the identity, so pieces 0 to k−1 are the data itself.
  • Any row, any time: row r depends only on r and k, never on how many pieces exist. That is what lets a repair make fresh indexes later that combine with the old ones.
  • Decoding takes exactly k pieces with distinct indexes below 256 and equal lengths, inverts their rows by Gauss–Jordan elimination and returns the k data pieces; with every data piece present it just copies them.

A generation's pieces

Shards::new(sealed, class, k) packages the sealed object under a fresh key, pads the package with zeros to k × piece length and cuts it into k data pieces. piece(i) gives any index. Shards::rebuild takes k pieces, checks that the zero padding after the package decoded as zeros, and sealed() undoes the transform and checks the class length.

data 0 | ⌈P/k⌉ | sky | 3 | package bytes from 0 data 1 | ⌈P/k⌉ | sky | 3 | the next slice data k−1 | ⌈P/k⌉ | sky | 3 | the last slice, zero padded piece r, k ≤ r < 256 | ⌈P/k⌉ | sun | 6 | row r of the matrix applied to the data pieces

Each listed index has a piece hash: 16 bytes of BLAKE3 in derive mode under hoi scatter piece v1 over object id ‖ generation ‖ index ‖ u32 BE length ‖ piece, so a piece can stand for no other. A reader checks every piece against it before rebuilding; three pieces of one generation and two of another rebuild nothing.

How many pieces

size.rs sizes each generation from the community's level ℓ and the number of independent places N the device chooses holders from. A party running a share ℓ of the places is assumed to hold ⌊ℓ·N/100⌋ of them. The smallest generation is chosen for which:

  1. No rebuilding

    The party gets k or more of all m indexes ever placed with probability at most 1 / (LIFE · 2g+1), LIFE = 1,000,000, so all generations of an object together stay under one in a million.

  2. No withholding

    The party gets n−k+1 or more of the n live pieces with probability at most the same bound.

  3. Readable

    At least k of n are up with probability at least 999/1000 when each holder is up 4/5 of the time.

  4. Uploadable

    n ≤ 3 × (k − 1): a browser's three links each carry at most k−1 pieces of a generation. And 3 ≤ k ≤ n − 2, n ≥ 5.

Up to 1000 places (EXACT_UP_TO) the risk is hypergeometric, exact for the places seen, and m is capped at the places; above, binomial with the level as the share, which is slightly stricter. Everything is exact integer arithmetic on a small big-integer type, never floats, so every host agrees on which generations meet a level, and the vectors fix the answers. With too few places there is no size and the object is not scattered.

Stamps on puts

Storage costs its sender in proportion to what it asks a holder to keep. A put carries a nonce such that BLAKE3 in derive mode under hoi scatter stamp v1, over holder endpoint ‖ locator ‖ u32 length ‖ u32 expiry day ‖ u64 nonce, has enough leading zero bits. The stamp is bound to all of these, so one made for one holder, piece, length or day is worth nothing for another.

Piece up to1 KiB2 KiB4 KiB16 KiB64 KiB256 KiB512 KiB1 MiB

Eight bits (STAMP_BASE_BITS) up to 1 KiB, one more for each doubling past that. A 1 MiB piece needs 18 bits, about a quarter million hashes (Stamps & work).

The manifest and the pointer

A manifest describes one generation. It holds the object key and the locator secret: whoever reads it can fetch and open the object, so it only ever travels sealed, inside MLS for private groups, or under the community's read key for open ones. It is canonical DAG-CBOR with one-letter keys (written in sorted order), decoded strictly: unknown fields are refused.

Floors every manifest keeps

  • A known level; k ≥ 3; k + 2 ≤ n ≤ 160; n ≤ m ≤ budget(n); places ≥ m; the class's piece length at k within 1 MiB.
  • As many hashes as holders, from n to m of them; no holder twice; keys for every holder or none.
  • At most 512 + 200 × 100 bytes to decode (about 85 bytes per index, keys included); a 15-of-28 manifest encodes in under 1900 bytes. Whatever decodes re-encodes to the same bytes. Debug output leaves the secrets out, and the key and locator secret are zeroized on drop.

Updates

A later manifest of the same object is checked by update_to before it counts. It must keep the object, sealed hash, key and class. Then it is one of two things:

UpdateRules
ExtendThe same generation: same level, places, k, n, m, locator secret and expiry; every earlier index, holder and key left as it was; at least one fresh index appended within the budget.
RegenerateThe next generation (g + 1, never a skip), with a locator secret of its own, living no shorter.

The reader also checks that a new generation's size meets a level and takes at most one regeneration a day. A Pointer is what members pass each other: canonical CBOR {v: 1, t: made_at, m: manifest}, at most 1024 + 200 × 64 bytes. The first pointer for an object makes it known; later ones are updates.

Sealed envelopes

Every request to a holder is sealed to the holder's X25519 key (xk) with HPKE (RFC 9180): base mode, DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, ChaCha20-Poly1305. The forwarder between them sees only the envelope. The holder answers sealed to a one-time key the request carries, so the forwarder cannot read the answer either, and an old answer opens under no new request. The implementation is hpke-rs 0.8 with its RustCrypto provider; envelope.rs only narrows the provider to this one suite.

Holder keys

A holder publishes its xk in its hellos, signed by its endpoint key over hoi/scatter-xk/1\n ‖ endpoint ‖ xk ‖ u64 BE expires_at. The key is derived from the endpoint key for each 30-day period (derive_key("hoi scatter xk seed v1", endpoint secret ‖ period)), so nothing new is stored and it changes by itself; it expires 7 days after its period ends (KEY_GRACE). Puts open with this period's key and, for 7 days, the last one; other requests open with any key of a piece's lifetime, since a reader may seal to the key a manifest listed. Over WebRTC, where a browser sees no endpoint, the holder also signs hoi/rtc-endpoint/1\n ‖ endpoint ‖ certificate hash, binding the certificate the browser pinned to the endpoint. Senders seal only to keys whose signature checks out against the authenticated endpoint.

Holders and their storage

A host turns the holder role on with set_piece_store. The node then answers sealed requests it can open:

  • put: a bad stamp is BadStamp; an expiry day before today or more than 400 days on (MAX_TTL_DAYS) is Refused; the same bytes again under a kept locator are Ok, different ones Taken; no room is Full.
  • get answers the piece if kept, unexpired and no longer than want_len; has answers whether it is kept and its length; both count as the piece being asked for today.
  • drop removes a piece only for the creator's token (its hash matches) or a signature by the community drop key whose id the piece was stored with. It retains an authorized-drop marker through the original inclusive expiry day. Valid repeats return the same result; wrong authority is Refused, an unknown locator is Unknown, and puts at a marked locator are refused.
  • Nothing about who sent a piece is kept. Requests are counted per link: 600 a minute and 16 MiB of puts (REQUESTS_PER_MINUTE, PUT_BYTES_PER_MINUTE), or 6000 and 128 MiB over a link that forwards for many devices. Over the limit there is no answer, and a peer that keeps at it is let go. A request that does not open earns its sender a penalty, unless it came through a forwarder.

hoi-store/src/pieces.rs keeps them: opaque bytes under a locator, with the expiry day, the creator's drop hash and the drop key id. Pieces are read on demand, never loaded whole at start, since a holder's budget runs to gigabytes.

SqlitePieces is a file of its own next to the node's store (DIR/pieces.db for hoi-node, pieces.db in the desktop's app data), outside its vault: the pieces are ciphertext and no author or community identifier is stored with them. What a holder of a private group's slots and pieces still sees, and can link, is in What a holder sees. A full store sheds expired pieces, then pieces nobody asked for in 30 days, oldest first. Every admitted piece reserves a bounded marker slot; unexpired markers are never evicted. Turning the setting off removes payloads and preserves live markers. MemPieces and in-memory SQLite enforce markers while running but do not advertise durable acknowledgements.

A durable holder advertises drop-journal and adds dj, an endpoint signature over its existing holder-key statement followed by a zero byte and drop-journal. Vouches preserve that proof. A requester verifies it and the ordinary holder-key signature; a forwarder's claim or a software version cannot upgrade an older holder. Storage and restoration explain the transaction and migration.

How the core stores and loads

Choosing holders and paths

  • Forwarders are this device's own links that forward (never a browser or phone it serves). Reachable holders are those the forwarders vouch for in their node lists, with a signed key that checks out.
  • Qualified holders: this device has known the holder for at least 2 days, sampled it in about 11 hours of its own running, and found it linked in at least 80% of those samples (HolderBar; the hourly counts decay over about a week); or the person's own devices vouch for it; or two introducers in different places, neither in the holder's own place, report it known and up at least that long. One node's list alone never makes a holder count. A community's rosters, where enough established voice lists a holder, count as one more place; holders that count only thanks to rosters share one introducer.
  • Places merge every node of one network (IPv4 /24, IPv6 /48) or one named operator, and each weighs the same. A generation gets one piece per place, at most ⌈n/8⌉ per wider block (/16, /32) and ⌈n/4⌉ per introducer over its whole life, never a place that held a sibling, and never a place one of its forwarders is in.
  • Paths: at least two forwarder places, and at most k−1 indexes of a generation through one forwarder place, so no forwarder place ever carries k. Holders that two forwarder places could not reach are left out of new placements for 6 hours.

Storing

scatter_store(content, level, expires_at) checks the level, a lifetime of at most 400 days and room for another operation (at most 256), seals the content, sizes generation 0 from the qualified places, checks the paths, places the n holders, makes the shards, and sends each holder its piece through a forwarder. Where it can it uses three hops: the request is wrapped for an exit forwarder that reaches the holder and sent through an entry forwarder in another place, so the link this device sends through never learns the holder.

lanes: Device | Entry | Exit | Holder Device: seal object, size generation, place holders, make shards Device: put for the holder: loc, stamp, drop hash, piece, sealed to its xk Device: wrapped for the exit: holder ‖ kind ‖ envelope, sealed to the exit's key Device => Entry: piece {op: wrap, rid, to: exit, env} Entry => Exit: the wrap, as any forwarded request Exit: opens the wrap: learns the holder, never the device Exit => Holder: piece {op: put, env} Holder: checks stamp and expiry day, stores under loc Holder --> Exit: stored, sealed to the one-time key Exit --> Entry: the sealed answer Entry --> Device: the sealed answer Device: every index stored: the manifest, with each holder's key

A holder that refuses gets its index sent to another place. A put whose answer never comes goes to the same holder through another forwarder (up to 4 tries), and then a fresh index replaces it, so no index is ever placed twice. When every index is stored or lost, scatter_take hands back the manifest.

Loading

scatter_load(manifest) checks the manifest's floors, then asks for k + 2 pieces (SPARES; one with "Use less data" and no home node), at random among indexes a forwarder outside the holder's place reaches; holders no forwarder vouches for are reached with the key the manifest lists, through any forwarder. Each piece is checked against its hash; a bad one or a failure asks another index. With k good pieces it rebuilds, checks the sealed hash and opens the object.

lanes: Device | Forwarder | Holders Device: manifest checked; k + 2 indexes chosen Device -> Forwarder: piece {op: get, rid, to: holder, env}, want_len = piece length Forwarder -> Holders: get, passed on unread Holders => Forwarder: got: piece, sealed to the one-time key Forwarder => Device: the sealed answer Device: piece hash checked; a bad piece asks another index Device: k good pieces: rebuild, undo the transform, check the sealed hash Device: open with K_obj: the content

Answers overdue after 60 s (ANSWER_TIMEOUT) count as unanswered. A load ends in Loaded, or fails with "These pieces do not make the post they were said to be." or "Too few places are online for this post right now. It is still kept; try again later." A store with too few places or paths fails with scatter-few-places or scatter-few-paths and the content stays as it is.

Keeping objects alive

keep.rs tracks every object this device sent or received a pointer for. Members' durable devices (desktops, nodes) probe each index with has through forwarders: every 6 hours for an object younger than 7 days, daily up to 30 days, then every 3 days. A holder's own "no" loses an index at once; silence loses it only after two failed probes through forwarders in different places at least 12 hours apart. Once a third of the spares are gone, the device waits a random 0 to 6 hours, stands down if someone else's update arrives, and otherwise rebuilds the generation and places fresh indexes in new places within the budget; with the budget spent it makes the next generation, at most once a day. An object whose fetches fail or stall 16 times in an hour is regenerated once with at least twice the pieces. A generation whose pieces rebuild into anything else is dropped and its sender not heard again for that object. Holders never repair: they cannot.

Where the apps use it

Private groups

A private group's outbox (Private communities) keeps posts, comments and edits in pieces whenever can_scatter holds: the level's generation 0 fits the qualified places, there are at least two forwarder places, and they have room for n pieces at k−1 each. Each such record becomes one object whose content is a JSON array with one records payload, kept until the group's 30-day retention. Attachments go in raw slices, each object as full as a class it fits:

magic | 13 B | coral | 2 | hoi slice v1\n header length | 4 B | sun | 1 | u32 BE header | n B | lilac | 4 | JSON {v: 1, community, hash, total, offset, posts} bytes | rest | sky | 4 | this slice of the item

When every object of a batch is stored, the group gets pointer payloads with the manifests, sealed inside MLS like any message; if any part fails, the batch goes whole as before. Votes, deletions, profiles and a device's own authorization records always go whole, so a renewed member is recognised before any pointer from it. The pieces are stored with the group's drop key id, so committers can drop a removed post's pieces. The app tells the two cases apart with the group's pieces (pieces or whole) and piecesLevel, the lowest level the newest generations kept here meet: "Posts go out in pieces through other public nodes: no single node holds or hands over a whole post, and the nodes that keep the pieces don't know who posted. Stopping one would take more than a tenth of the places its pieces go to."

Open communities

Limits carry scatter: {resist, open}: resist is the level (10, 15 or 20; communities raise it by the usual consent, Communities & the ledger), and open says whether an open community's posts travel in pieces. A new open community gets open: true unless its draft says otherwise. Then a post, comment or edit is kept in pieces and what the community syncs in its place is a pointer record (Record kinds): the record's id, its kind, an optional media hash, and the pointer sealed with hoi open pointer v1 under the read key derive_key("hoi read v1", community key), so holders that never joined cannot open it. Joined devices rebuild the record on their own device and never offer it whole; carriers keep and pass on the pointer records and take votes and replies to what they hold by id. The app says only what holds there: "No node that stores this community's posts knows who posted them, and no single node can stop a post."

Deletion progress

The core deletion journal saves known holders, locators and individual drop capabilities before dispatch. It resumes after restart, retries failed work with backoff, and reports local removal, record submission, queued/submitted work, acknowledgements, legacy removal, unknown/refused/unreachable targets and expiry separately. Missing authority and unknown generations stay visible as coverage gaps. A timeout or an expired target never proves erasure.

Accepted deletion suppresses repair, including work already in flight; known late placements enter cleanup instead of publishing a replacement. A holder that has not learned the drop can still serve old pieces. Even every known holder's acknowledgement proves neither complete inventory nor network-wide erasure, and recipients or malicious operators can keep copies.

Home nodes and holders

New clients place pieces through their own eligible scatter paths, falling back to whole-record delivery when those are unavailable. They do not start legacy home-delegated placements, whose format cannot recover the origin's deletion authority and placement correlation after restart. Existing legacy receivers and replies remain compatible; an unresolved legacy placement makes a local delete retryable before it changes the post.

A paired home node that says rb in its hello fetches and rebuilds objects for its own phones and browsers and hands them the content over the pairing link, so a phone needs one link instead of three forwarders; a device falls back to fetching through its own forwarders when the home node fails or does not answer within 120 s. Holders are hoi-node with --hold-pieces and desktops with the setting on (hoi-node, Desktop companion); browsers fetch and store through forwarders but hold nothing.

fuzz_target!(|data: &[u8]| {
    if let Ok(m) = Manifest::decode(data) {
        assert!(m.check().is_ok());
        assert_eq!(m.encode(), data);
        assert!(m.update_to(&m).is_err());

        assert!(p.manifest.check().is_ok());
        assert_eq!(p.encode(), data);

  • manifest.rs: any bytes as a manifest or pointer: no panic; whatever decodes keeps the floors and re-encodes to the same bytes; an update to itself is never accepted.
  • envelope_plaintext.rs: any bytes as any request's or answer's plaintext: no panic, and whatever parses writes back the same.
  • rebuild.rs: any pieces and indexes: rebuilding and undoing the transform never panic, and a sealed object that comes out has its class's length.
  • sizing.rs: any level, generation and places: sizing never panics, and every size keeps its own rules and meets its level.
