hoi-node

hoi-node is the hoi core without a window. One binary runs a home node for your phone and browser, a public node that carries open communities for strangers, a registry for public names, a packet relay, or several of these at once. This page lists every flag, every file it writes, every loop it runs, what it prints and what it refuses to print.

Source hoi-node/src/main.rs admin.rs index.rs trackers.rs packet_relay.rs routes.rs http.rs registry/ hoi-node.service Dockerfile

What it is

The crate hoi-node builds one binary of the same name. It links the Rust core (hoi-core with the sqlite feature), the network layer (hoi-net: iroh QUIC, WebRTC, the WebSocket link, the DHT, LAN beacons, port mapping), the storage layer (hoi-store) and three crates of its own concern: iroh-relay for the packet relay, hyper (server half, HTTP/1.1 only) for the registry, and reqwest on rustls with Mozilla's roots compiled in for talking to registries. The Crates page places it among the rest.

The node is a full participant: it checks every record it receives exactly as the apps do (Validation pipeline), keeps them in SQLite, syncs them (Sync & gossip) and lets them go when they expire (Expiry & removal). What differs is who it serves and what it carries. That is decided by its role flags.

Nothing built in

The binary names no node, registry or relay to start from. A node finds others through the invites it joins (--join), the node links it is given (--node), the devices that pair with it and the nodes that reach it. A registry is optional and only ever the one you name with --index. See Discovery.

Three facts shape everything below:

  • It keeps no logs of who connects. It prints its own status and nothing about peers, clients or records (Logging).
  • There is no admin endpoint on any port. The operator's tools run from a shell against the data directory (hoi-node admin).
  • One node per data directory. A lock file keeps a second node, and the admin tools that change the store, away from a running one (Storage).

Roles

The roles compose. The default is a home node that is also a public relay; flags take parts away or add a registry, a packet relay or a carrier for an index. main.rs derives the rest of the behaviour from three booleans: public, public_relay and peer_only.

Home node (the default)

A home node runs on a spare computer, a Raspberry Pi or a small VPS. On first start it creates an identity named after --name (default home node): it signs as its person's device. It listens for paired devices on --listen (default 127.0.0.1:7842), writes its pairing link to DIR/pairing-link and keeps its person's communities warm. Native nodes relay by default (a setting stored with the node, turned off with --no-relay): members' browsers and nodes that dial in may catch up from it, up to --daily-cap-gb (default 5) a day. Pairing and the link itself are described on Links & URIs.

Unless started with --no-public-relay it is a public relay too: public_relay defaults to !public. A public relay carries open communities that anyone asks it to (--carry any), asks the router to forward its UDP ports (--port-mapping), tells whoever connects about the other public nodes it reached, holds encrypted pieces for scattered delivery (2 GB by default) and writes a node link anyone may open to DIR/node-link. --public-relay is accepted and changes nothing: it is kept for service files written before it was the default.

Public node

--public sets public and peer_only. A public node has no person behind it: on a fresh data directory no identity is created, only a node label (set_node_name); a key already in the directory from an older carrier is kept. It stores and serves, never signs a community record and cannot vouch anyone in. It runs no pairing listener and writes no pairing file (one left from an earlier run is removed). Relaying is switched on unless --no-relay says otherwise, carrying defaults to any, pieces default to 2 GB. It is not anyone's public relay, so port mapping stays off unless --port-mapping is given (the installers add it). Without --notice it warns at start that people who connect are not told who runs it.

Registry role

--registry ADDR adds the public-name API on ADDR, kept in DIR/registry.db: the same requests, answers and database shape as the Node service and the Worker in registry/, so a namespace moves between them by copying the file. It composes with any role; the installers pair it with --public. The embedded registry section below covers the Rust side; the Registry page covers the API, the log of names and verification.

Packet relay

--packet-relay ADDR runs iroh's own relay server beside the node, so two nodes that cannot reach each other directly still connect through a relay their community's node operates. It forwards QUIC packets it cannot read by destination endpoint. See Packet relay.

Carrier for an index, and trackers

--index URL (repeatable) makes the node a carrier for that registry: it announces its public routes there, carries the open communities it lists and takes a newly published community straight from its founder's browser (The index loop). Separately, a public node announces itself to the trackers the communities it carries name (Trackers). No registry is needed for any role.

Holder of encrypted pieces

--hold-pieces GB keeps up to that many gigabytes of other people's encrypted pieces in DIR/pieces.db and answers sealed requests for them. A node that serves strangers (public or public relay) holds 2 GB unless told otherwise; --hold-pieces 0 turns it off. The node can read none of what it holds; Scattered delivery explains the pieces.

Startup, step by step

main() runs on a multi-threaded tokio runtime. Everything that can fail on configuration fails before a socket opens; a failure prints hoi-node: … to standard error and exits 1.

  1. Admin or node

    If the first argument is admin, run the operator's tools and exit with their code. Otherwise parse the flags.

  2. Carry mode

    any for a public node or relay; otherwise off without --index and index with it, unless --carry says.

  3. Data directory and lock

    Create DIR, take DIR/hoi-node.lock. A second node on the same directory exits: a hoi-node is running on DIR; stop it first.

  4. Store and core

    Open DIR/hoi.db and Node::open(db, "node", "https://hoi.sh/app/", system clock).

  5. Identity or label

    No identity yet: a peer-only node gets a label, any other creates an identity named --name. An existing identity with another name is renamed.

  6. Settings

    --new-pairing rotates the token. --no-relay/--relaying (on for public nodes and relays unless --no-relay) and --daily-cap-gb are written into the settings.

  7. Policies

    The carry policy and limit, the carry byte budget, the piece store (DIR/pieces.db), the refused keys, then the notice (--notice; without one, a public node or registry warns).

  8. Invites and links

    Each --join is joined and each --node opened; either failing exits.

  9. Registry database

    With --registry: load the release manifest, validate origins, routes, app URL, limits, registry URL and announcers, open DIR/registry.db and its log key. All before any socket.

  10. VPN gate

    With --vpn-only IFACE: wait (checking every 5 s) until the system routes internet traffic through it; bind the native transport and the HTTPS client to its IPv4 address. No IPv4 address exits.

  11. Packet relay

    Started first, so this node's own routes name it: its URL is inserted at the front of the relay list.

  12. Peer transport

    start_p2p: the iroh endpoint on --peer-bind with the relays.

  13. Pairing listener

    Unless peer-only: the WebSocket server on --listen, then --public-url as the advertised address.

  14. WebRTC

    start_rtc on --rtc-port unless it is 0. A failure is printed and the node goes on without it.

  15. Sweeper and status

    A task ticks every 5 s: scattered-delivery upkeep each tick, the expiry sweep every 36th tick (3 minutes). Then the status lines, the pairing file, the index and tracker loops, the DHT, the node-link, notice and address watchers, LAN beacons, link previews for paired browsers, checks of names that are domains, and the port mapper.

  16. Registry listener and mirrors

    Bind --registry ADDR (failure exits) and start one mirror loop per --registry-mirror.

  17. Run

    Wait for Ctrl-C or SIGTERM, passing router-forwarded public addresses to WebRTC and the native transport as they change.

Stopping

shutdown_signal() waits for Ctrl-C (SIGINT) or, on Unix, SIGTERM, the signal systemd, launchd and Docker stop a service with. Then, in order: the port mapper removes its forwards; the node-link, address, VPN, index, tracker, mirror, pairing and notice tasks are aborted; the registry and WebSocket listeners stop; every client- link is closed; WebRTC and the peer transport shut down; the node commits its state; it prints bye.

/// Ctrl-C, or the SIGTERM a service manager (systemd, launchd, Docker) stops a service with: the
/// node commits its state and removes its port forwards either way.
async fn shutdown_signal() {
    #[cfg(unix)]
    {
        let Ok(mut term) = tokio::signal::unix::signal(tokio::signal::unix::SignalKind::terminate()) else {
            let _ = tokio::signal::ctrl_c().await;
            return;
        };
        tokio::select! {
            _ = tokio::signal::ctrl_c() => {}
            _ = term.recv() => {}
        }
    }
}

The paired-device listener

Unless the node is peer-only, hoi_net::serve listens on --listen for WebSocket connections from the person's own devices: a browser on the same machine, the desktop app, or anything behind a TLS proxy named with --public-url. Phones and other browsers on the network usually pair over WebRTC on UDP 7844 instead, with no certificate or domain (Transports).

The credential check is the core's. A device that dialed in shows, in its first hello, either its own credential or the pairing link's token. A missing or wrong one ends the link without a word, so a web page cannot even learn that a home node listens there. The token pairs one device: that device gets a credential of its own (32 random bytes, stored only as a digest under the context hoi 2026 pairing credential v1) and the node issues the next token at once. refresh_pairing_file notices within 2 s and rewrites DIR/pairing-link, printing that a device paired, never the link.

A connection from loopback counts as local, unless the advertised address is wss://: behind a TLS proxy, loopback is the proxy, not you.

Containers

A loopback address inside a container cannot be published with -p. To pair from the host, listen on the container's interfaces (--listen 0.0.0.0:7842) and publish the port on the host's loopback only (-p 127.0.0.1:7842:7842). Never publish 7842 on every interface (-p 7842:7842 or -P): Docker's published ports bypass most host firewalls.

HTTP: the client and the server

hoi-node speaks HTTP in two places. http.rs is its one outbound HTTPS client, used to announce to and mirror an index and to mirror another registry. The registry's HTTP server lives in registry/mod.rs (below). Nothing else in the node speaks HTTP; peers use QUIC, WebRTC and the WebSocket link.

Routes and address rules

routes.rs defines the peer routes a node announces and a registry lists, and the address rules that decide which may be announced or stored. The same rules are line for line in registry/protocol.mjs, so a namespace accepts the same routes whichever implementation serves it.

ShapeForRules
rtc:<fingerprint>@<ip>:<port>browsers and phones (WebRTC)fingerprint: exactly 43 characters of canonical base64url of 32 bytes (the DTLS certificate's SHA-256)
<endpoint>@<ip>:<port>native nodes (iroh QUIC)endpoint: 64 lowercase hex characters

Every route is at most 128 characters. The address is v4:port or [v6]:port, nothing else: no host names, no zone ids, no trailing characters. The port is 1 to 65535. Unspecified and multicast addresses are always refused.

The rules are deliberately different. What a node is willing to say about itself is strict; what a registry accepts from a third party is just strict enough that nobody can make every device reading the directory probe addresses on its own network.

The index loop

Each --index URL runs one loop (index::spawn) against that registry's plain HTTPS API. The core decides what to carry and signs what is announced; the loop only talks HTTP on a schedule and prints its own status, never a peer's address. Every status line goes through Once, which prints a line only when it differs from the last, so a flapping connection does not fill the journal.

  1. Check the service

    GET /v1/meta until it answers with registry.apiVersion 2; other versions are refused (the public index speaks API version N, this node version 2).

  2. Announce

    Collect the node's rtc: and native routes, keep the announceable ones, loopback last. When the routes or the number of communities changed, or five minutes passed, ask the core to sign a NodeAnnouncement for the registry's origin and PUT /v2/nodes. With no announceable route it says no public route to announce yet (a public address or --rtc-advertise is needed).

  3. Mirror

    Unless --carry off: every five minutes, page through /v2/communities?prefix=&after=… and carry every carryable listing up to --carry-limit, 32 at a time, yielding the node between chunks so peers and listeners are not kept waiting.

  4. Take what browsers offer

    For communities a connected browser offers that the node does not hold, look up /v2/communities?community=KEY; if listed and carryable, carry it and pull the signed definition and records from that browser. A founder's first post lands here without pairing or an invite.

A listing is carryable only if indexed and compatible are true, its protocolVersion and indexVersion equal this build's (hoi_core::release_versions(), from the compiled release.json), and its community key is 64 lowercase hex. Nothing from the registry is trusted beyond the key and name: the signed genesis must still match the name and be open, or the core refuses the community.

Trackers

An open community may name up to two trackers in its limits: registries where public nodes that carry it say so, so a device whose invite routes have all gone stale can still find a carrier. trackers::spawn runs while relaying is on. Every 60 s it asks the core for the trackers named by the open communities this node carries (tracker_targets, empty unless the node is a public node: relaying and carrying for others), at most 16 (MAX_TRACKERS), skipping registries already given with --index. For each new tracker it starts the same loop as --index with mirroring off (announcing only); a tracker no carried community names any more is stopped. Which trackers is the communities' choice, never the node's.

Packet relay

packet_relay.rs wraps iroh-relay 1.4.1 (the version iroh uses, server and tls-ring features). The relay forwards encrypted QUIC packets by destination endpoint and keeps nothing but an in-memory table of who is connected now. It sees endpoint keys, addresses, timing and sizes, never contents. Transports covers where relays sit in a connection.

Who may use it

The Gate implements iroh-relay's AccessControl. On each connection it denies an endpoint on the block list (this relay's operator refuses this endpoint); with --packet-relay-members it also denies an endpoint the core does not know as a member of a community it carries (relay_member; this relay serves the members of the communities its node carries). Everyone else is allowed. iroh's clients send no token of their own, so the member gate stands in for a bearer token.

The block list is one 64-hex endpoint key at the start of each line; # lines and blank lines are skipped, anything after the key on a line is ignored, keys are read case-insensitively. hoi-node admin relay block|unblock|list edits it.

Which origin an announcement must name

With --registry-url the registry answers to that URL's origin only. Without it, loopback_origins reads the address the connection reached from the socket, never from a header: a connection to 127.0.0.1:P accepts announcements for http://127.0.0.1:P and http://localhost:P (no port for 80), one to [::1]:P for http://[::1]:P and http://localhost:P, and any other address accepts none (403 announcements-disabled). That is why a registry behind a TLS proxy needs --registry-url.

Mirroring another registry

Each --registry-mirror URL runs mirror::spawn: a first pass after 5 s, then one every 5 minutes. A pass is an audit, then an import.

  1. Audit the log

    Fetch /v2/log/head and check its signature against the key it names. Compare with what was saved: a changed log key or a smaller size is a fault. Read new entries 256 at a time, at most 40 pages (10,240 entries) per pass; check each entry hashes to its leaf, that a community key signed it, and that no name moved to another key and no key took a second name. Withheld entries arrive as leaves alone. Once every leaf is read, recompute the root and compare it with the head.

  2. Page the listings

    /v2/communities?prefix=&after=…, 50 a page, at most 40 pages, keeping only listings whose leaf is in the audited log.

  3. Import

    Re-verify each version 2 proof here, skip names already taken here, publish the rest. A name taken here by another key stays with the local first claim. Prints registry: mirrored N new names from URL.

A lasting fault (a changed log key, a log that shrank, an entry that does not hash to its leaf or that no community key signed, a moved name, a root that does not match the head) is stored in the witnessed table and stops that mirror until hoi-node admin registry unwitness URL. A head that does not verify or a registry that keeps no log is only retried. Either way the node says why once (registry: mirror of URL: not mirrored: …; retrying). Announced nodes are never mirrored: a public node announces to each registry it is given.

The release manifest

ReleaseSource is either the release.json compiled into the binary or a file named by --registry-release, read on every request so a notice can change without a rebuild. A file over 16 KiB is refused. Validation keeps exactly these fields and fails closed: schemaVersion 1; revision > 0; channel preview or stable; protocolVersion and each of 1 to 16 distinct supportedProtocols 1–64 characters of letters, digits, ., _, -, starting with a letter or digit, the protocol among the supported; indexVersion 1 to 2³¹−1; notice.title up to 100 and notice.message up to 1200 non-blank characters. A file that stops validating later makes requests that need it answer 503 unavailable.

hoi-node admin

The operator's tools work on the data directory from a shell, never over the network: there is no admin socket, port or endpoint to find or guess. Operators can stop serving; nobody can forge. There is no login or token either: the authority is the file system, so whoever can read and write the data directory (under the installers' unit, root through sudo) can run them. Nothing here prints a record's contents, only counts and the ids you gave.

The operator's notice

A public node tells people who runs it before it serves them. --notice FILE is JSON with camelCase keys, as the installers, the app's A node on a server page and the node setup app write it. Backups

Back up the whole directory with the node stopped, or with SQLite's backup tooling: copying hoi.db alone while the node runs is not a safe backup, and the WAL holds committed changes. The directory holds the person's keys on a home node. A store restored from an older backup comes back without later suppressions; suppress again before starting it. Turning a node off does not erase its database.
