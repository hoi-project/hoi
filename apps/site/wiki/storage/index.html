Storage

A hoi device keeps two kinds of thing: signed records exactly as they arrived, and a few JSON blobs of local state and keys. Records live in memory with the indexes the node needs; every change goes into an ordered journal that a backend makes durable: SQLite natively, an IndexedDB database or an OPFS log in the browser. On every person's device the backend is sealed by a local vault. At startup the node replays and re-checks everything it stored.

Source hoi-store/src/lib.rs · sqlite.rs · vault.rs · pieces.rs · hoi-crypto/src/vault.rs · hoi-core/src/state.rs · node.rs · idb.ts · opfs.ts · durable-settle.ts

The layers

The working set lives in hoi_store::Store. Durability goes through one trait, Persist, with exactly two methods: apply a batch of changes, and load everything at startup. The node collects changes as it works and hands them over in commit(), which every host runs after every call. Pieces kept for other people are the exception: a holder's budget runs to gigabytes, so they sit in a separate store that is read on demand (below).

What inserting a record does

  • Community. The first genesis for a key stays; the node refuses others.
  • Delegation. The device is the record's author. An existing delegation stays if it names a different root or expires no earlier; otherwise the new one replaces it, keeping any revocation time, including one that arrived early from the same root.
  • Revoke. A root revoking its own key burns it, and the person it speaks for. Revoking a device sets its revoked_at to the earliest time, but only when the revoker is the device's root; a revoke for an unknown device waits in revocations.
  • Identity. One with more work replaces the root's current one. One that commits to a different recovery key or person than the first burns the root: it was taken.
  • Rotate. Accepted when the signing recovery key is the one a root in the person's chain committed to; the earliest valid rotation away from a root wins, and the chain is relinked.
  • Post, comment, edit. Their words go into the search index (lowercase letters and digits, at least two characters, at most 64 each, at most 2,000 per record); a post's media hashes into media_refs.

remove undoes every one of these. root_of_at(key, at) answers what a cosignature made at at is worth: None for a device whose blessing had expired or been revoked by then, or a root already replaced.

What commit writes

Node::commit() first settles communities whose state changed, writes autobans due on a moderator's device, then appends the blobs that are dirty, in this order: profile-colors and profiles, mls, directory, scatter, state, keys. Record puts and deletes were queued as they happened. Then the whole batch goes to persist.apply in one call.

A failed save keeps the journal

If apply fails, the batch is not cleared. The next commit() sends the same changes again with any newer ones after them, so records, keys and state are retried together and newer state never lands before older records. core/crates/hoi-core/tests/persistence.rs fails two commits, renames the person, then lets storage work: the reopened node has the new name, every record, and a root key that still signs.

Hosts add a policy on top. hoi_net::Shared::with stops the network while saving fails: it drops the outbox, closes every link, sends one notice, and refuses incoming messages and new sync sessions until a commit succeeds, so remote traffic can't keep growing the unsaved journal (hoi-net/src/storage_tests.rs). The web worker's settler keeps the drained changes in a pending array until IndexedDB or OPFS accepted them, and only then sends queued messages and emits events.

export function createDurableSettler(node, persist, flushOutbox, emit) {
  let pending: Change[] = [];
  return async () => {
    pending = pending.concat(node.take_changes());
    await persist(pending);
    pending = [];
    // Events and outgoing records remain in the core until storage has succeeded.
    flushOutbox();
    for (const event of JSON.parse(node.take_events()) as unknown[]) emit(event);
  };
}

Local state and secrets

state.rs holds what a device remembers besides records: who you are, whom you trust, what you joined, settings. It is persisted as JSON and never sent anywhere. Both structs use deny_unknown_fields, so a field this build doesn't know makes the blob unreadable rather than silently dropped; and many fields are left out of the JSON while empty (skip_serializing_if), so a store that never used a feature still opens in older software, while one that did refuses to open there.

Secrets

Secrets is the keys blob, kept apart so a host can treat it separately. All values are hex unless noted: transport (the network key), root, device, pending_device, communities (community key → secret), rtc_cert (the WebRTC DTLS certificate and key, DER in base64url, because its fingerprint is in pairing links and invites), master (the recovery line's secret, until the person says it is saved) and remote (device keys this computer keeps and signs with for browsers, with labels). After loading, Secrets::wipe() zeroizes every string; the node keeps the parsed keypairs.

Replay: rebuilding state from records

Nothing derived is stored. Community states, standing, ladders and indexes are rebuilt from the records on every start by running each record through the same pipeline as a record from a peer. Node::open(persist, platform, web_base, clock):

  1. Load

    persist.load() returns every record's wire bytes and every blob.

  2. Check the format

    The format blob must parse as {version} with nothing else and a version from 1 to 3. A missing one means 1. Anything else fails with storage-incompatible: “Saved storage metadata is damaged or uses an unsupported format. No stored data was changed.”

  3. Read the blobs

    mls, state, profiles, profile-colors and keys must parse, and every secret key in keys must be a valid key (a remote device's secret must match its public key); directory and scatter start over if they don't; media and previews are collected.

  4. Record the format

    A store with no format, or an older one, gets {"version": 3} written. A missing node_id gets a random one.

  5. Sort the records

    Each wire is decoded. One this build can't decode stays on disk untouched and is counted in Boot.preservedRecords; it is neither indexed nor served. The rest are sorted by (priority(kind), created_at): communities, identities, rotations, delegations, revokes, ledger entries, vouches, then posts, comments, edits, reviews, votes, labels, reports, deletes, profiles, profile colors, pointers, rosters, shares, trust, wiki, tallies and blocklists.

  6. Ingest

    Each goes through ingest with Source::Load. A record the current rules refuse (other than a duplicate) gets a Delete queued. Identity work already in state.identity_work is not recomputed.

  7. Check the media

    A blob is kept only if its bytes hash to its name and the operator didn't suppress it; otherwise it is deleted.

  8. Migrate

    A store older than format 3 marks every private community's attachments as private blobs, because earlier stores didn't record where a blob was learned.

  9. Rebuild and tidy

    rebuild(&c) for every community, then sweep(), ensure_identity(), renew_delegation(), and a first commit(). Events from the replay are cleared.

Node::rebuild(c) is the community replay: it collects the community's ledger entries with their effective times, gathers the ladder's inputs, and calls hoi_moderation::Community::settle. Then it applies the outcome: removals whose contest window passed lose their bodies (a skeleton stays), overturned removals let records back in, and media the community hid or removed as illegal is deleted and its fingerprint remembered so altered copies are refused too. It runs at startup and whenever a community is marked dirty.

Two files with storage-sounding names

hoi-core/src/rebuild.rs is not about storage: it is a home node rebuilding objects kept in pieces for its own phones and browsers (rb in its hello, at most 16 rebuilds at a time for one device; a device waits 120 seconds for it before fetching itself). inject.rs is the injector, which sends a device's own new records through another link first. Both keep their bookkeeping in the scatter blob. See Scattered delivery.

Expiry and the sweep

Expiry is the real deletion mechanism. Store::expired(now) lists every record whose expires_at ≤ now, and Node::sweep() deletes them. Hosts run the sweep on a timer: hoi_net::spawn_sweeper ticks every 5 seconds and sweeps every 36th tick, and the web worker does the same (5-second rounds, a sweep every 36th), so about every three minutes. Each sweep also:

  • removes a community whose genesis expired, and marks the others dirty so their state is settled again;
  • lets removals take effect once their contest window passed;
  • drops skeletons past their own expiry, reading notes older than 30 days, late markers for records that are gone;
  • deletes media blobs no stored record references (orphan_blobs), each as a Blob { key: "m:…", value: None };
  • forgets deleted-id markers past their until, quiet strikes, bounces 30 days after they lifted, unfinished drafts after an hour and wanted media after an hour.

The Expiry & removal page covers what retention windows mean for people.

SQLite

Native programs keep one SQLite file per node (rusqlite, SQLite bundled). The schema is created on open:

  id BLOB PRIMARY KEY, community BLOB, expires_at INTEGER NOT NULL, wire BLOB NOT NULL);

valueBLOB, not nullIts bytes.
  • apply runs every change of a batch in one transaction: INSERT OR REPLACE for puts and blobs, DELETE for deletes, both tables emptied for Wipe. Either all of a commit lands or none of it.
  • load reads SELECT wire FROM records and every blob; the node indexes in memory.
  • snapshot returns the rows as Change::Put and Change::Blob with their ids, so the encrypted adapter can check each storage address.
  • checkpoint runs PRAGMA wal_checkpoint(TRUNCATE) and fails if another process keeps it busy (“Close other processes using this storage and retry.”). Together with secure_delete it removes old plaintext from the database and its WAL after a migration; it can't reach filesystem snapshots or earlier backups.

Records keep their canonical wire bytes, so the file stays readable by any later schema. hoi-node's registry role uses a separate registry.db with its own schema; see Registry.

The vault: encryption at rest

On a person's device the database holds only ciphertext and a little metadata. hoi_crypto::vault::LocalVault is a random 32-byte data key, wrapped once per way in; hoi_store::vault::EncryptedSqlite and idb.ts seal every record and blob with it and keep a sealed inventory of what should be there. It protects a locked database: not an unlocked process, and not a rollback to a complete older copy of the database.

The header

A passphrase vault (desktop and browser) starts with HOIV\x03 and a list of slots, each kind u8 ‖ len u16le ‖ body. There is exactly one passphrase slot and up to four passkey slots:

magic | 5 B | sun | 2 | HOIV 0x03 kind | 1 B | coral | 1 | 1: passphrase len | 2 B | mute | 1 | 102, little-endian wrapped key | 102 B | mint | 6 | a HOIK keystore blob of the 32-byte data key: Argon2id 64 MiB, 3 passes kind | 1 B | coral | 1 | 2: passkey (up to four) len | 2 B | mute | 1 | body length cred len | 2 B | mute | 1 | WebAuthn credential id length, at most 1023 credential | n B | lilac | 3 | the credential id, in the clear salt | 32 B | sky | 3 | PRF salt to ask the authenticator for wrapped key | 72 B | mint | 4 | sealed under BLAKE3-derived key of PRF ‖ salt

The credential ids and salts are readable so the page can ask the authenticator before anything is unlocked. A passphrase must be at least 15 characters and at most 1024 bytes. unlock refuses any passphrase slot whose Argon2id parameters are not the one supported cost, so a tampered header can't make the device run an attacker-chosen expensive derivation.

magic | 5 B | sun | 2 | HOIV 0x02 check | 68 B | mint | 6 | "hoi local vault key verified", sealed under the key: proves it is the right key

On phones the data key itself lives in the platform keystore under vault-key-v1: an iOS Keychain item with kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly, or on Android a blob encrypted with an AES-GCM key held by the Android Keystore. A missing or locked key fails closed.

Cells and the inventory

nonce | 24 B | coral | 3 | random, per seal ciphertext | n B | mint | 6 | XChaCha20-Poly1305 of the record's wire or the blob's bytes tag | 16 B | sun | 2 | Poly1305; the context string is the associated data

The key for a cell is BLAKE3 derive_key("hoi local vault cell v1:<address>", data key), with the address record:<id hex> or blob:<name>. A cell copied to another address doesn't open there. The inventory (vault-manifest, sealed at the address manifest) maps every address to the BLAKE3 hex of its current ciphertext: canonical CBOR {version: 1, cells: {…}} natively, the same shape as JSON in the browser. Every write seals the changed cells and a new inventory together; every open checks that the cells on disk are exactly the inventory's. So deleting a cell, injecting a valid cell from elsewhere, or putting back an older ciphertext or an older inventory all fail with “Saved data is damaged or cannot be unlocked. No data was replaced.”

Why the guard

An older build that knows nothing of vaults reads format, finds version 4294967295, which is outside 1 to 3, and refuses with storage-incompatible. It never mistakes an encrypted store for an empty one and starts writing plaintext into it. The storage compatibility tests check exactly that case.

Opening and migrating

  1. Find the header

    EncryptedSqlite::header looks for the vault blob. Encrypted markers (v: blobs, a manifest, the guard) without a header, or a header without a manifest, are damage, not a reason to start over.

  2. Unlock

    The passphrase, a passkey's PRF answer or the platform key opens the vault; a header that doesn't match fails closed.

  3. Open an encrypted store

    Decrypt every cell, check the inventory, and run a WAL checkpoint again in case an earlier migration committed just before a crash.

  4. Or migrate a plaintext one

    The host first opens the old data in memory (Journal::with_initial) to check that this build can read it, so damaged data is never rewritten because someone tried to unlock it. Then one transaction writes Wipe, every row sealed, the header, the guard and the inventory, and a TRUNCATE checkpoint flushes the old plaintext frames from the WAL.

Phones add a step in hoi-ffi's Split: older versions kept the keys blob in the platform keystore, so a migration moves it into the encrypted database atomically, writes the new vault key, reads it back to verify, and only then deletes the old entry; a crash in between retries the cleanup on the next open.

In the browser: IndexedDB and OPFS

The browser node runs in core.worker.ts, which owns storage. It picks one of two backends with openStore(name): the origin-private file system when the worker can open sync access handles and the store doesn't already live in IndexedDB, IndexedDB otherwise (a private window, an older browser, or a store made there before). The name is hoi.

One tab at a time

Before anything is opened, the worker takes a Web Lock named hoi-core with ifAvailable and holds it for its lifetime. A second tab gets blocked; taking over requests the lock with steal: true, and the tab that lost it releases its node, vault and store, then reloads. A browser without navigator.locks is refused: “This browser cannot safely open your saved data.” While locked or blocked, nothing holds the store open, so OPFS files stay free for another tab or a reset.

IndexedDB

Database hoi, version 1, two object stores with out-of-line string keys:

Object storeKeyValue
recordsrecord id, hex{wire: Uint8Array, community: string | null, expiresAt: number}; wire sealed
blobsblob name (vault, format, vault-manifest, v:…)Uint8Array

Each apply is one readwrite transaction over both stores that ends by writing the header, the guard and the new inventory, so a wipe keeps encryption on and a new identity can't fall back to plaintext.

The OPFS log

With sync access handles, a write is one append and one flush instead of an IndexedDB transaction. A store is the directory store-hoi with two files, log-a and log-b. Each file is a run of frames:

magic | 4 B | sun | 2 | HOIF (0x464f4948, little-endian) generation | 4 B | coral | 2 | u32le, the same in every frame of a file length | 4 B | mute | 2 | u32le, the body's length body | n B | mint | 8 | a batch of changes, already sealed by the vault crc | 4 B | sky | 2 | CRC-32 of the body
op | 1 B | coral | 1 | 1 put, 2 delete, 3 blob, 4 wipe id or key | 2 B + n | lilac | 4 | u16le length then UTF-8; 0xffff for null community | 2 B + n | lilac | 3 | put only; null for global records expiresAt | 8 B | sun | 2 | put only, f64le wire or value | 4 B + n | mint | 4 | u32le length then bytes; 0xffffffff for a deleted blob
  • Writing. One frame per apply: all of a commit or, after a crash, none. A first write into an empty file starts with a wipe. A short write is truncated back and fails: “Saving to this browser failed: it may be out of space.”
  • Opening. A file's log is its frames from the start up to the first one that is cut short, fails its CRC, changes generation or doesn't decode; its first frame must begin with wipe. The file with a valid log and the higher generation is the store, and a torn tail is truncated. If neither file holds a valid log and either holds more than an unfinished first write, the store is damaged and left as it is for the person to decide.
  • Compacting. Once the log passes 4 MiB and three times the live data (records count their wire plus 64 bytes), everything live is written as one frame into the other file under the next generation, then the old file is emptied. A crash in between leaves one of them whole; out of space, it keeps appending to the old one.
  • Taking over. A tab that just took the lock retries createSyncAccessHandle up to 20 times, 100 ms apart, while the old tab lets go.

Unlocking, migrating, resetting

lanes: Page | Core worker | Store | WasmNode Page -> Core worker: __vaultStatus Core worker -> Store: snapshot() Core worker --> Page: create, migrate, locked, ready or blocked Page -> Core worker: __unlock(passphrase) or __unlockPasskey(credential, prf) Core worker: WasmVault.unlock(header, …), or new WasmVault(passphrase) for a new vault Core worker: decodeSnapshot: check the header, guard and inventory, unseal every cell Core worker -> WasmNode: new WasmNode("web", base, records, blobs): replay and check Core worker => Store: no header yet: migrate(), one atomic rewrite, sealed Core worker -> WasmNode: first settle; start links and the 5-second timer Core worker --> Page: unlocked

A failed unlock never creates a new identity, changes the passphrase or rewrites ciphertext. If the passphrase opened the vault but the data inside couldn't be loaded, the error is saved-data. __addPasskey and __removePasskeys rewrite only the vault blob. __resetVault("RESET"), allowed only while locked, deletes the IndexedDB database without opening it and removes the OPFS directory; the page then clears the preferences it keeps in localStorage (hoi:theme, hoi:motion, hoi:sync-hidden, hoi:consent:network) and sessionStorage (hoi:sort). If saving fails while unlocked, the worker shows one notice (“This browser could not save changes. Sync is paused…”), keeps the changes, and runs no new call until they are saved.

Pieces kept for others

A node that holds pieces for scattered delivery (hoi-node --hold-pieces GB, or the desktop's switch while it is a public node) keeps them in a PieceStore: opaque bytes under a 32-byte locator, the last UTC day they are kept, the creator's drop hash and the community drop key's id, and nothing about who sent them. They are read on demand, never loaded at startup.

PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
CREATE TABLE IF NOT EXISTS pieces(
  loc BLOB PRIMARY KEY, expiry_day INTEGER NOT NULL, touched_day INTEGER NOT NULL,
  drop_hash BLOB NOT NULL, drop_key_id BLOB NOT NULL, bytes BLOB NOT NULL);
CREATE INDEX IF NOT EXISTS pieces_expiry ON pieces(expiry_day);
CREATE INDEX IF NOT EXISTS pieces_touched ON pieces(touched_day);
putStored, Exists, Full
A piece is never overwritten: a second put under the same locator answers Exists. When the budget is reached the store first sweeps expired pieces, then evicts pieces nobody fetched or probed for IDLE_DAYS = 30 days, oldest first, and only then answers Full.
get, hasbytes, length
Only while not expired; both count as touched today.
sweepcount
Deletes every piece whose expiry day has passed.

The file is pieces.db next to hoi.db, deliberately outside the vault: the pieces are ciphertext the node can't read and the metadata names nobody. On the desktop it exists only while the setting is on; turning it off deletes the file and its -wal, -shm and -journal sidecars. MemPieces is the in-memory version for tests and small holders.

A node started with --public or --peer-only has no person and makes no signing key (one already in its data directory is kept). The pairing-link file holds a pairing credential and is written readable only by the node's user. See hoi-node and Deploying & hosting.

Two other things a person may keep: a .hoikey file from exportIdentity (a HOIK keystore blob under its own passphrase of at least 15 characters, Argon2id 64 MiB and 3 passes, holding the root and device keys, community keys and the records needed to restore them), and the recovery line, which is never stored once the person said it is saved.
