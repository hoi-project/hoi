Discovery

No program in hoi names a node, a registry or a relay to start from. A device finds its first node in an invite, a node link or its own home node, and every public node it reaches passes on the other public nodes that node reached itself. This page explains each way programs find each other: node lists, public nodes, directory gossip, the DHT among public nodes, LAN beacons, trackers and registries. It also covers the limits that keep each one from being turned against the device that uses it.

Nothing configured

The software ships with no node list, no registry address and no default relay. The hoi-node header says it plainly: "Nothing here names a node, a registry or a relay to start from: a node finds others through the invites it joins, the node links it is given (--node) and the nodes that reach it." The published web app is built with no registry and no relay URL, so the registry and encrypted-relay code paths stay idle in it.

A device can start from any one of these:

The rule that runs through every mechanism on this page comes from net.rs: routes a registry or an announcement suggested "are only tried: they are saved, and passed on, once they delivered records." A route that delivers the community's records becomes a remembered member route (remember_member, up to 16 per community, forgotten after 30 days). Everything else stays on trial.

Why so cautious

A list of routes is an instruction to dial addresses. If a stranger's list were trusted, anyone could make every device that reads it probe a third party's address. So lists only ever add candidates to try, a stranger who dialed in can make a node dial nobody but itself, and a route that reaches a private network is passed on only between peers on such a network.

Routes and scopes

Every address in hoi is a route string. Two kinds exist, checked by valid_peer_hint in net.rs:

native route<endpoint>@<ip:port>
An iroh endpoint key as 64 hex characters, then a UDP socket address. A bare endpoint key with no address is valid too, but it reaches the node only through a relay, so lists never pass one on.
WebRTC routertc:<fp>@<ip:port>
rtc:, the base64url SHA-256 of the node's DTLS certificate (43 characters), @ and a UDP socket address. A browser needs nothing else to reach the node (see Transports).
limits≤ 128 bytes
Port not 0; address not unspecified and not multicast.

Who a route reaches is its Reach: the endpoint key, or the certificate fingerprint. Addresses change and these don't, so every list is compared by reach, never by address. How far an address reaches is its Scope:

In node lists a node tells a peer only routes at least as wide as the address that peer's connection came from (peer_scope), and a receiver takes only such routes. A browser that reached a node over the internet never hears of other nodes' 192.168.x.x routes that way. The person's own devices and home node count as Machine, so they hear every scope.

Who publishes an address at all

shares_internet_routes() is true for a headless node (platform == "node", its operator's own server) and for a public node. Any other device keeps only its machine and local-network routes in what strangers see, and says unlisted in its hello. A peer that says unlisted is "remembered nowhere": its connection address goes into no invite, catalog or node list, and nobody dials it back.

Public nodes

A public node is a native node that serves strangers right now. In code that is one line, is_public_node() = accepts_members() && accepts_carry():

  • accepts_members(): a desktop or hoi-node, the relay switch on, and today's relayed bytes under the daily cap (5 GB by default, --daily-cap-gb).
  • accepts_carry(): the carry policy is any, and on the desktop the person turned on Be a public node. hoi-node is public by its flags alone: a home node is a public relay unless started with --no-public-relay, and --public is the same with no pairing listener and no person's key.

A public node advertises what it does in its hello's feature list (fx). These are the features discovery depends on:

What a public node publishes

  • Its routes in every hello (published_routes, at most 8): up to 4 direct addresses, a bare endpoint id when it has relays, and up to 3 WebRTC routes.
  • A node link anyone can open, internet routes first, with its operator's signed notice (below). hoi-node writes it to DIR/node-link and refreshes the file whenever it changes. Only a public node has one.
  • Its operator notice in every hello to a stranger (nh, nt).
  • A catalog of the open communities it holds: each one's signed genesis, join routes, relays and a warmth hint. It also passes on the listings it heard from others (directory gossip).
  • Node lists: routes of the public nodes it reached itself, and the scattered-delivery holders it vouches for.
  • If it runs the DHT, an announcement under each open community's DHT key, and signed answers on its answer port.
  • If configured, signed node announcements to registries (--index) and to the trackers its communities name.

What it never publishes

  • What it was told. A node list is made only of nodes that answered as public nodes on links this node dialed. Routes it heard from others stay candidates and are never passed on.
  • Addresses of devices that say unlisted: browsers, phones, desktops that aren't public. They are never learned as member routes.
  • Routes narrower than the listener: no private-network or loopback route to a peer that came over the internet.
  • Private communities, anywhere: not in catalogs, hellos, find, the DHT or LAN beacons.
  • A community only its own devices listed. A listing that came only from its home node or its person's devices may be that person's own community, so it never reaches strangers.
  • Who asked. A carry request carries a genesis and no routes. The node keeps the reason it carries a community as one word (index or request), never a peer or an address.
  • Its person's name, hints or pairing secrets to strangers. Those go only to its own devices.

Node lists

A nodes message is how a device that reached one public node finds the others. A public node sends one after every hello and again whenever its list changes, and skips the send if the peer already has this exact list.

ttext
"nodes"
routes[text], ≤ 32, each ≤ 128 B
Routes of public nodes the sender reached itself, freshest first, a few per node (MAX_NODE_ROUTES).
h[vouch], ≤ 32, optional
Scattered-delivery holders the sender saw online itself: e endpoint, u share of hourly samples linked (percent, ≤ 100), d days known (≤ 30), optional k holder key and r up to 2 routes. Read leniently: a bad vouch is dropped, never the list. See Scattered delivery.

Who sends a list to whom

shares_nodes(peer) requires a hello that said nodes. After that it sends to the person's own devices and home node always, and to anyone else only while this node is a public node. An empty list still says something to a stranger: this node serves strangers.

node_list_for(peer) walks the known nodes that answered within 30 days, freshest first. It skips the peer itself (by reach), skips nodes whose dial failed in the last 600 s, and drops routes narrower than the peer's scope. It stops at 32 routes.

What a receiver does with one

  1. Rate

    At most 6 nodes messages per peer per minute are read; the rest are ignored.

  2. A peer that dialed in

    It proves nothing about anyone else. Its list is dropped. Only its own native routes on the address its authenticated connection came from (at most 2, caller_routes) become candidates, and only if it doesn't say unlisted. That is how a node that only dials out becomes known to the nodes it reaches.

  3. A peer this device dialed, or its own device or home node

    A peer we dialed that sent a list answered as a public node, so note_public_node puts it at the front of state.nodes. Its holder vouches are noted. Up to 16 routes of the list (TAKE_PER_LIST), each at least as wide as the peer's scope, become candidates.

  4. Candidates

    take_candidates drops invalid routes, routes with no address, routes already known, routes to this device or its home node, and routes to a node whose notice is pending or declined. The rest go to the front of node_candidates, at most 32, each for an hour.

The routes kept for a public node are only those bound to the connection, the same rule as remember_member. That means the address its authenticated QUIC connection came from, the native routes it gave for that same endpoint, and WebRTC routes that carry the certificate the DTLS handshake pinned or sit on the QUIC source address. trim_routes keeps at most 2 of each kind. A peer can't make a device keep someone else's address under its name.

The order nodes are tried in

directory_groups() lists nodes in this order: links the person opened (seen == 0), then nodes reached before, freshest first, then candidates, newest first. Each node's routes stay together. A node already connected, a node failed in the last 600 s, a node whose notice blocks it and this device's own routes are left out.

  • A browser or phone takes up to 8 WebRTC routes from it (discovery_candidates), never its home node's. The web worker keeps one discovery link: every 15 s it races 3 nodes at once, keeps the first that opens and closes the others.
  • A native public node takes the native routes of up to 3 nodes (directory_hints) into its dial loop, so it hears of new nodes and passes them on. A native node that isn't public dials no extra nodes.
  • A private group that still needs mailboxes takes routes of a few public nodes (directory_routes). See Mailboxes.

A dial that fails calls dial_failed(route). Every candidate for that node goes, and a known node rests for 600 s. The failure table holds at most 128 entries (4 × MAX_KNOWN).

Node links

A node link is a public node's address for anyone to open: no credential and no community. It is hoi://node?code=<code>, or the same query after #/node? in the web app's address (https://hoi.sh/app/#/node?code=…). The code packs the routes out of sight: a generic Base64 decoder shows no IP address.

magic | 4 B | sun | 2 | HON\x01 checksum | 16 B | coral | 3 | first 16 bytes of BLAKE3 of the deflated payload payload | ≤ 16 KiB in all | mint | 6 | deflated DAG-CBOR, XORed with a BLAKE3 stream keyed by "hoi node link obfuscation v1" and the checksum
KeyTypeMeaning
vuint1
w[text], ≤ 4WebRTC routes without the rtc: prefix: <fp>@<addr>

sbytes, 64The endpoint key's Ed25519 signature over the notice statement (required with n)

The mask is public, not a secret key. The checksum detects damage and does not authenticate. A query that mixes code with clear-text fields is refused, so nothing can change what the person previewed. Older links spelled the fields in the clear (w=…&p=…&nt=…&ns=…) and still open.

Opening one takes two calls. preview_node_link reads the link without dialing anything: host, scope, endpoint, and the notice if any, checked against the endpoint. open_node_link then refuses the link under the consent gate unless that notice was accepted. It trims the routes (2 per kind, none of this device's own) and puts the node at the front of state.nodes with seen = 0: tried first, passed on to nobody until it answers as a public node. Inside the app this is the A public node screen (NodeLink.svelte); a link without a notice needs one extra acknowledgement.

On a server

hoi-node --node LINK (repeatable) does the same for a headless node. Every hoi-node prints its own link at start and writes it to DIR/node-link.

Operator notices before connecting

A public node's operator tells people what the node processes and keeps and, if they choose, who runs it and where. A person's device reads that before it says anything of its own. The consent gate

Browsers, the desktop and phones turn the gate on (set_consent_gate(true)); a headless node never does. Under the gate, a stranger this device dialed hears nothing until its hello arrives. Then consent_check decides:

The stranger's helloOutcome
No nh (an older node, or a member's device)Proceed: our hello follows at once
nh without nt, bytes over 2048, a hash that doesn't match, or bytes that don't parsePenalize: the peer's score drops by 5
The same hash the person accepted for this nodeProceed
The same hash the person declinedClose, quietly
Anything elseKeep the words as a pending notice, emit a nodeNotice event, close quietly. Once the person accepts, the node is dialed again.

A device keeps at most 64 notices, decided or not; when full, the oldest one not accepted goes first. Declining answers any open link to that node with bye {reason: "declined"}, and the node is dialed on this device's own initiative no more (consent_blocks) until the person forgets the notice. A new notice from a known node replaces the old answer, since the words changed.

What the node has seen by then

The node saw the device's IP address when the connection opened, as any connection shows it. The app's own Network & Safety notice says so before the first connection is ever made, and the person must tick both boxes on it. What the device says of itself (its communities, hashed or named) waits for the person's answer.

What a hello reveals

A hello to a stranger is written so a peer learns only what it already knows. Its rules (version 2, SYNC_VERSION) from Node::hello:

  • c names in the clear only the communities whose routes led to this connection (routed_here): a carrier learns what a member came to it for.
  • Every other public community goes in ch as a salted hash, sorted so the order says nothing. The salt n is 16 fresh random bytes per connection, so the same list can't be recognised on the next one.
  • A browser with no endpoint sends a fresh random 32-byte node per connection, and no name: one carrier can't tie a person's visits together.
  • No hints, token, pt or lk to strangers; those go only between a home node and its devices.
context | — | lilac | 4 | BLAKE3 derive-key context "hoi 2026 hello community v1" salt | 16 B | sun | 2 | n, fresh per connection key | 32 B | mint | 4 | the community key 
pub fn community_hash(salt: &[u8; 16], community: &Id) -> Id {
    let mut h = blake3::Hasher::new_derive_key(COMMUNITY_HASH_CONTEXT);
    h.update(salt);
    h.update(community.as_bytes());
    Id(*h.finalize().as_bytes())
}

The receiver hashes each public community it holds under the sender's salt and looks for a match. It keeps the salted list for the connection, so a community it takes on later (a carry request, say) is found too (rematch). Both lists are capped at 1024 entries.

core/vectors/hello-salted.json pins a stranger hello (one key named, one salted under 5a5a…5a) and a home-to-device hello (both keys in the clear, with token, pt and lk). core/vectors/hello-hints.json pins the hints extension: per community c, peers p (≤ 16, ≤ 128 B each) and relays r (≤ 8, ≤ 512 B each), at most 64 communities. Hints are accepted only on a paired home-node link, and from one's own home node only once it delivered records.

Directory gossip

The directory is a device's list of open communities it heard of: what connected nodes carry now, and what it heard of before, from them and from the nodes they heard it from. A listing carries only the signed community definition and public join routes: no posts, profiles or pairing credentials. It is a discovery aid. Nothing in it joins anything or dials a route until the person chooses.

The catalog message

A catalog is a replacement snapshot, sent only when both peers said catalog: at most 64 entries and 256 KiB.

Who gets what

  • Own entries (open communities this node holds) go to its own devices, and to strangers only while it accepts members.
  • Relayed entries go to a peer that said directory and gets our own entries. A device that takes no strangers' connections (a browser, a phone, a desktop with its relay switch off) sends them only to public nodes it dialed itself (those that said carry). A browser's or phone's own communities stay salted hashes; it passes on only what strangers' public nodes listed.
  • A device that gets no catalog of ours never hears an empty one either.

Windows and rotation

To a peer that takes relayed listings, a catalog is the node's own communities first (up to 48, OWN_ROOM), then a window of relayed ones filling the rest of the 64. next_window chooses it in this order: own communities that didn't fit, then listings first heard within the hour (newest first, up to 16 places), then the rest in turn from where the last window ended (a cursor per peer). Nothing the peer listed itself, nothing private to this device's own devices, nothing older than 7 days and nothing refused goes in. The rotation always moves on, so a community carried by one public node comes to be known by every node a few hops away.

An animation of one item spreading through a mesh of devices, hop by hop. Each device checks it before passing it on and drops copies it already has.

A directory listing spreads the same way between nodes that say directory: a window at a time, every 300 s. Each node checks the genesis before keeping it, and a listing it already holds is merged (its routes first, the youngest age wins), not added twice.

Receiving a catalog

  1. Rate

    More than 60 catalogs from one peer in a minute ends the link with bye {reason: "too many community directory updates"}.

  2. Checks per entry

    The genesis must decode, be a community record with open admission, and not conflict with the genesis this node holds under that key. It must pass the stamp floor for a community record, the signature check, the content rules and the clock check. Private communities are skipped. Invalid peer and relay hints are dropped; routes stay passive until the person joins.

  3. Own entries replace the peer's snapshot

    Entries the peer stopped listing are withdrawn from the directory too, unless another connected node still lists them. A changed admission policy withdraws a listing at once. A change in the warmth hint alone is the same listing, so a peer can't make this node redraw its directory at will.

  4. Remember

    Known listings get the new routes first (8 kept) and relays (4 kept), and the youngest age anyone told. New ones are added within the connection's allowance of 128 new listings an hour, unless refused or older than 21 days.

Each Listing keeps g (the genesis, base64url), p and r (routes and relays, freshest first), first (first heard), held (when a node last listed it as its own), dialed (heard from a node this device dialed, or its own devices) and public (heard from a stranger's node). Over the limit, listings only callers brought go first, then the longest unconfirmed. The directory lives in its own storage blob, "directory", apart from the rest of the state: a cache that starts over if it can't be read.

gossip_directory is called from every sweep (every 36th 5-second round, about three minutes) and acts once 300 s have passed. It forgets listings no node confirmed for 21 days, gives each peer that says keeps its next window, and gives every other peer one at most every 1800 s. A peer that has no window yet gets one picked with the first catalog after its hello. The 1800 s rate exists because a public node serving dozens of browsers "would otherwise spend a gigabyte a day on windows alone."

What the app lists

discover_communities() returns this device's own open communities, those connected nodes list now and remembered listings, sorted by name. Equal names stay separate communities: listings are kept by key, and the app labels same-name, other-key results instead of merging them (nearby.ts, community-discovery.ts). Each DiscoveredCommunity carries id, name, color, description, a ready invite (with the genesis, the routes heard and up to 2 trackers), joined, live (a node connected now lists it) and seen. Known community state wins over any listing: a community whose admission changed away from open, or a private one, is never listed.

Carrying and warmth

Finding a community helps only if some node holds it while its members are away. A public node that says carry keeps an open community on request: anyone holding the signed genesis sends carry {g}, and the node answers carried {c, ok, reason?}. The request carries no routes, so a stranger never makes a public node dial an address of their choosing. The node learns members' routes from their own authenticated connections. Refusal reasons are full, busy, refused, not open, not accepting and invalid.

Warmth is how a device reads, from its own links, how well kept a community is (see Sync & gossip). Discovery uses it twice. A catalog entry's w hint tells a receiver how many durable copies the sender saw, which raises the receiver's network reading but never adds up across peers. And a public node spreads load: an open community it holds, with fewer than 3 durable copies as far as it can see (SPREAD_UNTIL), is offered to a public node that just said hello, to at most 2 such nodes per community per day and at most 3 communities per hello. The other node's own policy and limits still decide.

Finding carriers: find and found

When every route a device holds for a community has gone quiet, it tries three things in order (from find.rs): ask connected public nodes with find, ask the community's trackers, and, on a public node, look in the DHT.

  • Who asks: after a hello from a node that said find, and at every sweep, find_missing picks the open communities this device joined that no connected peer serves. It sends find {c} to up to 3 connected strangers that said find, at most once per community every 600 s (FIND_EVERY). The node learns that the asker looks for that community.
  • Who answers: a public node, for any community that isn't private there, at most 10 finds per peer per minute. found {c, r} lists up to 16 routes: its own published routes if it carries c, the public nodes it dialed that hold, list or were asked to keep c, and its directory listing's routes (public listings only). It sends nothing when it knows nothing.
  • DHT follow-up: a node that runs the DHT also queues a lookup (at most 32 queued) and remembers the asker for 120 s (at most 16 waiting per community). When the DHT answers, it sends a second found.
  • What the asker does: a found counts only if this device asked about c and the sender said find. Its routes, minus this device's own, go on trial (try_routes, at most 16 per community, in memory, never saved or put in invites).
lanes: Browser | Public node | DHT | Carrier Browser -> Public node: find {c} Public node --> Browser: found {c, r: [routes it knows]} Public node -> DHT: lookup BLAKE3("hoi dht node v1" ‖ c)[..20] DHT --> Public node: announced peers (IPv4 address, answer port) Public node -> Carrier: UDP query to the answer port Carrier --> Public node: signed answer {c, e, r, s, t} Public node --> Browser @mint: found {c, r: [checked routes]} Browser -> Carrier: dials a route on trial; kept once records arrive

The DHT among public nodes

Public nodes run a Mainline DHT node (the mainline crate) beside their other ports, so a community can be found by its key alone once every route anyone holds for it has gone stale. It differs from BitTorrent's use in three ways (hoi-net/src/dht.rs):

No outside bootstrap
The DHT is built with no_bootstrap(). It starts from what hoi's own links say: after a hello with a peer that also said dht, each public node sends dht {a}, at most 4 ip:port contacts (IPv4, each ≤ 64 B). These are the IPv4 hosts of its own public routes at its DHT port. Contacts from at most 64 peers are kept. Joining BitTorrent's worldwide DHT is one operator's choice (--dht-bootstrap HOST:PORT); once one node bridges, the others learn the wider network from each other.
The key never enters the DHT
Each open community a node carries (at most 64) is announced under a 20-byte hash of its key (dht_key, below), with the node's answer port as the announced port.
Answers are signed
A finder sends a small padded query to that port. The node answers with a statement its endpoint key signed for that community, which the core checks before any route in it is tried.
/// The DHT key for a community: the first 20 bytes of `BLAKE3("hoi dht v1" ‖ key)`.
pub fn dht_key(community: &Id) -> [u8; 20] {
    let mut h = blake3::Hasher::new();
    h.update(DHT_DOMAIN.as_bytes());
    h.update(community.as_bytes());
    let mut out = [0u8; 20];
    out.copy_from_slice(&h.finalize().as_bytes()[..20]);
    out
}

DHT_DOMAIN is "hoi dht node v1", the same constant that opens the signed statement. So the key is the first 20 bytes of BLAKE3("hoi dht node v1" ‖ community key); the doc comments write the prefix as "hoi dht v1", but the code hashes the constant.

The query and the answer

magic | 4 B | sun | 2 | HOI? version | 1 B | mute | 1 | 1 community | 32 B | mint | 4 | the community key nonce | 16 B | coral | 2 | random per query padding | 459 B | mute | 3 | zeros; anything else is refused
magic | 4 B | sun | 2 | HOI! version | 1 B | mute | 1 | 1 nonce | 16 B | coral | 2 | the query's payload | ≤ 1179 B | lilac | 6 | DAG-CBOR {c, e, r, s, t}

The padding keeps the answer from being much more than twice what was sent, so the answer port can't be used to amplify traffic at a spoofed address. The payload's fields are c (community key), e (endpoint key), r (routes, at most 8, only rtc: routes and native routes naming e), t (issued at, Unix seconds) and s (Ed25519 over "hoi dht node v1\n<e hex>\n<c hex>\n<t>\n<routes joined by ,>"). A finder refuses an answer whose community differs, whose t is more than 600 s ahead or older than 30 minutes (DHT_ANSWER_TTL), or whose key is weak or signature wrong. The query itself carries the community key in the clear to the answer port; only the DHT key is a hash.

Not iroh's discovery

The iroh endpoint is built from presets::Minimal with a custom, initially empty relay map, "without opting into N0's DNS, pkarr or relay infrastructure." Node addresses are not published to pkarr; the DHT carries only the community announcements above.

LAN beacons

Members of the same community on one network find each other with a small UDP multicast beacon. This is not mDNS and no service is involved. Native nodes send it (desktop and hoi-node); browsers can't. A stranger on the network sees only that some device sends hoi beacons, which its UDP traffic would show anyway.

Trackers

An open community may name up to two trackers in its limits (limits.trackers): registries where public nodes that carry it say so. Then a device whose invite routes have all gone stale can still find a carrier. Which trackers is the community's choice, never the app's or a node's. A tracker is an https:// address of at most 200 bytes, with no credentials, query, fragment or whitespace (plain http:// only on this machine, for tests). Like other limits, trackers change by consent (see Communities).

  • Invites carry them: field t, one or two. An accepted invite's trackers are kept with its routes until the community's own limits arrive. trackers_of(c) returns the community's own first, then the invite's.
  • Public nodes announce to them: tracker_targets(16) lists the trackers of the open communities a public node carries (invite-only communities' trackers never). hoi-node checks every 60 s and runs one announcing loop per tracker, the same signed announcement and loop as --index but without mirroring. It stops when no carried community names that tracker any more. A node that isn't public announces nowhere.
  • The app asks them, in any build including the published one, for communities it joined that no connected node serves: GET {tracker}/v2/nodes?community=<key>, at most 16 routes of at most 128 bytes, 10 s timeout. It keeps the routes for this device's kind (WebRTC for a browser, native otherwise) and hands them to publicJoin, so they go on trial. Each community is checked at most every 5 minutes, at most 16 per run.

Registries as optional discovery

A registry maps public names to community keys (the service itself is on Registry). Discovery uses two of its endpoints, and the published app uses neither: REGISTRY_URL comes from the registry address at build time and is empty there. Trackers are the exception above.

pub fn node_announcement_statement(registry: &str, endpoint: &Id, issued_at: u64, routes: &[String], communities: &[Id]) -> String {
    let communities: Vec<String> = communities.iter().map(|c| c.hex()).collect();
    format!("hoi public node v2\n{registry}\n{}\n{issued_at}\n{}\n{}", endpoint.hex(), routes.join(","), communities.join(","))
}

At most 8 routes (only rtc: routes and native routes naming the signing endpoint), and at most 64 open communities, the most recently joined when more are carried, then sorted. The registry origin must be https://host[:port] in lower case with nothing after the authority (http:// only for this machine). The registry refuses announcements more than ten minutes off its clock. hoi-node announces only routes with public addresses unless the registry runs on the same machine.

Lookups from the app

  • metadata(): GET /v1/meta, which must say API version 2 and schema version 3, with at most 16 publicNodes of at most 128 bytes each.
  • nodesFor(c): GET /v2/nodes?community=<key>: nodes that announced they carry it first, then the operator's configured nodes, then other live nodes, at most 16.
  • A public join link (#/public?c=<key>&name=…&p=…, PublicJoin.svelte) checks the name against the registry's verified, logged entry. It then calls publicJoin(key, routes) with up to 16 routes (the carriers first) and polls publicJoinStatus every 2 s while pending. The core still verifies every signed record. The signed genesis must arrive from a peer, its admission must be open and its name must match, or the join is rejected and its routes dropped.
  • In an app built with a registry, PublicConnectionDiscovery also asks for publicNodes (cached for 5 minutes) when no connected peer serves a joined open community, and hands the routes fitting this device to publicJoin.

Every request goes with no credentials and no referrer, no cache and no redirects, and times out after 10 s. A timeout is never taken as a claim that a name is free.
