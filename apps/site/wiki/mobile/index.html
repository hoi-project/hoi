Mobile libraries

For phones the repository ships libraries, not apps: a Swift package for iOS and an Android library module, both wrapping the same Rust core through UniFFI, with the platform's own key storage and the design tokens. An app built on them gets the whole HoiCore API as typed methods; keys, validation and storage stay in the core.

The layers

hoi-ffi, the crate

core/crates/hoi-ffi builds the library hoi_ffi as a staticlib (the iOS xcframework), a cdylib (Android, and generating bindings) and a lib (tests). It depends on hoi-core with the sqlite and ffi features, hoi-store with sqlite, hoi-net, hoi-types, hoi-crypto, tokio and uniffi 0.32. The ffi feature puts uniffi::Record and uniffi::Enum derives on the core's DTOs (hoi-core/src/dto.rs), so Me, CommunityView, PostDraft, Settings and the rest cross as typed values. A binary, uniffi-bindgen (feature cli), is built from the same crate so the generator always matches the library's UniFFI version.

Every method blocks

Storage, mining and validation run in place on the calling thread. Call from a background thread: a detached Task in Swift, Dispatchers.IO in Kotlin. Both wrappers do that for you through run.

The HoiNode API

Opening and the lifecycle

HoiNode::open(data_dir, keystore, listener) creates the directory, opens SQLite at <data_dir>/hoi.db through the key-store-backed vault, and opens the node with the platform mobile and the web base https://hoi.sh/app/ (where https invite links point). It sets the consent gate (operators' notices are read before the phone says anything), starts a tokio runtime with two worker threads named hoi and the expiry sweeper, and benchmarks this phone on a blocking thread: pow::benchmark(100_000) times the available threads (at most 16). Until that is in, stamp estimates assume 4 × 106 hashes per second. Opening replays and re-validates everything stored, so it belongs off the main thread.

MethodWhat it does

create_post, reply and edit mine their stamp inside the call: the draft is made under the node lock, the puzzle is mined without it (other calls and the link keep going), and the draft is published. A stamp event goes out before and after. wipe stops the link, wipes the node (keys in the key store too) and forgets "last synced".

/// Draft under the lock, mine without it (other calls and the link keep going), publish.
fn mined(&self, draft: impl FnOnce(&mut Node) -> Result<DraftDto, ApiError>) -> R<Published> {
    let d = self.api(draft)?;
    let puzzle = hoi_crypto::pow::Puzzle { prefix: unb64(&d.prefix)?, suffix: unb64(&d.suffix)?, bits: d.bits };
    let estimate = self.estimate_ms(d.bits);
    self.events.stamp_start(d.bits, estimate);
    let t = Instant::now();
    let nonce = hoi_core::dispatch::mine_puzzle(&puzzle);
    self.events.stamp_done(d.bits, estimate, t.elapsed().as_millis() as u64);
    self.api(|n| n.publish_draft(d.token, nonce))
}

Events

Every core event reaches the app as one JSON string, shaped like CoreEvent in packages/core-api:

JSONMeaningKotlin · Swift
{"type":"changed","communities":["<hex>",…]}Records arrived, expired or were removed there.HoiEvent.Changed · .changed(communities:)
{"type":"notice","text":"…"}Worth a toast.Notice · .notice
{"type":"net","status":{…}}The home-node link changed.Net · .net
{"type":"stamp","phase":"start","bits":N,"estimateMs":N}Work began on something you're signing.StampStarted · .stampStarted
{"type":"stamp","phase":"done",…,"tookMs":N}The stamp is done.StampDone · .stampDone

Other event types are dropped by both wrappers' decoders. events.rs sends a net event only when the status differs from the last one sent; while a link runs, a watcher checks the status every second (WATCH_EVERY) and a few times more after it stops. Contact with the home node is noted for "last synced", written to the file last-sync in the data directory at most every 30 seconds while connected (SYNC_WRITE_EVERY) and once more when the link stops or the node is dropped.

Keys: the platform key store

Phones keep one random 32-byte vault key in the platform key store, under vault-key-v1. SQLite holds only sealed record and secret-key payloads (including MLS state); the vault is LocalVault's platform kind (header HOIV\x02), which needs no password derivation because the operating system protects the key. Missing or locked keys fail closed. keys.rs wraps the database in Split, which opens the vault on first use:

  1. An encrypted database

    Read vault-key-v1 from the key store, unlock the header with it, open EncryptedSqlite, then remove any legacy keys entry. Without the key: "Unlock this device to access saved data. Its protected key is unavailable."

  2. An older plaintext database

    Older builds kept the identity keys in the key store under keys. If the stored state has an identity but neither the key store nor the database has its keys, stop: "Unlock this device to migrate saved data. Its identity keys are unavailable." If both have keys and they differ, stop: "Saved identity keys disagree. No data was replaced."

  3. Prove it first

    The candidate data is opened as a node through an in-memory Journal before anything is rewritten.

  4. Store the new key, read it back

    A fresh random key goes to vault-key-v1. The foreign key store returns no result, so the key is read back and compared before any plaintext is deleted.

  5. Encrypt, then clean up

    EncryptedSqlite::open rewrites the data sealed, importing the legacy keys atomically with the migration; then the keys entry is deleted and checked gone ("The device could not finish securing its old keys. Unlock the device and retry.").

A brand-new database reads no legacy keys at all, so a reinstall never inherits an old identity: the test a_fresh_database_never_inherits_identity_and_wipe_keeps_storage_encrypted checks that fresh storage gets an independent data key and that a wipe keeps encryption on. Another test simulates a crash after the ciphertext committed but before the old entry was erased: the next open retries the cleanup and refuses until it succeeds.

Android: KeystoreKeyStore

Values are encrypted with an AES-256-GCM key that lives in the Android Keystore (hardware-backed where the phone has it, alias sh.hoi.keys) and never leaves it. The ciphertext sits in noBackupFilesDir/hoi-keys/, one file per entry, named after the key with anything outside A-Za-z0-9._- turned to _, plus .bin. It can't be decrypted anywhere else, so it stays out of backups too. Access is serialized with a lock.

iv | 12 B | sky | 2 | GCM nonce chosen by the Keystore cipher ciphertext | n B | mint | 6 | the value; AAD is the entry's key name tag | 16 B | coral | 2 | GCM tag, 128 bits

Writes go through AtomicFile with an explicit fd.sync() before the rename commits: readback alone wouldn't make the only database key durable before a plaintext migration is committed. A value of null deletes the file; a file of 12 bytes or less, or one that fails to decrypt, reads as nothing.

iOS: KeychainKeyStore

Items are generic passwords in the data-protection keychain under the service sh.hoi.keys, one account per key, with kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly: readable after the first unlock since boot, so background refresh works, and never synced or restored to another device. set updates, or adds when the item isn't there; null deletes. The Keychain survives uninstalling the app; because the core drops keys it finds next to a brand-new database, a reinstall starts clean.

The home link on a phone

A phone is a client of a home node (the desktop companion or a hoi-node), over a WebSocket kept up by hoi_net::dial while the app is in the foreground. link.rs stops it cleanly: the socket closes at once, links named home-… are closed every 200 ms (REAP_EVERY) while the dial loop winds down, and a loop still running after 2 s (WIND_DOWN), sleeping out a backoff or stuck in a slow connect, is canceled. A new link waits for the old one to finish winding down.

lanes: OS task | Wrapper | HoiNode | Home node OS task -> Wrapper: BGAppRefreshTask or a WorkManager worker Wrapper -> HoiNode: sync_burst(20) on a background thread HoiNode -> Home node: WebSocket via hoi_net::dial Home node => HoiNode @sky: sync: what changed while the phone was away HoiNode: every 200 ms: connected? anything changed? HoiNode: reached, and quiet for 2 s HoiNode -> Home node: close (the app didn't have the link running) HoiNode --> Wrapper: true Wrapper -> HoiNode: refresh(): me, communities, net, last synced

On iOS keep max_seconds under about 25 for a BGAppRefreshTask; both wrappers default to 20.

Hoi.kt is the app's handle. Hoi.open(context, keyStore = KeystoreKeyStore(…)) opens the node in filesDir/hoi on Dispatchers.IO. It keeps me, communities, net and lastSyncedAt as StateFlows for Compose and reloads them after Changed and Net events, with one pending reload at most so bursts coalesce. Raw events pass through a MutableSharedFlow of 512 (dropping the oldest) and decoded ones through another of 64. run { it.… } calls any HoiNode method on Dispatchers.IO.

class HoiApp : Application() {
    val hoi = CoroutineScope(Dispatchers.Default).async { Hoi.open(this@HoiApp) }
    override fun onCreate() {
        super.onCreate()
        ProcessLifecycleOwner.get().lifecycle.addObserver(LifecycleEventObserver { _, e ->
            if (hoi.isCompleted) when (e) {
                Lifecycle.Event.ON_START -> hoi.getCompleted().foreground()
                Lifecycle.Event.ON_STOP -> hoi.getCompleted().background()
                else -> {}
            }
        })
    }
}

foreground() starts the home link, sweeps and refreshes; background() stops the link; syncBurst(maxSeconds = 20u) is for a WorkManager worker; pair(link) pairs and connects at once. Two extensions read failures: Throwable.hoiMessage (the core's sentence, else "Something went wrong.") and Throwable.hoiCode.

The Swift package

Package.swift (tools 5.9) targets iOS 16 and macOS 13. The binary target HoiCoreFFI is Frameworks/HoiCoreFFI.xcframework; the generated bindings in Sources/HoiCoreFFI/ and the hand-written Sources/HoiCore/ compile into one module, so import HoiCore gives both. HoiTheme is a separate target with the tokens and fonts.

Hoi is a @MainActor ObservableObject. Hoi.open(directory:keyStore:) opens the node on a detached task in Application Support/hoi, which defaultDirectory() creates and marks excluded from backup: keys never leave the phone, and records restored without them would make an identity that can't sign. It publishes me, communities, net and lastSynced, and every decoded event goes out on events, a PassthroughSubject. Events cross from the core's threads through an AsyncStream that keeps the newest 512.

@main struct HoiApp: App {
    @Environment(\.scenePhase) private var phase
    @State private var hoi: Hoi?
    var body: some Scene {
        WindowGroup {
            Group { if let hoi { RootView().environmentObject(hoi) } else { ProgressView() } }
                .task { hoi = try? await Hoi.open() }
        }
        .onChange(of: phase) { hoi?.scenePhaseChanged($0) }
    }
}

scenePhaseChanged(.active) starts the home link, sweeps and refreshes; .background stops the link. refresh() coalesces: a call while one runs sets a flag and the running one goes round once more. run { try $0.createPost(draft: d) } calls any method on a detached task.

Themes and design tokens

Colors, spacing, radii and motion come from one file, design/tokens/tokens.json. packages/tokens/scripts/generate.mjs (run with pnpm tokens) writes tokens.css, HoiTokens.swift and HoiTokens.kt into packages/tokens/generated/ and, because apps/mobile exists, a copy of each native file into ios/HoiCore/Sources/HoiTheme/HoiTokens.swift and android/hoi-core/src/main/kotlin/sh/hoi/core/theme/HoiTokens.kt. They are committed, so native developers never need Node for the palette; --check fails CI when any is stale.

On Android, HoiTheme(darkTheme, fonts) { … } maps the tokens onto a Material 3 color scheme (primary ink, secondary coral, tertiary cobalt, outline ink, error coral) and a typography at the web scale's phone minimums (display 44 sp black with −0.045 em tracking, headline 34 and 30 sp, title 19 sp extra bold, body 17 and 16 sp); hoi's own components read HoiTheme.colors, HoiTheme.mono and HoiTheme.community(name). Building the libraries

build-android.sh

  1. Check the tools

    cargo, rustup, cargo-ndk and an NDK r27 or later (ANDROID_NDK_HOME, or ANDROID_HOME with an ndk/ folder), and the Rust targets aarch64-linux-android, armv7-linux-androideabi, x86_64-linux-android; it says how to add what's missing.

  2. 16 KB pages

    Google Play wants 16 KB page alignment for native code on Android 15 and later; the script adds -C link-arg=-Wl,-z,max-page-size=16384 per Android target, so r27 gets it right too and host builds stay untouched.

  3. Build

    cargo ndk -t arm64-v8a -t armeabi-v7a -t x86_64 --platform 26 -o src/main/jniLibs build -p hoi-ffi --lib --release (--debug drops --release).

  4. Bindings

    uniffi-bindgen generate --library jniLibs/arm64-v8a/libhoi_ffi.so --language kotlin --config core/crates/hoi-ffi/bindgen.toml into src/main/java/uniffi/.

build-ios.sh

  1. macOS only

    Xcode 16 or newer, lipo, and the targets aarch64-apple-ios, aarch64-apple-ios-sim, x86_64-apple-ios (and with --macos, aarch64-apple-darwin and x86_64-apple-darwin for SwiftUI previews and swift test). Deployment targets iOS 16.0 and macOS 13.0.

  2. Build

    cargo rustc -p hoi-ffi --lib --crate-type staticlib per target (release by default, which is slow because of LTO; --debug for the dev profile), then one simulator library from the two simulator slices with lipo -create.

  3. Bindings and module

    Swift bindings from the device library with bindgen.toml; both crates' C headers go into one folder with a module map for HoiCoreFFI, kept in a folder of its own so it never collides with other xcframeworks' headers.

  4. Package

    xcodebuild -create-xcframework into Frameworks/HoiCoreFFI.xcframework; the .swift files into Sources/HoiCoreFFI/.

ffi_module_name = "HoiCoreFFI"

Tests

hoi-ffi/src/tests.rs drives the crate through its foreign interface with an in-memory key store and a listener that records events:

  • keys_go_to_the_keystore_and_records_to_sqlite: boot says mobile, the database key goes to the key store, the device label is "This phone", a post, reply and edit give six stamp events (start and done each), SQLite holds v:state and no plaintext keys, a reopen finds the same root key, and a locked key store refuses to open without changing the database.
  • a_fresh_database_never_inherits_identity_and_wipe_keeps_storage_encrypted.
  • json_calls_and_errors: call works and unknown methods or bad JSON are invalid.
  • import_report_json_keeps_its_order.
  • syncs_in_bursts_through_a_home_node.
  • In keys.rs: legacy identity and MLS migrate together; a missing legacy key creates no replacement; a failed key store write opens no node; an interrupted cleanup is retried.
