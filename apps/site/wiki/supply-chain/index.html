Supply chain & hardening

Everything hoi ships is built from pinned, audited inputs, and every page it serves locks itself down before it runs a line of script. This page lists each check on the dependencies, each patched crate and why, and the exact policies the website, the app and the desktop shells enforce.

Lockfiles and workspaces

Rust code lives in four Cargo workspaces, each with its own lockfile, so a dependency of one never leaks into another's checks. The core workspace stays free of SSH and WebKitGTK; the fuzz workspace keeps libfuzzer-sys out of the core's lockfile.

LockfilePackagesFrom crates.ioChecked by

Every Cargo build, test and install command in the scripts and workflows passes --locked, and every pnpm install passes --frozen-lockfile, so a lockfile that doesn't match its manifests fails instead of being rewritten. The root devDependencies are exact versions (playwright 1.56.1, @playwright/test 1.56.1, axe-core 4.14.0, binaryen 132.0.0), and tools installed in CI are pinned too (wasm-bindgen-cli --version 0.2.129 --locked, cargo-fuzz --locked --version 0.13.2).

cargo-vet

core/supply-chain/ holds the core workspace's cargo-vet records. The vet job runs cargo vet --locked in core/: every crate in core/Cargo.lock must be covered by an imported audit, an audit of the project's own, or an exemption at exactly its current version. So a new crate or a version bump fails until someone reviews it.

cargo-deny

Each application workspace has its own deny.toml. The deny job in security.yml, and the security job of a major release, run EmbarkStudios/cargo-deny-action with --all-features once per manifest (core/Cargo.toml, apps/desktop/src-tauri/Cargo.toml, apps/setup/src-tauri/Cargo.toml), then cargo audit --file <its Cargo.lock>. cargo-audit is the second reading: it fails on vulnerabilities, while deny.toml decides what unmaintained or yanked crates mean for each graph.

The dependency regression gate

scripts/check-dependency-security.mjs is a fast, offline guard over the three application lockfiles. It doesn't replace cargo-deny's current advisory data; it makes sure specific, known-bad states can never come back. It runs inside check:quick, so in Quick source checks and in every release, whatever its tier.

const mls = packages.some((entry) => entry.name === 'openmls');
for (const name of ['openmls_rust_crypto', 'openmls_basic_credential', 'dimpl', 'core-models']) {
  const entries = packages.filter((entry) => entry.name === name);
  const patched = entries.length === 1 && !entries[0].source;
  if (mls ? !patched : entries.some((entry) => entry.source)) errors.push(`${label}: ${name} must use the reviewed local patch; …`);
}

It prints "Dependency regression gate passed for core, desktop and the node setup app. Run cargo deny check for current advisories." Its tests check that every committed lockfile passes and that each guarded regression fails.

Vendored patches

vendor/ holds temporary, locally maintained patches of existing dependencies. They are not new crypto implementations and not an independently audited fork, and they keep their licenses and upstream attribution. The published providers still select the vulnerable RustCrypto 0.13 curve stack; these patches move them to upstream crypto releases. The core and desktop workspaces use the same [patch.crates-io] entries; the setup app has no MLS and needs none of them.

Keeping them honest

  1. Gate

    node scripts/check-dependency-security.mjs rejects vulnerable duplicates, the unmaintained macro, or a removed patch in either lockfile.

  2. Policy

    cargo deny check in both application workspaces for current advisories, licenses, sources and bans.

  3. Function

    cargo test --locked -p hoi-core -p hoi-net --test crypto_backend in core/: every supported MLS suite, AEAD authentication, signing, HPKE exporters, DTLS key exchange and interoperability with rcgen/ring certificates, invalid inputs and tampering included.

  4. Everything else

    The full Rust tests, native and desktop checks, the WASM build, the iOS device and simulator builds and the browser private-community tests. pnpm audit --audit-level low and the desktop frontend build after an npm change. The CI path filters include vendor/.

What was checked

The proof-tool source was compiled against hax 0.4.2 as a compatibility check; that is not a rerun of the upstream formal proofs. New crypto advisories or upstream releases need a fresh look even when these tests pass, and the patches go as soon as compatible upstream releases exist.

Content-Security-Policy

Static hosts such as GitHub Pages send no security headers, so every page carries its policy in a <meta http-equiv="Content-Security-Policy"> that @hoi/vite-plugin-hardening injects at build time (the dev server keeps HMR working without it). No page needs inline JavaScript, inline styles or style attributes, so no policy allows 'unsafe-inline'. The Tauri apps set their policy in tauri.conf.json, and the app's desktop and setup builds inject none.

Subresource Integrity and the service worker

The hardening plugin's generateBundle hook runs last (order: 'post', because Vite rewrites dynamic-import preload lists in its own generateBundle, and hashing earlier would leave stale values). It hashes every emitted chunk and asset with SHA-384, then adds integrity="sha384-…" and crossorigin to every <script src> and every <link rel="stylesheet"> or rel="modulepreload" that points at a bundled file. Tags that already have integrity, external URLs and data: URLs are left alone. A built page's entry looks like this:

<script type="module" crossorigin src="/assets/index-DxDvfslu.js" integrity="sha384-exbER/tRMJjeiQ1tFCLXbTBhrB29Ie4LMKUP1O40/p5rPM6kjgCk1Oa+gJBDTUnd">

The website builds with modulePreload: false (with scripts disabled, browsers cancel those fetches) and assetsInlineLimit: 0, so fonts and images are never inlined as data: URIs that the policy's font-src 'self' would refuse.

SRI can't cover what a script loads later: dynamic imports, workers and the WASM binary. The app's service worker covers those. At build time vite/sw-plugin.js records the SHA-256 of every file the build writes (except _headers, sw.js and release.json), and derives the cache name from all those hashes, so any change ships a new worker.

lanes: Page | Service worker | Same origin Page -> Service worker: register sw.js; reg.update() every hour Service worker -> Same origin: fetch every precached file, cache: 'reload' Same origin --> Service worker: the files Service worker: SHA-256 of each must equal the build's; one mismatch fails the install Service worker --> Page: installed and waiting Page: "A new version is ready · Reload" Page -> Service worker: skip-waiting, only after the click Service worker: activates, deletes older hoi-* caches; the page reloads

After that the worker serves hashed files cache-first and re-checks any file it has to fetch; index.html is network-first (its own SRI attributes pin the entry script and stylesheet); it never touches cross-origin requests; and it never answers for release.json, so an installed worker can't freeze a notice. It is registered only in production web builds: never in development, inside Tauri or in sandbox builds.

The app's file has the same six security headers with the app's policy, plus X-Robots-Tag: noindex, nofollow while the channel is preview and Cache-Control: no-store for its release.json. assemble-static.mjs merges the two so the site's stricter policy never matches anything under /app/ (Building & testing). Hosting the app on its own origin is stronger still: its keys then share nothing with the site.

No third-party requests

The website and the app load everything from their own origin: scripts, styles, fonts and images are bundled locally. Tests hold this in place:

  • apps/site/scripts/e2e.mjs fails on any request to another origin (data: and blob: aside), on every page, at every viewport, with and without scripts.
  • static-boundaries.test.mjs: the website's shared script calls no fetch, sendBeacon, localStorage, sessionStorage, indexedDB or document.cookie; the Pages build pins the registry and relay settings empty; the app's defaults name no registry or relay; a node starts with no relays, indexes, nodes or joins, and iroh starts from its minimal preset with only the relays given.
  • public-copy.test.mjs: no email address or deployment-configuration hint in any public page.
  • e2e-deployment.mjs: the assembled site, served with no headers at all, carries its policy in every page and needs no inline styles or scripts.

The website's robots.txt says it plainly: "hoi.sh is a static site with nothing to hide and nothing to track." Nothing in the site or app includes analytics or crash reporting. What the app does contact (nodes, a registry, relays) is described on Discovery and Transports.

The security policy

SECURITY.md states the project's status: hoi is preview software, compatibility may change and data may be lost, and there is no independent security audit or supported stable release yet.

  1. Report privately

    Use the repository's Security → Report a vulnerability page when private reporting is available, with the affected version, reproduction steps and impact.

  2. Never in public

    If that page is unavailable, don't put details in a public issue; ask the maintainer to enable a private reporting channel first.

  3. Nothing real

    Don't include real private keys, personal data or illegal material in a report.

It lists the current limitations openly:

  • Recipients can keep copies after posts expire (Expiry).
  • A public node can read the public records it stores. Private-relay encryption doesn't hide all connection metadata or prevent withholding (Mailboxes).
  • A compromised client distribution can expose the data and keys available to that client: check your download (Releases).
  • Recovery keys restore identity, not all local data or private-group state (Keys & identity).
  • Registry discovery depends on its operator: keep independent copies and full invites (Registry).

Issues that concern a documented limitation are still worth reporting when the impact is unexpected. Operators should read the relevant deployment guide before running a service.
