Test vectors

Twenty JSON files in core/vectors/ fix the exact bytes and outcomes every implementation must produce: records with their ids and signatures, sync messages, invites, sizing for scattered delivery, standing on the ladder, signed statements for registries. They are built deterministically, read back by tests in Rust, in WebAssembly and in JavaScript, and any difference fails the suite.

Source core/vectors/ hoi-validate/examples/vectors.rs hoi-validate/tests/vectors.rs scripts/test-core-wasi.mjs

Sixteen files are written by one generator, cargo run -p hoi-validate --example vectors. Four are committed files that a test rebuilds or checks byte for byte. "Generator check" means the test committed_vectors_are_current, which reruns the generator and fails on any difference.

The generator

core/crates/hoi-validate/examples/vectors.rs builds everything from fixed inputs: fixed seeds, fixed times, nonces searched from 0. Running it twice writes the same bytes on any machine, which is what lets a test compare files byte for byte.

const T: u64 = 1_790_000_000;
const DAY: u64 = 86_400;

fn key(n: u8) -> Keypair {
    Keypair::from_secret(&[n; 32])
}

fn make(name: &str, signer: &Keypair, mut r: Record, bits: u32) -> (Value, Wire, Id) {
    r.nonce = hoi_crypto::pow::Puzzle::new(&r, bits).search(0, 1, u64::MAX).expect("nonce");
    let canonical = r.encode();
    let (wire, id) = signer.sign_record(r);

}

The vectors' community uses Limits { pow_bits: 8, ..Limits::default() }, and every record is stamped at 8 bits. Identity work is searched from nonce 0 at the protocol floor, hoi_crypto::identity::MIN_BITS (4), so it is deterministic too. The scattered-delivery secrets, nonces and ephemeral seeds are fixed through hoi-crypto's deterministic feature; real devices draw all of them from the system.

Regenerating and checking

cargo run -p hoi-validate --example vectors              # rewrite core/vectors/*.json
cargo run -p hoi-validate --example vectors -- --check   # fail if they would change
cargo test -p hoi-validate --test vectors                # read them back
node ../scripts/test-core-wasi.mjs                       # the same, in wasm32-wasip1

--check prints stale: core/vectors/<name> for each file that would change and exits 1. It ignores only CRLF line endings, which Git may produce on Windows checkouts; every value and every encoded byte must match. The test committed_vectors_are_current runs exactly this check, failing with "core/vectors is stale: cargo run -p hoi-validate --example vectors".

The stamp bits are what each searched nonce happened to reach; every one is at least 8. Change one field and every derived value changes with it:

Editing a field of a record changes its canonical bytes, so its BLAKE3 id changes, so the signature over the old id no longer verifies.

This is why a vector's id and sig pin the encoding: one changed byte anywhere and both stop matching.

delegation-chain.json

The chain a receiver must hold to accept a device's post. Keys: root, device, delegation_id, post_id, statement (32 bytes: delegation_statement(root, device, ["*"], T + 180 days), the value the root signs), wires (the identity, delegation and post records, in that order) and a note.

{ "r": { "v": 1, "kind": "delegation", "author": "ed4928c6…", "nonce": 84,

The device signs the delegation (its consent) and the record carries root_sig, the root's blessing. The revoke in records.json at T + 180 stops records from the device created at or after that time. See Keys & identity.

tombstone.json and threshold.json

tombstone.json

Keys: comment_id, comment_wire, remove (a full record entry like those in records.json), remove_wire and note. The remove is a ledger record by mira, an owner: {seq: 1, action: "remove", target: <comment id>, reason: "rule 4, undisclosed vendor"}. After it, compliant nodes delete the comment's body, keep its id and the entry, and refuse to ingest it again (Expiry & removal).

threshold.json

Keys: proposal_id, note, entry. The entry is a rules ledger record, seq: 2, text "1. Be kind.\n2. Disclose vendors.", published by root and cosigned by root and jonas: two of the three owners, the genesis's threshold.

BLAKE3 of the canonical record with body.cosign removed, the nonce 0 and the author zeroed. Each cosigner signs these bytes, so all cosigners sign the same thing whoever publishes it and whatever stamp it gets.
cosign[{key, sig}]
Two entries; the test checks both signatures over proposal_id.

Sync and hello vectors

sync-transcript.json

Two nodes share 10 records and each holds 10 the other lacks. The ids are BLAKE3([i]) for i in 0–29: a_ids are 0–19, b_ids 10–29. messages lists five encoded messages with who sent them (and, for each want, how many ids it asks for). After both wants are answered with recs, both sides hold all 30.

lanes: a | b a -> b: hello {v: 2, node: 07…, name: "lena's browser", token, c: [community]} a -> b: have {c, ids: 20} b --> a: want {ids: the 10 b lacks} b -> a: have {c, ids: 20} a --> b: want {ids: the 10 a lacks} a .. b: each answers the other's want with recs

Every message is a CBOR map with its type in t; see Sync & gossip for the message set.

hello-hints.json

Keys: msg and note. A hello from node 01… naming community 02…, with one hints entry: {c: 02…, p: ["0303…03"], r: ["https://relay.example"]}. The note: an optional routing extension, accepted only on paired home-node links (a home node's own once it delivered records). hoi-core's test checks it round-trips and carries one hint with that peer.

carry.json

A carry request carries the signed genesis, as an invite does, and nothing else: no routes, so a stranger never makes a public node dial an address. Only nodes listing carry in hello.fx receive requests.

lanes: Browser | Public node Public node -> Browser: hello with fx including carry Browser -> Public node: carry {g: the signed genesis} Public node --> Browser: carried {c, ok: true} Public node --> Browser: or carried {c, ok: false, reason: "full"} Public node -> Browser: catalog {entries: [{g, p: [], r: [], w: 2}]}

Keys: community, carry, carried_ok, carried_full, catalog_with_warmth, note. The refusal reasons are invalid, not open, not accepting, full, busy and refused. catalog.w is the durable copies the sender saw besides its own, quantized, a hint taken as a maximum (Discovery).

warmth.json

hoi_sync::warmth::assess over first-hand observations, and assess_links over a device's own connections. Keys: note (the full definition), cases (16) and links (7). Each case has name, observation (own_durable, records, missing, media_wanted, media_present, holders[] with coverage, durable, operator, network, guarded, then last_sync, now, live, hinted) and the expected warmth.

The definition the note fixes: copies count once per independent place (holders sharing an operator key or a network, IPv4 /24, IPv6 /48 or this machine, are one place), and kept sums over places the most any holder there showed. The level reads kept: cold below one, cool below two, warm below three or while incomplete, hot from three; one level colder when less than half is here, nothing caught up for a week, or under half of the other durable copies are reached over a guarded link. Score: 0.6 × min(1, kept / 4) + 0.1 × spread + 0.1 × guarded + 0.12 × complete + 0.08 × fresh. hint is ⌊kept⌋ capped at 3, what a node attaches to its catalog entry. For links, effective = 1 / Σ share²; score 0.6 × min(1, effective / 4) + 0.25 × guarded + 0.15 × (1 − largest), kept inside its level's band (cool ≤ 49, warm 50–79, hot ≥ 80).

media.json and pdq.json

media.json

A 1×1 PNG with a location in a tEXt chunk (Location, 52.37N 4.89E), 102 bytes, and what sanitize() leaves: 69 bytes, the tEXt chunk gone and the rest copied as it is. Keys: mime (image/png), input, sanitized, hash (BLAKE3 of the clean bytes: what MediaRef.hash holds), w, h and note. check() refuses the input and accepts the result.

pdq.json

A 96×96 grayscale picture drawn from a formula, sanitized, and its eight PDQ hashes: as shown, mirrored left to right, upside down, turned half way, and those four transposed (hoi_validate::similar::Variants). Keys: note, mime, picture (the sanitized PNG), quality (100), hashes (8 × 64 hex), tolerance (4), match_distance (31, similar::MATCH_DISTANCE).

Within a tolerance

PDQ uses floating point, and floats round differently across hosts and implementations. So this is the one vector compared approximately: each recomputed hash must be within 4 bits of the committed one, and the quality within 2. A picture matches a listed hash when any of its variants is within match_distance bits (Media).

shamir.json

Shamir's secret sharing over GF(2⁸), byte by byte, in the AES field (x⁸ + x⁴ + x³ + x + 1): the same field as the app's first-run rehearsal in apps/web/src/lib/sayhoi/shamir.ts, so one file holds both. Social recovery splits a recovery line into five shares, any three of which bring it back.

hoi-crypto's test feeds these coefficients to split_with, compares the five shares byte for byte, and rebuilds the secret from shares 2–4. The Rust field arithmetic runs in constant time with no tables and no branches on secret values (Keys & identity).

A key split 3-of-5: any three pieces bring it back, two don't.

Registry and node statements

Five files fix signed text that two independent implementations must produce identically: the Rust core and hoi-node on one side, the JavaScript registry (registry/) on the other. Each holds a seed, so anyone can recompute the signature (Registry).

node-announcement.json

The body a registry receives from a public node, plus the seed and the statement for checking. Keys: seed (4b × 32), registry (https://registry.example), endpoint, issuedAt (1800000000), routes (an rtc: route and a direct one, both on 203.0.113.10), communities (11…, 22…), statement, signature.

hoi public node v2
<registry origin>
<endpoint hex>
<issued_at>
<routes, comma-separated, in the order others should try them>
<community keys, sorted, comma-separated>

No trailing newline. Binding the registry's origin means no registry can pass on what it was sent to another one: the Worker configured for https://registry.example accepts the vector, and one answering for itself refuses it with wrong-registry. hoi-node's test also refuses it 601 seconds after issuedAt (stale) or before it (future-dated).

community-registration.json

A version 1 name claim, signed by a community key from seed 2a × 32: community, name (garden_1.v2-test, already canonical), seed, statement, signature. The statement is "hoi community name v1\n<name>\n<community hex>". hoi-core's registration_signature_vector rebuilds the whole JSON object from the seed and asserts it equals the file; the Node registry, the conformance suite and hoi-node accept it unchanged and refuse it under any other name.

community-publication.json

A version 2 publication proof, which also binds the exact protocol and index edition: seed, name, community, protocolVersion ("0.3"), indexVersion (1), statement, signature. The statement is "hoi community index v2\n<name>\n<community hex>\n<protocol>\n<index>". hoi-core's publication_signature_vector rebuilds it; the registries list it as indexed; hoi-node accepts it as a v2 claim and refuses it as a v1 one.

When a vector changes

A vector changes only when the bytes or the outcome it fixes change, and then every device that computes it the old way disagrees with every device that computes it the new way:

  • A record's id is the BLAKE3 hash of its canonical bytes and its signature is over that id. A different encoding gives the same record another id, and older signatures stop verifying (Records & encoding).
  • The statements are signed text. A changed line, order or separator invalidates every existing proof, announcement and notice signature, and two implementations that differ by one byte refuse each other's.
  • Sizing, the ladder and warmth are outcomes every device must reach on its own. If two builds disagree, they pick different holders, give members different standing, or show different warmth for the same community.

So the test suite treats any difference as a failure, and an intended change is a protocol change:

  1. Change the code and its tests

    Cover the change with core tests, as CONTRIBUTING.md asks.

  2. Regenerate

    cargo run -p hoi-validate --example vectors from core/, and update any committed file a test rebuilds (shamir.json, name-log.json, the two community files).

  3. Run every reader

    cargo test --workspace, pnpm core:test:wasi, pnpm test (the registry's suites) and pnpm --filter @hoi/web test (the notice test).

  4. Declare compatibility

    Builds that read the old bytes can't read the new ones. That is what protocolVersion and supportedProtocols in release.json state, and they change only explicitly (Releases).
