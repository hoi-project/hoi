Trust & ranking

The community's ladder is shared: every device computes the same one. Trust is personal: how much a key counts on this device, from whom this person marked as a friend. It weighs votes for ranking and reports for autobans, and it is never sent anywhere. This page covers trust levels and weights, the Hot, Fresh and Loudest formulas, and the people a person can choose to listen to: labelers, blocklist keepers and tally aggregators. It ends with operator suppression and age proofs as a way into a community.

Trust levels and weights

hoi-trust is a tiny crate with no dependencies. Its first line says what it is for: how much a key counts on this device. Nothing in it is ever sent anywhere, so two devices can rank the same community differently, and that is intended.

LevelWhoWeight
meThis device's own person1.0
friendSomeone this person marked as a friend1.0
fofA friend of a friend: named in a friend's published trust statement0.5
memberA key this device first saw more than 90 days ago (MEMBER_AGE)0.25
newcomerEveryone else0.05
 
pub const MEMBER_AGE: u64 = 90 * 86_400;

impl Level {
    pub fn of(is_me: bool, is_friend: bool, is_fof: bool, key_age_secs: u64) -> Level {
        if is_me {
            Level::Me
        } else if is_friend {
            Level::Friend
        } else if is_fof {
            Level::Fof
        } else if key_age_secs > MEMBER_AGE {
            Level::Member
        } else {
            Level::Newcomer
        }
    }

    pub fn weight(&self) -> f64 {
        match self {
            Level::Me | Level::Friend => 1.0,
            Level::Fof => 0.5,
            Level::Member => 0.25,
            Level::Newcomer => 0.05,
        }
    }
}

Key age counts from when this device first saw the key (state.first_seen), never from what a record claims, so nobody backdates their way into a heavier weight. These levels have nothing to do with the community's ladder: a trusted member of a community is a "newcomer" here until this device has known their key for 90 days, unless someone made them a friend. The app shows the level on every person as their trust.

Friends and trust statements

Friends are local: set_trust(key, true) adds a key to state.friends on this device. It reaches others only in communities where this person shares whom they trust. Friends of friends need something published: a trust record, in which a person says whom they trust, in one community, by choice.

keys[bytes32]
0 to 256 person ids (MAX_TRUST), sorted, each once. Empty takes the last statement back.

A trust record has no parent, is 10 KiB at most, stamps at pow_bits − 8, and is rate-limited to 4 an hour and 12 a day. The latest per person and community replaces the earlier ones: the store drops the older. It expires with the community's retention.

  • A choice per community. share_trust(community, true) publishes a statement there; turning it off publishes an empty one in its place. Private communities are refused: their members keep who trusts whom to themselves.
  • Only friends known there. A statement in a community names only friends who are admitted there or have records of their own there, so sharing in one place says nothing about the rest.
  • Kept current. At each sweep, and whenever friends change, the device publishes a new statement where the friends it should name changed or the last would expire within two days (RENEW_BEFORE).

refresh_ring works out the ring again: degree 1 is the friends marked here; degree 2 is everyone named in each friend's latest usable statement in any community this device holds, besides this person and their friends. The ring is rebuilt when a trust record arrives and at every sweep, so expired or removed statements leave it. The person view shows up to three friends who named someone (trusted_by).

The two_people_with_different_rings_see_different_hot_orders_and_why test gives two readers the same records and different friends. Each sees a different Hot order, and the app explains why: a post's up-votes from friends and from friends of friends are counted separately.

The tally behind a post

Every device counts votes itself, from the vote records it holds. Nobody ships totals around (aggregators aside, below).

for (voter, (_, v)) in latest {
    if self.bounced(&voter).is_some() {
        continue;
    }
    t.score += v;
    if Some(voter) == me {
        t.mine = v;
    }
    let level = self.trust_level(&voter);
    let w = level.weight();
    if v > 0 {
        t.up_w += w;
        match level {
            hoi_trust::Level::Friend => t.friends_up += 1,
            hoi_trust::Level::Fof => t.fof_up += 1,
            _ => {}
        }
    } else if v < 0 {
        t.down_w += w;
    }
}
  • One vote per person. For each voter root, the vote with the highest seq counts. A vote is -1, 0 (retracts) or 1; the app writes seq as now × 1000 or one more than its last.
  • Bounced keys don't count. A key this device bounced for spam weighs nothing while the bounce lasts (bounces).
  • score is the plain sum shown next to a post. up_w and down_w are the weighted sums ranking uses. friends_up and fof_up say how many up-votes came from friends and friends of friends.

The community's ladder counts votes differently, for its own purpose: unweighted, from members only, toward the author's standing (trusted).

Ranking

Wilson lower bound

Hot ranks by confidence, not by raw counts. wilson is the lower bound of the 95% Wilson score interval (z = 1.96) on the weighted votes, so a post with 10 up-votes beats one with a single up-vote, though both are 100% positive.

/// Lower bound of the Wilson score interval (95%) on weighted votes.
pub fn wilson(up: f64, down: f64) -> f64 {
    let n = up + down;
    if n <= 0.0 {
        return 0.0;
    }
    let z = 1.96_f64;
    let p = up / n;
    (p + z * z / (2.0 * n) - z * ((p * (1.0 - p) + z * z / (4.0 * n)) / n).sqrt()) / (1.0 + z * z / n)
}

/// `hot = wilson(up, down) / (age_hours + 2)^1.5`, with a small floor so a
/// brand-new post with no votes yet still surfaces by freshness.
pub fn hot(up_w: f64, down_w: f64, age_secs: u64) -> f64 {
    let age_h = age_secs as f64 / 3600.0;
    (wilson(up_w, down_w) + 0.02) / (age_h + 2.0).powf(1.5)
}

pub fn loudest(up_w: f64, down_w: f64) -> f64 {
    up_w - down_w
}

Hot

So, exactly: hot = (wilson(up_w, down_w) + 0.02) / (age_hours + 2)^1.5, where age_hours is the seconds since the post's created_at divided by 3,600. The 0.02 floor lets a new post with no votes surface by freshness alone. Some values, worked from the formula:

Comments

Replies under a post sort by the author's trust first (me and friends, then friends of friends, then everyone), then by plain score, highest first, then oldest first. Removed comments keep their place as a Poof box.

Labelers

A labeler is anyone whose labels a person chooses to follow. A label from a labeler someone here follows, or one the community names by default in its limits, puts its target to sleep or adds a note on this device. A label from anybody else is refused, without penalty.

The label record

labeltext
Required, at most 40 characters on one line: spam, nsfw, off-topic, or a short note.
notetext, optional
At most 300 characters.

Its parent is the post or comment labelled. It is 512 bytes at most, stamps at pow_bits − 8, shares a rate group with reports (20 a day for newcomers, 200 a day for members) and expires with the community's retention. The app labels only posts and comments in public communities: "Private groups moderate among themselves: labels are for public communities."

What a label does

A node takes a label only from this person, a labeler they follow (state.labelers), or one of the community's default labelers (limits.labelers, at most 32). Anything else is refused at ingest as labels from a labeler nobody here follows, which costs the sender nothing. Taken labels then work like the ledger's: one of the hiding labels (spam, likely spam, hide, nsfw, illegal, off-topic, any case) makes the record nap, attributed to the labeler; any other label is a note. Why a record naps is decided in this order: a pending removal, the community's hides, an author the community blocked, your own hide, moderators' labels, then followed labelers' labels.

Following

follow_labeler(key, true) adds the key, marks every view changed, and starts every connection's sync over (reconcile_again): labels this device refused before arrive with the next sync. Your own labels always count here.

lanes: Reader's device | Peer | Labeler Labeler => Peer: label {parent: a post, label "spam"} Peer -> Reader's device: offers it in sync Reader's device: refused without penalty: nobody here follows them Reader's device: the reader follows the labeler Reader's device -> Peer: sync starts over: ranges and haves sent afresh Peer => Reader's device: the label, again Reader's device: taken: the post naps, "spam" by the labeler

The following_a_labeler_hides_what_they_labeled_within_one_sync test checks exactly that, and a_labeler_labels_from_the_app_and_a_community_default_counts_for_everyone checks that a community's default labeler counts for someone who follows nobody. In the web app, Labelers.svelte lists followed labelers and community defaults ("default in c/…"), how many labels each has here, and a box to follow one by key; it also lists followed aggregators.

Open blocklists

A list keeper (a group that tracks abuse imagery, or a community's own moderators) publishes the exact media hashes and picture fingerprints it refuses, signed, as a blocklist record. A person follows keepers as they follow labelers; every device of theirs then refuses those hashes, and pictures close to those fingerprints, in every community, besides its own list.

exact[bytes32]
BLAKE3 hashes of media bytes, sorted, each once, at most 1,000.
pdq[bytes32]
256-bit PDQ picture fingerprints, sorted, each once, at most 1,000.

A blocklist has no parent, is 72 KiB at most, stamps at pow_bits − 8, is rate-limited to 4 an hour and 12 a day, and expires with the community's retention. The latest per keeper and community replaces the earlier ones. A node takes one only from this person or a keeper they follow (state.blocklists); others are refused without penalty (a blocklist from a keeper nobody here follows).

How lists apply

refresh_lists builds the union of every followed keeper's latest list across every community this device holds. When it changes, the node deletes stored media whose hash is listed, looks again at stored pictures and deletes those whose fingerprint, in any orientation, is within 31 bits of a listed one (MATCH_DISTANCE, out of 256), and drops profiles whose picture is now blocked. Posts whose media hash a followed list names are held (its media failed the checks), and so are posts whose bytes, when they arrive, look like a listed picture: the device refuses those bytes and remembers their hash. The listed exact hashes stay the keeper's, kept apart from this person's own refusals, and stop counting the moment they unfollow. See media for fingerprints.

Publishing a list

publish_blocklist(community, text) reads one hash a line: a 64-character PDQ fingerprint, or blake3: and an exact media hash. Lines starting with # are notes, and anything after a comma or a space is ignored. Lists are for public communities only. A person's own list of fingerprints is separate: import_blocklist adds PDQ hashes to this device's own refusals and publishes nothing. In the web app, ListKeepers.svelte lists followed keepers with their counts ("N hashes · N fingerprints") and has a form to publish a list in one of the joined communities.

Tally aggregators

A browser holds part of a community; a durable node holds more. An aggregator is a device that counts a community's votes and publishes the counts, signed, as a tally record. People follow an aggregator as they follow a labeler. Its counts show next to a post's own and can order the feed when the person picks that. They never go into Hot or any other ranking on their own: an aggregator's word is its word.

counts[[post, up, down]]
At most 500 rows (MAX_TALLY), sorted by post id, each post once. up and down are plain counts.
  • Counting. For each post the device shows, each voter's latest vote once, unweighted. Posts with no votes are left out; of the rest, the 500 with the most votes are kept.
  • Publishing. set_aggregating(community, true) publishes at once and then every hour at the sweep (EVERY = 3,600 s). Only public communities this device keeps. A tally expires after the community's retention or 7 days, whichever is shorter, and the newest replaces the older.
  • Taking. A node takes a tally only from itself or an aggregator its person follows (counts from an aggregator nobody here follows). Tally records are 32 KiB at most, rate-limited to 4 an hour and 48 a day.
  • Showing. Each post lists every followed aggregator's latest count for it. The counted sort uses the first of them (followed aggregators are kept in key order).

Trust weighs reports too

Reports, signed flags against a key, are counted with the same weights. A reporter counts by the larger of their weight here and their standing in the community: trusted 1.0, established 0.5, anyone else 0. When the weighted reports against a key reach the community's autoban_threshold (12 by default), this device bounces the key. Fresh keys weigh 0.05 here and nothing on the ladder, so it takes 240 distinct fresh keys to reach 12. The Manage tab's flags show a weight from trust alone. Details are on spam.

Operator suppression

The person who runs a native node can stop serving something; nobody can forge anything. An operator can suppress an identified community, record or media blob: it is deleted on that node, never fetched, accepted or served again, and the refusal survives restarts. Nothing is signed and nothing is sent. A suppressed item is simply absent from that node, and every other node decides for itself.

TargetWhat it deletesWhat it refuses
communityEvery record of the community, the media only those records used, its skeletonsThe community, however it arrives: invites, carry offers, public joins, its genesis
recordThe record and its edits, and media only they usedThose ids, for good: marked deleted with no end date
mediaThe bytesThe hash; posts that show it are held

Only records that hold what people wrote or showed can be suppressed one by one: posts, comments, edits, reports, profiles and profile colors. A record whose absence would change who may speak or what is hidden (a genesis, an identity, a device or its revocation, the ledger, vouches, reviews, deletions, labels, votes) can't: suppressing it alone could bring back what a community removed. The operator suppresses its community, or the post it is about. Private groups aren't held in the open and can't be suppressed; the node leaves them instead.

Hosts reach this through hoi-node admin while the node is stopped: suppress community|record|media <id> with an optional --note (one line, at most 200 characters, the operator's own reference) and --evidence <dir>, then suppressions and unsuppress <id>. It is not part of the JSON dispatch the apps use, so no client and no peer can ask for it. An operator who must keep evidence first takes a copy (suppression_material): the signed records exactly as they arrived, which anyone can verify later, and the media. Lifting a suppression brings nothing back by itself; what was deleted stays deleted until sync, an index or a request brings it again. See hoi-node.

Age proofs as a way in

A community whose admission is age-proof lets a newcomer in once a moderator saw a proof that they are over 18, and nothing else about them. The proof is an SD-JWT VC presentation from an identity wallet. It is never published: the ledger entry that lets the person in says only age proof. How the presentation is built and verified is covered with keys & identity; this section covers the community's side.

What the community sets

  • limits.admission = age-proof, changed by consent like any limit.
  • limits.age_issuers: the raw public keys of the credential issuers it trusts, 1 to 8, each 32 bytes (Ed25519, EdDSA) or 33 or 65 bytes (P-256 SEC1, ES256). An age-proof community without one is refused (an age-proof community names the credential issuers it trusts). The Manage tab takes them as hex, one a line.

From then on, a newcomer's posts, comments, edits and profiles are held until they are admitted, and only admit entries admit anyone: the ladder runs with admits_only, so vouches give voice but let nobody in.

Getting in

lanes: Wallet | Newcomer's device | Moderator's device | Every device Newcomer's device: age_challenge: aud hoi:<community hex>, a nonce for this person and community, the trusted issuers Newcomer's device -> Wallet: the challenge Wallet --> Newcomer's device: a presentation disclosing only age_over_18, key-bound to aud and nonce Newcomer's device: checks it; makes a hoi-age-1- code Newcomer's device -> Moderator's device: the code, however they like Moderator's device: checks it again, now; community is age-proof; person not in yet Moderator's device => Every device @mint: ledger {action admit, target: the person, reason "age proof"} Every device: admitted; what they wrote while held goes out

The nonce is derived, so a proof made for one person or community is useless for another: BLAKE3 in derive-key mode with the context hoi age proof nonce v1, over the person's root key and the community key, first 16 bytes, base64url. The code carries everything the moderator's device needs to check it again:

person | 32 B | sun | 3 | the newcomer's root key community | 32 B | mint | 3 | the community key presentation | up to 16 KiB | sky | 6 | the SD-JWT presentation with its key binding, as text

What both devices check

age::check runs on the newcomer's device before it makes the code and on the moderator's before it admits. It accepts a presentation only if it is at most 16 KiB; signed by one of the community's issuers; not expired; using SHA-256 digests; disclosing age_over_18: true and nothing else; carrying a key binding (typ kb+jwt) signed by the credential's own holder key, for this community's aud and this person's nonce, made in the last 15 minutes (up to 60 seconds in the future); and whose sd_hash covers the presentation it came with. A code is checked against the clock when the moderator uses it, so it has to be used within those 15 minutes.

The moderator's device also refuses a code for a community that doesn't ask for age proofs and for someone already in ("They're in already."). The a_newcomer_is_let_in_by_a_proof_of_age_and_vouches_alone_dont test walks the whole flow: the newcomer's post is held, a vouch doesn't help, a proof made for someone else is refused, the right one admits them with reason age proof, their held post goes out, and no record anywhere holds the issuer's signed part of the presentation.

What never leaves the device

Everything a person decides about whom to listen to is local state, on this device only: friends, petnames, muted keys, followed labelers, followed blocklist keepers, followed aggregators, the communities this device counts for, bounces, this device's own media and picture refusals, and the first time it saw each key. None of it is a record, none of it syncs. What is published is only what a person chooses to publish: a trust statement, a label, a list, a tally, a report.

So two people holding the same records can see different orders, different napping posts and different weights, and both are right. The community's own decisions, its ledger and its ladder, are the part every device agrees on (communities, standing).
