Joining, step by step

This page follows eight paths from a link or a cable to the first record on screen: a browser opening a node link or an invite, a native node joining and finding public nodes, a fresh public node starting up, two devices on one network, pairing and linking a device, two browsers getting a direct link, and joining a private community. For each it lists every frame in order, who sends it, what each side keeps afterwards, and the timeouts, retries and caps that bound it.

What every link does first

Whatever the transport, both ends run the same conversation from hoi-sync: CBOR messages, one per WebSocket message, or framed with a 4-byte big-endian length on an iroh stream or a WebRTC data channel (see Transports and Sync & gossip). These rules hold on every path below:

  1. Who speaks first

    A node sends its hello as soon as the host opens a connection, with two exceptions. To a device that dialed it as a paired device (a client), it says nothing until that device showed its credential; a missing or wrong one ends the link without a word, so a web page can't even learn that a home node listens there. And under the consent gate (browsers, the desktop, phones), a device that dialed a stranger waits for the stranger's hello first.

  2. Everything starts with a hello

    A first message that is neither hello nor bye drops the link. The hello must arrive within 15 s. A hello with v other than 2 is answered bye {reason: "this node speaks sync version 2"}.

  3. A WebRTC link binds first

    On a WebRTC link the browser dialed, the node sends bind {s} right after its hello. It holds an Ed25519 signature by the node's endpoint key over "hoi/rtc-binding/1\n<node cert fp hex>\n<browser cert fp hex>\n<ufrag>\n<endpoint hex>". Until it checks out, the browser takes nothing but hello, bind and bye.

  4. After the hello

    The receiver runs, in this order: send_haves (a rng session per shared community, or have to an old peer), send_catalog, send_nodes, send_link_request, auto_request_carry, after_hello_find (dht contacts, find) and refresh_here. Each one sends only if its own rules say so.

  5. Limits on every link

    3000 messages per peer per minute before the peer starts losing score. A recs message carries at most 500 records (200 sent at a time, about 1 MiB). A want holds at most 5000 ids and is sent 200 at a time, with one page in flight per link. The largest message is 16 MiB plus 64 KiB.

Names in these diagrams

Addresses come from the documentation ranges (203.0.113.0/24, 198.51.100.0/24), as the test suites use them. <fp> is a 43-character base64url certificate fingerprint and <ep> a 64-hex endpoint key. N is a public node, a hoi-node serving strangers with default flags.

(a) A browser opens a node link

Kim's browser has a key and nothing else: no home node, no community. Someone shared a node link, https://hoi.sh/app/#/node?code=SE9OAV1m…. This is the path scripts/e2e-node-link.mjs runs end to end, with nothing configured anywhere.

  1. Read the link

    The app's A public node screen calls previewNodeLink. The core unmasks the code (HON\x01, checksum, deflated CBOR {v, w, p, n, s}) and checks the notice signature against the endpoint in the first native route. It returns NodeLinkPreview {host: "203.0.113.9:7844", scope: "internet", endpoint, notice, verified: true}. Stored: a pending notice in state.notices (asked: false), at most 64 kept.

  2. Accept and open

    acceptNotice(node, hash) marks the notice accepted. openNodeLink(link) trims the routes to 2 WebRTC and 2 native and inserts KnownNode {routes, seen: 0} at the front of state.nodes (at most 32). It returns DirectoryStatus {known: 0, waiting: 1, connected: 0, listings: 0}.

  3. Dial

    The worker's discovery round runs every 15 s (the first 3 s after start) while no discovery link is open. discovery_candidates() puts N's WebRTC route first: links opened here come before nodes reached earlier. Up to 3 nodes are dialed at once and the first to open wins; the losers are closed unused. The page opens an RTCPeerConnection with no ICE servers and writes N's half of the session itself. N answers a first binding request with one stateless probe; only after the browser's ICE agent answered it does a session start. N serves members' browsers only while it accepts members: otherwise the binding request gets no answer at all.

  4. N's hello and bind

    N's consent gate is off, so its hello goes out as the host connects: c empty (no route of N's led to this browser), its other public communities salted under a fresh n, its published routes, its features and its notice (nh, nt). Then bind {s}.

  5. The browser checks

    The notice hash matches the one accepted, so the consent check says proceed. The bind signature checks against the endpoint the hello named and the channel that opened. The browser's hello follows: a fresh random 32-byte node, no name, a salt of its own, its public communities hashed, features ending in unlisted (and direct if Direct links are on). It then asks N to carry up to 3 open communities its person founded (carry {g}) and sends find {c} for joined open communities nobody connected serves.

  6. N answers the stranger

    N matches the browser's salted hashes against what it holds (none yet). It sends catalog: its own open communities (up to 48) and a window of relayed listings, at most 64 entries and 256 KiB. Then nodes: routes of public nodes it reached itself, at least as wide as the browser's address, at most 32. N stores: nothing about the browser in its saved state. It says unlisted, so it is remembered nowhere; its peer entry lives in memory while the link does.

  7. The browser keeps what it heard

    Each catalog genesis is checked (decode, open admission, stamp floor, signature, content, time) before it enters the directory, at most 512 listings in a browser, marked dialed and public. The directory blob is written within 30 s of something new. N sent a list on a link the browser dialed, so note_public_node replaces the link entry with KnownNode {routes: [rtc:…@203.0.113.9:7844], seen: now}. Up to 16 routes of N's list become candidates for an hour. The status reads {known: 1, connected: 1}.

  8. Join from the list

    Communities now lists what N carries, each DiscoveredCommunity with a ready invite. Joining one is path (b) from step 4, with N already connected: the browser's next hello names the community in the clear, because its routes lead to N.

Timeouts on this path

WebRTC must open within 12 s on the browser's side and 15 s on N's. N holds at most 32 sessions, 8 of them opening, and takes 10 new ones per source address a minute. A node that never answered waits 60 s before it is tried again, doubling to 30 minutes, and its passed-on routes are dropped.

(b) A browser opens a community invite

Mira sent Kim an invite to c/garden: https://hoi.sh/app/#/join?code=SE9JAj…. Mira's browser asked the public nodes it was connected to to keep c/garden before it made the invite (carry_for_invite), so the invite names them.

lanes: Kim's browser | Public node N | Mira's browser -- Before anything is dialed -- Kim's browser: unmasks HOI\x02, checks the genesis signature Kim's browser: join: genesis stored, routes in state.bootstrap -- Connect -- Kim's browser -> Public node N: WebRTC to an invite route (h1p) Public node N --> Kim's browser: hello {ch: [salted c/garden …]}, bind Kim's browser: N's notice already accepted, else the link ends here to show it Kim's browser -> Public node N: hello {c: [c/garden]} (its route led here) -- Catch up -- Kim's browser -> Public node N: rng {c, n: 1, s: true, r: [the genesis id]} Public node N -> Kim's browser: rng {c, n: 41, s: true, r} Public node N --> Kim's browser: rng {c, n: 41, s: false, r: its ids} Kim's browser -> Public node N: want {ids: ≤ 200} Public node N => Kim's browser @coral: recs [genesis, identities, delegations, posts] Kim's browser: validates each record; remembers N as a member route -- Live -- Mira's browser => Public node N @coral: recs [a new comment] Public node N => Kim's browser @coral: recs [the comment]
  1. Read the invite

    The code is HOI\x02, a 16-byte checksum and the masked CBOR {v: 1, c, r, p, g, t?}; unlike a node link it is not deflated. previewInvite checks the genesis in g: it must decode, carry a valid signature by the community key and pass the content rules. Without g the core falls back to a stored genesis or the directory's. Nothing has connected yet.

  2. Network & Safety

    On first use the app shows its fixed notice and waits for both boxes to be ticked before anything connects.

  3. What the invite holds

    Its p lists up to 16 routes in the order Mira's device wrote them. First the carriers connected to her now (N's routes, bound to the connection her browser dialed), then the routes she joined with, then members she met (newest first). Two more public nodes she reached come last, so the invite leads into the network even when none of those answers. r holds up to 8 relays and t up to 2 trackers.

  4. Join

    join(link) needs Kim's key. It ingests the genesis (stored: state.joined[c] = {at, pinning: false} and the genesis record), then remember_hints (stored: state.bootstrap[c] = {peers ≤ 16, relays ≤ 8}, freshly supplied routes first) and remember_trackers (≤ 2). announce() sends a fresh hello to every connected peer.

  5. Dial

    The member round, every 15 s, takes rtc_candidates(): mailbox routes first, then accepted invite routes, routes on trial and members met (newest first). That is at most 8, never the home node's. It keeps up to 2 member links open (plus one per mailbox a private group needs), WebRTC with ufrag mode p. A node that refuses (a link closed within 60 s of opening) waits 60 s, doubling to 30 minutes.

  6. Hellos and the notice

    As in (a), N speaks first. If N's hello carries an operator notice Kim never accepted, the consent check keeps the words, the app shows them, and the link ends quietly. It is no refusal: once Kim accepts, the next round dials N again with no wait. Then Kim's browser names c/garden in c in the clear, since the invite's route reaches N, and hashes the rest. N already holds c/garden, so both sides know they share it.

  7. Reconcile

    Both said range, so each starts a session: rng {c, n: <records it holds>, s: true, r: entries}. The other always answers with s: false, splitting ranges whose fingerprints differ. The starter collects the ids it lacks and asks for them in pages of 200 with want, one page in flight per link across all communities. A session the peer stopped answering ends after 120 s. Details on Sync & gossip.

  8. Records

    recs arrive genesis, identities and delegations first. Each passes the full validation pipeline. Kim's browser stores: the records; and, because N delivered valid records of c/garden besides the genesis, remember_member saves N's connection-bound routes in state.learned[c] (≤ 16 per community, 30 days). When the want pages run dry: state.synced[c] and state.sync_completed[c].

  9. Live

    New records travel on the same link as recs. Mira's comment reaches N, which checks it and passes it to every peer in c/garden, Kim included. Kim's browser can't be dialed, so what Kim posts is readable by others once a node carrying c/garden has it.

Stalls

A link with want ids outstanding and no progress for 120 s counts as stalled; the worker checks every 30 s and reconnects it. More than 100,000 ids pending from one peer ends the link with bye {reason: "too much pending catch-up"}.

(c) A home node joins a public community and finds public nodes

Lena's Raspberry Pi runs hoi-node as a home node: a public relay by default, so a public node too. It joins c/garden with --join INVITE, or because Lena's paired browser is in it. A paired device's hello makes its home node join every public community the device names, pinned, until it holds 256.

lanes: Home node H | Public node N | Public node P -- Dial loop, every 5 s -- Home node H -> Public node N: QUIC hoi/sync/1 to <ep>@203.0.113.9:7843 Home node H .. Public node N: both send hello (no consent gate on a headless node) Home node H -> Public node N: rng for c/garden; dht {a: [own DHT contact]} Public node N --> Home node H: rng, catalog, nodes {routes: [P …]} Home node H: dialed N, N sent a list: N kept; P a candidate Public node N => Home node H @coral: recs after want Home node H: N delivered records: N's route in state.learned -- Up to 3 other public nodes -- Home node H -> Public node P: QUIC (from directory_hints) Public node P --> Home node H: hello, catalog, nodes Home node H -> Public node P: carry {g} for a community with too few copies Public node P --> Home node H: carried {c, ok: true}
  1. Join

    As in (b) step 4, without a key: a native node may hold and serve a community without one. Stored: state.joined, the genesis, state.bootstrap.

  2. Dial loop

    Every 5 s the iroh host asks bootstrap_hints(): native routes from accepted invites, routes on trial, members met within 30 days, and up to 3 other public nodes (only because H is public). Mailbox and forward routes come too. It skips nodes connected now and nodes waiting out their retry: 2, 4, 8, 16, 32 then 60 s. Each attempt has 20 s to connect, and then 15 s to open the one bidirectional stream. At most 32 iroh connections run, in and out together.

  3. Hellos

    Both nodes send hellos. Each names in the clear the communities whose routes reach the other and salts the rest. H's features include keeps, carry, find and, with the DHT up, dht; there is no unlisted, since a headless node publishes its addresses.

  4. DHT contacts

    Both run the DHT, so each sends dht {a: ["203.0.113.5:7846"]}: the IPv4 hosts of its public routes at its DHT port, at most 4. Stored: contacts from up to 64 peers, used to start the DHT with no outside router.

  5. Reconcile and fetch

    As in (b). Once N delivered valid records of c/garden over a connection H dialed, remember_member keeps <ep>@203.0.113.9:7843 (the address the authenticated connection came from) and N's routes for that same endpoint. Up to 2 of its WebRTC routes for browsers are kept too, but only routes bound to this connection.

  6. Directory and node list

    N's catalog goes into H's directory (up to 4096 listings on a native node). N's nodes list arrived on a link H dialed, so N enters state.nodes and P's routes become candidates. From then on directory_hints() hands up to 3 such nodes' native routes to the dial loop.

  7. Spreading load

    When a public node that takes carry requests says hello, H offers it open communities it holds with fewer than 3 durable copies. That is at most 3 per hello and at most 2 nodes per community a day. P answers carried {c, ok, reason?}, decided by P's own policy and budgets: 8 accepted a minute, 128 a day, 256 communities.

  8. When nobody serves c/garden

    At every sweep (about 3 minutes) H sends find {c} to up to 3 connected nodes that said find, at most every 600 s per community, and queues a DHT lookup. Routes in a found answer go on trial; one that delivers records is kept.

A desktop is the same, with two differences

Its consent gate is on, so it waits for a stranger's hello and checks the notice before speaking. And unless its person turned on Be a public node, it says unlisted, dials no extra public nodes and sends no node lists to strangers.

(d) A fresh public node bootstraps

An operator starts hoi-node --public --notice notice.json --node 'https://hoi.sh/app/#/node?code=…' on a new server. There is nothing else: no registry, no relay, no list of peers.

lanes: New node S | Public node N | Mainline DHT | Browser -- Start -- New node S: no key (a label only); relay on; carry any; notice signed New node S: --node link: N into state.nodes, seen = 0 New node S: UDP 7844 WebRTC, 7846 DHT, 7847 answers, 7848 LAN; writes DIR/node-link -- First link -- New node S -> Public node N: QUIC hoi/sync/1 Public node N --> New node S: hello, catalog, nodes, dht {a} New node S -> Public node N: hello, catalog, nodes, dht {a} New node S: N kept; N's list into candidates; up to 3 nodes dialed -- DHT from hoi's own contacts -- New node S -> Mainline DHT: rebuild from N's contact (table empty, 60 s apart) New node S -> Mainline DHT: announce_peer(dht_key(c), answer port) per carried community Public node N: S dialed in: only S's own route on that address is a candidate (1 h) -- Later, once that link is gone: N dials S back -- Public node N -> New node S: QUIC hoi/sync/1 New node S --> Public node N: hello, nodes: N keeps S Public node N -> Browser: nodes {routes: [S …]} Browser -> New node S: WebRTC; then path (a)
  1. Start

    A public node has no person: it stores and serves, never signs, so it gets a label and no key. Relaying is on and the carry policy is any. The notice is checked and signed by the transport key; without --notice the node prints a warning that people are not told who runs it. --join invites are joined and --node links opened. Stored: KnownNode {routes, seen: 0} for N.

  2. Ports

    The iroh endpoint binds, and its found and direct addresses become routes (up to 8). WebRTC listens on UDP 7844, and by default the router is asked to forward ports (PCP, NAT-PMP or UPnP). The DHT listens on 7846 and answers on 7847 (relaying, carry any, no --no-dht), and LAN beacons use 7848 (no --no-lan, no --vpn-only). The node link goes to DIR/node-link; it is checked every 2 s and rewritten when it changes.

  3. First link

    The dial loop tries N's native route. S has no consent gate: both hellos go out at once. N is public, so it sends S its catalog and node list. S dialed N and N sent a list, so N becomes a known node, and up to 16 of N's routes become candidates. directory_hints() then hands the native routes of up to 3 public nodes to the dial loop.

  4. With no link at all

    S waits. A public node that dials in and sends its nodes list makes S dial nobody from that list. Only that node's own routes, on the address its connection came from (at most 2), become candidates. When S dials it back and it answers with a list, S keeps it. That is how a node that only ever dials out becomes known to the nodes it reaches.

  5. The DHT, from inside

    The DHT was built with no bootstrap. Every 10 s the loop checks: while its routing table is empty and some peer sent dht contacts, it rebuilds the DHT node from them, at most every 60 s. Then it announces each open community it carries (at most 64) under dht_key(c) with its answer port, every 15 minutes or when the list changes. It also runs the lookups the core queued.

  6. Gossip

    Every sweep, about every 3 minutes, gossip_directory runs once 300 s have passed since the last time. It forgets listings unconfirmed for 21 days and sends each peer its next window of relayed listings: peers that say keeps every time, others at most every 1800 s.

  7. Optional announcements

    Every 60 s S looks at the trackers its carried open communities name (at most 16) and keeps one announcing loop per tracker. With --index URL it also announces to that registry with PUT /v2/nodes every 5 minutes, mirrors the registry's listed communities every 5 minutes (50 names a page, up to 40 pages) and carries what is compatible.

  8. Being found

    S's list reached N on a link S dialed, so N takes only S's own routes, on the address the connection came from, as candidates for an hour. N's loop never dials a node it is connected to. Once that link is gone, N may dial S back as one of the 3 nodes it takes from its list, and when S answers that link with a list, N keeps S and lists it to everyone it serves. Browsers that reach N then hear of S in N's next nodes message. Meanwhile anyone who opens S's own node link reaches it directly.

(e) Two devices on one network

Mira's desktop and Lena's home node sit on the same home network and are both in c/garden. Neither knows the other's address. Only native nodes send beacons; a browser on the same network reaches the home node through its pairing link instead.

lanes: Desktop | Multicast group | Home node Home node -> Multicast group: HOIL\x01 n=1, tag(c, now/600), sealed(ep, port) every 30 s Multicast group -> Desktop: the same 96 bytes (group 239.255.70.74, port 7848, TTL 1) Desktop: tag matches c/garden in this or the last window; opens sealed Desktop: route <ep>@192.168.1.5:<port> on trial for c/garden -- Next dial round, within 5 s -- Desktop -> Home node: QUIC hoi/sync/1 Home node --> Desktop: hello (the home node speaks at once) Desktop: consent gate: no notice, or one already accepted: proceed Desktop -> Home node: hello {c: [c/garden]} (the trial route led here), unlisted Desktop .. Home node: rng both ways, want, recs Desktop: records delivered: route kept in state.learned Home node: the desktop says unlisted: remembered nowhere
  1. Beacon

    Every 30 s each native node sends one datagram to 239.255.70.74:7848: HOIL\x01, a count (at most 8 joined, non-private communities), then per community a 16-byte tag and 74 sealed bytes. For one community that is 96 bytes. The tag is a keyed BLAKE3 of the 10-minute window number under a key derived from the community. The sealed part holds the endpoint key and the QUIC port, under another key derived from the community. Someone who doesn't know c/garden learns nothing from it.

  2. Hear

    Every hoi node on a machine shares port 7848 (address reuse). A node takes at most 120 beacons a minute. It matches each tag against the communities it joined for the current and the previous window, opens the sealed part, and skips its own endpoint. Stored: <ep>@<sender IP>:<port> in trial_routes[c], in memory only, at most 16 per community.

  3. Dial

    Both nodes hear each other and both dial loops (every 5 s) include routes on trial. An incoming QUIC connection is taken only while the receiver accepts members: its relay switch is on (native nodes turn it on the first time they start, native_defaults in node.rs) and today's cap isn't used up. A desktop whose person turned the switch off takes no incoming link, so then only its own dial opens one. When both dials are accepted they converge on the connection the lower endpoint id started.

  4. Hellos

    The home node has no consent gate and speaks first. The desktop dialed a stranger, so its gate holds its own hello until the home node's arrives. A home node without a notice, or with one the person accepted, means proceed; any other notice ends the link quietly and is shown to the person first. A route on trial counts among the community's routes, so the desktop names c/garden in the clear. The home node finds it either named or among the salted hashes.

  5. Sync and keep

    Range reconciliation as in (b). The trial route led to a node that delivered valid records, so the desktop's remember_member moves it into state.learned[c] and drops it from trial. The home node remembers nothing about the desktop: a desktop that isn't a public node says unlisted.

When beacons stay off

hoi-node --no-lan or --vpn-only, and the desktop in "Only through my VPN", send and hear nothing: a beacon would go out on the home network. Private communities never beacon.

(f) Pairing and linking a new device

Mira's phone has no key. Her desktop serves her devices as a home node and shows a QR code. Linking happens in two parts: pairing gives the phone a credential with the home node, and linking has a device that holds her root key bless a device key for the phone. scripts/e2e-rtc.mjs runs this with a hoi-node home and a desktop browser holding the key. Keys and delegations are on Keys & identity.

Pairing

lanes: Phone | Home node H Home node H: serving: serve_token (18 random bytes), link_key (32 bytes) Phone: scans …#/pair?code=: HOP\x01 {u, t, w, n} Phone: pair: state.home = {url, token, rtc, proven: false} -- Connect: WebSocket first, then WebRTC (mode c) -- Phone -> Home node H: WebRTC to rtc:<fp>@192.168.1.5:7844, ufrag h1c… Home node H: a client: says nothing yet Phone -> Home node H: hello {token: pairing token, c: [all], hints, name} Home node H: token matches: new credential; new pairing token Home node H --> Phone: hello {token: credential, pt, lk, serves: true, name} Home node H --> Phone: bind {s} Phone: keeps credential; the old link is spent Home node H -> Phone @mint: rng and recs for every shared community
  1. The home node serves

    set_serving(url) makes serve_token (18 random bytes, base64url) and link_key (32 bytes). The pairing link packs {v: 1, u, t, w, n?}: the WebSocket address (ws:// only to this machine, otherwise wss://), the token, up to 4 WebRTC routes and the node's name. It is deflated and masked under HOP\x01, at most 4096 bytes. A phone on the same network can use the WebRTC routes without any certificate.

  2. Pair

    previewPair shows where the link really points (device, network or internet), whatever name it gives. pair(link) stores state.home = {url, token, name, rtc, spent: none, next: none, link_key: none, proven: false}. The app then takes the token out of the address bar and history.

  3. Connect

    The worker tries the WebSocket first, with 5 s to open; on a phone it skips a loopback address when the link has WebRTC routes. Then it tries each WebRTC route group with ufrag mode c, which the node maps to a paired-device session. Failures back off 1 s, doubling to 60 s.

  4. The device speaks first

    Its hello carries token (the pairing token), every public community it is in, in the clear, its hints (routes per community), its name and its features. To its home node a device sends no salt.

  5. Admit

    The home node compares the token, in constant time, against the digests of every paired device's credential ("hoi 2026 pairing credential v1"), then against its pairing token. A match on the pairing token issues a credential of 32 random bytes and replaces the pairing token: the link pairs one device, so one left in a screenshot pairs nobody else. Stored on H: the credential's digest in state.paired (at most 32 devices; the least recently seen goes first) and the new serve_token. A wrong token ends the link with no reply.

  6. H joins and answers

    H joins every public community the phone named that it doesn't hold (up to 256, pinned) and keeps the phone's hints. Its hello to the phone carries token (the new credential), pt (the next pairing token, so the phone can show the next device's link), lk (the link key), serves: true and its name. H also sends a fresh hello to its other devices so they show the new link. On WebRTC, bind follows.

  7. The phone keeps its secrets

    take_home_secrets stores the digest of the spent link ("hoi 2026 spent pairing link v1"), the credential as its token from now on, next and link_key. The home node's hints wait until it delivered valid records (proven): a pairing link could have come from anyone.

Linking: four digits

lanes: Phone | Home node H | Mira's desktop browser Phone -> Home node H: link {m, b: seal(req {code, c: commit(nonce)})} Home node H -> Mira's desktop browser: the same link, unread Mira's desktop browser -> Home node H: link seal(chk {device, n: 16 bytes}) Home node H -> Phone: the same link Phone: digits from (device key, its nonce, the 16 bytes): shows 4 digits Phone -> Home node H: link seal(rev {device, n: nonce, to}) Home node H -> Mira's desktop browser: the same link Mira's desktop browser: commitment checks: shows the same 4 digits Mira's desktop browser: Mira says yes Mira's desktop browser -> Home node H: link seal(ok {code: approval}) Home node H -> Phone: the same link Phone: link_complete: signs as Mira from now on
  1. Ask

    link_home(label) works only on a device with no key that has a home node. It makes a request code (hoi:link:…, naming a pending device key and a label) and a 32-byte nonce. It sends link {m, b} on every link that can carry it. m is the first 16 bytes of derive_key("hoi 2026 link mailbox v1", link key), and b is {t: "req", code, c} sealed under the link key, where c commits to the nonce.

  2. Pass on

    The home node passes a link from one of its devices to all its other devices, unread. It holds the link key itself, so the envelope doesn't hide linking metadata from it. Signed consent and the root's blessing are what establish authority.

  3. Challenge

    A device with Mira's root key answers chk {device, n} with 16 random bytes of its own; hoi-node never answers, it has no screen. At most 4 asks are kept, each for 600 s; digits on screen are never pushed out by a new ask.

  4. Reveal

    The phone takes at most 3 challenges, one per root device. For each it shows four digits: derive_key("hoi 2026 link check v1", device ‖ nonce ‖ n), first 4 bytes as a little-endian number, mod 10,000. Then it sends rev {device, n: nonce, to: n}.

  5. Compare

    The root device checks the revealed nonce against the commitment, works out the same digits and shows them. Neither side can steer the result.

  6. Approve

    On yes, ok {code} carries the same approval the manual codes carry (with at most 64 community geneses, 256 KiB). On no, no {device} clears the phone's request. The phone stores its blessed device key and delegation; private community geneses and MLS keys are left out of ordinary linking.

Link limits

12 link messages a minute from a device (its own home node isn't counted). A sealed payload is at most 512 KiB. A request reconnecting gets the same challenge again, so it shows the same digits.

(g) Two browsers get a direct link

Mira and Kim both turned on Direct links with members' browsers, and both are linked to N over WebRTC in c/balcony. N introduces them; their browsers then talk to each other without N. scripts/e2e-direct.mjs stops N afterwards and shows Mira's next post still reaching Kim.

lanes: Mira's browser | Public node N | Kim's browser Public node N --> Mira's browser: here {c, y: handle M, h: [handle K]} Public node N --> Kim's browser: here {c, y: handle K, h: [handle M]} Mira's browser: M < K, so Mira offers; gathers ICE with N as STUN (≤ 3 s) Mira's browser -> Public node N: sig {p: K, d: key ‖ offer} Public node N -> Kim's browser: sig {p: M, d: key ‖ offer} Kim's browser -> Public node N: sig {p: M, d: key ‖ answer} Public node N -> Mira's browser: sig {p: K, d: key ‖ answer} Mira's browser .. Kim's browser: data channel opens (within 15 s) Mira's browser -> Kim's browser: hello (hashed communities), then rng Kim's browser => Mira's browser @coral: recs
  1. Features

    A browser with Direct links on says direct. A native node whose WebRTC listener runs, while it accepts members, says signal and answers plain STUN on its WebRTC port: at most 20 answers per source a minute and 6000 in all, each at most 52 bytes.

  2. Handles

    N gives each direct link a random 16-byte handle. To each it sends, per shared non-private community, here {c, y: its handle, h: other handles}, at most 16, sorted, and only when the list changed. It refreshes after each hello and at every sweep.

  3. Who offers

    Of two handles, the lower offers. The core hands the page Offer {via, to, stun} with up to 4 stun: addresses: the routes the browser dialed N by. Nothing else is ever contacted. A browser keeps at most 4 direct links open and tried together, and tries the same pair again only after 600 s.

  4. Offer and answer

    The page gathers candidates for up to 3 s, then sends one description each way, with no trickling. It travels as sig {p: handle, d}, where d is a 16-byte random key for this run of the app followed by the JSON {type, sdp}, at most 8 KiB. N passes a sig only between two links that said direct and share a community, at most 30 a minute from each, naming the sender by its handle.

  5. Open

    The data channel (negotiated id 0, ordered) must open within 15 s. Each browser then treats the other as a peer: net_connect("direct-<id>"), a hello naming communities only hashed, range sync, live recs. Every record is checked as from anyone. If two links reach the same browser, both sides keep the one ranked lowest by the offering side's key and the two handles, and close the other.

Why it is off at first

Two browsers on a direct link learn each other's IP addresses. N sees who talks to whom, by handle, as it sees their links anyway. No direct links are made for private communities.

(h) Joining a private community

Private communities are MLS groups, and their members' records never travel in plain sync (MLS internals are on Private communities). At the level of messages, joining takes one hand-over from the newcomer and is delivered back through holders and, where configured, an encrypted relay.

lanes: Newcomer | Committer | Holders | Encrypted relay Newcomer: hoi:private-request:… {package, records, pickup {key, holders ≤ 4}} Newcomer .. Committer: the request is handed over out of band Committer: private_invite: commit, Welcome, Bootstrap Committer -> Encrypted relay: PUT /v2/rooms/<old room>/objects/<id> (the commit) Committer -> Encrypted relay: PUT /v2/rooms/<new room>/objects/<id> (Bootstrap) Committer -> Holders: piece put at pickup slot i (sealed to the newcomer's key) Newcomer -> Holders: piece get slot 0 of each holder, 5 s to 120 s apart Holders --> Newcomer: the sealed invitation Newcomer: private_join: Welcome processed, in the group Newcomer -> Encrypted relay: GET /v2/rooms/<room>/objects?after=0 (signed read) Encrypted relay --> Newcomer: object list; then each object by id
  1. Request

    private_join_request() builds an MLS KeyPackage, the newcomer's identity records, a one-time X25519 pickup key, and up to 4 holders its app reaches, in places of their own. The result is hoi:private-request:<base64url CBOR>. Stored: a pending request, reused for 7 days. The person hands it to a member.

  2. Invite

    An owner's or moderator's device runs private_invite. In a group whose membership follows its records, an admit ledger entry goes first. Groups hold at most 128 members. The commit is sealed for the room of the epoch it leaves; the Welcome and a Bootstrap payload (identity records, the genesis, role proof) belong to the new epoch. The invitation is hoi:private:<base64url {v: 2, welcome, bootstrap}>.

  3. Pickup

    The invitation is padded to a multiple of 4096 bytes and sealed to the newcomer's pickup key, at most 1 MiB. The committer stores it on each holder the request named at slot BLAKE3_keyed(derive_key("hoi invitation pickup v1", key), u32(i)), with piece put through its forwarders. A holder never overwrites, so a taken slot moves the writer to the next (8 slots, kept 7 days). Anyone who saw the request can compute the slots, but only the newcomer's key opens what is there. See Scattered delivery.

  4. Look

    The newcomer's app looks at slot 0 of each holder, first every 5 s and more slowly up to every 120 s, and joins as soon as one opens. The member may also hand the invitation back directly.

  5. Join

    private_join(invitation) processes the Welcome and reads the Bootstrap records. Stored: the MLS group state (client-held), the community's records from the Bootstrap.

  6. Read the room

    From now on objects are sealed for the current epoch's room. Each commit moves the group to a new room address, derived from that epoch's secret. With an encrypted relay, the app lists GET {relay}/v2/rooms/{room}/objects?after={cursor} (at most 64 per page, 64 pages), signs each read (x-hoi-read-time, x-hoi-read-nonce, x-hoi-read-signature), fetches objects by id (4096 bytes to 1 MiB, SHA-256 equal to the id) and uploads its own with PUT plus x-hoi-expires and x-hoi-signature. Groups without a relay keep the same objects in mailboxes on holders. See Mailboxes & encrypted relays.

Relay limits

Each request times out after 15 s; a pass catches up at most 8 epochs and downloads at most 64 MiB. The app keeps objects for 30 days; the relay protocol allows at most 31. A signed read is valid for 300 s. In an app built with no relay URL (the published one), the relay path stays idle; groups whose objects live in mailboxes sync without it.
