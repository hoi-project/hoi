Registry

A registry maps public names to community keys inside its own namespace, keeps every name it retained in a signed append-only log, and lists public nodes that announced themselves. It is optional: the published app uses none. Three implementations speak one API on one database shape. This page documents every endpoint and field, the log's bytes and hashes, and exactly how a client checks what a registry tells it.

What a registry is, and is not

A registry is a naming and discovery service. It reserves a public name such as c/hiking for one community key, keeps the owner's signed proof of that, says which protocol and index edition the community was published for, and points apps at public nodes that may carry it. It serves no HTML, app assets or user content: no posts, messages, profiles, owners or membership lists, and no account system. Browsing, signature checking, name pinning and peer selection happen in the client.

It is never an authorization service or the community's identity. Its operator can omit an entry or stop the service; it cannot change the community key, sign the community's records or disable an existing invite. A signature proves the community key approved a name, not a real-world identity or who registered first. A registry entry alone cannot supply a community either: at least one compatible node must hold its records and be reachable. See Discovery for how apps find communities without one.

Each registry is its own namespace

Names are unique within one registry while it runs. Independently operated registries can reserve the same name for different keys; when none is reachable, two communities may carry the same name under different keys, and the apps show both keys without merging them. A name is not a global identity. Compatibility filtering never releases an old name for somebody else.

Three implementations

All three answer the same requests with the same status codes, headers and bodies, and keep the same SQLite tables, so a database file moves between the first two by copying it. One conformance suite runs against each (Conformance).

Names, keys and signed statements

Public names

A public name is 1 to 32 ASCII letters, digits, ., _ or -, starting with a letter or digit. It is trimmed and lowercased before anything else (normalizeName, community_registration_name), so Hiking and hiking are one name. Local display names can still use Unicode and spaces without making a registry claim. The app accepts the familiar c/name spelling in search and strips the c/.

Strong keys

Community keys and endpoint keys are 32-byte Ed25519 public keys written as 64 lowercase hex characters. keyIsStrong (key_is_strong in Rust) refuses a key that would verify forged signatures: one of libsodium's seven small-order points (the sign bit masked off), a non-canonical encoding (y ≥ p, p = 2²⁵⁵ − 19), or bytes that are no valid point. Node's verifier accepts small-order points, so the registry refuses them itself, like the Rust core. Signatures are 128 lowercase hex characters (64 bytes).

The three statements

Each claim is an Ed25519 signature over exact UTF-8 bytes: lines joined by \n, no final newline. The name must be canonical first.

export function registrationStatement(name, community) {
  return `hoi community name v1\n${name}\n${community}`;
}

export function publicationStatement(name, community, protocolVersion, indexVersion) {
  return `hoi community index v2\n${name}\n${community}\n${protocolVersion}\n${indexVersion}`;
}

export function announcementStatement(registry, endpoint, issuedAt, routes, communities) {
  return `hoi public node v2\n${registry}\n${endpoint}\n${issuedAt}\n${routes.join(',')}\n${communities.join(',')}`;
}

The core creates the community's proofs at the moment it creates the community and then discards the community's signing key; only the public proofs are kept, so a reservation can be retried after an outage from the device that created it. Older communities have no proof and stay usable by invite. A key file carries up to 64 proofs of each kind, so a restored device can still claim its names (Keys & identity).

The shared vector

core/vectors/community-registration.json pins the v1 claim: the Ed25519 seed 2a…2a (32 bytes of 0x2a), its public key 197f6b23…368d61, the name garden_1.v2-test, the exact statement and the signature 028a8eb3…347900. The Rust core, hoi-node's registry and the JavaScript conformance suite accept it without translation and refuse it once the name changes. Its siblings community-publication.json (the same key, protocol 0.3, index edition 1) and node-announcement.json pin the other two statements (Test vectors).

GET and PUT /v1/communities

GET /v2/nodes

?community=<64 hex> and nothing else (400 Ask for the public nodes carrying one community key.). The answer is {publicNodes}: the operator's configured routes, then routes of announced nodes that list that key, then the other announced nodes, each group one route per node per round, at most 16. For a withheld community the answer is the general order, naming nobody as its carrier. Any app may read this, wherever it is served: as a tracker, the registry's list of carriers is public.

Uncertain answers

Retry the same signed claim after a timeout. Retrying an identical claim is safe and answers 200; an uncertain response must never lead to creating a replacement community key. The app turns a failed request into "availability is unknown", never into "the name is free".

Origins, CORS and headers

The operator lists exact browser origins (an environment setting, or --registry-origin): an http(s) origin with no path or trailing slash, or the desktop's tauri://localhost. The opaque origin null is always refused. A request without Origin is not a browser and passes; the carrier and scripts send none.

  • A request whose Origin is not allowed answers 403 origin-denied and changes nothing, except a GET of /v2/nodes or a log path: those are public, answered with Access-Control-Allow-Origin: *.
  • An allowed origin is echoed in Access-Control-Allow-Origin. The Worker also treats its own origin as allowed.
  • A preflight (OPTIONS) answers 204 with Access-Control-Allow-Methods (GET or GET, PUT) and Access-Control-Allow-Headers: Content-Type, or 405 if the requested method is not one of them. Preflights are not counted against any budget.
  • No cookies or credentials are required, set or read.

Every answer carries Content-Type: application/json; charset=utf-8, Cache-Control: no-store, X-Content-Type-Options: nosniff, Referrer-Policy: no-referrer, Strict-Transport-Security: max-age=31536000; includeSubDomains and Vary: Origin.

Reservations and publications

The database holds permanent name → community pairs under two uniqueness constraints (a name has one key, a key has one name), separate community → {protocolVersion, indexVersion} index metadata, and the owner-signed proofs. SQLite arbitrates both constraints inside one BEGIN IMMEDIATE transaction, including across processes.

  1. Withheld?

    A claim touching a withheld name or key, or a row whose name or key is withheld, answers 409 withheld and learns nothing about the row.

  2. Reserve

    INSERT … ON CONFLICT DO NOTHING RETURNING. A new row, or the same mapping again, is 200. The name with another key is 409 name-taken with the existing mapping, so the app can offer that community. The key with another name is 409 community-registered.

  3. Index metadata (v2)

    If the key already has metadata with another protocol or edition: 409 index-version-conflict, and nothing changes. Metadata is immutable; a legacy reservation gains it only with a valid v2 proof for the same name and key.

  4. Proof

    Insert the signature as claim version 1 or 2 (ON CONFLICT DO NOTHING: the first retained proof of each version stays).

  5. Log

    Append the retained claim to the log of names in the same transaction, once (below).

Old reservations are never silently assigned the current protocol, and compatibility filtering never frees a name. Duplicate offline communities stay different communities and are never merged: a creation made without reaching the registry stays provisional, and only a successful reservation makes its name registered. Checking availability reserves nothing.

Node announcements

Public nodes started with --index URL (and trackers, see hoi-node) announce their own routes and the keys of the open communities they carry. This is the only table with a time in it. Routes are addresses a node deliberately advertises; addresses and public keys can still relate to people.

Route rules are the same in both languages (validateRoute, validate_route; see hoi-node for the address table): loopback, private, link-local, carrier-grade NAT, unspecified and multicast ranges are refused, the documentation ranges are allowed so the shared vectors work.

Admission, in order

  1. Announcements off

    403 announcements-disabled: This registry lists only operator-configured public nodes. Then a query is 400, a non-JSON type 415, an oversized body 413.

  2. Which origin

    The configured URL's origin, or, with none, the loopback address the connection reached (read from the socket, never a header): http://127.0.0.1:P or http://[::1]:P, and http://localhost:P. With no origin to answer to: 403 announcements-disabled. The Worker, without the public URL, answers to the origin requests reach it at.

  3. For another registry

    A body whose registry is some other origin: 400 wrong-registry.

  4. Verify

    Exact keys, strong endpoint, fresh issuedAt, valid routes and communities, signature: else 400 invalid-announcement.

  5. Allowlist

    With announcers configured (at most 1024), an endpoint not among them: 403 announcer-not-allowed. Verification still comes first.

  6. Refused node

    An endpoint the operator dropped: 403 announcer-refused; nothing is stored.

Storage: 30 minutes, 64 nodes

In one transaction the registry deletes announcements whose issuedAt is older than 30 minutes (NODE_TTL_SECONDS = 1800): expired rows are pruned when new announcements arrive. It then upserts the node: a newer announcement replaces the node's routes and communities; an older one changes nothing. first_seen stays with the node's first live announcement. Finally it keeps the first 64 nodes by first_seen, then issued_at, then endpoint (MAX_ANNOUNCED_NODES): when the list is full, the nodes that were there first stay and a newcomer is not kept, so a flood of fresh keys cannot push out the carriers people rely on.

The answer is 200 with what discovery now holds for that node, {endpoint, routes, communities, issuedAt}, or the announcement with retained: false when it was not kept. A node unheard of for 30 minutes drops out and frees its place. There is no withdrawal API: stop announcing and the listing lapses. Carriers re-announce every five minutes.

Discovery order

selectPublicNodes(configured, live, community): the operator's configured routes always come first (nobody can announce them out of the list); then nodes that announced carrying community; then the other live nodes (newest first). Each group is taken one route per node per round, so a node announcing eight routes cannot crowd out the rest. Duplicates are dropped and the list stops at 16 (MAX_PUBLIC_NODES), which is also the most a client accepts. In allowlist mode only allowed nodes are live; refused nodes never are.

The log of names

Every registry keeps a public log of each owner-signed claim it retained, in the order it retained them: an append-only Merkle tree in the shape of RFC 6962, whose head the registry signs with its own Ed25519 log key. A registry can still choose what it answers, but it cannot tell two people two keys for one name without logging both, where anyone who reads the log sees it. Entries never change or disappear; a withheld listing's entry is served as its leaf alone.

Entries

An entry is UTF-8 text with seven lines. For a v1 reservation the protocol and index lines are empty.

"hoi name log v1" | 15 B | mute | 3 | fixed first line \n | 1 B | mute | 1 | version | 1 B | sun | 1 | 1 or 2 \n | 1 B | mute | 1 | name | 1–32 B | coral | 3 | canonical \n | 1 B | mute | 1 | community | 64 B | mint | 2 | hex key \n | 1 B | mute | 1 | protocolVersion | 0–64 B | sky | 2 | empty for v1 \n | 1 B | mute | 1 | indexVersion | decimal | sky | 2 | empty for v1 \n | 1 B | mute | 1 | signature | 128 B | lilac | 4 | the retained proof, hex 
export function logEntryText({ name, community, proof }) {
  const v2 = proof.version === 2;
  return `hoi name log v1\n${proof.version}\n${name}\n${community}\n${v2 ? proof.protocolVersion : ''}\n${v2 ? proof.indexVersion : ''}\n${proof.signature}`;
}

The name_log table assigns each entry the next index (SELECT COUNT(*)) and refuses a duplicate text (entry … UNIQUE, inserted WHERE NOT EXISTS). The entry is built from the proof as stored, so an idempotent retry adds nothing. A community that first reserved its name with v1 and then published with v2 has two entries; a refused claim has none.

Leaves, nodes and the tree

0x00 | 1 B | mute | 1 | leaf prefix entry text | n B | sun | 5 | UTF-8 leaf | 32 B | coral | 3 | SHA-256 of the two 0x01 | 1 B | mute | 1 | node prefix left | 32 B | sky | 3 | hash of the left subtree right | 32 B | sky | 3 | hash of the right subtree node | 32 B | coral | 3 | SHA-256 of the three

The root of n leaves, MTH(D[n]): the empty tree is SHA-256("") (e3b0c442…b855); one leaf is its own root; otherwise split at k, the largest power of two below n, and hash 0x01 ‖ MTH(D[0:k]) ‖ MTH(D[k:n]). An audit path PATH(m, D[n]) and a consistency proof PROOF(m, D[n]) follow RFC 6962 exactly; the server keeps every leaf hash in memory, caught up from the table on each request, since entries never change.

The signed head

"hoi name log head v1" | 20 B | mute | 3 | fixed first line \n | 1 B | mute | 1 | logKey | 64 B | lilac | 3 | hex public key \n | 1 B | mute | 1 | size | decimal | sun | 2 | entries in the tree \n | 1 B | mute | 1 | root | 64 B | coral | 3 | hex MTH \n | 1 B | mute | 1 | timestamp | decimal | peach | 3 | Unix seconds when signed

GET /v2/log/head signs a fresh head on every request: {logKey, size, root, timestamp, signature}. The log key's 32-byte secret is made on first use (log_secret, one row, id = 1) and kept in the database with the names it signs for, so the key moves with the file: hoi-node and the Node service opening the same file produce the same signed head. The key is the registry's own; it never signs names, only heads.

The vector

core/vectors/name-log.json holds seven entry texts (the v1 and v2 claims for garden_1.v2-test, then v1 claims name-2 to name-6), their leaves, the root of every prefix from 0 to 7 entries, seven audit paths and nine consistency proofs, one entry with its fields and text, and a head signed with the fixed secret 42…42 at timestamp 1793800000: log key 2152f8d1…81db12, size 7, root 4e2fe945…0192db. hoi-node's log.rs and the JavaScript log.mjs are both held to it.

How clients verify

Authority comes from the community key, not from a successful HTTPS response. registry/public/verify.js and registry/public/log.js are shared by the app and the conformance suite and use WebCrypto only. apps/web/src/lib/registry.ts puts them together.

Reading an answer

readRegistryJson refuses a body over 128 KiB (by Content-Length or while streaming) and decodes UTF-8 strictly. Requests go out with credentials: 'omit', referrerPolicy: 'no-referrer', cache: 'no-store', redirect: 'error' and a 10 s timeout. Metadata must say apiVersion 2 and schemaVersion 3 and list at most 16 routes of at most 128 characters; /v2/nodes the same limits.

Checking an entry

verifyRegistryEntry(value, release): the name must match ^[a-z0-9][a-z0-9._-]{0,31}$, the key 64 lowercase hex, the proof version 1 or 2 with exactly its keys (signature, version or indexVersion, protocolVersion, signature, version). It rebuilds the statement and verifies the Ed25519 signature against the community key. With a release, the listing's versions must equal the proof's (or be null for v1), its flags must be booleans, and the client recomputes compatible itself from the authenticated versions and its own supportedProtocols; indexed is true only if both agree. Anything wrong: The directory entry could not be verified. Use a trusted community invite.

Pins

The device keeps a trust store in IndexedDB, database hoi-registry-trust-v1 version 2, scoped to the registry's URL (absolute, without a trailing slash):

One read-write transaction compares and saves a whole verified result set; IndexedDB serializes them across tabs. A 404 for a pinned name stops too (This previously verified public name is missing from the directory.). Blocked, full, corrupt or unavailable storage stops discovery rather than falling back to memory; there is no bypass or reset button. Clearing browser data removes the pins.

Checking the log

Exact lookups and writes (lookupIndexed, lookup, publish, reserve, and the entry a 409 conflict returns) are pinned and then checked against the log. Directory pages are not, one request each; a name is checked when it is opened.

  1. Head

    verifiedLogHead: exactly the five keys, hex shapes, safe integers, and a valid Ed25519 signature by the key it names over the head statement.

  2. Against the saved head

    A different log key, a smaller size, or the same size with another root: This registry's public log no longer matches what this device saw before.

  3. Consistency

    If the head grew from a saved size above 0, GET /v2/log/consistency?first=OLD&second=NEW and verifyConsistency (RFC 9162 §2.1.4.2; sizes up to 2³⁰, paths up to 64 hashes).

  4. Inclusion

    The leaf of logEntryText(entry), then GET /v2/log/proof?leaf=…&size=NEW and verifyInclusion (RFC 9162 §2.1.3.2) against the head's root. A missing or wrong path: This registry did not show this name in its public log.

  5. Keep

    advance(head).

What pins prove

Pins detect changes after the first lookup on this device. They are not an independent witness of who first registered a name, and a first lookup trusts the registry's answer as far as the signature and the log can show.

Mirrors and audits

A registry is one participant among others. hoi-node --registry-mirror URL makes a registry hold another's names when that one stops, and audit its log while it runs. Every five minutes (first after 5 s) it:

  1. Checks the other's head

    It must be signed by the key it names, with the same key and no smaller size than last time.

  2. Reads every new entry

    256 per request, up to 10,240 per pass; each text must hash to its leaf and hold a claim a community key signed, exactly as that claim logs; no name may move to another key and no key take a second name (kept in witnessed_names). Every leaf is kept (witnessed_leaves).

  3. Recomputes the root

    Once all leaves are read, it must equal the head's root; the head is saved in witnessed.

  4. Imports

    Pages through /v2/communities?prefix= (50 a page, 40 pages), keeps the listings whose leaf is in the audited log, re-verifies each v2 proof, and publishes it here when the name and key are both still free. A name already taken here stays with the local first claim: both communities exist under their distinct keys, and the app shows both.

A registry whose log changed its key, shrank, does not match its head, or moved a name is no longer mirrored, and the node says why once; hoi-node admin registry unwitness URL starts the audit over. Legacy v1 names without a versioned proof are not mirrored, nothing is ever taken over, and announced nodes are not mirrored: a public node announces to each registry it is given.

Release metadata and compatibility

release.json at the repository root defines protocol compatibility and the index edition; every surface is built from it. The registry validates it at startup (an invalid one stops the service before it listens) and, on the Node service and hoi-node, reads it again for each metadata and directory request, so an updated notice or compatibility filter takes effect without a rebuild. A replacement file over 16 KiB, or one that stops validating, fails closed with 503. Changing it does not upgrade old records or installed clients.

Limits and rate budgets

Three global, in-memory, fixed one-minute windows: reads (every GET, logs and metadata included), name claims (PUT /v1 or /v2/communities) and announcements (PUT /v2/nodes). Each has its own counter, so a flood of reads cannot stop names being claimed or carriers announcing. No client identifier is retained, which also means the budgets give no fairness under attack: per-address limits belong at the edge, where the provider already sees addresses (a Cloudflare WAF rule, or nginx limit_req_zone $binary_remote_addr).

The database

Eight STRICT tables, the same in all three implementations. Nothing in them is a post, profile, owner or client address, and there is no access log.

The file's version is PRAGMA user_version = 5 (DATABASE_VERSION): 4 added the operator's lists, 5 the log. A registry refuses a newer file (This registry database requires a newer registry server.) rather than serve what its operator withheld. Schema 0–2 files from older Node services are upgraded in place without inventing proofs or versions: legacy rows stay reserved, unsigned rows are excluded from current discovery, and their owners retry the signed claim. A schema-3 file gains public_nodes.first_seen. The Node service and hoi-node open it with journal_mode=WAL, synchronous=FULL, busy_timeout=5000, foreign_keys=ON. A Durable Object has no user_version; the Worker keeps its version in a registry_schema table and accepts versions 2 to 5.

One file per namespace

Run a single database for a public namespace: independent copies cannot share a uniqueness guarantee. Several processes may share one local SQLite file; do not put it on an unsupported network file system or replicate it with last-write-wins storage. Back it up with SQLite's backup tooling, including committed WAL contents; copying the main file alone while the service runs is not a safe backup. Do not put it under a static website directory.

unhide and allow-node undo them. admin.mjs takes --db FILE (default the database file, then hoi-registry.db), refuses to create a missing file (a typo must not make an empty namespace next to the real one), and on any error prints the reason and exits 2. Both shell tools work while the registry runs, which reads the database on every request. A Durable Object's database is reachable from no shell, so the Worker's lists are configuration: comma-separated names, keys or endpoint keys, applied when the new version starts (syncOperatorLists replaces both tables), so removing an entry lifts it.

  • Withholding keeps the reservation: nobody else can claim the name or key (409 withheld), lookups by name or key answer 404 withheld without the mapping, prefix lists and mirrors leave it out, /v2/nodes?community= names no carrier for it, and its log entry is served as a leaf only.
  • Dropping a node deletes its announcement and refuses its next ones (403 announcer-refused).
  • Neither touches the community: its key, records and invites stay valid wherever else they are held. Carriers keep what they carry until their own operators act.
  • list shows withheld entries (what they cover, since when), refused nodes, and nodes announced now with route and community counts, to build an allowlist from.

A database backup taken before a change still holds the listing as served; a restored backup serves it again until the step is repeated.

Connecting the apps

Every build defaults to no registry, and the project's own deployment pins it empty. A copy of the app uses one only when built with the registry address (HTTPS, or HTTP on loopback; no credentials, query or fragment); the web build then allows that exact origin in its content security policy, and the desktop scripts add it to the native policy. All builds sharing a namespace must use the same registry, and its the allowed browser origins must list their origins. The app sends the public name, community key, versions and the public proof; never cookies, tokens, profile names, posts or member routes. Builds without a registry keep names local and unregistered.
