Media

Pictures, sound and video travel apart from the records that mention them, by BLAKE3 hash. The sender's device strips everything that isn't the picture or the sound; every receiver checks the bytes are exactly what sanitize would produce, structure tiled to the last byte, nothing hidden. Pictures get a perceptual fingerprint, so a device that refuses one image refuses its altered copies too.

Two functions: sanitize and check

media.rs has one walker per format with a fix flag. With fix set it builds clean bytes; without, it refuses anything the clean version wouldn't have.

sanitize(bytes)on the sender
Sniffs the type from the bytes (never from a file name or a claim), strips everything that isn't the picture or the sound (EXIF with GPS positions, XMP, comments, thumbnails, embedded color profiles, titles, tags, attachments, trailing data such as the video of a "motion photo" after a JPEG), then runs check on the result. Its output is what gets hashed and shared.
check(mime, bytes)on every receiver
Accepts only what sanitize would produce: the claimed type's size cap, bytes that sniff as that type, a known container whose structure tiles the file exactly, only allow-listed chunks and boxes, no metadata, nothing after the end marker, sane dimensions. It doesn't decode pixels or samples; browsers and OS decoders do that, sandboxed.

That kills polyglots (a file that is also HTML, a ZIP or a script) and metadata leaks on arrival. A PNG with <html><script>… appended fails check ("png has data after its end"); sanitize cuts the tail off.

pub fn check(mime: &str, b: &[u8]) -> R<Info> {
    let cap = max_size(mime).ok_or_else(|| format!("{mime} is not a media type hoi carries"))?;
    if b.len() as u64 > cap {
        return err("media is too big");
    }
    if sniff(b) != Some(mime_static(mime)) {
        return err("media bytes don't match their type");
    }
    let info = match mime {
        PNG => png(b, false)?.1,
        JPEG => jpeg(b, false)?.1,
        GIF => gif(b, false)?.1,
        WEBP => webp(b, false)?.1,
        OGG => ogg(b, false)?.1,
        MP4 => mp4(b, false)?.1,
        WEBM => webm(b, false)?.1,
        _ => unreachable!("max_size knows the list"),
    };
    image_dims(&info)?;
    Ok(info)
}

PNG

After the 8-byte signature, chunks of length (u32 BE) ‖ type (4) ‖ data ‖ CRC-32, where the CRC (IEEE) covers type and data and must be right.

  • The first chunk is IHDR of exactly 13 bytes; a second IHDR is refused.
  • Bit depth and color type must be a valid pair: grayscale (0) at 1, 2, 4, 8 or 16 bits; palette (3) at 1, 2, 4 or 8; RGB (2), gray+alpha (4) and RGBA (6) at 8 or 16. Compression and filter method 0; interlace 0 or 1.
  • A 16-bit image may have at most MAX_PIXELS_16 pixels.
  • IDAT chunks must be consecutive ("png image data is split up"), and there must be at least one.
  • IEND is empty and ends the file: data after it fails check and is dropped by sanitize.
ChunksTreatment
IHDR, PLTE, IDAT, IEND, tRNS, gAMA, cHRM, sRGB, sBIT, bKGD, pHYs, acTL; and for APNG fcTL, fdATkept, copied as they are
any other ancillary chunk (lowercase first letter): tEXt, zTXt, iTXt, eXIf, iCCP, tIME…sanitize drops it; check: "png carries a … chunk"
an unknown critical chunk (uppercase first letter)refused by both: "png has an unknown critical chunk"

The vector core/vectors/media.json is a 1×1 PNG with a tEXt chunk holding a location: its input, the sanitized bytes with the chunk gone and everything else copied as is, and hash, BLAKE3 of the clean bytes, which is what a MediaRef names.

JPEG

A JPEG is walked marker by marker from FF D8. Fill bytes (FF before a marker) are allowed. Each segment's length must be at least 2 and fit. A second SOI, TEM (01) or a restart marker outside a scan is "a marker out of place". After each SOS the entropy-coded data runs until a marker that is neither a stuffed FF 00 nor a restart FF D0–FF D7. EOI (FF D9) ends the file: anything after it, such as the MP4 of a motion photo, fails check and is cut by sanitize. There must be a frame header.

The one piece of EXIF kept

Without its orientation a phone photo shows sideways, so sanitize reads the Orientation tag (0x0112, values 1–8) from the original EXIF, in either byte order, and, unless it is 1, writes one fixed APP1 segment of its own just before the first scan. check accepts an APP1 only if it is exactly this segment for a valid orientation, and only once.

/// The only EXIF a shared JPEG may carry: big-endian TIFF, one IFD0 entry, Orientation.
fn exif_orientation_segment(o: u16) -> Vec<u8> {
    let mut p = b"Exif\0\0MM\0\x2a\0\0\0\x08\0\x01".to_vec();
    p.extend_from_slice(&[0x01, 0x12, 0x00, 0x03, 0, 0, 0, 1]);
    p.extend_from_slice(&o.to_be_bytes());
    p.extend_from_slice(&[0, 0, 0, 0, 0, 0]);
    p
}

GIF

The header and logical screen descriptor (13 bytes; width and height little-endian at offsets 6 and 8) and the global color table if the flags say there is one. Then blocks until the trailer 3B; data after it fails check and is cut by sanitize.

  • Image descriptor (2C): kept, with its local color table and data sub-blocks; the LZW minimum code size must be 2–8. At most 2,000 frames; at least one.
  • Graphic control extension (21 F9): kept (frame timing and transparency).
  • Application extension (21 FF): kept only for NETSCAPE2.0 and ANIMEXTS1.0 (looping).
  • Every other extension (comments 21 FE, plain text, other applications such as XMP): dropped; check: "gif carries comments or other extensions".

WebP

The RIFF size field plus 8 must be the file's length exactly (sanitize may cut trailing bytes after it). Chunks of type ‖ length (u32 LE) ‖ data, padded to an even length, must fill the file exactly.

ChunkRule
VP8Xfirst, exactly 10 bytes; canvas width and height are 1 + 24-bit values. The ICC (0x20), EXIF (0x08) and XMP (0x04) flags are cleared by sanitize and refused by check ("webp says it carries metadata").
VP8 lossy frame: at least 10 bytes with the start code 9D 01 2A; 14-bit width and height
VP8Llossless frame: at least 5 bytes starting with 2F; 14-bit width − 1 and height − 1
ALPH, ANIM, ANMFkept (alpha, animation)
anything else (ICCP, EXIF, XMP , unknown)dropped; check: "webp carries metadata or an unknown chunk"

There must be an image (VP8 , VP8L or ANMF). sanitize rebuilds the RIFF container from the kept chunks.

Ogg Opus

Every page starts OggS with version 0 and carries a correct Ogg CRC-32 (polynomial 0x04C11DB7, computed with the checksum field zeroed). At most 100,000 pages.

  • One logical stream: every page has the first page's serial number, and page sequence numbers run 0, 1, 2… without gaps.
  • Only the first page has the beginning-of-stream flag; the last page has the end-of-stream flag.
  • Page 0 holds exactly the OpusHead packet: at least 19 bytes, version byte at most 15, at least one channel.
  • The OpusTags packet starts on page 1 and may span pages (continuation flag set), but must end exactly at a page end: tags never share a page with audio.

check accepts only clean tags: a vendor string of at most 64 printable ASCII bytes, zero user comments, nothing after them; otherwise "opus carries tags". sanitize replaces the tags packet with one of its own (vendor hoi, no comments) on a fresh page 1, renumbers the audio pages from 2 and recomputes every CRC. Artist, title, cover art and every other comment are gone.

MP4

Boxes of size (u32 BE) ‖ type; size 1 means a 64-bit size follows, size 0 means "to the end of the file" (only at the top level). Boxes must fit inside their parent and tile it exactly, nested at most 12 levels below the top, at most 200,000 boxes.

BoxesTreatment
top level: ftyp, moov, mdat, free, skip, wide, moof, mfra, sidx, stypallowed
containers walked into: moov, trak, mdia, minf, stbl, dinf, edts, mvex, moof, traf, mfratheir children are checked the same way
metadata at any level: udta, meta, uuidsanitize renames it free and zeroes its contents; check: "mp4 carries metadata"
any other top-level boxsanitize: renamed free and zeroed; check: "mp4 carries a … box"

Blanking in place keeps every size and offset where it was, so sample tables still point at the right bytes: the clean file is exactly as long as the original. The file must start with exactly one ftyp and have a moov and media (mdat or moof). Location, camera and the recording app live in udta and meta; they come out as zeros.

WebM

EBML elements: an id of 1–4 bytes and a size of 1–8 bytes; the "unknown size" value is refused, and children must tile their parent exactly (at most 500,000 per parent).

  • At the top level only the EBML header (first), one Segment, and Void. The header's DocType must be webm ("only webm, not other matroska files").
  • Inside the segment only SeekHead, Info, Tracks, Cluster, Cues, Void and CRC-32; Tags, Attachments, Chapters and anything else are refused by check ("webm carries metadata or attachments") and blanked by sanitize.
  • Inside Info: Title, DateUTC, MuxingApp, WritingApp and SegmentUUID (who made it, when, with what) are blanked or refused. Inside each TrackEntry: its Name.
  • There must be Tracks.

Blanking turns an element into a Void element (EC) of the same total length, filled with zeros, so the file keeps its length and every offset.

On the sender's device

  1. Fit (web app)

    A photo straight off a phone is often bigger than 2 MiB. The composer's fitImage (apps/web/src/lib/media.ts) re-encodes still JPEG, PNG and WebP files over 2 MiB or with a side over 2560 pixels in the browser's own decoder: JPEG stays JPEG, the rest becomes WebP (keeping transparency), trying 2560, 2048, 1600 and 1280 pixels at qualities 0.86 to 0.72 until it fits. Re-encoding drops everything that isn't the picture too. Animations, audio and video pass untouched.

  2. Sanitize and hash

    prepare_media in the core takes at most four files, runs media::sanitize on each ("That file won't do: …") and hashes the clean bytes with BLAKE3.

  3. Look

    Pictures and videos get a look. A picture this device can't decode is refused ("That picture can't be read here, so nobody else could check it either. Try saving it as JPEG or PNG."), and one that matches media blocked here is refused too. In the browser the look happens in a worker before the draft (the core then finds it by hash, or asks to attach the picture again).

  4. Reference and keep

    A MediaRef per item goes into the post; the bytes are kept locally, marked private until a public post that uses them is accepted.

  5. Standing

    check_standing refuses media from anyone below trusted before anything is stamped: "Images and other media unlock for trusted members: established, active, and well received."

How a post names its media

A post's media field is an array of MediaRef maps, omitted on the wire when empty. The bytes travel separately, by hash.

hashbytes32
BLAKE3 of the sanitized bytes.
mimetext
One of the seven types.
sizeu64
The exact length of the bytes, 1 to the type's cap.
w, hu32, optional
Width and height in pixels: required for images (1–16,384, product at most 16,777,216), forbidden for audio and video ("only images state dimensions").
alttext, optional
A description for people who can't see the picture: one line, at most 500 characters.

The content stage checks the references (media_refs): at most four, a known type, a size in range, no hash twice, dimensions as above, alt text as a line, and at most 24 MiB in total. These need no bytes, so a record with impossible media is refused before anyone fetches anything.

Fetching media

On the sync link, two messages move media (Sync & gossip): bwant { ids } asks for up to MAX_BWANT (32) hashes, and blob { id, data } carries one item, at most MAX_BLOB (16 MiB).

lanes: Device | Peer | Author's device -- The post arrives first -- Peer -> Device: recs [post with media refs] Device: the post passes the pipeline; its author may share media here -- Asking -- Device -> Peer: bwant {ids: [hash]} Peer: serves only bytes of visible posts in a community the device shares Peer: not here yet: owed to Device, up to 256 per peer Peer -> Author's device: bwant {ids: [hash]} (its own request) Author's device => Peer @peach: blob {id, data} Peer => Device @peach: blob {id, data} -- Checking -- Device: BLAKE3(data) = id, else the peer loses 5 points Device: check(mime), size and dimensions equal the ref, else the author takes a strike Device: look, then keep or refuse

Asking

request_missing_media runs after records arrive, when a peer says it shares a community, after media arrives, and on every sweep, if the person's auto_media setting is on (it is by default). It looks at the posts of the public communities this device joined that are forwardable (not held, author not blocked), and picks the hash attempted longest ago that isn't here, isn't refused, hasn't failed, and isn't private. It keeps one request outstanding at a time and asks again after MEDIA_RETRY (120 seconds), so one unavailable picture can't starve the rest and catch-up stays under the transport's byte budget. The request goes over iroh-blobs to one peer that serves it that way, if there is one, else as a bwant to every peer that said hello and shares the community.

Serving

on_bwant sends bytes only for hashes that a forwardable, non-private post uses in a community the asking peer shares, never private media. One answer holds at most 16 MiB in all; an older client that asks for 32 large blobs at once gets a prefix and asks again for the rest. A hash that isn't here yet (a home node relaying a post that just came from its author's device) is remembered as owed, up to 256 per peer, and sent as soon as the bytes arrive.

Checking what arrives

  1. The hash

    Bytes that don't hash to their id are the sender's fault: 5 points off its score, and a bye ("media that doesn't match its hash") once it falls to −20.

  2. Wanted at all

    Media that is already here, refused, or failed before is ignored; so is media no usable post here uses ("nobody here asked for it"), and media that isn't public.

  3. The checks

    media::check with the type the post states; the length must equal size, and for images the dimensions must equal w and h. Bytes that hash right but fail are the author's fault: the hash goes on the device's bad-media list, the post is held ("its media failed the checks"), and the author's key takes a content strike (weight 3).

  4. The look

    Pictures and videos are fingerprinted. If the look matches something this device refuses, the hash is refused for good and the bytes are never kept. A picture that passed the checks but can't be decoded counts like bad media: refused, struck, held.

  5. Room

    A device keeps at most MEDIA_CAP, 512 MiB, of media; beyond that new media isn't stored and can be fetched again later. Media no stored post uses any more is deleted on the next sweep.

let ok = hoi_validate::media::check(&mref.mime, &data)
    .ok()
    .is_some_and(|info| data.len() as u64 == mref.size && (!hoi_validate::media::is_image(&mref.mime) || (info.w == mref.w && info.h == mref.h)));
if !ok {
    self.state.bad_media.insert(id);
    self.mark_state();
    let now = self.now();
    self.offence(author, c, (post, made), Offence::Content, now);
    self.mark_changed(c);
    return true;
}

Between native nodes: iroh-blobs

A desktop app or hoi-node turns on iroh-blobs (set_blobs; other platforms can't) and says blobs in its hello's features. Its endpoint accepts two ALPNs: hoi/sync/1 and iroh-blobs' own. Instead of a bwant on the sync link, it fetches a picture or video from a peer that said blobs and is reached over QUIC, on a connection of its own. iroh-blobs verifies the bytes against the BLAKE3 hash as they stream, so a bad peer is caught at its first wrong chunk, and a large file never waits in front of records on the sync link. What arrives then goes through every check a blob message gets.

lanes: Fetching node | Core | Serving node Core -> Fetching node: take_blob_fetches [{peer, endpoint, hash, size}] Fetching node -> Serving node: QUIC connect, ALPN iroh-blobs Serving node: a sync link with this endpoint? else refused Fetching node -> Serving node: get {hash} Serving node: blob_to_serve: shared, pinned, public, else refused Serving node => Fetching node @sky: the blob, verified chunk by chunk Fetching node: refused unless the stream's size equals the post's size Fetching node -> Core: blob_fetched(peer, hash, bytes) Core: the same checks as a blob message
  • Who is served. A connection is taken only from an endpoint with a sync link here (blobs_link); each request only for media of a public, forwardable post in a community that peer shares and this node pins. Requests for many blobs, pushes and observing are refused.
  • The serve cache. Bytes are copied into an in-memory store just before they are sent; past SERVE_CACHE (64 MiB) the ones asked for longest ago leave first.
  • Limits. A fetch takes at most FETCH_SECS (60 seconds) from dialing to the last byte, and is never longer than the size the post states.
  • Falling back. When a fetch fails, the node asks the same peer with bwant and, for the rest of that link, takes that community's media from it that way.

Scattered and private media never go this way: private attachments travel inside the encrypted group (Private communities), and media of open communities kept in pieces travels as pieces (Scattered delivery).

Whose media a device fetches

A device asks for media only for posts that are forwardable here: the post is not held and its author isn't blocked by the community. Since a post with media from anyone below trusted standing is held ("media unlocks for trusted members"), devices fetch media only from trusted members' posts (and owners' and moderators'). Newcomers' and members' pictures are never downloaded, so they never land on anyone's disk. It asks any peer that shares the community; the hash, not the peer, vouches for the bytes.

A person can turn automatic media off (auto_media): then nothing is fetched, and other people's profile pictures aren't shown either.

Profile pictures and colors

A profile picture is a tiny JPEG signed into a profile record, one per community: { image: bytes, seq: u64 }. An empty image brings back the identicon drawn from the key. hoi_validate::avatar checks it at the content stage, so the pixels are bounded before anything stores, shows or fingerprints them:

pub fn avatar(image: &[u8]) -> Result<(), Reject> {
    if image.is_empty() {
        return Ok(());
    }
    if image.len() > hoi_types::MAX_AVATAR_BYTES {
        return Err(bad("profile picture exceeds 4 KiB"));
    }
    let info = media::check(media::JPEG, image).map_err(bad)?;
    if !matches!((info.w, info.h), (Some(w), Some(h)) if w == h && w > 0 && w <= hoi_types::MAX_AVATAR_SIDE) {
        return Err(bad("profile pictures must be square and at most 128 pixels"));
    }
    similar::examine(media::JPEG, image).map_err(|_| bad("profile picture cannot be decoded"))?;
    Ok(())
}

Making one in the web app

profile-picture.ts crops a square (zoom 1–4, offsets −1 to 1 on each axis), draws it on a white background, and encodes JPEG on a canvas: 128 pixels a side at qualities 0.85, 0.7, 0.55 and 0.4, then 96 and 80 pixels, until it fits in 4,096 bytes ("This picture cannot be made small enough. Try a simpler crop."). The core's set_avatar then sanitizes it (the canvas's JFIF segment goes), checks it, and refuses it if it matches media blocked on this device. Only bounded JPEG bytes from the core are ever rendered, as a data: URL, so no picture can be a remote address that tracks readers.

Where the picture goes

  • The choice is kept on the device with a revision: the larger of now × 1000, one more than any revision seen from this person, and one more than the last.
  • It is published into a community after the person's next post or comment there, as a profile record expiring with the community's retention, but only if the picture is empty or the person is trusted, an owner or a moderator there. Its seq is the larger of the revision and one more than the previous record's. The newest per person and community wins; older ones are held ("a newer profile is known").
  • A device shows someone's picture only for people who are visible, not blocked, not banned and trusted (or owners and moderators) in that community, and only with automatic media on. Pictures from private communities stay inside them.
  • Profile records count in their own rate window (2 an hour, 6 a day) and get the 8-bit stamp discount. Their kind is capped at 5 KiB encoded.

Identicon colors

A profile-color record { color, seq } picks the identicon's palette, independent of the picture: mint, sky, lilac, peach or sun, or empty for the color derived from the key. Values are palette names, never CSS or URLs. It is published the same way, with no standing needed, and has its own rate window and revisions.

Perceptual hashes

The BLAKE3 hash catches the same bytes; a perceptual fingerprint catches the same picture, re-encoded, resized, lightly cropped or brightened. hoi uses PDQ, Meta's open 256-bit perceptual hash, so fingerprints can be checked against public PDQ hash lists. similar.rs is a port of pdqhash 0.1.1 (Apache-2.0), itself a port of Meta's reference; where the two differ it follows the reference.

How a fingerprint is made

  1. Check, then decode

    Only pictures that passed media::check are decoded, with the format the type names (never a guess), the stated dimensions as hard limits and at most 96 MiB of decoder memory. Above MAX_PIXELS or a decode failure: Unreadable. JPEGs are turned the way their EXIF orientation says, as they are shown. Animations count by their first frame; transparency is ignored. Native hosts catch decoder panics; the browser decodes in a separate worker, so a decoder bug costs one picture, never the node.

  2. Luma

    0.299 R + 0.587 G + 0.114 B per pixel. Sides of 1,024 pixels or more are first averaged over whole blocks of pixels, so that no side stays at 1,024 or more (SHRINK is 512).

  3. Blur

    Two passes of a box filter along rows and then columns, each window ceil(side / 128) wide: a tent filter. Pictures with a side under 5 pixels have no fingerprint.

  4. Sample

    64 × 64 samples at the centers of a regular grid.

  5. DCT

    The 16 × 16 low-frequency corner of their 2-D DCT, DC terms dropped (frequencies 1–16 on each axis).

  6. Bits

    One bit per coefficient: set when it is above the median (taken with Torben's method). 256 bits, 32 bytes.

  7. Quality

    PDQ's gradient score, 0–100: the whole steps of 100/255 between neighboring samples, summed, divided by 90, capped at 100. Under MIN_QUALITY (50) a picture is too flat to tell apart from others and gets no fingerprint.

A picture turned a quarter, upside down or mirrored is the same picture. All eight of those variants come from one DCT, since turning and mirroring only swap and negate coefficients, so examine_variants costs barely more than one hash. A picture matches a listed hash when any of its eight variants is within MATCH_DISTANCE, 31 differing bits (PDQ's usual threshold); lists keep the hash as shown. Floats round differently on native and wasm, so the same picture can come out a bit or two apart: hashes are compared by distance, never for equality.

/// Bits that differ between two hashes, 0–256.
pub fn distance(a: &[u8; 32], b: &[u8; 32]) -> u32 {
    a.iter().zip(b).map(|(x, y)| (x ^ y).count_ones()).sum()
}

/// Whether two hashes are the same picture.
pub fn matches(a: &[u8; 32], b: &[u8; 32]) -> bool {
    distance(a, b) <= MATCH_DISTANCE
}

Video

A video gets a look only where a host can play it: a handful of frames spread over its length, each fingerprinted like a picture. The core takes at most 16 frames (MAX_FRAMES); the web app samples 8 with the browser's own player, muted and never attached to the page, drawn at most 512 pixels a side, giving up after 30 seconds. A video matches when at least half its frames, and at least two, match frames of a video this device refuses. Hosts that can't play a video (a headless node, a browser without the codec) say Nothing, and only the exact hash list applies.

The vector

core/vectors/pdq.json holds a sanitized 96 × 96 grayscale PNG (picture), its eight PDQ hashes in the order of Variants (as shown, mirrored left to right, upside down, turned half way, then those four transposed), its quality (100), the match_distance (31) and a tolerance of 4 bits for comparing across implementations.
