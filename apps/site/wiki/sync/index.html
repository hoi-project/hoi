Sync & gossip

Two hoi devices that meet say hello, compare what they hold of each community they share by range fingerprints, fetch what they lack in bounded pages, and from then on push every new valid record to each other as it arrives. This page is that conversation: every message and field, every cap, the order of a session, the reconciliation algorithm, how live records spread, how media is fetched, and the warmth reading a device makes of what it saw.

One conversation, any pipe

hoi-sync defines what two nodes say to each other over any byte pipe: the home-node WebSocket, hoi/sync/1 on iroh between native nodes, and WebRTC data channels from browsers (the pipes are on Transports). Live records ride the same link as catch-up, so there is no separate gossip protocol: a community's "topic" is simply the set of linked peers that listed it, and a new record goes to each of them.

A → B  hello { communities }            B → A  hello { communities }
       (to strangers: only those its routes led here for, the rest as salted hashes)
B → A  rng   { c, s, r }  (each shared community: B starts a session to learn what A holds,
A → B  rng   { c, r }      fingerprints of ranges, split where they differ)
B → A  want  { ids }      (what B lacks)          …and A starts its own session
       (to a peer that doesn't say `range`: have { c, ids }, every live id, instead)
A → B  recs  { [wire] }   (genesis, identities and delegations first)
later: recs  { [wire] }   (live: every new record, gossiped to peers in its community)
A → B  bwant { ids }      (media bytes a visible post references, by BLAKE3 hash)
B → A  blob  { id, data } (one item per message; A checks the hash and the bytes)

Every message

Each message is one canonical CBOR map whose t names it (at most 16 bytes). Decoding refuses a message over MAX_MESSAGE, a list over its cap, a field of the wrong type, and an unknown t, so a peer can't make a node allocate or loop on its say-so. An undecodable message costs the sender 5 points of peer score.

hello

The first message on every link, from both sides, and sent again whenever what it says changes (a community joined or left, a transport address changed, a notice set): a newer hello replaces the last one, and when what the host says about a link changes what our hello names, a hello still waiting in the outbox is replaced in place. Nothing but hello or bye is taken before it.

Communities as salted hashes

A stranger learns only what it needs. A hello to anyone but your own devices names in the clear only the communities whose routes led to that connection (a carrier learns what a member came to it for) and lists the others as hashes salted for that connection. Only a peer that already knows a key can match it, and a fresh salt per connection keeps the same list from being recognized on the next one. The hashes are sorted, so their order says nothing about the keys behind them.

pub const COMMUNITY_HASH_CONTEXT: &str = "hoi 2026 hello community v1";

pub fn community_hash(salt: &[u8; 16], community: &Id) -> Id {
    let mut h = blake3::Hasher::new_derive_key(COMMUNITY_HASH_CONTEXT);
    h.update(salt);
    h.update(community.as_bytes());
    Id(*h.finalize().as_bytes())
}

The receiver hashes every public community it is in under the peer's salt and adds the matches to what the peer listed. It keeps the salt and hashes for the life of the link, so a community it takes on later (rematch, or a carry it accepts) is found among them without asking again. The vector hello-salted.json pins this: under salt 5a × 16 a stranger's hello of 165 bytes names community 8a88e3dd… in c and lists 8a875fff… only as 1995a315… in ch, while the 279-byte hello from a home node to its device names both in the clear and carries token, pt and a 32-byte lk.

What a node does with a hello

  1. Credential

    From a device that dialed this node, the first hello must show a credential or the pairing link's token; otherwise the link ends without a word (Transports).

  2. Version

    Not 2: bye "this node speaks sync version 2".

  3. Notice

    On a person's device, a stranger's notice not accepted yet ends the link here, to be read first; a hello that lies about its notice costs score.

  4. Communities

    Private communities are dropped from c (a peer can't opt a private group into plaintext sync by guessing ids); salted hashes are matched. A home node joins and pins what its device lists (while it is in fewer than 256), then sends its own hello, with a new credential if the device just spent the link.

  5. Hints and routes

    Routes that aren't valid hints are dropped. Hints are remembered only from a credentialed device or a proven home node; from a home node not yet proven they wait until it delivers records.

  6. Then

    The node starts a session for every shared community (rng, or have), and sends its catalog, its node list, pending link asks, carry requests and finds, as each applies.

have, want, recs

The catch-up messages. A have goes only to a peer whose hello doesn't say range (every current program says it, so have is the path for older peers and for the test vector); otherwise reconciliation finds the same ids with far fewer bytes. Either way, what one side lacks is asked for with want and answered with recs.

have

{t: "have", c, ids}: every live record id the sender offers of one community it holds the genesis of, at most 100,000. The receiver keeps the ids it neither holds nor deleted nor keeps a removed record's skeleton of as pending wants, and counts what the peer listed for warmth. If its pending ids from this peer, across all communities, would pass 100,000, it says bye "too much pending catch-up". A have also subscribes the peer to the community on this link. A peer this node dialed by a route it already trusted, listing records held here besides the genesis, is remembered as a member worth pointing newcomers at; a peer that dialed in proves that by delivering records instead.

want

{t: "want", ids}, at most 5,000. The answering side sends, for each id it holds:

  • only records of communities the peer subscribes to on this link (or no community at all), never private content, never a record held back or by a key the community blocked, never one kept only in pieces;
  • profile records and palette choices only to a peer that said profile or profile-color;
  • a person's own identity or device blessing that never came back from anywhere only to that person's own devices;
  • with each record its carriers, the records a peer needs before it: the author's identity, each later root's identity and rotation, and the device's delegation;
  • at most 16 MiB of records in one answer (MAX_BLOB): older or hostile peers can ask for 5,000 maximum-size records in one frame, so the answer is bounded before it is built.

The records are sorted into dependency order (below), then by time, and cut into recs messages of at most 200 records or about 1 MiB each.

Paging

The asking side never has more than one page outstanding per peer, across all communities: one page at a time keeps a catch-up below the link's byte budget (200 maximum-size records plus their carriers fit the bounded queue). A page is up to 200 ids. When every id of it has arrived from that peer, the next page goes out. When nothing is pending and no range session is still open, the community is caught up with that peer: the time is saved as sync_completed, which warmth reads. A catch-up that made no progress for 120 seconds with ids outstanding is stalled, and the host drops and redials the link.

recs

{t: "recs", recs: [wire, …]}, at most 500 accepted. Each wire is one signed record as it travels (Records & encoding). The batch is ingested together, dependencies first, settling the standing ladder before contributions so their authors' new standing applies, and every record passes the full validation pipeline. Peer score (Spam & rate limits) follows what came:

What camePeer score
a valid new record+0.1, up to 10
a duplicatenothing; it still shows the peer holds it
bytes that don't decode−2 each
a record refused with a peer strike (it doesn't decode, is too big, or its signature is bad)−2
forged identity work−30: one is one too many, however many good records came before; the rest of the batch isn't looked at
at −20 or belowbye "too many invalid records", link closed

A record made within the last ten minutes (CLOCK_SKEW, 600 seconds) counts as live gossip, an older one as catch-up: only a live record over its author's rate budget strikes the author. Valid records of a community delivered by a peer make it a remembered member and an "other holder" of a carried community; from your home node they prove it is the node you meant to pair with. After every batch the node offers what it has to every peer again (a genesis may just have arrived), settles standing, and asks for missing media.

Range-based set reconciliation

Two peers learn which records the other holds that they lack without either listing every id, after Aljoscha Meyer's range-based reconciliation and Negentropy. Records are ordered by (created_at, id). A message partitions that whole order into consecutive ranges, each ending at an exclusive upper bound, each either settled (Skip), a fingerprint of the sender's records in it, or the sender's ids in it.

Two devices hold almost the same records. Each sends fingerprints of sixteen ranges; ranges whose fingerprints match are settled at once, and the ones that differ are split again, or listed as ids once they are small, until each side knows exactly the few records it lacks.

Matching ranges cost one fingerprint each; only the differences are looked at closely.

The fingerprint

The ids in a range are added up as 256-bit little-endian integers, modulo 2²⁵⁶, and the sum and the count are hashed with a key of their own; the first 16 bytes are the fingerprint. The same set gives the same fingerprint whatever order it was summed in, and it can be summed over any range.

pub fn fingerprint(items: &[Item]) -> [u8; 16] {
    let mut sum = [0u64; 4];
    for (_, id) in items {
        let mut carry = 0u128;
        for (i, limb) in sum.iter_mut().enumerate() {
            let v = u64::from_le_bytes(id.0[i * 8..i * 8 + 8].try_into().expect("8 bytes"));
            let s = *limb as u128 + v as u128 + carry;
            *limb = s as u64;
            carry = s >> 64;
        }
    }
    let mut h = blake3::Hasher::new_derive_key("hoi 2026 range fingerprint v1");
    for limb in sum {
        h.update(&limb.to_le_bytes());
    }
    h.update(&(items.len() as u64).to_le_bytes());
    h.finalize().as_bytes()[..16].try_into().expect("16 bytes")
}

Bounds

A bound is (at, id); Bound::END, past every record, is (u64::MAX, ff × 32). Between two neighbouring records the sender picks the shortest bound above the first and at or below the second: no id at all when their times differ, else just enough of the second's id to tell them apart. On the wire a bound's id loses its trailing zero bytes, so most bounds are a time and an empty byte string.

The rules

One side starts (initiate) and learns what the other holds; each side starts its own session for each shared community, so each learns what to ask for. A set of 64 ids or fewer (IDS_THRESHOLD) goes as one list in the first message; a larger one as 16 fingerprints (BRANCHES) of equal-sized chunks of the sender's records.

The responder always replies, so the starter knows when it is done; the starter replies only while something is still open, and stops when nothing is. Neighbouring skips merge into one. A message carries at most 8,192 ranges (MAX_RANGES): a side that would need more to split answers the rest of the differing ranges with its ids, which always settles them. The ids a starter lacks become pending wants, asked for in pages as above.

On the wire

{t: "rng", c: community, n: how many records the sender holds there, s: true if the sender began this session, r: [entries]}. Each entry is a CBOR array:

upper.at | uint | sun | 2 | the bound's created_at upper.id | 0–32 B | coral | 3 | the bound's id, trailing zero bytes cut mode | 1 B | mute | 1 | 0 skip, 1 fingerprint, 2 ids fingerprint | 16 B | sky | 4 | mode 1 only ids | n × 32 B | lilac | 4 | mode 2 only

A receiver refuses an rng with no ranges or more than 8,192, a bound id longer than 32 bytes, bounds not strictly ascending, a last bound that isn't END, a fingerprint that isn't 16 bytes, an entry with extra parts, or more than 100,000 ids in all.

The live window

What a node reconciles, and lists in a have, is what it would offer the peer: the community's records that haven't expired and that it passes on (not held back, the author not blocked, not kept only in pieces, not waiting for an injector), profile kinds only to peers that take them, and of those the newest 100,000. Since every compliant node deletes records at expires_at and refuses them afterwards, the window is the community's retention window (Expiry & removal), and expired records can't sneak back in. Ids a starter finds lacking that it deleted, or keeps a removed record's skeleton of, are not asked for.

What it costs

In the crate's tests, two sides of 1,000 shared records with 7 and 5 extra each learn exactly what they lack while moving less than a quarter of two full id lists; the same set settles in one round; 20,000 records with every third missing on one side, ten records a second, settle within five rounds. In hoi-core, two nodes with about a thousand records in common, seven new on one and four on the other, reconcile in less than a sixth of the bytes two full have lists would take, about 5 KB when the test was written, and no have is sent at all.

A full catch-up session

In hoi-core a session is per peer and per community. Sending rng as starter marks the community as ranging with that peer (when it last moved, whether the peer answered yet). The responder's first answer tells the starter the peer holds the community at all (it reconciles it, so it holds the genesis) and how many records (n), which warmth uses. A session the peer stopped answering ends after two minutes, at the next sweep, and what it found is asked for as usual. A peer that leaves and comes back on the same link gets a fresh session.

lanes: Device A | Device B -- Hellos -- Device A -> Device B: hello {c / n, ch, fx: [range, …]} Device B --> Device A: hello {c / n, ch, fx: [range, …]} Device A: B shares the community: A starts a session -- A learns what B holds -- Device A -> Device B: rng {c, n: 1,012, s: true, r: 16 fingerprints} Device B --> Device A: rng {s: false, r: skip, skip, 16 fingerprints, skip, …} Device A -> Device B: rng {s: true, r: ids where small, fingerprints where still large} Device B --> Device A: rng {s: false, r: B's ids in those ranges} Device A: nothing open: lacks = B's ids it doesn't hold -- B learns what A holds, the same way -- Device B -> Device A: rng {s: true, …} Device A --> Device B: rng {s: false, …} -- Pages -- Device A -> Device B: want {up to 200 ids} Device B => Device A @mint: recs {carriers first, then by kind and time} Device A: every record validated; when the page is complete, the next one Device A -> Device B: want {the next 200} Device B => Device A @mint: recs Device A: nothing pending, no session open: caught up -- From now on -- Device B => Device A @sky: recs {each new record as it is accepted}

Live push

Whenever a node accepts a record (made here, or arrived from a peer, but not while loading from storage, and never one decrypted from a private group or rebuilt from pieces), it queues the record with its carriers as one recs message to every linked peer that:

  • said hello, and is not the peer the record came from;
  • lists the record's community on this link (in its hello, as a matched salted hash, or by reconciling it); a record without a community (an identity, a blessing, a revocation) goes to every such peer;
  • takes the kind (profile, profile-color);
  • is one of the person's own devices, for the person's own identity and blessings: everyone else gets those with the records they come with.

There is no hop count and no time to live. Each receiver validates the record before anything else, and passes it on only if it accepted it; a record it already holds is a duplicate, accepted by nobody twice, so the flood stops by itself. A peer subscribed to the community now holds one more of this node's records, which warmth counts. Bytes passed along for others are added up for the person's own statistics.

A new record starts on one device and goes to each linked peer that lists its community. Each peer checks it first and passes it on only if it accepted it, so the record reaches the whole mesh hop by hop and never goes around twice.

No topic, no hop count: acceptance is what spreads a record, and duplicates stop it.

lanes: Author's browser | Home node | Member's node | Member's browser Author's browser: stamps, signs, validates its own post like any record Author's browser -> Home node: recs {identity, delegation, post} Home node: validates every record; accepts the post Home node => Member's node @sky: recs {carriers, post}: every peer listing the community Home node: not back to the author's browser Member's node: validates; accepts Member's node => Member's browser @sky: recs {carriers, post} Member's node: nothing back to the home node it came from; a copy from elsewhere would be a duplicate

A device's own new record in an open community may instead go sealed to an injector first, through a forwarder in another place, so the node it links through can't tell the record started there; the device then holds it back from its own links until it comes back from elsewhere, or for two minutes (Scattered delivery). Directory listings spread by a gossip of their own: a sweep at least five minutes after the last sends each peer the next window of relayed catalog entries, and a browser or phone a window every 30 minutes (Discovery).

Media: bwant and blob

Records reference media by BLAKE3 hash, MIME type, size and, for pictures, width and height (Media). The bytes travel separately, and only when someone asks.

  • Asking. With automatic media on (auto_media, the default), a node asks for the media of visible posts in its public communities that it lacks and doesn't refuse (its own or a followed blocklist, media that failed the checks before). It keeps one request outstanding at a time and asks for the same item again after 120 seconds (MEDIA_RETRY), least recently tried first, so one unavailable picture can't starve the rest. It stops asking once it holds 512 MiB of media (MEDIA_CAP). The ask goes over iroh-blobs to one peer that said blobs (Transports), else as bwant {ids: [hash]} to every peer that lists the community.
  • Answering. Up to 32 hashes per bwant; only bytes of visible public posts in communities the two share; one blob {id, data} per item; at most 16 MiB in one answer, the rest left for the next ask. An item not here yet (a home node relaying a post that just came from its author's device) is owed, at most 256 per peer, and sent once it arrives.
  • Checking. BLAKE3(data) must equal the id: otherwise the sender's fault, −5 peer score, and at −20 bye "media that doesn't match its hash". Then the bytes must be exactly what the post claims: sniffed type, size, and a picture's width and height. Bytes that hash right but fail are the author's fault: the post stays held and the author's key takes a strike. A picture is then fingerprinted against refused pictures before it is kept (Media).

bye, and every reason

{t: "bye", reason} ends a link. A bye from your home node becomes the network error the app shows; any bye makes the receiver drop the link. Silence is a reason too: a device without a valid credential, and a stranger whose notice waits for the person, hear nothing.

How the core drives it

The node keeps a PeerState for every link the host announced with net_connect. It queues its hello at once, except to a device that dialed it (that one hears nothing before its credential) and, under the consent gate, to a stranger it dialed (that one's hello comes first). Everything else follows from net_receive, one whole message at a time:

self.count_in(peer, bytes.len(), now);
// Someone else's device that dialed in: only while relaying is on and under today's cap.
if self.peers.get(peer).is_some_and(|p| !p.client && !p.home && p.meta.incoming && p.meta.direct.is_none()) && !self.accepts_members() {
    …
    self.send_msg(peer, Msg::Bye { reason: reason.into() });
    return false;
}
…
st.msgs += 1;
if st.msgs > MSGS_PER_MINUTE && self.peer_scores.penalize(peer, 1.0) {
    self.send_msg(peer, Msg::Bye { reason: "too many messages".into() });
    return false;
}
let msg = match Msg::decode(bytes) {
    Ok(m) => m,
    Err(_) => return !self.peer_scores.penalize(peer, 5.0),
};
if !said_hello && !matches!(msg, Msg::Hello { .. } | Msg::Bye { .. }) {
    // everything starts with a hello
    return false;
}

Then one handler per message. Whatever the handlers want to say goes into the outbox, which the host drains with take_outbox after each call; on native builds Shared::with routes it into each link's bounded queue, and the web worker sends each entry on the matching WebSocket or data channel. Nothing in the conversation is a UI call. The app's own calls (net for the status, pair, join, requestCarry and the rest) go through one JSON entry point, Node::call(method, args) in dispatch.rs, used by the web worker and the Tauri shell; the network calls are separate functions the host calls directly. The full API is on Core API.

Warmth

Warmth reads who else holds a community's live records, the way a torrent client reads availability. A community is cold when no other durable node holds it (a lone desktop reads cold too: its own copy is the one at risk), cool when one other independent place holds a copy, warm with two, and hot with three or more that hold everything this device knows of and caught up recently. People see one word and one bar; the parts are in the details.

It is a pure function of what one node observed first hand on its own links: what connected peers handed over or took, what others listed that isn't here yet, when the last catch-up finished. Nothing is trusted from a peer's say-so except the one-hop hint a node may attach to its catalog entry (w), which is taken as a maximum and never added up. A warmth reading is not a delivery receipt: it says how many copies this device could see, not that any post reached anyone. Private communities have none: they sync through their encrypted relays.

What is observed

hoi-core gathers one Observation per community. Each peer that said hello and offered the community is one Holder, one per authenticated endpoint (a node reached twice is still one copy):

coverage0 to 1
(the genesis if it showed it + what it listed + records this node gave it + valid records it delivered) ÷ this node's live records. What a peer listed counts only for a peer this node dialed by a route it already trusted, and minus what is still missing from it: a stranger's inventory alone warms nothing. With nothing held here yet, any record counts as a full copy.
durablebool
Its hello says keeps: a desktop or hoi-node, never a browser or phone. The peer's own word.
operatorOption<u64>
Who runs it, from its verified notice: the first 8 bytes of BLAKE3 over its operator and contact, case and spacing ignored. A claim, so it only ever merges places.
networkOption<u64>
The IPv4 /24 or IPv6 /48 its address is in, or "this machine" for loopback.
guardedbool
The link is encrypted and its other end was checked: this device dialed a route it chose, or the transport authenticated the peer's endpoint.

Besides the holders: records (live, forwardable records here), missing (the most any one peer listed that hasn't arrived, ignoring stalled links), media referenced and present, last_sync (the last finished catch-up), whether a connected peer lists the community now (live), and the best w a durable peer's catalog gave (hinted). own_durable is whether this device is a desktop or node.

Copies are counted by place

Holders that share a declared operator or a network, directly or through a third, are one place, because one party or one outage takes them all: ten nodes in one rack are one copy's worth of safety. places_of groups them (a union-find over both keys); each place counts the most any holder in it showed, and kept is the sum over places of the durable holders. The same grouping places scattered pieces.

A node's catalog hint for a community is ⌊kept⌋ capped at 3 (hint), read again at most once a minute so a busy node's catalog stays cheap to send.

The warmth of your connections

The same keys read the device's own links (every link that said hello, except devices it serves): effective places is the inverse Simpson index over links per place (3 for three links in three places, 1.6 for four links of which three share one place). Cold with no links; cool when every link goes through one place or fewer than half are guarded; hot with 3 effective places or more, none carrying over half the links and nine in ten guarded; warm in between. The score, 0.6 × min(1, effective ÷ 4) + 0.25 × guarded + 0.15 × (1 − largest), is kept inside the word's band (cool ≤ 49, warm 50–79, hot ≥ 80) so the bar never says more than the word.

Places

hoi_sync::place uses the same idea to decide where a generation of scattered pieces goes (Scattered delivery), pure, with the caller bringing the candidates and the randomness so the core and the simulator place pieces by the same rules. A Candidate has an operator (from its notice, a claim that only merges), a network (IPv4 /24, IPv6 /48, or this machine: one network is one place), a wider block (IPv4 /16, IPv6 /32) and an introducer (where this device first learned of it).

  • One piece per independent place, never a place that held a sibling of the same generation, nor the places of this object's forwarders.
  • At most ⌈n/8⌉ pieces of a generation of n in one block, and ⌈n/4⌉ through one introducer, over the generation's whole life (earlier holders count).
  • Places are drawn uniformly, each weighing one however many nodes it has or how long they've been up; a place's node is drawn uniformly among its candidates within the caps. None when the caps or the places leave too few.

The sizing that decides how many pieces assumes a party's share of the candidates is its share of real places; these rules are what keep it so.

Carrying a community for others

Public nodes keep communities available on request. Anyone who holds a community's signed genesis (a member, or anyone with its invite) may hand it to a node whose hello says carry; the node stores and serves the community like a pinner, without being a member: it has no standing, signs nothing and vouches nobody in. The request carries the genesis and nothing else: no routes, so an unpaired stranger never makes a public node dial an address of its choosing. A sender that adds routes anyway is ignored, not obeyed. The node learns where members are the way it learns everything else, from peers that prove they hold records.

  • Policy. off (only what the operator joined, or a paired device brought), index (also what a registry it mirrors lists) or any (also what peers ask for); hoi-node carries on request by default (--carry any; off with --no-public-relay), the desktop only while Be a public node is on, browsers and phones never.
  • Pace. 4 requests a minute per peer, both ways (a requester paces itself too); more are ignored and cost score. 8 accepted a minute and 128 a day, whoever asks; the rest hear busy.
  • Budget. 256 communities carried by default (--carry-limit), at most half of them on request, and 256 MiB of their records and media together (--carry-mb).
  • Letting go. A community carried on request that nobody else delivered or fetched for 14 days, or whose records never came within an hour, or that doesn't fit the byte budget (the longest untouched first), is let go and its records deleted: they were taken on a stranger's word. An index listing is never let go for idleness. Nothing about who asked is kept: the origin is a word, request or index.

A device asks, unasked, every public node that says hello for up to three of the open communities its person owns (or is sharing an invite to) that the node doesn't list yet. A public node shares the load the same way: it offers the open communities it holds to another public node that says hello, while it sees fewer than three durable copies of one, at most two such offers per community a day. Forwarding pieces for others

A public node with an endpoint key says fw and passes sealed piece requests on to the holder they name, and the holder's sealed answer back, so a holder never sees the address of the device that stores or fetches, and the forwarder never sees a piece. It reads nothing it passes: the envelope is sealed to the holder, the answer to the asker's one-time key. What it keeps is what routing an answer needs while it is on its way (which link asked, under which request id) and counters; nothing about which holder a device used outlives the answer.

lanes: Device | Forwarder | Holder Device -> Forwarder: piece {o: put / get / has / drop, r: a, to: holder, e: sealed to the holder} Forwarder: a link to that holder now? one it saw itself and can dial? else gone Forwarder -> Holder: piece {o, r: b, e} Holder --> Forwarder: piece {o: stored / got / had / dropped, r: b, e: sealed to the asker} Forwarder --> Device: piece {o, r: a, e}
  • It passes requests only to holders it is linked to now, or to holders it saw itself and knows how to reach (nobody makes it dial an address of their choosing), queueing at most 128 requests and 32 MiB for up to 20 seconds while it dials.
  • A holder it can't reach gets the asker a gone at once (one unsealed byte of envelope), so the asker tries another way rather than waiting; so does a request whose holder link closes while an answer is due.
  • A holder it doesn't know may be reached one hop further, through a linked forwarder whose node list vouches for that holder with its key; a request that came from a forwarder goes no further.
  • At most 4,096 answers on their way back; a link that only forwards may send a holder 6,000 requests and 128 MiB of puts a minute, since many devices' requests arrive over it.

What pieces are, and how a device stores and rebuilds an object, are on Scattered delivery and Mailboxes & encrypted relays.

The sync transcript, step by step

core/vectors/sync-transcript.json pins the message flow of a catch-up with have lists. Two nodes share one community (8a88e3dd…). There are 30 ids, BLAKE3([i]) for i from 0 to 29: a holds the first 20, b the last 20, so they share 10 and each lacks 10. a's hello lists no features, so neither side reconciles by ranges; this is exactly what a current node does with a peer that doesn't say range.

lanes: a | b a -> b: hello {v: 2, node: 07 × 32, name: "lena's browser", token: "t0k3n", c: [8a88…], serves: false}: 128 B a -> b: have {c: 8a88…, ids: its 20}: 729 B b --> a: want {the 10 of those b lacks}: 353 B b -> a: have {c: 8a88…, ids: its 20}: 729 B a --> b: want {the 10 of those a lacks}: 353 B a .. b: each answers the other's want with recs; both hold all 30
  1. hello

    A browser's hello to its own home node: a name, a token, the community in the clear, no salt. Its seven keys in canonical order are c, t, v, name, node, token, serves: 128 bytes.

  2. a's have

    Every live id a holds of the community: {c, t: "have", ids: [20 × 32 bytes]}, 729 bytes.

  3. b's want

    b runs hoi_sync::missing over a's list: the ids it doesn't hold, in the order listed, without repeats, at most 5,000. They are a's first ten. In the node, the want goes out first, then b's own have, as here.

  4. b's have

    b's 20 ids, the last ten of which are the ones a lacks.

  5. a's want

    The last ten of b's list. The vector's note: after both wants are answered with recs, both sides hold all 30 ids.
