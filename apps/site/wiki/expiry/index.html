Expiry & removal

Time does the deleting. Every record carries the moment it fades, no later than its community allows, and every compliant device deletes it then and leaves it out of reconciliation. Removals and deletions leave a small tombstone so the record can't come back. This page covers the rules for expires_at, what each kind is given, what is exempt, the sweep, tombstones, saved posts, sync, and what no protocol can promise.

Every record has an end

expires_at is a required field of every record's envelope, in Unix seconds, signed with the rest (records). It can't be changed without changing the id and breaking the signature. The shape check refuses a record that expires before it is created (expires before it is created). Then the time stage of the pipeline checks it against this device's clock:

pub fn time(record: &Record, now: u64, live: bool, max_retention: Option<u64>) -> Result<(), Reject> {
    if record.created_at > now + CLOCK_SKEW {
        return Err(Reject::FromTheFuture);
    }
    if live && record.created_at + CLOCK_SKEW < now {
        return Err(Reject::TooOld);
    }
    if record.expires_at <= now {
        return Err(Reject::Expired);
    }
    let cap = max_retention.unwrap_or(KEEP);
    if record.expires_at > record.created_at.saturating_add(cap) {
        return Err(Reject::ExpiryTooFar);
    }
    Ok(())
}

All four have the code time and blame nobody: the sending peer loses no score and the key gets no strike.

Records sit on a timeline from their created_at to their expires_at. As the clock passes each expires_at, that record fades from every device. A removed post's body goes early, but its tombstone, the id, where it was and why, stays until the post would have expired.

Forgetting is the default: the end is written into each record when it is signed.

The retention window

A community's limits.max_retention is the longest a record in it may live: 15,552,000 seconds (180 days) by default, anywhere from an hour to ten years (3,600 to 315,360,000 seconds). It is changed by consent like every limit (changes by consent). The web app offers 1, 7, 30, 90, 180 and 365 days, and says "Every device deletes posts older than this. No archive, on purpose."

The cap a record answers to is the more lenient of the window in effect when it says it was made and today's (which limits apply). A device that joined after the community shortened its window still takes posts members took under the longer one. Records made since must fit today's.

Changing the window doesn't touch what exists

Each record keeps the expires_at it was signed with. Shortening the window deletes nothing sooner, and lengthening it keeps nothing longer. Only records made afterwards get the new window.

The window also sets other clocks: the deadline of a proposal is one window after it (proposals); the standing window for trusted is 90 days or the retention, whichever is shorter; ledger entries that aren't kept expire with it, so a ban lasts one window unless renewed.

What is exempt

Some records must outlive the window because everything else is checked against them. exempt_from_retention lists them; for these, the time check uses KEEP, 100 years (100 * 365 * 86_400 seconds), as the cap instead of the community's window.

pub fn exempt_from_retention(record: &Record) -> bool {
    match &record.body {
        Body::Community(_)
        | Body::Delegation { .. }
        | Body::Revoke { .. }
        | Body::Identity { .. }
        | Body::Rotate { .. }
        | Body::Vouch { .. }
        | Body::Share { .. }
        // a page is its whole history: each edit builds on the ones before
        | Body::Wiki { .. } => true,
        Body::Ledger(l) => l.action.kept_until_superseded(),
        _ => false,
    }
}

The node adds one more case: a review that answers a proposal is also taken with no retention cap, because the answers decide it and must last as long as it.

Everything else in a community fades with its posts: removals, bans, unbans, labels, pins and admissions included. A genesis expires too, a hundred years on; when it does, the sweep drops the community.

The sweep

Expiry is the real deletion mechanism. Node::sweep deletes everything past its expiry, lets contested removals take effect once their window passed, and frees unused media. Hosts call it every few minutes. The parts about expiry, in order:

  1. Find what expired

    Store::expired(now) lists every record with expires_at ≤ now.

  2. Delete it

    Each one leaves the in-memory store and its indexes (by community, by author, by parent, the copy-paste fingerprints, search words, media references). A Change::Delete goes to storage. Its id leaves this person's saved list. If it was a genesis, the community goes; otherwise the community is marked to settle again.

  3. Ripen removals

    Communities with a removal whose contest window has passed are marked to settle, which deletes those bodies (tombstones).

  4. Settle

    Contributions that left the standing window, ledger entries that expired, and removals that ripened change the ladder (settling).

  5. Forget what has run out, free media

    Tombstones whose record would have expired anyway, notes of what was read older than 30 days, and late markers for records no longer held go first. Then media bytes no stored record refers to any more are deleted (orphan_blobs), with a storage change for each. Last, deleted ids past their date, quiet strike scores, and bounces lifted more than 30 days ago are forgotten.

On disk

Deletes reach storage through the Persist interface (storage). On desktop, mobile and hoi-node, SQLite runs DELETE FROM records WHERE id = ? inside one transaction per batch of changes, with PRAGMA secure_delete = ON, so freed pages are zeroed rather than left with old bytes, and synchronous = FULL. The records table keeps each record's expires_at beside its wire bytes. In the browser, the core hands its changes to a journal the host drains into IndexedDB.

Tombstones

A removal by a moderator or a delete by the author ends a record before its time. Two things stay behind, so the record can't come back and the thread keeps its shape.

The skeleton

skeletonize removes the body from the store and from disk and keeps a Skeleton in this device's local state:

/// What stays of a removed or deleted record: no body, just where it was and why it went.
pub struct Skeleton {
    pub community: Id,
    pub parent: Option<Id>,
    pub author: Id,
    pub kind: String,
    pub created_at: u64,
    pub expires_at: u64,
    /// Root that removed it; `None` when the author deleted it.
    pub by: Option<Id>,
    pub reason: String,
    pub at: u64,
    pub ledger: Option<Id>,
}

Opening a removed post gives "Poof. Removed by mira: rule 4." A removed or deleted comment keeps its place in the thread as a Poof box with who removed it and why, and replies under it stay. The skeleton is kept until the record's own expires_at, then the sweep drops it: by then the record would have faded anyway.

The deleted set

The store also remembers the id in its deleted set, until the record's expires_at. Ingest refuses a deleted id however it arrives (removed), and sync never asks for one (sync). If the record does arrive after its removal took effect, the node refuses it and marks it deleted again. Suppressed records are marked deleted with no end date (suppression). If the community overturns a removal, the skeleton and the deleted mark go, and the record can return with the next sync from someone who still has it.

The vector

vectors/tombstone.json gives a comment and an owner's remove entry for it ("rule 4, undisclosed vendor"), both as signed wire bytes. After the removal, compliant nodes delete the comment's body, keep its id and the entry, and refuse to ingest it again.

Removal: napping first

A moderator's remove doesn't skeletonize at once. The record naps for the contest window (72 hours by default, at most 14 days): it stays stored, shown as removal pending: <reason>, and established members can veto the removal. When the window passes without enough vetoes, the next settle skeletonizes it. Removals whose reason starts with illegal or privacy skip the wait, and for illegal ones the post's media is deleted and refused from then on. The full sequence, with the veto window, is on communities.

A record the community hid by review is different again: it naps for everyone but is never deleted early, and fades at its own expires_at (hides). The exception is media in a post hidden as illegal: every device deletes those bytes and never fetches them again.

Deletes by the author

An author can end their own post or comment early with a record of kind delete: an empty body whose parent is the target.

  • Only the author. Nodes apply a delete only to a post or comment in the same community, by the same root (only the author can edit or delete). A deletion arriving before its target waits in bounded pending storage; it cannot suppress the target until ownership is checked. Any of the author's devices can sign it.
  • At once. There is nothing to contest: as soon as a node takes the delete it skeletonizes the target with the reason deleted by the author and no remover.
  • Small and cheap. 512 bytes at most, stamped at pow_bits − 8, sharing a rate budget with edits: 30 an hour, 100 a day.
  • As long as the target. The delete record expires when the target would have, so it travels to devices that still hold the target for as long as that matters.

Progress survives restart

The core retains a deletion job before sending requests: the signed delete, known piece locations and only the capabilities needed to remove them. Failed saves remain retryable. The deletionProgress API distinguishes local removal, record submission, queued and submitted work, durable holder acknowledgements, legacy removal observations, unknown/refused/unreachable targets and expiry. Missing capabilities or unknown generations remain gaps; a timeout is never proof that bytes are gone.

A holder that acknowledges durable deletion has removed the payload and saved a marker that refuses replay through the original inclusive UTC expiry day. A holder that has not heard the drop may still serve its old piece. The requesting device must keep the local state needed for retries and dissemination; all known targets acknowledging does not prove that every target was discovered. This is bounded eventual deletion, and it cannot erase recipients' copies, exports or an operator's private backups. See scattered delivery.

Deleting known posts and comments

The core can delete every post and comment of yours that this device holds, as one confirmed list. previewBulkDeletion lists them by community and names what it cannot account for: private groups it cannot use, posts known only by a pointer, pieces it holds no drop authority for, and communities it never caught up in. It never claims to know your whole history. confirmBulkDeletion saves exactly that list; new posts need a new preview. Each target still gets its own signed delete, with the current time and inside the 30-an-hour window, so a long list takes hours or days. Progress survives restart, and the same snapshot never signs twice. Cancelling stops what isn't signed yet; signed deletes carry on. A wipe forgets the list, and recovering your identity restores signing, not the list or lost drop authority.

Clearing a device after deleting

Clearing local data (Wipe, or recovery while the vault is locked) is always possible and sends nothing: unfinished deletions on that device stop, and nothing reports them as done. To clear only once nothing is stranded, the core reports cleanupReadiness. It stays blocked while a deletion of yours isn't signed, while a signed one still needs the device (until its post's lifetime and its pieces' storage days end, even if every holder answered), and while the device alone can drop pieces it stored of someone else's deleted post. clearAfterDeletion checks that again, with the revisions the person saw, before any key goes; a new post or deletion in between refuses it. Neither kind of clearing reaches other devices, exported backups or other members' copies, or guarantees the storage is physically erased.

Records dropped without a tombstone

Some records are replaced, not removed, and go without a trace (drop_record): an older vouch or review by the same person for the same target (answers to a proposal aside, which are all kept), an older trust statement, tally or blocklist by the same person in the same community, and a device's older roster. Their ids are marked deleted until they would have expired, so they aren't fetched again. A root that burns itself takes everything it signed with it, on every device.

Leaving, bundles and media

Leaving a community

leave takes the community off this device's joined list, forgets its routes and catch-up state, and stops carrying it; a private group's keys are forgotten. It doesn't delete the records already held: from then on the node refuses new records for a community it isn't subscribed to, and what it holds fades at each record's own expires_at. The app says so: "Your copy fades on its own schedule."

Bundles

An exported .hoibundle is a CBOR map (t: "hoi-bundle", v: 1, the community key, and the records) holding exactly what this device would pass on: unexpired records that aren't held, with the identities and blessings their authors need. Removed bodies aren't in it, because they are no longer stored. Importing one runs every record through the full pipeline as an import: genesis records first, then the rest in dependency order. Records that expired since the export are refused, and vouches, reviews and ledger entries that claim a time more than an hour before this device's last catch-up count from when they were imported (late records). The file itself, once saved, is outside the app and never expires.

Media

Media bytes have no expires_at of their own; they live as long as some stored post refers to them. When the last post using a blob expires or is removed, the next sweep deletes the bytes. A device keeps at most 512 MiB of media (MEDIA_CAP): beyond it, new media isn't stored and can be fetched again later.

Saved posts

Saving a post puts its id on a list in this device's local state (state.saved). The list never syncs and is never shared; the Saved screen notes that it is kept on this device only and never passed along.

A saved post is not a copy. It lives as long as the record does: when the sweep deletes an expired record, when a removal or a delete skeletonizes it, or when an operator suppresses it, its id leaves the saved list too. Saving keeps a post easy to find while it lasts; it doesn't keep it past its expires_at.

Expiry and sync

Reconciliation compares sets (sync). Expired and removed records must not count as differences, or two devices would keep handing each other what both should forget. Three filters keep them out:

  1. What a device offers

    A device's set for a community, for range fingerprints and for have lists alike, is only its records with expires_at still ahead and that it may pass on (not held, author not blocked).

  2. What a device asks for

    Of the ids a peer has and this device lacks, it asks only for those it doesn't hold, hasn't marked deleted and holds no tombstone for. Removed, deleted, superseded and suppressed ids are never requested.

  3. What a device takes

    Whatever arrives anyway passes the time check: an expired record is refused, and a removed one is refused by the deleted set.

lanes: Your device | Peer -- At expires_at -- Your device: sweep: the post is deleted here, with its media if nothing else uses it Peer: its clock is behind: the post is still in its set -- Next sync -- Peer -> Your device: rng range fingerprints: they differ by that post Your device -> Peer: want its id (it isn't in the deleted set) Peer => Your device: recs [the post] Your device: refused: already expired, code time; nobody is blamed, nothing is stored -- A removed post -- Peer -> Your device: have lists a removed post's id Your device: never asked for: the id is in the deleted set until it would have expired

The honest limits

Expiry makes forgetting the default everywhere the software runs as written. It can't force a stranger's disk.

  • A modified app can ignore expiry and keep everything it ever saw. Signed records stay verifiable wherever they are kept.
  • Copies outside the app outlast it. Exported bundles, backups, screenshots and copied text don't expire. Anyone who could read a public community could keep what they read.
  • Deleted isn't always gone from the disk. SQLite's secure_delete zeroes freed pages, but the code's own note says it cannot erase filesystem snapshots or earlier backups. Turning off a node doesn't erase its database.
  • Each device judges by its own clock. A device whose clock runs behind deletes later, and keeps offering what others already dropped; they refuse it.
  • Removal reaches who listens. A removal, a delete or an operator's suppression is acted on by each device that receives it and runs compliant software.
  • Private communities fade on their own schedule. Their encrypted objects on relays have their own expiry, 30 days by the app's default (mailboxes). Members can keep their own copies; removing a member changes future keys, not what they already received (private communities).
